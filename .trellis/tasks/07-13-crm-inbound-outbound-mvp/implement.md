# CRM 入库与出货 MVP 实施计划

## 实施前提

- 用户已审阅 `prd.md`、`design.md` 与本计划并明确批准后，才执行 `task.py start` 和编码。
- 实施前运行 `trellis-before-dev`，读取后端、前端及跨层规格；不触碰已有 `Item` 业务代码和用户现有的未提交改动。
- 首次导入的两份工作簿为只读输入；导入前复制到受控路径并记录文件校验值，不修改原文件。

## 有序步骤

1. 建立领域持久化与 Alembic 迁移。
   - 新增库存模块相关 ORM：两类主数据、三类手工单据及明细、库存日记账、历史来源行、导入批次与迁移对账期初。
   - 使用 UUID、UTC 时间、Decimal 米数、整型匹数、软删除字段及新单据的分类型单号唯一约束。
   - 更新模型导出和 Alembic revision；不改变 `Item` 表或 API。

2. 实现库存模块服务和仓储层。
   - 实现主数据 CRUD/停用、三类单据的多明细创建/更新/软删除/恢复、库存和联想查询。
   - 从业务明细生成库存日记账，聚合校验所有待写入库存键，确保一次操作全部成功或全部失败。
   - 以语义化应用错误表示冲突、库存不足、无效主数据和不可编辑迁移记录。

3. 实现 API 路由与 DTO。
   - 在 `app/modules/inventory/router.py` 声明带 response model 的薄路由，在 `app/api/main.py` 注册。
   - 添加分页列表、库存明细、联想与主数据接口；使用当前用户依赖保护接口。
   - 为输入模型落实日期、单号、占位值、正整数匹数和正 Decimal 米数校验。

4. 编写后端测试。
   - 覆盖主数据、三类单据、同单多明细、库存汇总、编辑、软删除、恢复、负库存拒绝、单号唯一、遗留占位值拒绝和历史例外。
   - 覆盖历史单行同时产生入/出成品变动，以及迁移对账期初只补足到零且不可通过业务接口修改。
   - 验证认证、422 校验、409 业务冲突与 `detail + request_id` 错误契约。

5. 实现一次性历史导入器及其测试。
   - 使用明确的工作簿路径参数读取两份 Excel，保留每个来源行及原库存快照。
   - 覆盖坯布两种表头、`退走` 映射、空加工单位回退工作表名、遗留占位值、成品一行双方向和迁移对账期初。
   - 实现导入批次防重、全事务回滚、对账报告和 dry-run；在测试数据库以两份实际样本的副本验证来源行数与余额输出。

6. 生成客户端并实现前端业务 feature。
   - 运行 `bash ./scripts/generate-client.sh`，只接受工具生成的 `frontend/src/client/**` 变更。
   - 建立 `features/inventory` 的四组页面、页面私有组件和 React Query 查询/失效策略；使用 Ant Design 6 的 Table、Form、DatePicker、Select/AutoComplete、Modal/Drawer、Popconfirm 和状态组件。
   - 新增受认证的薄 route 文件，并在菜单配置中加入库存管理入口；不改变既有 Dashboard、Items、Rules 或 Admin 行为。

7. 端到端场景和导入验收。
   - 手工验证来料入库、坯布退走、成品出货、库存明细追溯、编辑/删除/恢复、主数据停用和占位值限制。
   - 在隔离数据库执行一次真实历史导入 dry-run 和实际导入；核对来源行数、待清洗数、对账期初数和按库存键余额差异，保存报告后才用于本地运行库。

## 验证命令

从仓库根目录或各命令要求的目录运行：

```bash
bash backend/scripts/lint.sh
cd backend && uv run pytest tests/
bash ./scripts/generate-client.sh
cd frontend && bun run lint
cd frontend && bun run build
bash ./scripts/test.sh
```

若环境限制导致任一命令不能运行，记录完整失败输出、受影响范围和已执行的等价检查；不得为通过质量门槛而重新引入裸 `uv` PATH 依赖。

## 高风险点与回滚

- 数据库迁移和首次历史导入是高风险步骤。先在副本数据库演练；生产/本地目标库仅在对账报告确认后执行。
- 导入失败或对账不通过时，使用导入批次 ID 回滚该批次生成的历史来源行、日记账和迁移对账期初，再修正映射重跑；不通过业务 UI 手工补数。
- 若前端路由或菜单回归，撤销本 feature 的 route/menu 改动即可，后端 API 与数据不依赖旧 Item 页面。
- 完成实现后运行 `trellis-check`；仅当范围、迁移、客户端生成、测试和 UI 验证均通过后进入收尾流程。
