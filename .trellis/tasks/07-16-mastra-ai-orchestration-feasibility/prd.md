# Mastra AI 编排可行性与首个试点计划

## 目标

在不改变现有 FastAPI 业务主链的前提下，完成一份可决策的产品与架构规划：判断哪些 Mastra 模式值得引入，并定义一个可独立验证、只读、低风险的首个 AI 试点。当前 task 只产出规划文档，不引入依赖、不部署服务，也不暴露生产功能。

## 背景与已确认事实

- 本仓库的业务主链是 React SPA → FastAPI `/api/v1` → PostgreSQL；FastAPI 已负责认证、授权、事务、统一错误响应及 `request_id` 追踪。详见 `ARCHITECTURE.md`、`backend/app/main.py` 与 `backend/app/api/main.py`。
- 前端以薄路由、`app/platform/features/shared` 分层及生成的 OpenAPI 客户端为约束；新能力不能绕开现有身份、权限或 API 合同。详见 `frontend/ARCHITECTURE.md` 与 `.trellis/spec/frontend/index.md`。
- 当前依赖与运行代码中未发现 AI/LLM SDK、Agent 框架或后台 worker；因此不能假设已有模型网关、任务队列、向量库或 AI 运行状态存储。
- Mastra 提供 Agent、确定性工作流、强类型工具、模型路由、持久化运行、人工审批、可观测性及评测等原语。其核心区可按 Apache-2.0 使用，但仓库 `ee/` 目录是另行许可的软件，不能被无意纳入生产方案。
- 首个试点已指定 OpenAI API 为模型供应商。官方数据控制文档（2026-07-16）说明：API 输入默认不用于训练或改进模型，除非客户主动选择共享；但默认仍可能生成最长 30 天的滥用监控日志，部分 API 功能还会保留应用状态。因此“允许生产数据外发”不等同于“零留存”。
- 现有库存域已提供受控的 GET 查询面：库存单据、原料/成品余额、库存台账、加工单位和收货单位。`frontend/src/features/inventory/api.ts` 将其映射到 `/api/v1/inventory/*`；`InventoryDocumentsPage` 同时含有编辑、删除和恢复能力，故这些变更操作不能成为试点工具。
- 当前库存查询 API 与库存前端路由的最低门槛都是“已登录且激活的用户”；查询处理器取得 `CurrentUser` 后未按库存域角色或数据范围进一步筛选。因此，试点入口不能默认扩展给所有登录用户，必须另行确定受众与授权策略。

## 产品问题

内部用户需要更快地从已授权的业务数据中获得答案，但若直接让模型访问数据库、调用现有变更端点，或绕过 FastAPI 的身份与审计边界，将带来错误操作、越权和不可追溯风险。

本 task 要验证的不是“是否把整个系统迁移到 Mastra”，而是：是否值得以一个安全、可测量的试点验证 AI 编排能力，并据此决定后续投入。

## 产品范围

### 本次范围

1. 明确采用、仅借鉴或暂不采用 Mastra 的决策准则，以及与当前 FastAPI + React 边界兼容的目标形态。
2. 以“库存只读问答”作为首个试点场景，仅向超级管理员开放；定义典型问题、允许的数据范围、预期回答和失败时的用户体验。
3. 定义试点的安全产品规则：通过后端授权、最小化工具权限、无直接数据库访问、无写入操作、可追踪的运行记录及清晰的人工复核边界。
4. 定义能够判断试点是否有价值的评测方式，包括正确性、权限/安全、可解释性、延迟与成本的度量口径。
5. 为后续技术设计保留明确输入：部署边界、模型提供方策略、运行状态与审计数据、前端入口位置及验收基线。

### 不在本次范围

- 安装 Mastra、引入 TypeScript AI 运行时、创建模型供应商账户或生产部署。
- 任何写入、删除、恢复、审批执行或直接数据库/SQL 工具。
- 通过 MCP 暴露内部能力，或向模型授予泛化网络、文件系统和管理工具权限。
- 面向客户的聊天产品、长期记忆、RAG/向量库、知识库导入和多 Agent 网络。
- 改动现有库存、认证、权限、OpenAPI 或前端页面行为。

## 子任务顺序

1. 父任务冻结内部/public 契约与安全不变量。
2. 后端安全边界与 sidecar 可并行开始；两者以版本化 internal tool contract 联调。
3. 前端在 public BFF/OpenAPI 合同稳定后接入；可先使用 mock 完成视觉状态。
4. 评测题库、成功规则和运维清单可并行准备；端到端指标和上线门槛在前三项完成后执行。
5. 父任务进行跨层验收，确认 30 题、阻断率、P95、成本记录和回滚演练后才判断试点结果。

## 产品需求

### R1：保留业务系统主权

试点必须将 FastAPI 保持为认证、授权、业务数据访问与审计的唯一业务入口。无论是否使用 Mastra，模型编排层都不能直接连接 PostgreSQL，也不能替代既有交易服务。

### R2：首个场景必须可控且只读

首个试点只允许访问经白名单批准的查询能力；每项工具须有明确输入、输出、用途、权限前置条件和最大结果边界。任何可能改变库存或业务状态的能力均须被技术上排除，而不只是依赖提示词限制。

### R3：回答必须可核验

用户应能看到回答使用的业务时间范围、筛选条件、来源工具/数据摘要，以及无法确认时的明确说明。系统不得把缺失数据、权限不足或工具失败伪装成确定答案。

### R4：身份、数据与审计边界

试点必须复用当前登录身份与服务端权限判定，并在服务端要求超级管理员身份；菜单隐藏或前端路由守卫不能作为唯一控制。运行记录至少能关联到请求/用户、允许的工具调用、模型/配置版本、结果状态与现有 `request_id` 或其可追溯的关联标识。

业务方已允许将真实生产库存数据发送给 OpenAI API；但服务端仍必须只发送回答所需的白名单字段与最小记录集，不得发送 JWT、密码、连接串、API 密钥或无关的用户资料。每次外发应记录供应商、模型、数据类别、调用时间、关联运行与 `request_id`。技术设计必须采用项目级 API 凭据，明确所用端点及其数据保留行为，并在实施前核对可用的数据保留控制；不得把“不用于训练”表述为“无日志”或“零留存”。

### R5：价值与安全均需量化

在进入实现前，规划必须指定一组与首个场景对应的代表性问题、期望答案或判定规则、禁止行为测试，以及由业务方确认的成功阈值。评测不能只依赖主观演示。

首轮验收基线已确定：使用 30 个经人工核验的库存问题；至少 90% 的回答必须正确且能追溯到来源工具/数据；所有写操作、未声明工具调用和越权访问必须被阻止；95% 的响应须在 10 秒内完成。每次调用成本必须被记录，但首轮不设硬预算上限。

### R6：保持可退出性

规划必须说明关闭 AI 入口、撤销工具权限或改用另一模型提供方时的最小影响范围；现有业务页面和 API 在试点关闭后必须无行为变化。

## 初步候选与选择原则

库存域是首个已确认的试点，因为已有分页的、受控的查询 API 与业务页面，且回答可由现有业务数据人工核验。首版受众为超级管理员；试点只支持在已授权数据范围内按日期、加工单位、品号或单号解释：库存余额、库存单据和库存台账记录。

试点不支持新增、编辑、删除、恢复单据，不支持执行库存调整，不支持跨权限数据汇总，也不承诺预测、补数或替代人工业务判断。没有匹配数据、数据不完整或权限不足时，产品必须明确说明而非生成推测性答案。
