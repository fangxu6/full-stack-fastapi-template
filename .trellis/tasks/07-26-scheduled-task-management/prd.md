# 定时任务管理系统

## Goal

提供一个受控、可审计的定时任务管理能力。运维或业务管理员可通过已部署 Python
实现类的完整路径创建、配置、启停和人工执行任务，而无需为每项任务修改 Celery Beat
源码。

## Background

- 后端已经使用 Celery + Redis：默认单队列、Worker 单并发、JSON 序列化、晚确认与
  至少一次执行语义；Beat 和业务时区均为 `Asia/Shanghai`。
- Redis 仅保存 broker 和短期技术结果。任务定义、运行历史、库存日报和告警限频状态都
  必须保存在 PostgreSQL。
- 当前固定 Beat 包含每日测试邮件、库存日报创建和库存日报投递重试；库存日报任务在
  `app.modules.inventory`，自身在数据库边界保持幂等。
- 新独立实体遵循 BIGINT generated-always identity 与模块数据库命名空间契约；任务定义
  是用户维护的业务配置，必须使用完整审计字段。运行记录是自动化技术记录，不伪造
  “系统用户”。

## Requirements

### Scheduling and execution

- 复用现有 Celery/Redis；不引入 APScheduler、第二个调度器、队列或工作流引擎。
- 固定 Beat 每分钟投递扫描任务。扫描器读取 PostgreSQL 定义，在计划所在的上海本地
  分钟内创建自动运行；落在后续分钟即视为错过，直接推进到下一个未来时点，不补跑。
- 每个任务定义只有一个标准五段 Cron（分钟、小时、日、月、周），按
  `Asia/Shanghai` 解释，`next_run_at` 以 UTC 存储。Cron 使用 Celery 解析器，日与星期
  同时受限时采用 AND 语义。
- 任务类路径必须是已部署代码中的
  `app.modules.<business_module>.scheduled_tasks.<Class>`，保存、更新和运行时均验证
  模块范围、导入对象、基类和 Pydantic 配置模型；不允许任意函数、表达式或脚本执行。
- 每次运行冻结类路径、已校验配置、计划时点和触发方式。之后编辑任务只影响新运行；
  已排队运行继续使用旧快照。
- Worker 只接收运行 ID，在任务内建立数据库 session、加锁领取记录、执行实现类并写回
  状态。业务实现自行在其持久化边界保证幂等；通用运行器不自动重试业务失败。
- 同一任务定义最多一条排队或执行中运行。自动到期时已有活动运行，创建一条已跳过的
  历史记录、推进下一时点并告警；人工操作遇到活动运行返回冲突。
- 停用取消尚未开始的排队运行；已经开始的运行允许完成。软删除要求没有活动运行，
  删除即停用并从默认列表和扫描器排除；恢复后保持停用并重新计算未来时点。

### Task configuration and manual operations

- 新建任务默认停用，显式启用后才参与自动调度；人工立即运行和单个历史补发不依赖
  启用状态。
- 所有实现类默认支持人工立即运行和单个历史补发，不增加实现类级开关。立即运行以请求
  当刻的上海时间作为业务参考；历史补发必须选择过去 90 天内、精确匹配 Cron 的时点。
- API 使用服务端 Pydantic 校验 JSON 配置；配置和运行快照不得保存密码、令牌、连接串或
  其他凭据，实现类仅通过环境设置读取凭据。
- 管理页包含受 RBAC 保护的任务列表、创建/编辑、启停、软删除/恢复、立即运行、单时点
  补发和运行历史。配置以 JSON 文本编辑；可读取类的 Pydantic JSON Schema，但不创建
  动态表单或 Cron 未来时点预览。

### Inventory migration

- 将库存日报“每日创建”和“15 分钟投递重试”迁移为首批受管任务，删除等价固定 Beat
  条目，保留现有日报聚合、SMTP 投递、时区和幂等逻辑；每日测试邮件继续是固定任务。
- 初始化数据在 IAM bootstrap 后幂等创建并自动启用这两条任务，使用真实
  `FIRST_SUPERUSER` 作为定义审计创建人；不会覆盖管理员之后的任何修改。
- 日报创建若已排队但 Worker 在上海时间 08:15 后才实际开始，则标记已跳过，不补发，
  保持当前窗口语义。

### Observability, alerts, and retention

- 运行历史保存状态、时间、触发方式、计划时点、冻结快照和安全错误类别/摘要；不保存
  任意业务返回内容或完整异常堆栈。自动运行不写审计用户，手工运行记录实际触发人。
- 保留运行记录及冻结快照 90 天，由每日固定清理任务删除；任务定义不做物理删除。
- 通过现有 SMTP 向 `SCHEDULED_TASK_ALERT_RECIPIENTS` 全局收件人发送运维告警。触发：
  运行失败、类路径/冻结配置无法加载、因活动运行跳过。手工冲突不告警，不发送恢复邮件。
- 同一任务与告警类别一小时内最多一封。成功运行清除运行失败和活动阻塞的限频状态；
  类路径或配置错误仅在有效配置保存后清除限频状态。
- `staging`/`production` 中缺少 SMTP 或告警收件人时，Worker 和 Beat 拒绝启动，HTTP API
  可继续启动；`local` 仅记录无法投递告警。类路径/配置因部署变化失效时任务保持启用，
  跳过当次、告警，并在代码或有效配置修复后自动恢复后续调度。

### Authorization

- `scheduler.jobs.read`：查看任务定义、配置、Schema 和运行历史。
- `scheduler.jobs.manage`：创建、更新、启停、人工运行、补发、软删除和恢复；依赖 read。
- 平台管理员自动拥有两项权限；其他角色通过现有 RBAC 显式授予。

## Acceptance Criteria

- [ ] `scheduler_job` 与 `scheduler_run` 使用 `scheduler_` 命名空间、BIGINT identity、
  显式约束和索引；定义满足完整审计字段，运行记录明确实现技术记录例外。
- [ ] API 只接受受限类路径和严格 Pydantic JSON 配置；非法路径、非任务类、无效 Cron、
  无效配置、凭据字段和客户端审计字段均被拒绝。
- [ ] 扫描器仅在计划分钟创建运行，错过计划不补跑；Cron 时区、AND 语义、下一时点和
  同任务活动运行的跳过语义有自动化测试。
- [ ] Worker 以运行 ID 领取执行，支持晚确认后的过期租约重领；成功、失败、取消、跳过
  均有可追踪状态，且不持久化原始异常或业务返回数据。
- [ ] API 与管理页完整支持任务 CRUD、启停、删除/恢复、立即运行、90 天单时点补发、
  配置 Schema 与分页运行历史，并正确执行 `scheduler.jobs.read/manage` 权限。
- [ ] 库存日报两项计划通过初始化数据自动创建且启用；固定 Beat 不再重复投递，08:15
  后实际开始的日报运行跳过，原有日报投递任务仍可执行。
- [ ] SMTP 告警覆盖三类事件、每任务每类别每小时限频、成功/有效配置清除规则，以及
  非本地环境 Worker/Beat 的启动前配置失败。
- [ ] 每日清理只删除超过 90 天的运行和快照；迁移升级、降级和测试数据库清理覆盖新增表。

## Out of Scope

- 任意 Python、函数、表达式、上传脚本或外部代码执行。
- 多 Cron 计划、Cron 后续时点预览、日期范围批量补发和超过 90 天的历史补发。
- 每实现类的人工操作开关、通用业务重试、人工确认、值班排班、升级链路、恢复提醒。
- 变更库存日报业务口径、SMTP 投递语义、Celery 基础运行时参数或新增队列。

已确认的后续能力见 [deferred-iterations.md](deferred-iterations.md)，不构成本期验收。
