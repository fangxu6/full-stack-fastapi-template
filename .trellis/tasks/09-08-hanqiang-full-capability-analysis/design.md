# 技术设计：Hanqiang 全量能力分析与 prod 文档

## 1. 交付边界

本任务是文档整理和生产落地设计，不改运行时代码。提交级文档是历史证据，当前模板源码、`.trellis/spec/` 和 `docs/llm-wiki/` 是当前基线事实源；两者冲突时必须分别标注“历史实现”和“当前模板事实”。

## 2. 证据处理

1. 以 `rg --files docs/hanqiang-core-contributions` 得到的提交级文件清单为全集。
2. 逐文件提取标题、SHA、变更主题、影响边界、复用契约、历史缺陷、验收要求和 CodeGraph/Git 复核路径。
3. 通过文件名和索引链接做覆盖校验，修复总索引遗漏，不用总索引中的旧计数作为全集。
4. 将重复提交按能力生命周期合并，但在矩阵中保留每个来源文件，确保结论可追溯。

## 3. 能力分类模型

每项能力只能有一个主归属，并可标注跨层消费者：

- 现有平台基线：IAM/权限、审计/请求追踪、邮件 Outbox/Celery、Scheduler、基础配置与数据库事务。
- 后端候选：密钥与 Redis 运行时、通用枚举、数据导入/导出与安全文件存储、文件监控/远程抓取安全、事件回调、通知 Adapter、审批流、服务通信、外部集成。
- 前端候选：应用壳/权限导航/标签页、通用枚举与列表筛选、导入导出交互、平台能力管理界面、前端容错与共享工具。
- 交叉治理：状态迁移、幂等/租约、权限与租户、审计/观测、配置/密钥、迁移/发布/回滚。

能力决策使用四种值：

| 决策 | 含义 |
| --- | --- |
| `reuse-existing` | 模板已有等价接缝，只补 prod 约束或消费说明 |
| `candidate` | 历史证据表明是独立平台能力，满足真实需求后可建任务 |
| `defer` | 有价值但缺少真实消费者、外部契约或必要前置条件 |
| `no-platform-action` | 单一业务、展示细节或不能安全复用的历史实现 |

## 4. Prod 文档结构

确认保留的能力写入 `docs/hanqiang-core-contributions/prod/`，每份文档按同一顺序组织：

1. 目标、用户/运维价值和非目标；
2. 启动条件、所有权与边界；
3. 领域模型、状态迁移和不变量；
4. API、事件、任务或前端契约；
5. IAM、租户隔离、敏感数据和安全威胁；
6. 幂等、并发、租约、超时、重试、死信和恢复；
7. 审计、日志、指标、Trace/Request ID 与告警；
8. 配置、密钥、依赖和环境差异；
9. 数据迁移、兼容窗口、发布、回滚和运维检查；
10. 单元/集成/API/UI 验收清单；
11. 来源提交和明确不复制的历史行为。

不适用章节保留并明确说明“不适用及原因”，避免不同能力的生产标准漂移。暂缓能力使用同一入口格式的短文档，只写门槛、依赖、禁止提前建设范围和未来任务拆分。

## 5. 与当前模板的集成原则

- 后端能力优先接入 `backend/app/core/*`、`backend/app/infra/*`、`backend/app/modules/*` 的现有边界；简单 CRUD 不凭历史目录复制。
- 所有业务状态在所属模块内建立状态迁移矩阵，不创建跨领域全局状态机。
- 后台任务只传 ID/JSON 可序列化上下文，PostgreSQL 保存业务事实；Celery 不作为完成事实源。
- 外部 HTTP、文件、通知和密钥必须经过受控 Adapter/策略边界；不允许任意 Python 路径执行或前端单独判权。
- 前端页面进入 `app/*`、`platform/*`、`features/*` 或 `shared/*` 前通过现有分层和 shared admission 规则；API 类型继续来自生成客户端。

## 6. 发布与回滚形状

文档更新按“矩阵/索引 → prod 入口 → 总报告”顺序完成。任何未来代码任务必须另建 Trellis 子任务，并在其自身计划中决定迁移、OpenAPI、E2E 和回滚；本任务不引入占位 API 或 UI。
