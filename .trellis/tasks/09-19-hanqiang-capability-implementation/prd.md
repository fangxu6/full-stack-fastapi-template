# Hanqiang 平台能力实施落地：事件回调内核

## Goal

交付可独立验证的事件回调内核，使未来业务模块能够在自己的事务中登记事件，在提交后可靠地调用代码注册的处理器，并在进程故障后恢复处理。当前价值是建立经过验证的基础能力；不宣称已经交付业务闭环或可直接上线的 Webhook 产品。

## Background and Confirmed Facts

- 归档任务 `.trellis/tasks/archive/2026-09/09-08-hanqiang-full-capability-analysis` 完成的是研究与设计，未实施事件运行时代码。来源入口是 `docs/hanqiang-platform-capability-assessment.md` 和 `docs/hanqiang-core-contributions/prod/prod-event-callback-webhook.md`。
- **已确认范围**：第一期只做内核，不绑定真实业务消费者，Webhook 与具体业务适配器延期。这是本任务对历史“有消费者才启动”门槛的明确范围调整，不代表其它候选能力也获得实施授权。延期清单见 [deferred-iterations.md](deferred-iterations.md)。
- 当前已有 PostgreSQL、IAM/RBAC、AuditEvent、Request ID、EmailOutbox、Celery、Scheduler 和 Actor 机制；没有统一租户模型。2026-09-19 的源码与方案复核依据、问题严重度及修正映射见 [research/requirements-review.md](research/requirements-review.md)。

## Requirements

### R1. 平台内核边界

内核拥有事件信封、不可变发布记录、处理器匹配、投递状态、租约、重试、恢复和审计。业务模块未来拥有事件语义、资源快照、资源授权与副作用幂等。测试假处理器只存在于隔离测试环境，不注册为生产能力。成功状态只表示处理器按协议正常结束。

### R2. 当前模板边界

复用现有权限、事务、Actor、审计与 Celery 运行时。资源 ID 和 payload 均不能作为授权凭据；不新增伪租户字段，也不声称提供租户隔离。数据库投递记录是唯一执行事实源，Broker 确认不代表执行成功。不重构 EmailOutbox/Scheduler 为通用框架。

### R3. 生产契约与失败恢复

必须明确数据约束、状态迁移、发布/处理协议、输入限制、并发、失败恢复、观测、迁移与回滚，并以行为测试验证：

- 发布与调用方业务事务同成同败，提交前不发消息、不调用处理器。
- 区分派发租约和执行租约；扫描有批量上限，发送失败不消耗处理次数，过期租约可恢复。不得每轮重复发送全部积压记录。
- 执行是 at-least-once，不承诺只执行一次或全局顺序。旧 Worker 的结果不得覆盖新尝试或重复产生审计。
- 沿用现有 Outbox 的有限自动重试基线：最多 8 次执行尝试、失败后等待 15 分钟。`FAILED` 保留记录；人工重放仍在后续适配范围，不把改状态或重新生成事件 ID 当作补偿方案。

原设计高风险缺口：扫描未定义派发预占（`backend/app/modules/scheduler/run_lifecycle.py:97`、`backend/app/modules/scheduler/orchestration.py:42`）；lease token 未列入模型。详见复核记录 F-02/F-03。

### R4. 增量交付与验证边界

本期交付事件内核、必要迁移、任务接入和测试，不新增业务 HTTP API、菜单或前端页面。跨数据库、Broker、Worker 的链路必须用真实隔离运行时验证，eager 测试不能代替进程故障与消息恢复验收。

采用 [e2e-api-tests.md](e2e-api-tests.md) 记录跨层流程：内部协议填写为流程入口，HTTP 仅使用已有健康检查，不为测试增加产品 API。未来公开 schema、路由或权限变化仍需同步 client、guards 和菜单验证。

### R5. 发布幂等和快照稳定性

`event_id` 是内核唯一发布去重键。同 ID、同业务内容重试返回原发布记录，不增加投递或审计；同 ID、不同业务内容明确冲突。并发发布遵循同样规则，不能破坏调用方已有事务写入。

请求/追踪上下文变化不应让同一事件重试变成冲突，首次发布的上下文保留不变。可选 `idempotency_key` 是传递给未来消费者的业务信息，不形成另一套数据库去重规则。输入修改、处理器修改和不同处理器间共享可变对象均不得篡改已保存的快照。

原设计中自动生成 trace ID 与“比较完整信封”的矛盾归入本需求；测试需要覆盖跨请求重试和并发冲突（F-01）。

### R6. 注册、版本与零订阅行为

处理器仅由受信代码显式注册，键稳定、重复键启动失败，发布端和 Worker 使用同一版本的注册声明。禁止数据库 import 路径、任意脚本与表达式。

发布时冻结匹配的处理器集合；无匹配时仍保存事件但不创建投递，以后新增处理器不自动消费历史事件。重复发布也不得隐式补投。版本不支持、注册项缺失等契约错误有明确的失败分类和无副作用保证。

### R7. 审计、日志与身份归属

发布/状态变化与对应 AuditEvent 在同一事务提交；审计写入失败不能留下已提交的状态变化。重复命令和旧租约结果不增加语义审计。

继承现有 Actor 语义：发布归属调用方；首个执行尝试保留发起人，自动重试/恢复归属 System Actor。原始发起人不能被重试覆盖，也不能通过 payload 指定 Actor。

事件/投递 ID、处理器键、状态和错误分类写入数据库及受控审计。普通运行日志沿用封闭字段边界，不加入业务标识、payload 或任意异常文本；受控处理异常不得泄漏到 Celery 默认详细异常记录。当前规范依据：`backend/app/core/observability.py:188`、`backend/app/core/celery.py:149`、`backend/app/modules/audit/service.py:13`（F-04/F-05）。

### R8. 数据生命周期与兼容

应用回滚停止发布与派发、保留事件/投递/审计数据；删表 downgrade 仅用于隔离迁移测试，不作为有数据环境的常规回滚。本期不自动清理事件事实，不能把 AuditEvent 的既有 365 天清理规则误认为事件 payload 的保留策略。

真实业务启用前须另行确认数据分类、保留周期、容量和长时间处理的超时/幂等策略。当前不实现清理平台、人工重放或历史 attempt 明细表。

## Acceptance Criteria

| ID | 对应需求 | 可观察验收结果 |
|---|---|---|
| AC-01 | R1、R2、R4 | 生产注册表无假处理器；无新增 HTTP/前端/业务发布者；不新增并行权限、Scheduler 或 Outbox 框架。 |
| AC-02 | R3、R5、R7 | 业务事务回滚后，发布、投递、审计均不存在；Worker 不可见未提交事件，也不触发处理器。 |
| AC-03 | R5 | 顺序及并发同 ID/同内容最终只有一份发布和一组投递；不同内容冲突；请求/追踪变化不冲突；其它事务写入不被错误回滚。 |
| AC-04 | R5、R6 | 不合法/超限 JSON 拒绝且无写入；调用方及处理器修改快照不影响持久化或其它处理器；无匹配、版本不支持、重复注册和历史不补投行为明确。 |
| AC-05 | R3 | 两个扫描器不在有效派发租约内重复预占；每批最多 100 条；单条发送失败不阻断其它记录，不增加 attempt，下一轮可重试。 |
| AC-06 | R3 | 重复任务只产生一次有效 claim；未到重试时间不执行；执行成功/异常/8 次耗尽/处理器缺失均进入规定状态。 |
| AC-07 | R3 | Worker 中断后可恢复；旧 token 的成功和失败结果均为 no-op；处理器副作用后崩溃允许重复调用且不伪称 exactly-once。 |
| AC-08 | R7 | Actor、原始 request ID 和语义审计准确；审计失败回滚状态；敏感标记不进入日志、异常输出和 Broker 结果；正常日志不含业务标识。 |
| AC-09 | R4 | PostgreSQL + 独立 Redis + 独立 Worker/扫描入口验证真实持久化、派发、执行与故障恢复，并记录命令和结果。 |
| AC-10 | R8 | 隔离库 upgrade/downgrade/upgrade 通过；约束、中文注释、模型发现和清理顺序正确；应用回滚演练保留数据。 |
| AC-11 | R2、R4 | 后端完整 lint/type/format、事件测试和受影响 Celery/Outbox/Scheduler/审计回归通过，任务上下文校验通过且无无关修改。 |

## Out of Scope

- Webhook、具体业务事件适配器、入站回调、动态订阅/配置 UI、任意 Python/表达式/URL、级联编排和工作流设计器。
- 通用枚举、文件平台、文件监控、通知 Adapter、服务通信、审批或外部集成中心。
- 多租户平台、人工重放、历史 attempt 表、事件历史补投、自动数据清理、告警平台、新队列或新部署框架。
