# Hanqiang 平台能力实施落地

## Goal

基于已完成的 Hanqiang 全量能力分析，把被确认有真实需求的候选平台能力以当前模板的边界、权限、审计、异步任务和数据事实约束落地为可运行代码。实施必须按可独立验收的能力切片推进，不复制历史项目的业务字段、目录结构或不安全执行器。

## Background and Confirmed Facts

- 归档任务 `.trellis/tasks/archive/2026-09/09-08-hanqiang-full-capability-analysis` 已完成研究和生产设计，但明确未实施运行时代码。
- `docs/hanqiang-platform-capability-assessment.md` 将候选能力归为：通用枚举与参考数据、文件导入导出与安全存储、事件回调与最小 Webhook；文件监控、通知 Adapter、审批、服务通信、外部集成中心均为暂缓。
- 当前模板已有 IAM/RBAC、`AuditEvent`、Request ID、EmailOutbox、Celery、Scheduler、数据库事务和前后端分层，实施必须复用这些边界。
- 归档评估要求具体 Adapter 先确认真实消费者；当前任务先落地不依赖具体业务的事件回调内核，并把 Webhook 和业务适配器登记为后续独立迭代，不把它们变成占位 API、页面或配置。

## Requirements

### R1. 平台内核边界

第一期不绑定具体业务消费者。内核只拥有事件信封、事件登记、投递状态、处理协议、租约/幂等/恢复和审计；业务模块未来拥有事件语义、资源快照和业务处理。用测试假执行器验证内核，不将假执行器作为生产能力暴露。

### R2. 当前模板边界

复用现有 IAM、租户/所有权、审计、Request ID、数据库会话、Celery/Outbox、配置和前端生成客户端边界。不得创建平行权限体系、平行任务事实源、任意 Python 执行、任意 URL 回调、前端单独判权或跨领域全局状态机。

### R3. 生产契约

每个实施切片必须在任务设计中明确数据模型与状态迁移、API/事件/任务契约、权限与租户隔离、输入校验、安全威胁、幂等与并发、失败恢复、审计与观测、配置/密钥、迁移、测试、发布和回滚。

### R4. 增量交付

能力按独立切片实现和验证；本期不增加面向业务用户的 API、菜单或前端页面。未来公开后端 schema 变更时同步生成前端 client，路由或权限变更时同步验证服务端授权、前端 guards 和菜单可见性。

## Acceptance Criteria

- [ ] 事件内核的发布、持久化、处理、失败恢复和审计契约已确认并记录，测试假执行器覆盖完整状态路径。
- [ ] 实施任务的 `prd.md`、`design.md`、`implement.md` 和适用的 E2E 计划完成并获批准后，任务才进入 `in_progress`。
- [ ] 第一切片仅修改事件内核运行时代码、测试和必要数据库迁移，不复制无关历史能力。
- [ ] 通过单元、数据库/任务集成和失败副作用验证；检查租户上下文、幂等、审计、Request ID、租约、重试/恢复和回滚行为。
- [ ] 未新增 Webhook、业务事件、动态配置 UI、菜单、密钥字段或宽松 fallback 占位物。
- [ ] 通过 Trellis 质量检查、相关 spec 检查和任务校验，工作区无无关修改。

## Confirmed Decision

第一期只实施事件回调内核，不实施最小出站 Webhook，也不绑定具体业务消费者。内核通过稳定的事件发布协议和处理器协议为未来业务提供接缝，使用测试假执行器完成可运行验收。这样可以先交付平台底座，但事件字段语义、业务快照、消费者幂等和外部安全策略必须留给未来适配任务。

## Out of Scope for the First Slice

- 没有真实消费者的通用审批流、外部集成中心、WeCom/其它通知 Adapter、服务通信、文件监控和远程抓取。
- 最小出站 Webhook、任何业务事件发布者、任意 Python 路径、任意表达式、任意 URL、复杂级联编排、全量工作流设计器或与历史项目一致的业务页面。
- 未被第一切片直接需要的 API、前端菜单和配置。事件内核自身需要的数据库迁移属于当前范围。

## Planning Status

用户已确认“只实施事件回调内核，Webhook 和具体业务适配器延期”的范围。当前进入设计与实施计划审阅；任务在计划审批前保持 `planning`，不启动代码实施。
