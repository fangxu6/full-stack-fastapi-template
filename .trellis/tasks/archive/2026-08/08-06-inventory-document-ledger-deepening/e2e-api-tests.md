# Inventory Document and Ledger API E2E Test Plan

## Environment

- Backend: `http://127.0.0.1:8000`
- Health: `/api/v1/utils/health-check/`
- Use a dedicated database whose name ends in `_test` or `_pytest`; never use
  the development database.
- Use dedicated users with the exact inventory permissions required by each
  case. The request session owns HTTP commits and rollbacks; importer and
  correction executor setup owns its explicit transaction phases.

## Cases

| ID | Endpoint / Flow | Setup Data | Request | Expected Response | Persistence / Side Effects | Failure Assertions |
| --- | --- | --- | --- | --- | --- | --- |
| E2E-001 | Unit lifecycle and active resolution | User has `inventory.masters.read` and `inventory.masters.manage`. | Create a processing unit with surrounding whitespace, list it by normalized name, update its name and then set `is_active=false`. | `POST`/`PUT` return `200`; list returns one normalized unit with `count=1`. | One unit row remains active-history compatible, with normalized name and audit attribution. | Creating a document with the inactive unit returns `400` `Processing unit is not active`; no document, line, or ledger row is committed. A duplicate normalized name returns `409`. |
| E2E-002 | Document create and ledger invariant | Active processing unit; user has `inventory.documents.manage`, `inventory.documents.read`, `inventory.balances.read`, and `inventory.ledger.read`. | `POST /api/v1/inventory/documents` with a `RAW_RECEIPT`, one line, and `quantity_rolls: "0.50"`; then read the document, raw balance, and ledger. | Create/detail return `200`; line and ledger expose `"0.50"`; balance is `"0.50"`. | One document, line, and ledger entry commit together; the ledger movement is positive and queries/export remain readable. | A `RAW_RETURN` of `0.60` returns `409` with the existing negative-balance detail and leaves document count, ledger rows, and balance unchanged. Zero, negative, or three-decimal roll input returns `422` with `detail` and `request_id`. |
| E2E-003 | Direct document mutation guard | A non-legacy document with ledger effects. | Call `PUT`, `DELETE`, and `/restore` for the document with `inventory.documents.manage`. | Each direct mutation returns `409` with `detail: "INVENTORY_CORRECTION_REQUIRED"`. | Original document fields, `deleted_at`, document lines, ledger entries, and balance remain unchanged. | No partial line replacement, soft-delete, restore, or ledger mutation is persisted after any rejected request. |
| E2E-004 | Standard document workbook import and rollback | Active processing unit; workbook uses the generated `单据导入` headers and repeats one document number across two lines. | `POST /api/v1/inventory/excel/imports/documents` as multipart `workbook`; include repeated `document_types` when page scope is required. | Valid grouped workbook returns `201` with `created_documents` and document numbers; invalid group or out-of-scope type returns `422` with worksheet/row/column/field/message and `request_id`. | Valid input creates grouped documents, lines, and ledger effects through the new seams; no import helper commits independently. | Any issue rolls back the whole workbook, including an earlier valid group. An inactive or unknown unit reports the cell issue and persists no document. |
| E2E-005 | Legacy historical import compatibility | Two legacy workbooks containing raw and finished historical rows, source dates, balances, and workbook/sheet names. | `POST /api/v1/inventory/excel/imports/legacy` with `raw_workbook` and `finished_workbook`; then export RAW and FINISHED ledgers. | Import returns `201` with an `import_batch_id` and report counts. Exports return `200` XLSX with the expected headers and rows. | `InventoryImportBatch`, `LegacyImportRow`, historical documents/ledger entries, raw cell snapshots, legacy flags, and reconciliation openings retain traceability. Export remarks preserve historical source details. | Re-importing the same byte sources returns the existing `409` conflict and creates no second batch or duplicate ledger entries. Invalid legacy rows return `422` with source worksheet/row coordinates and roll back the batch. |
| E2E-006 | Correction request and approved document application | A document with current `updated_at`; request user has `inventory.corrections.request`, reviewer has `inventory.corrections.review`; isolated scheduler execution is available. | Create an `UPDATE_DOCUMENT` request with timezone-aware `expected_updated_at`, typed proposal, and reason; approve it; run the correction executor; read request, document, ledger, and balance. | Create returns `201 PENDING_REVIEW`; approve returns `200 APPROVED` with one pending work item; executor produces `APPLIED/SUCCEEDED`; repeated approval/execution is idempotent. | Approved application changes the document and replaces its line/ledger effects atomically; balance reflects the proposal; one applied audit event records only the fixed metadata keys. | Invalid/naive timestamps, unknown fields, missing proposal/reason return `422` with no correction row. Stale approval returns `200 STALE` with no work item. Negative-balance application becomes terminal failure with unchanged document/ledger and no automatic retry. |
| E2E-007 | Approved delete/restore correction operations | A document with ledger effects and a current correction target; same request/reviewer setup as E2E-006. | Submit and approve `DELETE_DOCUMENT`, execute it, verify deleted document/ledger behavior; submit and approve `RESTORE_DOCUMENT`, execute it. | Each request reaches `APPLIED`; executor work item/attempt reaches `SUCCEEDED`. | Delete sets `deleted_at` and marks linked ledger effects deleted atomically; restore clears `deleted_at`, restores ledger visibility, and preserves the original audit creator. | Direct delete/restore remains blocked by the correction gate. A restore that would create a negative balance fails without changing document or ledger state. |
| E2E-008 | Query and export boundary preservation | Documents, active/inactive units, raw/finished ledger rows, and a historical row exist; user has read permissions only. | Exercise document list/detail, raw/finished balances, ledger list, suggestions, and `/excel/ledger` with date, processing-unit, receiving-unit, and document-number filters. | Read endpoints return the existing `data/count` shapes with deterministic filtered results; export returns an XLSX attachment. | Read/export paths do not create or mutate inventory rows; document-linked filters exclude unrelated historical rows while unfiltered export retains them. | Missing permission returns `403`; unauthenticated access returns `401`; invalid pagination/query enum returns unified `422` with `detail`, `request_id`, and `X-Request-ID`. |
| E2E-009 | Transaction and permission regression | Dedicated manage/read users, one active unit, and a clean isolated database. | Run successful HTTP writes, expected domain failures, standard import failures, and correction failures under TestClient or local HTTP. | Successful writes commit exactly once; expected failures retain their existing status/detail contract. | No partial business, audit, import, correction, line, or ledger rows survive a failed HTTP request; explicit importer/worker transactions remain caller-owned. | Verify manage/read permission matrix for units, documents, Excel, ledger, and correction routes; every changed error path retains the global `detail + request_id` envelope. |

## Execution

- Verify the health endpoint and isolated database before running the cases.
- Reuse the existing inventory API/importer/correction fixtures where possible;
  add only focused assertions for the moved module entry points.
- Run the focused inventory API, importer, correction, and request-unit-of-work
  tests, then the full relevant backend test scope against the isolated database.
- Record response bodies, database assertions, and any concrete environment
  blocker in the task validation notes and `implement.md`.
