Problem

The permission interface is reached through a direct route read, repeated Query declarations, and separate menu metadata. Cache, retry, and error behavior can diverge.

Solution

Concentrate permission fetching, cached state, and error classification in one module. Let guards, sidebar, and pages consume that locality; keep route files thin.

Wins

  • locality: one permission read
  • leverage: one retry policy
  • tests hit one interface
ADR note: aligns with the existing frontend rule that permission logic stays centralized; it does not require a design-system migration.

Problem

Master data, document commands, ledger writes, balance queries, suggestions, and Excel compatibility share one implementation surface. The core document/ledger invariant is mainly reached through route tests.

Solution

Concentrate the document-to-ledger invariant behind one deep module, leave master data separate, and keep Excel as an adapter into that module.

Wins

  • locality: ledger bugs stay together
  • leverage: one command path
  • tests target the invariant
ADR note: fits ADR-0002 and ADR-0006 only if the existing request-scoped transaction owner remains outside the module.

Problem

One service contains definition validation and run persistence while one task file contains dispatch, execution, alerting, retry, and cleanup phases.

Solution

Give task definition and run lifecycle distinct depth, with Celery and outbox kept as adapters around PostgreSQL state.

Wins

  • locality: lifecycle state is explicit
  • leverage: runtime tests stay focused
  • seam: adapters are replaceable
ADR note: ADR-0005 already defines the runtime; this candidate is only worth reopening if the current task registry/run coupling causes measurable change friction.

Top recommendation

Candidate A: deepen the permission access module

It has the smallest credible scope, a visible current duplication pattern, and direct leverage across route guards, navigation, feature pages, retry behavior, and tests. It can improve locality without changing backend contracts or the existing design system.

Next decision: choose a candidate to explore through the grilling loop. No interface or implementation should be committed from this report alone.
