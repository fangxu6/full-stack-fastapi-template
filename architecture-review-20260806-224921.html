Candidate 01

Deepen scheduler execution outcomes behind the lifecycle seam

Strong in-process

Files

  • backend/app/modules/scheduler/run_lifecycle.py:146-195
  • backend/app/modules/scheduler/tasks.py:171-254
  • backend/app/modules/scheduler/scheduler_alerts.py:1-45
  • backend/tests/modules/scheduler/test_scheduler_tasks.py:71-457

Problem

The durable run lifecycle module owns claim and persistence, but the Celery adapter still resolves the task, classifies configuration/skipped/failed outcomes, chooses terminal fields, clears success alerts, and sends failure alerts. A run's outcome contract crosses the seam that ADR-0012 intentionally concentrated.

Solution

Deepen the scheduler execution module around outcome classification and terminal transition intent. Keep Celery message delivery, task invocation, and the existing alert module as adapters/orchestration; keep PostgreSQL persistence and the request/background transaction owners unchanged.

Wins

  • locality: outcome rules co-locate
  • leverage: task and lifecycle tests narrow
  • interface: terminal intent is explicit
  • alerts stay behind one seam
Deletion test: deleting an execution module would force configuration, skipped, failure, and alert-selection rules back into the Celery adapter. Concentrating those rules keeps orchestration thin and preserves depth.
ADR fit: revisits no decision. It completes ADR-0012's locality goal without merging Beat and Worker or adding a generic workflow framework.

Candidate 02

Separate correction request review from attempt execution

Worth exploring in-process

Files

  • backend/app/modules/inventory/correction_service.py:230-696
  • backend/app/modules/inventory/correction_service.py:697-960
  • backend/app/modules/inventory/correction_router.py:1-180
  • backend/app/modules/inventory/scheduled_tasks.py:60-127
  • backend/tests/api/routes/test_inventory_corrections.py:104-362

Problem

The 960-line implementation owns two different state families: HTTP request creation, review, recovery, and read projection; then background attempt leases, claims, application, and terminal failure. The route and scheduled-task callers use separate parts of one broad interface, so a status invariant crosses a weak seam.

Solution

Deepen one request-review module and one attempt-execution module. Keep document mutation in the existing document module, keep explicit transaction ownership in the route/task callers, and let each new module absorb only the state transitions it already owns.

Wins

  • locality: each state family is local
  • leverage: route and task callers narrow
  • tests hit one interface
  • lease rules stop leaking
Deletion test: deleting an attempt-execution module would push lease and terminal-state rules into scheduled_tasks; deleting a request-review module would push authorization and approval rules into routes. Splitting concentrates complexity instead of moving it.
ADR fit: aligns with ADR-0002 and ADR-0006. The seam must not own commit or rollback, and it must not introduce a generic state-machine framework.

Candidate 03

Split workbook adapters from import orchestration

Worth exploring adapter

Files

  • backend/app/modules/inventory/importer.py:74-210
  • backend/app/modules/inventory/importer.py:212-372, 505-805
  • backend/app/modules/inventory/router.py:95-136
  • backend/tests/modules/inventory/test_importer.py:56-429

Problem

The implementation handles the modern document template, legacy workbook header detection, date and quantity normalization, movement inference, issue aggregation, import-batch persistence, audit binding, and explicit commit/rollback. The format seam and transaction seam meet inside one file.

Solution

Give the modern template and legacy workbook family separate adapters for reading and normalization. Keep one import orchestration module responsible for normalized records, issue aggregation, batch identity, document/ledger writes, and caller-owned transaction behavior. Two adapters make the seam real; no new dependency is needed.

Wins

  • locality: format rules stay local
  • leverage: another format reuses orchestration
  • parser tests avoid database setup
  • transaction policy stays explicit
Constraint: the HTTP document import uses the request-scoped transaction, while import_workbooks() is a CLI-style caller that commits or rolls back explicitly. The adapter seam must not take ownership of either transaction.

Candidate 04

Keep the PM2 display adapter lossless

Strong adapter

Files

  • scripts/pm2-json-prefix.cjs:23-65, 86-89
  • scripts/pm2-json-prefix.test.cjs:8-32
  • ecosystem.config.js
  • .trellis/spec/backend/logging-guidelines.md:135-144

Problem

The adapter parses a child JSON line and returns only a human-readable prefix plus selected detail fields. The active logging specification requires the original child JSON after that display prefix, but the current implementation discards it. The interface is readable to operators but shallow for collectors.

Solution

Keep parsing only for deriving the display prefix, then append the exact original JSON line. Preserve non-JSON pass-through and child stderr/exit behavior. Add one assertion that a structured line retains fields omitted from the display prefix.

Wins

  • locality: presentation stays outside logging
  • leverage: operators and collectors share one payload
  • tests assert payload preservation
  • adapter seam becomes deterministic
Contract drift: `.trellis/spec/backend/logging-guidelines.md` says PM2-managed lines contain the original JSON after the display prefix. This is a correctness repair with leverage across collection and diagnosis, not a new logging module.
