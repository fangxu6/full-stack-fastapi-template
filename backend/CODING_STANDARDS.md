# Backend Coding Standards

This document defines the backend coding standards for `backend/` in this repository.

## 1. Scope and Principles

- Scope: all Python code in `backend/app`, tests in `backend/tests`, and backend scripts.
- Prioritize readability, correctness, and explicit typing over clever shortcuts.
- Keep changes focused; avoid unrelated refactors or large formatting-only diffs.

## 2. Language and Toolchain Baseline

- Python version: `>=3.10,<4.0`.
- Dependency and environment management: `uv`.
- Type checking: `mypy` in strict mode.
- Lint/format: `ruff` and project pre-commit hooks (`prek`).
- Testing: `pytest`.

## 3. Project Structure

- API routes live in `backend/app/api/routes/`.
- Dependency providers and request context helpers live in `backend/app/api/deps.py`.
- Data models and schemas live in `backend/app/models/`. Use submodules for different domains (e.g., `user.py`, `item.py`). Export public models in `backend/app/models/__init__.py`.
- CRUD operations (pure DB interactions) live in `backend/app/crud/`.
- Business logic (orchestrating CRUD, emails, external services) lives in `backend/app/services/`.
- Core configuration/security/database setup lives in `backend/app/core/`.
- Database migrations live in `backend/app/alembic/`.

## 4. Naming Conventions

- Modules and file names: `snake_case.py`.
- Variables/functions/methods: `snake_case`.
- Classes and Pydantic/SQLModel types: `PascalCase`.
- Constants and environment-style values: `UPPER_SNAKE_CASE`.
- Route handler names should be descriptive verbs, e.g. `create_user`, `read_items`.

## 5. Formatting and Imports

- Use 4 spaces for indentation.
- Follow ruff/isort import ordering; remove unused imports.
- Keep one logical concern per function and keep functions small when practical.
- Use UTF-8 and end every file with a trailing newline.

## 6. Type Safety and Data Modeling

- Add type hints for all function signatures and key local values.
- Treat `mypy` strict warnings as errors to fix, not to silence.
- For Pydantic/SQLModel data flow, prefer `model_validate` and `model_dump`.
- For partial updates on SQLModel entities, prefer `sqlmodel_update`.

## 7. API and Error Handling

- Raise `HTTPException` with explicit `status_code` and actionable `detail`.
- Keep API contract changes backward-aware when possible; if changed, update frontend client generation flow.
- Validate inputs at schema boundaries; avoid passing unvalidated dicts deep into business logic.

## 8. Logging, Side Effects, and Security

- Do not use `print`; use configured logging paths.
- Never commit secrets or modify `.env` files in feature changes.
- Keep authentication/authorization checks explicit in route and dependency layers.

## 9. Testing Standards

- Add or update tests for each behavior change in `backend/tests`.
- Prefer deterministic tests with clear arrange-act-assert structure.
- For bug fixes, add a regression test that fails before and passes after the fix.

## 10. Commands and Quality Gate

Run these before submitting backend changes:

```bash
cd backend
uv sync
bash scripts/lint.sh
uv run pytest tests/
```

For full-stack/container validation, use root-level test scripts when required.

## 11. Generated and Restricted Areas

- Do not hand-edit alembic autogenerated migration internals unless necessary and reviewed.
- Keep migration history linear and reviewable.
- Do not modify environment secrets or unrelated infrastructure config as part of backend feature work.

## 12. Pull Request Expectations

- One logical change per PR when possible.
- Include rationale (why), not only implementation details (what).
- Mention any schema/API changes and required follow-up actions (e.g. client regeneration).
