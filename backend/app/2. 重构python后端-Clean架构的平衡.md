在 Python 和 FastAPI 的技术栈下，且没有复杂外部依赖的单体系统中，==直接套用最标准的 Clean 架构（定义大量的 Abstract Base Class 作为 Port、手写无数个 DTO 转化器）通常会变成过度设计==。

Python 的核心优势是简洁与快速迭代。为了不让硬边界拖慢单体系统的开发进度，建议采用“轻量级 Clean 架构”（也称洋葱架构的实用简化版）。

---

## 1. 推荐的目录结构 (FastAPI 特化版)

在单体 Python 项目中，用模块化的方式来划定边界。不要按“层”拆分顶层目录，而是按“业务功能 (Domain)”拆分，这样未来系统变大时极易重构：

```text
app/
├── core/                  # 全局基础设施
│   ├── config.py          # 配置管理 (Pydantic Settings)
│   └── database.py        # 数据库连接池初始化 (SQLAlchemy/Tortoise)
│
└── modules/               # 业务模块集（按业务自治）
    └── orders/            # 以“订单模块”为例
        ├── domain.py      # 【核心】纯 Python 对象 (Pydantic/Dataclasses)，无 ORM
        ├── usecases.py    # 【应用】业务逻辑编排 (CreateOrder, CancelOrder)
        ├── router.py      # 【驱动适配器】FastAPI 路由与入参校验
        └── repository.py  # 【被动适配器】SQLAlchemy 增删改查实现
```

## 2. Python 落地轻量 Clean 的 4 个核心技巧

## ① 巧用 Pydantic 划分边界（拒绝手写繁琐的 DTO）

在 Java 中需要写 Entity、DTO、VO。在 Python 中，你可以让 Pydantic 同时充当多个角色，但要保持逻辑隔离：

- `domain.py`：定义业务的核心数据结构（使用 `pydantic.BaseModel` 或 `dataclass`）。绝对不要引入 SQLAlchemy 的 `Base`。
- `router.py`：定义 API 的入参（`OrderCreateSchema`）和出参（`OrderResponseSchema`）。
- 在 `usecases.py` 中，只接收和返回 `domain.py` 中定义的纯领域对象。

## ② 依赖注入：利用 FastAPI 的 `Depends` 实现反转

Python 是动态语言，不需要为了解耦非要写 `ABC`（抽象基类）作为 Port。可以直接利用 FastAPI 自带的依赖注入机制：

```python
# app/modules/orders/repository.py
class OrderRepository:
    def __init__(self, db_session):
        self.db = db_session
    def save(self, order_domain): ...

# app/modules/orders/usecases.py
class CreateOrderUseCase:
    def __init__(self, repo: OrderRepository):
        self.repo = repo
    def execute(self, user_id: int, items: list) -> OrderDomain:
        # 纯业务逻辑
        return self.repo.save(order)

# app/modules/orders/router.py
@router.post("/orders")
def create_order(payload: OrderCreate, db = Depends(get_db)):
    # 在这里组装：将数据库连接注入 Repo，再将 Repo 注入 UseCase
    repo = OrderRepository(db)
    usecase = CreateOrderUseCase(repo)
    return usecase.execute(payload.user_id, payload.items)
```

## ③ 什么时候可以“越界”？（单体系统的特权）

既然外部依赖不复杂，为了开发效率，可以允许以下适度妥协：

- 查询（Read）操作直接走 Repo：如果只是前端要展示一个简单的列表，不需要任何业务逻辑，`router.py` 可以直接调用 `repository.py` 的查询方法，跳过 `usecases.py`。
- 异常处理集中化：业务层（UseCase）直接抛出自定义的 Python 异常（如 `OrderNotFoundError`），在 FastAPI 全局注册 `exception_handler` 捕获它们并返回 404/400，避免在每一层都写 `try-except` 转发。

## ④ 数据库模型（ORM）必须隔离

在 Python 中最容易犯的错误是把 SQLAlchemy 的 Model 传来传去。

- 记住：`models.py`（SQLAlchemy 模型的定义）只能被 `repository.py` 看到。
- 进入 `usecases.py` 的数据，必须已经是转成领域对象（Domain Object）或字典的纯粹数据。

## 3. 给你的启动建议

由于是单体系统且依赖简单，前期千万不要引入微服务或者多项目（Submodule）结构。

1. 第一步：直接用上述的目录结构，在一个单体仓库中开发。
2. 第二步：编写业务逻辑时，确保 `usecases.py` 内部没有 `import sqlalchemy` 或者是任何第三方 API SDK 的代码。只要保证这一点，你的核心业务就是安全的，未来随时可以轻松迁移或重构。
