# Python 后端架构规则：ORM 隔离与实用边界

## 1. 规则定位

本规则用于后续 Python / FastAPI 后端项目的架构取舍。

目标不是严格套用 Clean Architecture，也不是让每张表都额外创建一套领域实体、DTO 和 Mapper，而是在开发效率和长期可维护性之间取得平衡。

核心原则：

> ORM 不需要完全隔离，但不能随意泄漏到模块边界外。

也就是说，SQLAlchemy Model 可以在 repository、crud、service 内部使用；但 API、任务、事件、跨模块调用等边界不应直接暴露 ORM 对象。

## 2. 简单 CRUD 可以复用 ORM

以下场景允许直接复用 SQLAlchemy Model，不强制新增领域实体类：

- 基础资料维护
- 配置表
- 字典表
- 简单列表查询
- 简单增删改查
- 没有复杂状态流转
- 没有跨表一致性规则
- 没有外部系统调用
- 没有后台任务或事件联动

推荐结构：

```text
router -> service/crud -> ORM
```

允许做法：

- repository / crud 直接操作 ORM
- service 内部接收和返回 ORM
- 简单接口由 Pydantic response schema 序列化 ORM
- 简单查询直接返回列表 DTO / dict / schema

不需要为每张简单表额外创建：

- Domain Entity
- Mapper
- UseCase
- Repository Interface
- Response Entity

## 3. 复杂业务才隔离 ORM

以下场景建议隔离 ORM，不要把 SQLAlchemy Model 当成业务对象到处传：

- 审批流
- 工单系统
- 质量流程
- 报表任务
- 文件导入 / 文件监控
- 事件回调
- 状态机
- 多表事务
- 外部系统调用
- Celery / 定时任务
- 跨模块协作

复杂业务推荐结构：

```text
api -> application/service -> repository -> ORM
```

必要时增加：

- Command
- Query
- Result DTO
- Domain Value Object
- Domain Service
- Repository
- Mapper

但仍然不要求每张表都建领域实体。只给核心业务概念建领域对象，例如：

- WorkOrder
- ApprovalProcess
- InspectionRequest
- ReportTask
- FileImportJob

明细表、关联表、日志表通常不需要单独领域建模，除非它们承载独立业务规则。

## 4. 边界规则

### 4.1 API 边界

API 入参和出参必须是 Pydantic schema、dict 或明确的 response model。

不建议：

- router 直接写 SQLAlchemy 查询
- router 直接操作 ORM 状态
- API response 直接依赖 ORM 的全部字段
- 把 ORM 对象原样作为接口契约

允许：

- router 调用 service
- service 返回 ORM 后由 response schema 过滤字段
- 简单 CRUD 中 router 调用 crud，但不在 router 内写复杂业务

### 4.2 Service 边界

service 可以使用 ORM，但要控制泄漏范围。

允许：

- service 内部 import ORM
- service 内部组合多个 ORM 查询
- service 返回 ORM 给同模块 router

不建议：

- service 把 ORM 传给另一个业务模块
- service 把 ORM 放进事件 payload
- service 把 ORM 放进 Celery task 参数
- service 长链路传递 ORM，导致隐式 session 依赖

复杂业务的 service 应优先返回 Result DTO 或明确的业务结果对象。

### 4.3 Repository / CRUD 边界

repository / crud 是 ORM 的主要归属地。

允许：

- 直接 import ORM
- 写 SQLAlchemy 查询
- 返回 ORM
- 执行 flush / refresh

建议：

- repository / crud 不主动 commit
- 事务提交由 application/service 或统一事务工具负责
- 复杂业务不要过度依赖通用 CRUD，应有专门 repository 或 query service

### 4.4 任务边界

Celery、APScheduler、后台任务不应传 ORM。

任务参数应使用：

- id
- code
- command payload
- 可序列化 dict
- Pydantic schema

任务内部重新开启 session，重新加载所需数据。

### 4.5 事件边界

事件 payload 必须可序列化，不允许包含 ORM 对象。

推荐事件数据：

```json
{
  "entity_id": "...",
  "event_type": "...",
  "operator_id": "...",
  "changed_fields": {}
}
```

事件处理器需要数据时，应通过 id 重新查询。

### 4.6 模块边界

跨模块调用尽量传：

- id
- code
- command
- query
- result DTO
- dict

不要跨模块传 ORM 对象。

## 5. 事务规则

事务只能有一个主人。

推荐：

```text
api -> application/service -> repository
       ↑
       这里决定 commit / rollback
```

规则：

- repository / crud 默认不主动 commit
- 一个写入用例尽量一次提交
- 失败时整体回滚
- 需要提交后发事件的，用 post-commit event
- 不在事务中途调用不可回滚的外部系统

简单 CRUD 可以先保留现状，但新项目和新模块优先采用统一事务边界。

## 6. 是否需要新增实体类的判断

不需要新增实体类：

- 只是数据库表的增删改查
- 没有复杂业务规则
- 没有状态流转
- 没有跨模块传递
- 没有外部任务或事件

建议新增领域对象或结果对象：

- 业务概念不等于单张表
- 一个操作会影响多张表
- 有状态机或状态流转规则
- 需要跨模块调用
- 需要进入任务队列
- 需要发布事件
- 单测需要脱离数据库验证核心规则

## 7. 默认落地策略

新项目建议从简单规则开始：

```text
app/
├── api/
├── core/
├── services/
├── repositories/
├── models/
├── schemas/
└── tasks/
```

当某个业务域满足以下任一条件时，再升级为模块化结构：

- 超过 3 个路由文件
- 超过 3 个 service
- 出现多表事务
- 出现状态机
- 出现后台任务
- 出现外部系统调用
- 出现事件发布

升级后结构：

```text
app/modules/<domain>/
├── api/
├── application/
├── domain/
├── infrastructure/
└── tasks/
```

## 8. 一句话原则

简单 CRUD 复用 ORM，复杂业务隔离 ORM；service 内部可以用 ORM，API / 任务 / 事件 / 跨模块边界不要暴露 ORM。
