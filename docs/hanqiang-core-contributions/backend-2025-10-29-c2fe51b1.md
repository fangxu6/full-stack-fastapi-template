## 本次提交建立的能力

该提交将旧的角色权限实现替换为一套以“功能（Feature）”为授权原子的数据模型，并新增功能、角色、用户角色和权限查询 API。功能树既可以描述前端模块、菜单、按钮，也可以承载 API 权限键；角色通过关联表拥有功能，用户通过关联表拥有角色。

当前代码仍以此模型为主线：`require_permission()` 被 27 个路由文件使用，权限服务负责从用户、角色、功能三层聚合有效权限。它适合作为其它项目的后台管理 RBAC 基座，但不应把前端隐藏元素当作安全边界。

## 可迁移架构

```text
功能注册表 Feature
  ├─ 树关系：module -> menu -> button / api
  ├─ 权限键：FeatureKey，例如 "role:write:update"
  └─ UI 元数据：Path、ComponentPath、Icon、SortOrder
        ↓
角色 Role --< RoleFeature >-- Feature
用户 User --< UserRole >-- Role
        ↓
PermissionService 聚合当前用户的有效 FeatureKey
        ↓
FastAPI Depends(require_permission(...)) 在服务端拒绝未授权请求
        ↓
前端拉取权限、过滤路由和控制交互（仅改善体验）
```

### 最小数据模型

| 实体 | 职责 | 复用时必须保留的约束 |
| --- | --- | --- |
| `Common_Feature` | 功能注册表与树节点 | `FeatureCode`、`FeatureKey` 唯一；`ParentID` 自引用；启用和软删除状态影响授权结果。 |
| `Common_Role_Master` | 角色主数据 | `RoleCode`、`RoleName` 唯一；系统角色应禁止删除和关键属性修改。 |
| `Common_Role_FeatureDetail` | 角色-功能多对多 | `(RoleID, FeatureID)` 为复合主键；角色删除级联，功能删除受限，避免留下无归属授权。 |
| `Common_User_RoleDetail` | 用户-角色多对多 | `(UserID, RoleID)` 唯一；查询时仅计算未软删除的关联。 |

本项目的主键存为 MySQL `BINARY(16)` UUID，并在 API 边界转换为字符串。迁移到其它项目时可以改用原生 UUID 或字符串主键，但必须统一 ORM、关联表和响应序列化，不能混用字节数组与字符串 ID。

## 服务端授权契约

`app/dependencies/permission_check.py` 提供三个可直接复用的 FastAPI 依赖工厂：

```python
Depends(require_permission("role:read:list"))
Depends(require_permissions("role:write", "role:create"))
Depends(require_permissions("report:read", "audit:read", logic="OR"))
```

- 单权限与默认多权限使用 AND；`logic="OR"` 明确表示任一满足。
- 非管理员先由 `PermissionService.get_user_permissions(..., only_enabled=True)` 聚合权限，再按权限键精确匹配；拒绝时记录审计日志并返回 HTTP 403。
- 当前实现把 `ADMIN` 视为超级管理员。其它项目应把这一规则写入身份/授权策略，并配套管理员角色变更审计，避免以用户名或前端标记绕过授权。
- 权限键是跨端契约。建议统一为 `<资源>:<动作>:<范围>`，例如 `role:read:list`、`role:write:update`；后端、路由元数据和前端不得各自发明别名或隐式层级匹配。

### 当前公共 API 面

| 能力 | 当前接口或服务 | 可复用用途 |
| --- | --- | --- |
| 功能注册 | `/api/features/tree`、功能 CRUD、`FeatureService` | 管理授权树和给前端提供导航元数据。 |
| 角色授权 | `/api/rbac/roles/{role_id}/permissions` | 读写角色的 `feature_ids` 集合。 |
| 用户角色 | `/api/users/{user_id}/roles` | 读写用户的角色集合。 |
| 当前用户权限 | `/api/users/permissions`、`/api/users/menu`、`/api/users/button-permissions` | 登录后加载权限、菜单和按钮权限。 |
| 路由保护 | `require_permission`、`require_permissions`、`require_admin` | 在每个受保护端点的服务端边界执行授权。 |

接口命名可随目标项目调整，但“角色授权写入 FeatureID，运行时校验 FeatureKey”的分工不应混淆。

## 初始化与变更流程

该提交同时引入 `RBACInitService`、功能配置和版本记录。可复用的运行流程是：

1. 先通过数据库迁移创建四张 RBAC 表、唯一约束和索引。
2. 将功能树维护为受版本控制的清单，例如 `config_Feature.json`；每个节点包含稳定的 code、key、类型、父节点和排序。
3. 部署时执行幂等同步：按稳定 code/key 查找，新增或更新可管理字段，不删除仍被引用的历史节点。
4. 再初始化系统管理员角色及管理员-角色关联；重复执行必须无副作用。
5. 功能清单、角色授权或用户角色变更后，使登录态权限缓存失效并重新加载。

生产环境应由迁移工具负责建表和演进。历史提交中“表不存在时自动建表”的兼容逻辑只适合安装修复，不宜作为新项目的常规启动策略；启动并发控制也应使用目标数据库支持的租约锁或部署编排锁。

## 当前项目的兼容边界

- `app/api/v1/routes/permissions.py` 的 `/api/permissions/*` 仍以 `PermissionDefinitions` 构造静态权限树；它是旧接口兼容层，不是 `Common_Feature` 数据模型的唯一事实源。新项目只保留一种树来源。
- 现有前端允许部分 `read` 权限做兼容匹配，而后端依赖按权限键精确判断。复用时应先确定统一的匹配规则，优先使用精确匹配加显式通配符，避免前端显示可操作但后端拒绝。
- `Feature` 同时承载菜单、按钮和 API 的前提是权限键稳定。若目标项目需要 ABAC、组织范围或数据行级授权，应在 RBAC 通过后增加独立的资源范围策略，而不要把范围编码进大量角色。

## 迁移验收清单

- 非管理员在服务端无法调用未授权端点，直接请求返回 403。
- 同一用户拥有多个角色时，权限为角色权限集合的并集；禁用/软删除的角色、功能和关联不生效。
- 修改角色授权后，重新登录或刷新权限可以立即观察到菜单、按钮和 API 访问的同步变化。
- 系统角色、系统功能不能被普通管理接口删除；迁移或初始化重复执行不产生重复关联。
- 功能树中每一个对外暴露的 `FeatureKey` 都能追溯到至少一个后端授权点或明确的纯 UI 用途。
