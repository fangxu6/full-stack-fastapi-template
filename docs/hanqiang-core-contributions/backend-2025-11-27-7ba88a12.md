## 这次提交解决的问题

加密工具已尝试读取 `settings.encryption_key`，但 `Settings` 既没有声明该字段，`Settings.load_from_yaml()` 也没有把 YAML 根节点的 `encryption_key` 传入运行时配置。因此下列配置虽然存在，却不会进入运行时 `settings.encryption_key`：

```yaml
encryption_key: "<Fernet key>"
```

`7ba88a12` 的改动只有两行，补齐了“配置模型字段”和“YAML 映射字段”之间的缺口：

```python
class Settings(BaseSettings):
    encryption_key: Optional[str] = Field(
        default=None, description="Fernet 对称加密密钥"
    )

    @classmethod
    def load_from_yaml(cls, yaml_path: str = "config.yaml") -> "Settings":
        # ...
        return cls(
            # 其它配置段
            encryption_key=config_data.get("encryption_key"),
        )
```

它修复的是配置装配，不是新的加密算法、密钥轮换机制或权限功能。任何在 `Settings` 添加的新顶层字段，都必须同时检查加载器是否完成映射；仅在 Pydantic 模型声明字段并不能保证 YAML 值会被使用。

## 受影响的加密链路

提交当时，`PasswordEncryption` 的取值顺序是：环境变量 `ENCRYPTION_KEY`，再到 `settings.encryption_key`，最后在缺失时生成临时 Fernet 密钥。没有 YAML 映射时，第二步恒为空，部署重启后生成的新临时密钥会使先前写入的密文不可恢复。

```text
部署密钥来源
        |
        v
环境变量 ENCRYPTION_KEY
        | 未设置时
        v
config.yaml 根级 encryption_key
        |
        v
Settings.load_from_yaml() -> settings.encryption_key
        |
        v
PasswordEncryption / Fernet
        |
        v
加密的 SMTP、FTP、数据源等敏感字段
```

CodeGraph 的当前调用追踪显示，`PasswordEncryption` 被邮件配置、FTP 配置和数据报表数据源等多个服务使用；`FTPConfigService` 通过 `settings.fernet_cipher` 加密 FTP 密码和私钥，WXWork 配置则使用专用 Fernet 工具。故此类配置错误的影响范围不仅是启动日志，而是所有依赖历史密文的管理功能。

需要区分历史事实与后续演进：在 `7ba88a12` 时，`settings.fernet_cipher` 仍只读取 `ftp.fernet_key`；当前代码已经演进为 `ftp.fernet_key`、`wxwork.fernet_key` 优先，缺失时回退到全局 `encryption_key`。不能把这项后续回退逻辑误写为本提交的原始行为。

## 可复用的配置契约

新项目应使用一个有明确优先级的密钥解析入口，而不是让每个业务服务自行读取环境变量、YAML 或生成密钥。推荐的逻辑契约如下：

| 项目 | 要求 |
| --- | --- |
| 密钥标识 | `ENCRYPTION_KEY` 或密钥管理系统中的同名逻辑标识；必须是有效 Fernet key。 |
| 部署优先级 | Secret manager / 环境注入优先，其次是未提交的本地部署配置；优先级应由加载器显式实现并测试。 |
| YAML 结构 | 若保留 YAML，使用根级 `encryption_key`，并保证其映射到 `Settings.encryption_key`。 |
| 专用密钥 | `ftp.fernet_key`、`wxwork.fernet_key` 可以覆盖全局密钥，但必须记录用途、轮换方式和回退规则。 |
| 消费接口 | 服务只调用 `get_fernet(purpose)` 或等效的集中入口；禁止各处直接读取 `os.getenv()`。 |
| 可观测性 | 可以记录“密钥来源/版本已加载”，绝不记录密钥正文、完整密文或可逆配置。 |

Fernet key 需要是 URL-safe Base64 编码的 32 字节密钥。配置加载阶段应验证格式，并在生产环境缺失或无效时阻止启动；不能把“生成临时密钥”作为生产降级方案。临时密钥可使本次加密成功，却必然导致重启后无法解密。

## 配置加载与优先级边界

当前加载器会读取 YAML 后以显式初始化参数构造各个 `BaseSettings` 对象。复用时不要因为使用了 `BaseSettings` 就假定环境变量一定覆盖 YAML：初始化参数、环境变量、默认值之间的优先级必须由实际加载方式验证。

建议把解析分为三步：

1. 读取非敏感的基础 YAML，定位运行环境和可选默认值。
2. 将 secret manager 或环境变量作为显式覆盖层合并到最终配置，而非依赖隐式行为。
3. 对数据库 URL、JWT 密钥、Fernet 密钥等必填机密进行启动前校验，并输出脱敏的配置来源诊断。

任何配置 API、异常消息和启动日志都不得返回 `encryption_key`。配置文件、`.env` 和密钥版本记录应与源码仓库隔离；历史提交中出现过的示例密钥或真实密钥都应视为需要轮换的泄露风险。

## 密钥轮换与数据迁移

全局密钥一旦已用于持久化数据，变更它不是普通配置发布，而是数据迁移：

1. 为每条密文记录保存或推断 `key_version`，保留旧版本密钥的只读解密能力。
2. 先部署“按版本解密、用新版本加密”的双读逻辑。
3. 批量解密旧密文并用新密钥重新加密，记录失败项，且保留可回滚的备份。
4. 对 SMTP、FTP 私钥、第三方应用 Secret 和数据源密码分别抽样验证可解密、可连接。
5. 全量对账完成后再撤销旧密钥访问权限，不能直接替换后重启。

本项目当前的部分字段没有统一的密钥版本列，因此新项目应在首次设计时纳入版本，而不是等到密钥泄露后才从密文格式猜测使用的是哪把密钥。

## 不应原样复制的历史行为

- `PasswordEncryption` 在密钥缺失时生成临时 Fernet key，是开发便利行为；生产环境必须 fail fast。否则数据可写不可读，属于数据丢失风险。
- 只补 `Settings.encryption_key` 而不补 `load_from_yaml()` 映射，仍然无法读取 YAML；反过来只传 YAML 值而没有模型字段也缺少类型、验证和统一入口。
- 不要把明文密钥写进受版本控制的 `config.yaml`，也不要在日志里输出密钥或完整连接串。
- 全局密钥回退给专用业务密钥是兼容策略，不代表所有敏感类型都应共用一把密钥。权限隔离要求较高时应按用途或租户分域。

## 迁移验收清单

- 设置 YAML 根级密钥且未设置环境变量时，`Settings.load_from_yaml(...).encryption_key` 等于该 YAML 值。
- 设置环境覆盖时，最终使用的来源符合书面优先级，并且测试覆盖该优先级，不依赖框架默认行为。
- 缺失、格式错误或长度错误的密钥在生产模式启动即失败；日志不泄露密钥。
- 用旧密钥写入的 FTP/SMTP/第三方 Secret 在部署后仍能正确解密；密钥轮换后旧版本密文的迁移结果可审计。
- 同一运行进程中所有敏感字段服务都通过集中加密入口获取密钥，而不是各自读取配置或静态保存 Fernet 实例。
