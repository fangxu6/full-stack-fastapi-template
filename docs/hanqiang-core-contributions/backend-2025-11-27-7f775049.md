## 原始端到端链路

```text
HTTP /api/enum/*
        |
        v
enum_routes.py
  Pydantic 请求校验 + { code, message, data } 成功包装
        |
        v
EnumService
  业务约束 + UUID 转换 + commit/rollback + 缓存失效 + 操作日志
        |
        v
CRUDEum（当前已演进为 CRUDEnum）
  SQLAlchemy 查询 + 递归 CTE + 软删除过滤
        |
        v
Common_Enum (MySQL BINARY(16) UUID)
        |
        +--> Redis：分类/分类列表/树缓存
        +--> operation log：创建、更新、删除、启停
```

服务层是规则集中处，CRUD 层只负责查询和基础存在性检查。API 边界把 `BINARY(16)` UUID 转为字符串，避免把 bytes 直接传给前端或日志。

## 数据模型与原始约束

物理表为 `Common_Enum`，字段采用项目既有的 PascalCase 命名和 `IsDeleted` 软删除约定。

| 字段 | 原始定义 | 作用与约束 |
| --- | --- | --- |
| `EnumID` | `BINARY(16)` 主键 | 枚举 ID；服务创建时使用 `uuid.uuid4().bytes`。 |
| `ParentEnumID` | 可空自引用外键，物理删除时 `SET NULL` | 形成分类内外均可引用的树；应用层负责循环检测。 |
| `EnumCode` | `TINYINT NOT NULL`，普通索引 | 展示/业务代码；服务层实际限制为 `0..127`。 |
| `EnumName` | `VARCHAR(50) NOT NULL UNIQUE` | 全表唯一的稳定名称，不是“分类内唯一”。 |
| `EnumCategory` | `VARCHAR(50) NOT NULL`，普通索引 | 分类键，也是分类/树缓存键的一部分。 |
| `EnumValue`、`EnumDesc`、`Remark` | 可空字符串 | 面向业务消费的值、描述和备注。 |
| `DisplayOrder` | `INT NOT NULL DEFAULT 1` | 分类列表和树节点的排序主键。 |
| `IsEnabled`、`IsSystem`、`IsDeleted` | `BIT(1)` | 启停、系统项保护和软删除。 |
| `CreatorID`、`CreateTime`、`UpdaterID`、`UpdateTime` | 审计字段 | 原始实现固定写入 `SYSTEM` 身份和 `datetime.utcnow()`。 |

原始索引只有 `ParentEnumID`、`EnumCode`、`IsEnabled` 和字段定义带来的 `EnumName` 唯一索引；没有 `(EnumCategory, EnumCode)` 唯一索引，也没有数据库级“父子同分类”约束。

### 原始业务规则

| 规则 | 原始实现 |
| --- | --- |
| 名称唯一 | 写前查询未删除记录，表上再以全局 `UNIQUE(EnumName)` 兜底。软删除后名称仍不能复用。 |
| 编码唯一 | 仅在服务层检查同一 `EnumCategory` 的未删除记录；并发写入仍可能得到重复编码。 |
| 代码范围 | 服务层限制 `0..127`，但创建/更新 Schema 写的是 `0..255`，两层不一致。 |
| 父节点 | 创建或更新时父节点必须存在；沿父链检查循环。 |
| 系统项 | 系统枚举禁止删除，禁止修改名称和代码；其余字段及父节点仍可修改。 |
| 删除 | 只将 `IsDeleted` 置为 `1`；有未删除子节点时拒绝删除。 |
| 启停 | 启用/禁用只改当前节点，不级联子节点。 |
| 审计 | 成功提交后调用操作日志；日志失败不回滚已经提交的枚举数据。 |

## 原始 API 契约

成功响应统一为：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 方法和路径 | 输入 | 原始行为 |
| --- | --- | --- |
| `GET /api/enum/categories` | 无 | 返回未删除分类及 `total`；缓存 1 小时。 |
| `GET /api/enum/category/{category}` | `include_disabled=false` | 返回指定分类；默认过滤禁用项；缓存 30 分钟。 |
| `GET /api/enum/tree/{category}` | 无 | 递归 CTE 取该分类树，再由服务组装 `children`；原始实现不筛禁用节点；缓存 30 分钟。 |
| `GET /api/enum/value/{enum_name}` | 名称 | 返回单条，缺失时 404。 |
| `GET /api/enum/search` | `keyword`、`category`、`is_enabled` | 模糊搜索仅匹配 `EnumName`，无分页。 |
| `GET /api/enum/batch` | 多个 `names` query 参数 | 按名称批量查询；代码中导入的 `BatchQueryRequest` 未被该端点使用。 |
| `GET /api/enum/{enum_id}` | UUID path | 按 ID 返回单条，缺失时 404。 |
| `POST /api/enum` | `EnumCreate` | 创建节点、失效相应分类缓存、写操作日志。 |
| `PUT /api/enum/{enum_id}` | `EnumUpdate` | 部分更新；Schema 不允许改分类或 `IsSystem`。 |
| `DELETE /api/enum/{enum_id}` | UUID path | 软删除；系统项或有子节点时报业务错误。 |
| `PATCH /api/enum/{enum_id}/enable` / `disable` | UUID path | 修改单节点启用状态。 |
| `POST /api/enum/cache/refresh` | 无 | 尝试预热分类、所有分类列表和树。 |
| `DELETE /api/enum/cache` | 无 | 删除枚举前缀下全部键。 |
| `GET /api/enum/cache/status` | 无 | 返回 Redis 启用状态、命中/未命中计数、键数和刷新时间。 |

业务异常在创建、更新、删除路由中被统一映射为 HTTP 400，即使服务异常对象携带了不同的内部 `code`。路由没有设置 `response_model`，因此 `EnumResponse` 等 Schema 在原始实现中主要承担请求/类型说明，而不是运行时响应校验。

## 树、软删除与跨层语义

原始 `get_tree()` 先从 `ParentEnumID IS NULL` 的未删除根节点开始，再通过递归 CTE 连接子节点。服务层将 CTE 平铺结果转成 `children` 嵌套结构，并以 `(DisplayOrder, CreateTime)` 排序。

这里有三项必须明确写入新项目契约的行为：

1. 原始列表默认只返回启用项，但树接口返回未删除项而不筛 `IsEnabled`，两种读取语义不一致。
2. 父节点存在性检查不限制 `EnumCategory`。跨分类挂父节点会使子节点在按分类取树时无法从正确根节点到达。
3. 软删除不会触发数据库外键的 `ON DELETE SET NULL`。应用层虽禁止删除仍有子项的节点，但历史脏数据或绕过服务层的写入仍可能造成孤儿树。

API 与数据库之间还存在一项边界修复：本提交把 `RequestValidationError.errors()` 先交给 `jsonable_encoder`。当 UUID path 或 `ParentEnumID` 校验失败时，错误详情可被 JSON 序列化，而不会在异常处理器中再次失败。

## 原始缓存机制

| 项目 | 原始行为 |
| --- | --- |
| Redis 开关 | Redis 未启用时直接绕过缓存，业务查询仍可完成。 |
| 键格式 | `<redis.key_prefix>enum:categories`、`...:category:<category>`、`...:category:<category>:all`、`...:tree:<category>`。 |
| TTL | 分类 3600 秒；分类列表和树 1800 秒。 |
| 失效时机 | 创建、更新、删除、启用、禁用在 `commit()` 后按分类失效。 |
| 故障策略 | 读取失败视为未命中；写入失败记录 warning，不中断主业务。 |
| 管理接口 | `clear` 删除前缀下全部键；`status` 使用前缀统计。 |

原始实现使用 Redis `KEYS` 按模式扫描并删除键。小数据量时能工作，但生产实例上会阻塞 Redis；新项目应以 `SCAN` 分批删除，或维护可失效的 key set / 版本号。

`refresh_cache()` 也是原始实现中不能照抄的细节：它先读取分类，再调用会优先命中旧缓存的 `get_categories()`、`get_by_category()` 和 `get_tree()`，却没有先失效缓存。因此“刷新”可能只是重新返回旧值，而不是真正回源预热。

## 不应原样复制的历史边界

### 授权与审计身份

原始所有路由只依赖 `get_db`，没有 `get_current_user` 或动作权限依赖。只要调用方可直达该服务，任何人都能创建、修改、删除、启停枚举和清空缓存；客户端还可在创建时提交 `IsSystem=true`。原始服务也把所有审计字段和操作日志写成 `SYSTEM`。

这是一项安全边界缺口，而不是可选的简化。复用时至少应做到：

- 管理读、写、删除、启停和缓存管理使用彼此独立的服务端权限；缓存清除属于管理员操作。
- 公开下拉/树读取与后台管理页面权限分开。若枚举本身不敏感，业务表单的选项读取不应因没有“枚举管理页面”权限而失效；若有租户、工厂或密级范围，则读取也必须做数据范围过滤。
- `CreatorID`、`UpdaterID`、操作日志用户和范围都来自经认证的当前用户；`IsSystem` 只由受控初始化或管理员流程写入。

### 数据完整性和并发

- 若编码在分类内必须唯一，应建立可执行的数据库约束，而不只依赖“先查再写”。对 MySQL 软删除场景，要明确业务键是否允许复用：不允许复用时用普通唯一键；允许复用时采用经过迁移验证的活动键方案，例如生成列加唯一索引。
- 要么保持 `EnumName` 全局唯一，并让按名称查询无歧义；要么改为 `(EnumCategory, normalized_name)` 唯一，并从 API 开始要求同时传分类。不要在两种语义之间混用。
- Schema、服务和数据库必须共享同一代码取值范围。原始 `0..255` 与 `0..127` 的差异会让请求先通过 Schema、再在服务层失败。
- 父节点校验应同时检查未删除、相同分类、可见范围和非自身；循环检测只应作为数据库约束不足时的补充，不能把树完整性只寄托在前端。
- `EnumUpdate.ParentEnumID` 也需要 UUID 格式校验；原始实现只给创建 Schema 配了该校验。

### 事务、日志和缓存

- 明确事务边界：枚举写入、审计记录和缓存失效的失败策略必须可解释。至少在 `commit()` 失败后 `rollback()`；如果审计必须可追溯，使用同一事务审计表或 outbox，而不是在提交后静默记录日志。
- 分类重命名或移动节点会影响旧分类和新分类的缓存，不能只失效当前对象的一个分类键。原始更新不允许改 `EnumCategory`，这一限制应在 API 设计中显式保留或完整实现迁移失效。
- 缓存键必须包含租户、工厂或权限范围版本；否则后续加入范围过滤后可能把一个范围的数据返回给另一个范围。
- `refresh` 应先失效或递增缓存版本，再明确选择“只刷新元数据”或“同步预热所有分类”。大分类集合不宜在单个 HTTP 请求中做全量预热。

## 推荐的可复用设计

新项目无需复制原仓库的类名、统一响应壳或 MySQL `BINARY(16)` 细节，但应保留以下职责边界：

| 层次 | 推荐职责 |
| --- | --- |
| Migration / Model | 建表、外键、唯一键、索引、字段注释和软删除策略；数据库选型决定 UUID 表示。 |
| Schema | 只定义外部请求和响应，统一代码范围、字符串长度、UUID 和可选字段规则。 |
| Repository / CRUD | 返回原始持久化对象，集中 `IsDeleted`、范围和排序过滤；不提交事务。 |
| Service | 校验父子同域与循环、系统项策略、并发冲突翻译、事务、审计和缓存失效。 |
| Route | 认证、动作授权、输入输出和 HTTP 状态码；不拼接业务 SQL。 |
| Consumer | 表单优先使用分类/批量读取，缓存其自身短生命周期状态；不得自行假设全局名称唯一。 |

建议先固定三项产品决策，再实现表和接口：

1. **身份键**：`EnumName` 是机器稳定键、展示名，还是两者兼有。展示名可改时，应另设不可变 `EnumKey`。
2. **作用域**：数据是全局、租户、组织还是工厂范围。作用域字段、唯一键、查询条件和缓存键必须同时设计。
3. **层级语义**：父子是否必须同分类、禁用/删除父节点如何影响子节点、最大层级和排序冲突如何处理。

如果只有平铺下拉选项，不要预先加入自关联、递归 CTE 和树接口。只有实际需要多层选择或继承语义时，才引入层级模型。

## 迁移验收清单

- [ ] migration 已创建物理表、外键、唯一键、索引及完整中文表/列注释；生产环境未依赖 ORM 自动建表。
- [ ] API UUID、Schema、服务和数据库的整数范围一致；非法 UUID、超范围代码、空名称和超长字段分别得到可序列化的 4xx 响应。
- [ ] 同分类重复编码、重复名称、并发创建、跨分类父子、自身父节点、祖先循环、删除有子节点和删除系统节点均有自动化验证。
- [ ] 已书面决定软删除后业务键能否复用，并由真实数据库唯一约束验证，而不是只靠应用层预查询。
- [ ] 未认证、无管理权限、无删除权限、无缓存管理员权限的请求无法绕过服务端；业务下拉读取的范围策略与管理权限解耦。
- [ ] 创建、更新、删除、启停后缓存不会返回旧数据；范围/租户隔离进入缓存键；缓存清理不用 Redis `KEYS` 阻塞主实例。
- [ ] 审计记录含真实操作者、操作前后值和范围；审计失败与主事务的关系符合系统合规要求。
- [ ] 树、列表、批量查询和前端树构造对禁用项、软删除项、孤儿项和排序的行为一致且有覆盖。
