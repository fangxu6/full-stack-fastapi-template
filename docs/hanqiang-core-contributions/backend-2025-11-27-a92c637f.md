## 这次提交建立的能力

原有 Redis 配置只有 `url`，缓存管理器、同步 Redis 客户端和 Celery 分别直接读取它。部署到外部 Redis 并使用密码时，配置不够直观，也容易让不同运行时采用不同连接串。

`a92c637f` 新增 `RedisConfig.redis_url` 作为统一解析属性：显式 `url` 非空时直接使用；否则由 `host`、`port`、`db`、`password` 和 `use_ssl` 组装 `redis://` 或 `rediss://`。随后将三个消费者统一切换到该属性：

| 文件 | 变更职责 |
| --- | --- |
| `app/core/config.py` | 增加组合式 Redis 字段与 `redis_url` 解析属性。 |
| `app/core/cache.py` | 异步 `CacheManager` 用统一 URL 建立 Redis 缓存连接。 |
| `app/core/redis_client.py` | 同步 Redis 单例用统一 URL 懒连接，供锁、限流和业务协调器使用。 |
| `app/core/celery_app.py` | Celery broker/result backend 用统一 URL。 |
| `config.yaml` | 增加外部主机、密码和 TLS 的示例字段。 |
| `app/api/v1/routes/cache_routes.py` | 新增全局缓存删除并预热枚举缓存的 API，并在 `api_router.py` 注册。 |
| `app/api/v1/routes/enum_routes.py`、`README.md` | 补充枚举接口描述、隐藏 GET 刷新入口和接口文档。 |

这不是单纯改一份 YAML。Redis 在该项目同时承担缓存、分布式协调、限流、任务队列 broker 和任务结果后端，连接串的变化会影响多个运行时。

## 原始配置契约

提交中的解析逻辑等价于：

```python
class RedisConfig(BaseSettings):
    url: str | None = None             # 非空时优先
    enabled: bool = False
    host: str = "127.0.0.1"
    port: int = 6379
    db: int = 0
    password: str | None = None
    use_ssl: bool = False

    @property
    def redis_url(self) -> str:
        if self.url:
            return self.url
        scheme = "rediss" if self.use_ssl else "redis"
        auth = f":{self.password}@" if self.password else ""
        return f"{scheme}://{auth}{self.host}:{self.port}/{self.db}"
```

调用链为：

```text
config.yaml / 环境配置
        |
        v
RedisConfig.redis_url
   |             |              |
   v             v              v
CacheManager   SyncRedisClient  Celery broker/result backend
异步缓存        同步锁/限流       Worker / Beat / 异步任务
```

`CacheManager.connect()` 仅在 `redis.enabled=True` 时创建异步客户端并 `PING`；连接失败后关闭缓存能力，`get()` 返回 `None`、`set()`/`delete()` 返回失败值。这一降级仅适用于可重建的缓存。

同步客户端则以配置启用状态初始化，首次访问 `.client` 时再连接。CodeGraph 显示它被限流、编辑锁、文件监控、邮件、FTP、报表任务协调等多处消费，且当前还有异步 Redis 包装和 Redis 锁模块。因此目标项目必须先分清每个用途是“可选缓存”还是“正确性依赖的协调/锁”，不能把所有 Redis 故障都统一降级。

## Redis 角色分级

复用此设计前，应按用途建立故障策略：

| 用途 | Redis 不可用时 | 推荐策略 |
| --- | --- | --- |
| 功能树、表头、枚举等派生缓存 | 可以回源数据库 | 记录指标和告警，避免缓存失败影响读请求正确性。 |
| 登录限流、一次性令牌、幂等键 | 取决于安全要求 | 高风险认证入口采用 fail closed 或本地受限兜底，策略必须显式。 |
| 分布式锁、任务并发槽位、执行租约 | 不可静默降级 | 无锁继续执行可能产生重复任务或并发写入，应失败或暂停调度。 |
| Celery broker/result backend | 不可按缓存处理 | Worker、Beat 和 API 启动时验证连通性及认证；失败应以部署故障处理。 |

本提交虽然让 Celery 使用同一 `redis_url`，但 `settings.redis.enabled` 仅被缓存/客户端连接逻辑检查，`Celery(...)` 在 import 时仍会把该 URL 作为 broker/backend。新项目应把“是否启用缓存”和“任务系统可用性”拆成独立配置与启动校验，避免关闭缓存时意外生成或使用任务 broker URL。

## 新项目推荐的安全配置

完整 URL 和离散字段同时存在的目的在于兼容部署环境，不是让两者在各模块任意选择。只保留一个规范化输出，并在应用启动时校验：

```yaml
redis:
  enabled: true
  # 两种方式二选一：URL，或 host/port/db + secret 注入的 password
  url: ""
  host: "redis.internal.example"
  port: 6379
  db: 0
  use_ssl: true
  socket_connect_timeout: 5
  socket_timeout: 5
  max_connections: 50
  key_prefix: "myapp:prod:"
```

`password`、完整 Redis URL、TLS 证书路径和 ACL 用户名应来自 Secret manager 或环境注入，不应提交到 `config.yaml`。本提交的历史样例曾包含明文外部 Redis 密码，复制配置前必须删除并轮换该类凭据。

原始字符串拼接没有对密码做 URL 编码，包含 `@`、`:`、`/`、`#` 等保留字符时会产生错误或歧义 URL；日志中打印完整 `redis_url` 还会泄露密码。新项目更稳妥的做法是将 `host`、`port`、`db`、`username`、`password`、TLS 参数分别传给 Redis 客户端，或使用可靠 URL builder 对用户名和密码百分号编码，并始终脱敏日志。

还应明确：

- `rediss://` 仅表示使用 TLS；生产环境还应配置证书校验策略和 CA，不能因连通性问题关闭验证；
- Redis 6+ ACL 应使用最小权限的专用用户，而不是共用默认用户；
- key prefix 至少含应用和环境，例如 `myapp:prod:`，测试、预发布和生产不能共享命名空间；
- TTL 应服务于业务新鲜度，不能只复制“功能树一小时、用户权限五分钟”的历史数值；权限变更仍需要显式失效。

## 缓存失效接口的历史风险

本提交注册了：

```text
POST /api/cache/refresh
GET  /api/cache/refresh  (隐藏于 OpenAPI)
```

它会通过 `SCAN` 删除 `<key_prefix>*` 和 `enum:*`，再调用 `enum_service.refresh_cache(db)` 预热枚举。`cache_routes.py` 在提交中没有身份或权限依赖，GET 入口同样执行写操作。README 将枚举管理操作描述为管理员功能，但路由实现并未据此执行鉴权，文档与安全事实不一致。

这段实现不能原样复用，原因包括：

- 任意网络可达的调用方都能冲掉大量缓存并触发数据库预热，构成可用性和成本风险；
- GET 具有副作用，可能被预取、代理、爬虫或链接扫描触发；
- `SCAN` 后收集全部键再删除没有分页上限、执行锁、审计或速率限制；
- 模式匹配依赖字符串前缀，配置错误可能删除不属于该应用的键；
- Redis 不可用时返回 `redis_deleted_keys=0` 后仍继续刷新枚举，调用方无法仅从“success”判断完整失效是否发生。

可复用的最小安全版本应只提供受 `require_permission("cache:write:refresh")` 保护的 `POST`，接受预定义 namespace 名称而非任意 pattern，使用游标分页删除、分布式互斥锁、调用审计和结构化结果。高风险的全局清理应进入运维任务或受控管理命令，而不是公开 API。

## 枚举与缓存边界

`a92c637f` 对 `enum_routes.py` 的主体变动是补充 OpenAPI `summary`/`description`，并增加隐藏的 `GET /api/enum/cache/refresh` 便利入口；枚举 CRUD、缓存刷新和状态接口的业务实现并非由此提交新建。迁移时应将“枚举数据变更”和“缓存失效”放在同一服务事务边界：写入成功后失效或重建对应 namespace，不能依赖管理员记得另调一个全局清理 URL。

`EnumService` 使用 `settings.redis.key_prefix` 派生枚举缓存前缀，`CacheManager` 对功能树、用户权限和表头翻译分别维护 TTL 和失效方法。它们说明了一个可复用原则：键的拥有者负责精确失效；全局 pattern 删除只能作为受控的事故恢复工具。

## 迁移验收清单

- 显式 URL、有密码的组合式配置、无密码本地配置、TLS 和错误凭据分别能构造或明确拒绝连接，且日志中不出现明文密码。
- 密码含 URL 保留字符时仍能正确认证，或配置加载阶段报出可操作的验证错误。
- 缓存 Redis 不可用时，允许回源的读取仍正确；锁、限流、并发协调和 Celery broker 不会被误降级为“正常继续”。
- API、Worker、Beat 使用相同的规范化连接配置；关闭缓存不改变任务队列的配置语义。
- 权限、功能树、枚举等数据变更后，能够精确失效对应 key namespace；跨进程/多实例场景也能在约定时间内一致。
- 缓存刷新仅允许已授权管理员通过 POST 触发，并记录操作者、namespace、删除数量、预热结果和异常；GET 请求永不改变状态。
- 对 RedisConfig 的 URL 优先级、字段校验、密码脱敏、缓存连接失败和 Celery 配置添加单元/集成测试。CodeGraph 当前未发现 `RedisConfig` 的直接覆盖测试。
