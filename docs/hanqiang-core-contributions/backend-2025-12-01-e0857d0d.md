## 本提交补齐的端到端能力

```text
配置文件中的 feature registry
  -> menu:enum_management + enum:* 动作键
  -> /api/enum 路由的 require_permission(...)
  -> EnumService / CRUDEnum
  -> Common_Enum（软删除、启停、父子结构）
  -> Redis 枚举缓存 + operation log

前端 EnumManagement
  -> GET /api/enum/categories
  -> GET /api/enum/all
  -> 在浏览器按分类组树和执行 CRUD
```

`GET /api/enum/all` 是这次完成提交最关键的接口：它返回所有未软删除枚举项，按 `(EnumCategory, DisplayOrder, CreateTime)` 排序，并包装为 `{ items, total }`。配套前端提交 `57b44e86` 首屏依赖该接口；若只部署前端或只部署前序 `7f775049`，管理页会请求不存在的 `/all` 路由。

### 原始 API 契约

成功响应统一为：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 端点 | 原始权限 | 本提交后的行为 |
| --- | --- | --- |
| `GET /api/enum/categories` | `enum:read:list` | 返回分类与数量。 |
| `GET /api/enum/category/{category}` | `enum:read:list` | 默认只取启用项；`include_disabled=true` 取未删除项。 |
| `GET /api/enum/tree/{category}` | `enum:read:list` | 返回父子树和 `total`；首版 `total` 是根节点数，不是所有节点数。 |
| `GET /api/enum/value/{name}`、`/{id}`、`/search`、`/batch` | `enum:read:list` | 单项、搜索和批量读取。 |
| `GET /api/enum/all` | `enum:read:list` | 新增：一次性返回全部未软删除项，包含禁用项，无分页。 |
| `POST /api/enum` | `enum:write:create` | 创建；首版服务仍将操作者写成 `SYSTEM`。 |
| `PUT /api/enum/{id}` | `enum:write:update` | 更新，新增可写 `IsSystem`；首版服务仍将操作者写成 `SYSTEM`。 |
| `DELETE /api/enum/{id}` | `enum:delete:remove` | 软删除；系统项或有未删除子节点时拒绝。 |
| `PATCH /api/enum/{id}/enable`、`/disable` | `enum:write:toggle_status` | 单节点启停。 |
| `POST` 或隐藏的 `GET /api/enum/cache/refresh` | `enum:admin:cache` | 预热/刷新缓存；隐藏 GET 接口仍可访问且受权限保护。 |
| `DELETE /api/enum/cache`、`GET /api/enum/cache/status` | `enum:admin:cache` | 清除缓存、读取进程内命中统计和键数量。 |

路由虽导入了 `BatchQueryRequest`，实际批量端点使用重复 query 参数 `names`。新项目应只保留一种契约，给批量长度、单项长度和 URL 总长度设边界；大量名称更适合受权限保护的 JSON body `POST /query`。

## 权限注册：可复用的部分与缺口

`config_Feature.json` 一次性注册：

| feature key | 职责 |
| --- | --- |
| `menu:enum_management` | `/system/enum` 菜单及 `EnumManagement` 组件。 |
| `enum:read:list` | 分类、树、详情、搜索、批量和全量读取。 |
| `enum:write:create` | 新增枚举或首项隐式建立分类。 |
| `enum:write:update` | 编辑枚举。 |
| `enum:delete:remove` | 软删除。 |
| `enum:write:toggle_status` | 启用/禁用。 |
| `enum:admin:cache` | 缓存刷新、清除和状态查看。 |

把动作权限放在 API 依赖上，是本提交相对 `7f775049` 的实质安全改进。复用时要补齐三点：

1. feature JSON 只是种子/注册资料。发布流程必须幂等导入、核验角色授权、记录版本，不能假定仓库内有文件就代表生产数据库已存在这些权限。
2. `enum:read:list` 不应天然等同于“能读取所有枚举”。业务下拉读取、后台全量管理读取和缓存管理应按数据敏感度、租户、组织/工厂范围分开授权。
3. 路由取得了 `current_user`，但首版没有把它传给 `EnumService`。因此 `CreatorID`、`UpdaterID` 和操作日志仍使用固定 `SYSTEM` 身份，权限控制和审计事实源是断开的。当前服务已改为接收当前用户；移植时必须由 service 从认证主体写审计字段，而不是只在 route 中声明依赖。

### `IsSystem` 不能交给普通更新权限

本提交把 `EnumUpdate.IsSystem` 暴露给 API，并在 service 中把它转换为 `0/1` 后写入模型。既有“系统枚举不能改名称/代码、不能删除”的保护，会因此被获得普通编辑权限的调用方绕开或放大：普通项可被标为系统项，系统保护本身也不再是受控初始化操作。

复用规则应是：

- `IsSystem` 仅由初始化 migration、受控管理命令或独立的高权限流程写入；普通创建/更新 DTO 不含该字段。
- 系统项策略写在服务端，至少覆盖名称、代码、分类、父级、启停和删除，并明确哪些字段允许修正。
- 若需要系统项转移，使用独立动作权限、双人审批或发布流程，并完整记录操作者、前值、后值和原因。

## 全量读取、树和缓存的边界

`/all` 解决管理页首屏加载，但它不是所有业务消费的默认接口：无分页的全量拉取会随分类和租户增长放大响应、缓存和前端组树成本，也容易绕开“业务只应看已启用/本范围数据”的规则。

推荐按场景分层：

| 场景 | 推荐接口语义 |
| --- | --- |
| 普通业务下拉 | 按分类、作用域和启用状态读取；服务端分页或限制上限。 |
| 级联选择 | 服务端按分类返回可见树，禁用父/子和孤儿项的规则统一。 |
| 枚举管理页 | 受独立管理权限和范围授权的分页/按分类加载；数据规模确实小才允许 `/all`。 |
| 后台批量校验 | body 批量查询，限制数量并返回未命中项，不以浏览器全量缓存代替服务端校验。 |

首版缓存实现有几个不能照抄的细节：

- `refresh_cache()` 先查询数据库分类，再调用会优先命中已有缓存的 `get_categories()`、`get_by_category()` 和 `get_tree()`，没有先失效；“刷新”可能只是再次读取旧值。
- `_invalidate_cache()` 使用 Redis `KEYS` 扫描整个前缀。键数量变大时会阻塞 Redis；使用 `SCAN` 分批、缓存版本号或受控 key set。
- 分类/树缓存 key 不含租户、组织、工厂、语言或权限范围；后续加入范围过滤会造成跨范围数据泄露。缓存键或版本必须包含所有影响结果的维度。
- 缓存命中统计和 `last_refresh` 存在单个 API 进程内，集群下不能代表全局健康；监控应由 Redis 指标或集中式遥测提供。
- 首版分类列表默认筛掉禁用项，而树路径的首版查询对启用语义不一致。新项目要在接口契约中明写禁用父/子节点的返回与选择规则。

缓存故障可降级为直接查库，但写入后缓存失效是否属于事务的一部分、失效失败后如何补偿，必须明确。不要通过静默吞掉失败让管理页长期显示旧枚举。

## 继承的模型与数据完整性约束

本提交沿用前序 `Common_Enum`：`BINARY(16)` ID、自关联 `ParentEnumID`、全局 `EnumName`、分类内 `EnumCode`、`IsEnabled`、`IsSystem` 和 `IsDeleted`。它没有新增 migration，因此以下问题仍由首版继承：

- `EnumCode` 的分类内唯一性主要靠“先查再写”，并发下需要数据库级唯一约束或可靠的冲突翻译。
- `EnumName` 的全局唯一与“按分类搜索/前端预检”容易冲突；要么坚持全局稳定键，要么改成分类/范围内唯一并同步修改 API。
- 父节点存在性检查、循环检查、删除子节点检查需要同时考虑同分类、未删除和数据范围，不能仅在前端组树时处理。
- 软删除后业务键是否可复用是产品决策；普通唯一索引、生成列和活动键的设计不同，必须由 migration 和真实数据库验证。

本提交虽增加了 `IsEnabled` 和 `IsSystem` 的显式布尔转换，但 Schema、服务、数据库和前端仍应共享同一 `EnumCode` 范围、长度和空值规则。首版服务限制 `0..127`，不能让 UI 或导入接口接受更宽范围后再在服务层失败。

## 与前端和部署的版本依赖

配套前端 `57b44e86` 已依赖 `/api/enum/all` 和 `enum:read:list`。正确发布顺序是：

1. 先部署包含 `Common_Enum` 建表/索引的数据库版本，并导入 feature/header 资料；验证菜单和动作权限已出现在权限服务中。
2. 部署后端路由和服务，确认未授权请求得到 401/403，读写角色拥有最小必要权限。
3. 部署前端管理页；用小数据集验证分类、全量、树、搜索、创建、启停、删除和缓存管理。
4. 再启用业务模块的枚举消费；不要让业务运行依赖管理页浏览器里的 `/all` 结果。

这次提交的 `config.py` 改为在多层父目录搜索 `config.yaml` 并打印实际路径，`password_encryption.py` 仍允许没有密钥时生成临时 Fernet key。两者不是枚举功能的依赖：生产系统应使用明确的配置来源和受控密钥；临时加密键会让进程重启后无法解密既有密文，路径打印也不应成为敏感部署细节的日志来源。

## 推荐的可复用设计

| 层次 | 推荐职责 |
| --- | --- |
| Migration / model | 定义作用域、唯一键、父子约束、软删除策略、索引和字段注释；从空库可重复部署。 |
| Permission registry | 将菜单、读、写、删除、状态、缓存管理注册为可版本化种子，并在部署后校验实际授权。 |
| Repository | 只做 `IsDeleted`、范围、排序、锁定和数据访问；不把认证或缓存逻辑散入查询。 |
| Service | 解析当前用户和范围、校验系统项/父子/唯一性、处理事务、审计、缓存失效和冲突映射。 |
| Route | 认证、动作权限、输入输出、HTTP 状态码和统一响应壳；将当前用户传入 service。 |
| Consumer | 业务下拉只调用受限查询；管理页专用全量/树接口不作为业务正确性来源。 |

至少先写清三项决策：枚举名称是全局机器键还是可改展示名；作用域是全局还是按租户/组织/工厂；禁用/删除父节点如何影响子节点和业务已引用的数据。没有这三项，`/all`、树、缓存和权限只能得到暂时可用但不可扩展的实现。
