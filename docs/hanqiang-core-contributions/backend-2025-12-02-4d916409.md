### 原始端到端链路

```text
POST /api/wxwork/send
  -> require_permission("wxwork:send:create")
  -> WXWorkSendService.create_send_task()
       -> 查配置和模板、校验动态参数与接收人
       -> 创建 Sys_WXWork_SendLog（初始 SENDING）
       -> process_send() 同步取 Token、渲染 JSON、调用企业微信
       -> 更新主日志 + 创建 Sys_WXWork_SendLog_Detail

GET /api/wxwork/send-logs / {id} / retry
  -> WXWorkLogService
       -> 查询主日志与尝试明细，或重置状态后投递 Celery 占位任务
```

首版 `POST /send` 的 HTTP 状态是 `202 Accepted`，响应文案是“消息已入队”，但实际在 API 请求内直接执行 `process_send()`。这不是异步队列语义，调用方不能据此假设返回即为已持久化待处理、随后由 worker 可靠投递。

### 推荐的异步状态机

新项目应先确定“接收成功”和“渠道送达”的不同语义，再实现接口：

```text
API 校验 -> 事务内写 PENDING 日志和幂等键 -> commit -> 投递任务
                                           |                  |
                                           |                  v
                                           |        worker 原子领取 PENDING -> SENDING
                                           |                  |
                                           |                  v
                                           |        渲染、取 Token、调用渠道、写尝试明细
                                           |                  |
                                           +---- 成功 SUCCESS / 部分成功 PARTIALLY_FAILED
                                                              / 可重试失败 PENDING + NextRetryTime
                                                              / 不可重试失败 FAILED
```

1. API 仅在主日志事务提交且任务已成功写入 outbox/队列后返回 `202`；否则返回可重试的失败，不得声称“已入队”。
2. worker 用条件更新或行锁领取 `PENDING`，避免重复消费；渠道调用可能超时但实际已送达，因此要持久化调用幂等键，并定义超时后的查询/人工确认策略。
3. 每次实际尝试先递增 `RetryCount`，再追加一行 detail。人工重试不得将历史计数重置为 `0`；若业务要区分人工重新投递，可新增 `RetryGeneration` 或新建逻辑发送记录。
4. `NextRetryTime` 必须由调度器消费，并区分网络超时、限流、Token 失效、参数错误和无效接收人。固定错误不应无意义重试。
5. 无论 Token、JSON 解析、渲染、HTTP 或落库在哪一步异常，都要将已领取日志收敛到可解释终态或可调度的 `PENDING`，不能永久停在 `SENDING`。

首版的 `wxwork_tasks.send_wxwork_message()` 只记录日志并返回成功；`WXWorkLogService.retry()` 将失败日志改为 `PENDING` 后投递的正是这个占位任务。因此首版“手动重试”不会真正再次发送。该差异必须在迁移前消除，而不能只改前端提示。

## 模板与消息体契约

首版把 `CardContent` 序列化为 JSON 文本，以正则识别 `{{[a-zA-Z_][a-zA-Z0-9_]*}}`，再在序列化后的 JSON 字符串中替换变量。此法可快速跑通，但动态值若带引号、反斜杠或结构化内容，替换后可能得到非法 JSON，甚至改变原 JSON 语义。

复用时应先 `json.loads()` 模板，再递归遍历对象：

- 只对字符串值中的占位符替换；键名、对象结构和非字符串标量不靠字符串拼接改写。
- 根据 `ParamDefinitions` 校验必填、类型、长度、允许值和 URL；未知变量和未使用变量都要有明确策略。
- 渲染后的内容再次按企业微信 `msgtype` 的 JSON Schema 或渠道校验规则验证。`template_card` 的 URL 等必填字段不能依赖运行时猜测。
- 对模板版本采取不可变版本或发布状态。正在发送的日志必须记录实际 `TemplateVersion` 或渲染快照，避免编辑模板后无法复现历史消息。
- 模板“渲染预览”和“真实测试投递”分成两个动作。后者必须显式选择测试接收人、记录审计并隔离生产消息。

接收人采用 `individuals` 和 `departments`，首版会去重并拼成企业微信 `touser`/`toparty`。新项目应限制单次接收人数、校验部门 ID 和用户 ID 格式，并在返回部分失败时展示渠道给出的无效目标，不要只记录笼统的失败文案。

## 密钥、Token 与可观测性

首版在数据库内保存加密 `Secret`、缓存 `AccessToken` 和过期时间；`app/utils/encryption.py` 使用 Fernet。它解决了明文落库问题，但不等于完成密钥管理：加密主密钥不应和密文一起放入仓库或普通配置文件，也要支持轮换、访问审计和最小化解密范围。

必须写入复用方案的最低要求：

- `Secret`、Fernet/KMS 主密钥、企业微信 Token、HTTP `Authorization` 和渠道响应中的敏感字段只从受控密钥存储或环境注入；列表、详情、操作日志和异常响应全部脱敏。
- 首版 `config.yaml` 曾包含具体企业微信/Fernet 配置。任何来自该历史版本的环境都应旋转相关 Secret、Token 与加密键，并从 Git 历史和部署产物中清理暴露面；本文不复写其值。
- 首版发送路径把接收人、动态参数、渲染内容、完整消息体和企业微信响应写入 `info` 日志；首版 `get_access_token()` 也会在 debug 输出完整响应。这会泄露 PII、业务内容和令牌。新实现只记录配置/模板标识、数量、受控错误码和关联 ID；诊断内容写入受权限保护且已脱敏的审计存储。
- Token 缓存应以 `(tenant, config)` 为键、提前失效并防止缓存击穿。多 worker 场景需要分布式互斥；渠道返回 Token 失效时只允许一次受控刷新再重试原请求，避免无限循环。

`5aaa334e` 后续加入 Redis 分布式锁避免并发刷新，`5b65edac` 后续增加过期 Token 的受控重试。这些是有价值的演进，但都不属于首版能力；移植时应与真正的异步 worker 一并设计和测试。

## `IsActive/is_active -> IsEnabled/is_enabled` 迁移

这次替换影响的不只是企微配置和模板。原始提交同时涉及用户模型/兼容层、认证响应和当前用户依赖、员工与旧用户 Schema、邮件目标与邮件模板、CRUD/服务过滤、特性和角色模型，以及前端对应的类型、表单、筛选和本地用户状态。它是一项跨 API 契约迁移，不是数据库字段的简单改名。

建议按以下顺序实施：

1. **确定语义。** `is_enabled` 表示资源是否可用；它不应混同软删除、账号锁定、审批状态或“当前在线”。每一类实体分别定义禁用后的登录、读取、发送、关联和历史展示规则。
2. **扩展存储。** 以版本化 migration 新增/回填 `IsEnabled`、索引和注释；对于零停机发布，在过渡期由单一兼容层双读/双写，避免各业务服务自行写两套字段。
3. **切换服务端事实源。** ORM、查询条件、认证、权限依赖、邮件收件人解析和发送前检查统一读 `IsEnabled`。所有写请求和响应 DTO 统一使用 `is_enabled`，数据库命名可保留项目既有 PascalCase。
4. **兼容外部调用。** 缓存的当前用户、JWT/Session 声明、后台任务负载、导入导出、Webhook 和前端缓存都可能仍带 `is_active`。过渡期在 API 边界映射并打指标，达到约定窗口后删除旧别名。
5. **验收后收缩。** 全仓搜索、数据对账、接口契约测试和旧客户端监控均通过后，才删除 `IsActive/is_active` 字段、兼容属性和兼容请求参数。

首版企微发送只检查配置/模板是否存在且未软删除，**未检查 `IsEnabled`**。移植时必须在创建日志、worker 领取和人工重试三个时点校验禁用状态，并定义禁用后已排队日志是取消、失败还是允许完成。

## 不能原样复制的历史行为

| 首版行为 | 风险 | 新项目要求 |
| --- | --- | --- |
| HTTP 202 但同步直发 | 超时占满 API worker，客户端无法判断是否已送达或是否该重试。 | 真正 outbox/队列化，或返回同步语义的 200；两者不可混称。 |
| 重试任务是占位实现 | 状态变为 `PENDING` 却没有后续投递。 | worker 必须通过 `log_id` 重建上下文并真实执行；增加集成测试。 |
| `RetryCount` 在人工重试时归零，`NextRetryTime` 不被消费 | 上限失效、历史不可审计、任务遗失。 | 计数单调、尝试明细追加、调度器消费到期记录。 |
| 异常无统一收敛 | Token/渲染/HTTP 异常可遗留 `SENDING`。 | 用 `try/finally` 和明确错误分类更新日志。 |
| 服务常量 `MAX_MSGID_LENGTH=128` | 已迁移到 191 的列仍会被无声截断。 | 常量、Schema、ORM 和 migration 共用同一长度约束。 |
| 模板对 JSON 字符串正则替换 | 特殊字符导致解析失败或内容注入。 | 结构化递归渲染和渲染后 Schema 校验。 |
| `config.yaml` 含渠道/加密配置 | 密钥进入版本库和构建产物。 | 配置只保留示例键名；密钥进 Secret Manager，泄露后立即轮换。 |
| 迁移只 `ALTER` 两列 | 新环境没有四张企微表时迁移失败。 | 独立创建表、FK、索引、初始数据和列扩容 migration，并从空库演练升级。 |

## 推荐的模块拆分

| 层次 | 推荐职责 |
| --- | --- |
| Channel adapter | 把企业微信的 Token、请求、错误码和响应标准化；不处理 HTTP 用户权限或数据库事务。 |
| Template renderer | 结构化渲染、变量/类型校验、渠道消息结构校验；可纯函数测试。 |
| Notification service | 解析业务意图、生成幂等键、写主日志/outbox、选择渠道和重试策略。 |
| Worker | 原子领取、调用 adapter、追加尝试明细、收敛状态、安排下次重试。 |
| Repository | 只做持久化、软删除/范围过滤、锁定和查询；不自行提交事务。 |
| API route | 认证、动作权限、输入输出和正确的同步/异步 HTTP 语义。 |
| Operations | 仅查看脱敏日志和允许受控人工重试；不直接修改发送状态。 |

业务模块不应直接构造企业微信 JSON 或持有 `Secret`。它们只提交稳定的通知类型、模板版本、接收人引用、动态数据和幂等键；渠道差异留在 adapter 和模板层。

## 迁移验收清单

- [ ] 空数据库可按 migration 创建配置、模板、主日志、尝试明细、外键、索引和长度约束；升级、降级和已有数据升级均演练通过。
- [ ] Secret、Token、接收人、动态数据、消息体和渠道响应不出现在列表 API、普通日志、异常响应或操作审计中；密钥轮换有演练记录。
- [ ] 配置、模板、接收人、动态参数、模板版本和消息结构均在发送前验证；禁用或软删除资源的发送语义明确且被 worker 再次校验。
- [ ] `POST /send` 的状态码与实际执行方式一致；重复提交、请求超时、worker 重投和渠道超时均不会制造无法解释的重复消息。
- [ ] 每次实际投递都会追加 detail；`RetryCount`、`MaxRetryCount`、`NextRetryTime`、状态和错误分类一致，日志不会卡在 `SENDING`。
- [ ] 成功、全部无效、部分无效、Token 失效、限流、网络故障、渲染失败、数据库失败和 Celery 不可用都有自动化覆盖。
- [ ] `IsEnabled` 的数据库、ORM、DTO、认证、服务查询、缓存/JWT、邮件/通知消费者和前端契约均完成迁移；旧 `is_active` 兼容窗口有监控和删除计划。
- [ ] 无权限、跨范围或直接调用重试 API 的请求无法读取配置/日志或发送消息；前端隐藏按钮不是唯一控制。
