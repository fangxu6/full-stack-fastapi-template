## 原始调度链路与目标语义

```text
FTP 传输失败
  -> RetryLogic 计算下一次时间
  -> Redis Sorted Set: transfer:retry_queue
  -> Celery Beat（每 10 秒）
  -> FTP worker: process_retry_queue_task
  -> 领取到期记录并调用 TransferService.process_retry_task
  -> 更新文件传输状态 / 再次安排 / 终止
```

迁移后 FastAPI 只应提交业务记录或任务意图，不应以 `asyncio.sleep()`、应用生命周期任务或每个 Uvicorn worker 的本地 scheduler 维持可靠重试。Beat 是调度者，worker 是执行者；生产中每种职责都必须有明确的单实例/高可用策略。

## `5b298070` 的实际缺口

这次提交的结构说明了迁移时最容易遗漏的两类契约。

### 任务注册名、路由名和 Beat 名不一致

原始 task decorator 注册的是短名：

```text
process_retry_queue_task
```

但 `task_routes` 和 `beat_schedule` 使用的是全名：

```text
app.tasks.ftp_tasks.process_retry_queue_task
```

Celery 的 task name 是协议的一部分，不能由 Python 文件路径“自动推断”。在这个版本中 Beat 可能发布一个 worker 未注册的全名任务，结果是 `Received unregistered task` 或消息被拒绝；即使 worker 能消费，路由规则也不会命中短名任务。

新项目应把任务名定义为一个共享常量，并让 decorator、`send_task()`、Beat、route、监控和测试全部引用它。若已存在旧队列消息或历史发布者，增加显式全名/短名兼容别名并在迁移窗口后移除，不能悄悄更名。

### 消费任务调用了当时不存在的方法

原始任务执行：

```python
await retry_queue_service.consume_retry_queue(
    executor=ftp_transfer_service.process_retry_task
)
```

但同一提交树中的 `RetryQueueService` 仅有 `add_retry_task()`、`get_due_tasks()` 和 `remove_task()`，没有 `consume_retry_queue()`。因此 worker 实际执行会抛 `AttributeError`，随后按 Celery 的最大三次重试失败。这个问题不能通过“成功创建 Beat 项”发现，必须由真实 worker 集成测试暴露。

### Redis 队列本身不具备可靠领取语义

首版 `get_due_tasks()` 以 `ZRANGEBYSCORE` 读出所有到期 JSON，`remove_task()` 再单独 `ZREM`。两个 worker 可以同时读到同一条，再各自执行一次；worker 崩溃又可能在已执行但未删除、或已删除但未落库之间留下不一致。Redis 禁用时 `add_retry_task()` 直接返回，重试意图会被静默丢弃。

Redis Sorted Set 可作为延迟调度索引，但不应是唯一事实源。至少需要原子 claim/ack，或以数据库中的 retry/outbox 行为事实源，Redis 只是可重建的加速层。

## 推荐的可复用调度设计

```text
传输事务
  -> 写 TransferFile 状态、RetryAttempt、NextRetryAt、Outbox 事件
  -> commit
  -> outbox publisher 投递稳定的 task name（失败可补偿）
  -> worker 条件领取待处理文件
  -> 使用稳定文件 ID 执行、写 attempt、更新终态或下次重试时间
  -> Beat/reconciler 只扫描数据库中已到期但尚未投递/卡住的记录
```

| 责任 | 推荐规则 |
| --- | --- |
| 任务 payload | 仅传 `transfer_id`、`file_ids`、重复文件策略、版本/幂等键等稳定 ID；不传数据库对象、连接、密钥或完整文件内容。 |
| 幂等领取 | 使用 `status + version` 条件更新、`SELECT ... FOR UPDATE SKIP LOCKED` 或带租约的 claim，保证同一文件同一 attempt 仅一个 worker 实际传输。 |
| 延迟重试 | 由 `NextRetryAt` 和明确错误分类决定；限流/网络错误可退避，认证/路径/格式错误通常应直接终止。 |
| 任务发布 | 事务提交后经 outbox 发布；broker 不可用时保留待投递记录并可重放，不能仅记录日志后返回成功。 |
| 失败收敛 | worker 超时、进程丢失、重复消息、SFTP 断连和数据库提交失败都必须令文件记录进入可解释终态或可重领状态。 |
| 清理 | 文件、attempt、任务 ID、错误摘要和重试原因都保留审计；按保留期归档/删除，而不是只清 Redis 成员。 |

若数据量很小，最小可行方案仍应是“数据库状态 + 单个 Beat + 单个 worker 队列 + 条件领取”，而不是恢复每个 Web 实例各自启动 APScheduler。

## Celery 与部署契约

原始 Celery 配置有 JSON 序列化、`acks_late=True`、`task_reject_on_worker_lost=True`、FTP 队列和 10 秒 Beat。它们只提供投递基础，不自动带来业务幂等：worker 丢失后的 requeue 会重复执行，所以持久化状态机仍不可省略。

生产部署至少要验证：

1. 运行独立 worker，并订阅 `ftp` 队列；启动后检查 `registered tasks` 中存在 Beat 实际发送的精确名称。
2. 运行一个受监控的 Beat 实例，或使用带分布式锁/HA 的 scheduler；不得让多副本无协调地扫同一 retry 集合。
3. broker、result backend、Redis 重试索引和 FTP 数据库状态的故障边界明确；尤其不要把 Redis 同时当 broker、延迟队列和唯一状态库而没有恢复方案。
4. 任务参数、队列名、超时、重试次数和 worker 并发度由配置/常量集中定义；部署脚本不应复制 task name 字符串。
5. 指标至少包含：到期量、领取量、成功/失败/超时、重复领取、下一次重试延迟、最老待处理记录和 unregistered-task 数量。

`task_time_limit=600`、`soft_time_limit=540` 是所有任务的粗粒度默认值。FTP 大文件、断点续传和远端吞吐应有任务级时间预算；在软超时中落状态和释放租约，在硬超时后由恢复任务判定是否可重试。

## 迁移验收清单

- [ ] Beat、task decorator、task route、`send_task()`、队列名和监控使用同一稳定 task name；升级期间旧名有显式 alias 和删除期限。
- [ ] 从真实 worker 执行到期重试记录，不依赖 import 成功或 Beat 日志；验证不会出现 unregistered task、缺失消费方法或错误队列。
- [ ] 同一文件的并发 worker、重复消息、worker 丢失和数据库/Redis短暂故障不会重复传输或丢失重试意图。
- [ ] 重试的事实源持久化，`NextRetryAt`、attempt、错误摘要和终态可查询；Redis 延迟索引可从数据库重建。
- [ ] SFTP 超时、断链、远端重复文件策略、断点续传、软/硬超时和最大重试耗尽均有状态收敛与自动化测试。
- [ ] 每个 worker 使用属于自身事件循环的数据库连接并在任务结束后释放；没有 Web 进程全局 async session 穿透到 Celery。
- [ ] 运维已验证 worker/Beat 存活、队列积压、最老到期记录、失败率和任务注册清单，并演练 broker 不可用后的 outbox 补投。
