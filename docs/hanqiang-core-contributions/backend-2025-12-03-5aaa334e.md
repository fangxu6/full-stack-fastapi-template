## Token 刷新竞态与提交后的调用链

CodeGraph 当前调用链如下：

```text
WXWorkSendService.process_send()
  -> WXWorkConfigService.get_valid_token()
  -> token 缺失或 <= now + 5 min
  -> WXWorkConfigService.refresh_token()
       -> crud_wxwork_config.get(config_id)
       -> with redis_lock("wxwork:token:refresh:{config_id}")
       -> db.refresh(db_obj)
       -> 再检查 TokenExpiredTime > now + 5 min
       -> decrypt_secret(Secret)
       -> WXWorkAPI.get_access_token()
       -> 持久化 AccessToken/TokenExpiredTime
  -> WXWorkAPI.send_message()
  -> errcode 为失效类时 refresh_token() 后最多重发一次
  -> handle_send_result() 更新发送日志及明细
```

锁的关键步骤必须保持顺序：

1. 锁粒度至少包含租户/企业微信配置 ID，不能使用全局锁，否则不同配置互相阻塞。
2. 获锁后重新读取数据库。第一个 worker 刷新完成后，后续 worker 应直接复用新 Token，而不是再次请求微信。
3. 未获锁时不能盲目返回缓存 Token。只有重新读取后确认 Token 至少还有安全窗口（当前为 5 分钟）才返回，否则返回可重试的 `503 Token 刷新中`。
4. 释放必须比较随机 owner token；禁止无条件 `DEL`，否则锁过期后旧 worker 可能删除新 worker 的锁。

## 首版锁实现的边界与风险

原始 `app/utils/redis_lock.py` 的实现是同步上下文管理器：`get_sync_redis_client()`、`time.sleep()`、同步 `set/eval`，默认 `ttl=30`、`retry_times=3`、`retry_delay=0.1`。在 `async def refresh_token()` 中使用它会阻塞当前事件循环；重试等待期间同一 worker 的其他请求也可能被拖慢。

此外：

- Redis 未启用时 `acquire()` 直接返回成功，实际是无锁模式。单进程开发可接受，生产多 worker 必须禁止静默降级并在启动或调用边界显式失败/告警。
- TTL 没有续租。刷新、网络重试或 Redis 抖动超过 30 秒时锁会自然过期，第二个 worker 可能进入临界区。TTL 必须大于最坏刷新耗时，或实现续租和 fencing token。
- `redis_lock()` 只保证释放阶段不误删他人锁，不保证 Redis 故障期间的业务一致性；应将刷新结果视为可重复、版本化写入，并处理锁服务不可用。
- `retry_times` 是尝试次数而不是总等待时间；应根据 P99 刷新延迟、Redis RTT 和 API 限流设置，而不是复制默认值。

更适合异步服务的最小边界是使用同一事件循环内的 Redis 客户端和异步 `SET NX EX`，或把刷新协调放到同步 worker；不要在 async request path 里调用阻塞 `time.sleep()`。高价值配置还应增加 token 版本/更新时间条件写入，避免旧响应覆盖新响应。

## 企业微信发送与日志安全契约

`process_send()` 在 Token 无效时只对明确的可恢复错误做一次强制刷新重试；当前后续代码将 `40001/40014/42001` 视为可重试错误，非这些错误直接进入业务失败分类。重试必须满足：

- 同一发送日志只重试一次，避免 Token 错误造成无限发送。
- 记录原始 `errcode/errmsg`、刷新结果和最终响应，但不得记录 `access_token`、`corpsecret`、完整收件人或完整消息体到 INFO/生产日志。
- 发送成功后以企业微信 `msgid` 和本地发送日志 ID 建立关联；渠道已接受但响应超时应进入 `unknown`/待核验，而不是自动再次发送。
- `WXWorkSendService.process_send_by_log_id()` 只接收稳定的 `log_id`，worker 从数据库重新读取配置、模板、动态数据和收件人快照。

提交将完整请求体移到 DEBUG，但 DEBUG 在生产环境也可能被启用；更稳妥的实现是在日志结构化字段层做字段级 allowlist/掩码，并对 `invaliduser` 等错误详情限制长度。

## 当前跨模块影响

CodeGraph 显示 `app/utils/redis_lock.py` 当前被企业微信配置刷新以及文件监控、报表 schema task、班次时间等模块使用；锁工具的同步/降级语义变化具有公共层 blast radius。当前代码库还存在异步 `app/core/redis_lock.py`（延迟初始化、异步客户端、`redis_lock(name, ttl_seconds=...)` 和 `dedup_once()`），两者不是同一 API，复用时必须统一命名和实现，避免调用方误导入错误模块。

`extract_user_info()` 当前被配置、模板和发送日志路由调用，返回 `(UserID, UserCode)`，不验证字段存在、不规范化 UUID，也不替代 `require_permission()`。调用方仍必须在路由依赖层完成鉴权，并在写库前使用统一 `to_uuid_bytes()`。

## 推荐的可复用设计

| 组件 | 推荐职责 |
| --- | --- |
| `TokenStore` | 保存加密 Secret、当前 Token、过期时间、版本和更新时间；Secret 永不出现在响应或普通日志。 |
| `TokenRefresher` | 先读缓存，再按配置 ID 获取分布式锁；获锁后二次检查；刷新后条件写入并发布指标。 |
| `DistributedLock` | 异步 `SET NX EX`、owner token、Lua/原子释放、明确的 Redis 不可用策略、可选续租/fencing。 |
| `ChannelClient` | 只负责 HTTP 请求和响应解析；不得自行缓存 Token 或实现第二套刷新锁。 |
| `SendWorker` | 以发送日志 ID 领取持久化工作项，限制一次重试，记录业务终态和渠道消息 ID。 |
| `Redaction` | 统一字段级日志脱敏；INFO 只保留配置 code、模板 code、数量和 trace ID。 |

建议把锁 key 规范化为 `lock:{tenant}:{provider}:{config_id}`，并记录 `lock_wait_ms`、刷新次数、命中二次检查次数、刷新失败数和 Token 剩余 TTL，便于判断锁是否真的降低了重复刷新。

## 复用验收清单

- [ ] 并发启动多个 worker 刷新同一配置时，企业微信 `gettoken` 只调用一次，其余 worker 读取到同一有效 Token。
- [ ] 锁竞争时缓存 Token 已过期或仅剩不足安全窗口，调用方得到可重试的 `503`，不会使用 stale Token 发送。
- [ ] Redis 锁 TTL 到期、Redis 短暂不可用、网络超时和 worker 崩溃后，锁不会被错误释放，业务状态可恢复。
- [ ] 异步请求路径不执行阻塞 `time.sleep()`；刷新耗时超过 TTL 时有续租或明确失败策略。
- [ ] 条件更新/版本校验阻止旧刷新响应覆盖更新的 Token；重启后 Token 仍可按密钥策略解密。
- [ ] 企业微信失效 Token 只触发一次受控重试；非 Token 错误不重试，最终状态和渠道 `msgid` 可查询。
- [ ] INFO、WARN、ERROR 日志不含 `access_token`、`corpsecret`、完整收件人和完整消息体；DEBUG 也有字段级掩码和长度限制。
- [ ] 配置、模板和发送日志路由都通过统一身份提取函数，并保留权限依赖与 UUID 边界校验。
- [ ] 使用真实 Redis、测试数据库和至少两个 worker 完成并发刷新、锁过期、刷新失败和重复发送演练。
