这不是单纯的“修一个 Python 版本 bug”。它将 API 与任务执行拆到不同进程，改变了返回语义、事务边界、故障恢复和审计方式。

## 根因与正确的生命周期模型

FastAPI 的 async session/engine 可以绑定其运行 loop；Celery prefork worker 是独立进程，task 又可能通过 `asyncio.run()` 反复创建和关闭新 loop。若把 Web 进程创建的 async engine、连接池、session factory、HTTP client 或 Future 带进 Celery，就会出现：

```text
Future attached to a different loop
Event loop is closed
connection cleanup 在已经关闭的 loop 上执行
```

正确解决方式不是压掉报错，而是建立所有权：

```text
Celery 同步 task
  -> 唯一的 coroutine runner 创建任务 loop
  -> 在该 loop 内创建 engine / session factory / client
  -> 打开 session，执行领域 service，commit 或 rollback
  -> finally 关闭 session/client 并 dispose engine
  -> runner 关闭 loop
```

任何 `AsyncSession`、ORM 对象的 lazy relation、连接、异步锁、Future 或 `AsyncClient` 都不得跨这个边界传递。任务 payload 只传 JSON 可序列化的稳定 ID、枚举值和有限长度参数；worker 从数据库重新读取当前事实。

## 原始异步投递链路

```text
邮件 API
  -> send_task("send_email_async_task", queue="email")
  -> email Celery task -> 独立协程/会话 -> EmailSendService

FTP 创建、补传、延迟重试
  -> send_task("process_transfer_task", [transfer_id, file_ids, strategy], queue="ftp")
  -> FTP Celery task -> TransferService.process_transfer_batch_by_id()

企微发送/人工重试
  -> 写 SendLog -> send_task("wxwork_send_message", [log_id])
  -> WXWork Celery task -> process_send_by_log_id()
```

这次提交使企业微信的 `POST /send` 终于从“HTTP 202 但 API 内同步直发”转向 worker 投递；FTP 的多个传输入口也从本地协程转向队列。邮件 API 则立即返回 `success: true`、`message_id: null`、`task_id`，其语义只能是“broker 接受了发布请求”，不是邮件已经发出。

### 原始任务与队列契约

| 任务名 | 队列 | 原始 payload/行为 |
| --- | --- | --- |
| `send_email_async_task` | `email` | 配置、目标、模板、变量、附件、创建人 ID；由 API 直接 `send_task()`。 |
| `process_retry_queue_task` | `ftp` | 周期消费 FTP 重试队列；承接前一提交的 Beat 迁移。 |
| `process_transfer_task` | `ftp` | `transfer_id`、可选 `file_ids`、`duplicate_strategy`；worker 按 ID 取数执行。 |
| `wxwork_send_message` | `wxwork` | `log_id`；worker 读发送日志、配置、模板和参数后发送。 |

任务名必须和 Celery decorator、route、Beat、`send_task()` 和历史积压消息一致。`5b298070` 的 FTP 全名/短名不一致在这里仍需面对；当前代码随后通过双 alias 兼容，不能在新系统中靠“队列刚好为空”回避协议迁移。

## 首版实现中不能照抄的部分

### 全局补丁和错误抑制

原始 `celery_utils.py` 在模块导入时执行三件事：

1. 无条件 `nest_asyncio.apply()`。
2. monkey patch SQLAlchemy 私有方法 `Pool._close_connection`，对包含 `Event loop is closed` 或 `attached to a different loop` 的 `RuntimeError` 直接忽略。
3. `run_async_task()` 临时替换 `sys.stderr`，过滤 `Event loop is closed` 和 `Exception in callback` 的输出，再调用 `asyncio.run()`。

这些做法有全进程副作用，并会把真正的连接泄漏、错误 loop 归属、回调异常或清理失败伪装成正常任务完成。SQLAlchemy 私有 API 的签名也可能随依赖升级变化。复用时必须删除这种“按错误文本吞异常”的处理；先修复资源归属，再让未预期的异常完整进入日志、指标和 Celery 失败状态。

### `NullPool` 与不 dispose 不是完整生命周期管理

原始邮件、FTP、企微 task 在协程内创建 `create_async_engine(..., poolclass=NullPool, pool_pre_ping=False)`，并注释“不调用 `dispose()`，让 NullPool 自然清理”。`NullPool` 能减少连接跨 loop 复用，但不会替代确定性的关闭；未释放 engine/client 会让资源清理依赖 GC 和进程生命周期，长驻 worker 下仍可能泄漏文件描述符或积累连接问题。

每项资源必须有明确 `finally`：session 结束后 rollback 未提交事务、关闭客户端、`await engine.dispose()`。当前 FTP task 已演进为 `_task_session_factory()`：在 task loop 中创建 engine/session factory，并在上下文退出时 dispose，这是应复用的方向；不要复制首版“不 dispose”。

### 失败返回值与 Celery 状态不一致

原始 FTP task 在重试耗尽后返回 `{"success": false, "error": ...}`，而不是抛出异常。对 Celery 而言这通常是 `SUCCESS` task state，监控若只看 task state 会把业务失败算为成功。企业微信 task 捕获异常后标记发送日志失败再 `raise`，行为则不同；不同模块的失败协议不一致。

新项目要选择一个规则并贯通：可恢复故障调用 `self.retry()`；不可恢复故障记录持久化业务终态后抛出受控异常，使 task 为 `FAILURE`；若确实返回业务失败对象，监控和调用方必须显式以该对象判定失败，不能只读 Celery state。

### 迁移未覆盖所有本地协程

本提交把多处 FTP `asyncio.create_task()` 改为 `send_task()`，但该版本的 `transfer_service.py` 仍保留至少一处 `asyncio.create_task`。因此不能把它描述为“完全消除 Web 进程内后台任务”。迁移清单必须以调用点清单和运行时观测验收，而不是提交标题。

### API 接受与持久化投递不是同一件事

邮件 API 直接发布任务后返回“已入队”；企微在创建发送日志后发布，发布失败时尝试标记失败；FTP 也在事务流程中直接 `send_task()`。broker 发布成功不代表业务数据库状态和任务消息是原子一致的：可能有记录无任务、任务先看到未提交数据，或客户端超时后重复请求。

可靠实现需要 transactional outbox：业务事务内写状态和 outbox，提交后 publisher 投递，投递成功才记录 outbox 已发布；后台 reconciler 重放未发布记录。API 返回 `202` 必须代表一个可查询的持久化 job/log 已被接受，而不是只代表调用过 `send_task()`。

## 推荐的可复用实现边界

| 层次 | 推荐职责 |
| --- | --- |
| API / service | 校验输入、写业务记录/attempt/outbox、返回 job ID 或 log ID；不在 Web loop 用 `create_task` 跑可靠任务。 |
| Outbox publisher | 读已提交 outbox，使用稳定 task name 投递，记录 broker task ID、投递时间和失败原因；可幂等重放。 |
| Celery task | 只协调 task 生命周期、限时、retry 和指标；payload 只含稳定 ID。 |
| Async resource scope | 在 task 所属 loop 内创建 engine/session/client；rollback、close、dispose 在 finally。 |
| Domain worker service | 用 ID 领取持久化工作项，校验状态/租约/幂等键，执行业务并追加 attempt；不信任过期 payload。 |
| Reconciler | 回收 worker 丢失、租约过期、outbox 未投递、`SENDING` 超时和延迟重试任务。 |
| Monitoring | 分别记录 broker publish、Celery state、业务终态和最老待处理记录；不能用其中一个代替另一个。 |

对于一个确实只在 Celery prefork worker 调用的 runner，`asyncio.run(coro)` 可以是最小实现；但它必须拒绝在已有运行 loop 中调用，且 coroutine 创建后只能交给一次 runner。若同一进程有多线程/gevent/eventlet 或嵌入式 worker，需要专门选择并验证 event-loop 并发模型，不能靠 `nest_asyncio` 通用化。

## 邮件、FTP、企微的领域验收重点

| 通道 | 不能省略的持久化事实 | 典型重复/失败风险 |
| --- | --- | --- |
| 邮件 | EmailSendHistory、收件人快照、模板版本、附件引用、outbox/task ID、attempt、终态。 | API 超时后重投、SMTP 已接受但响应丢失、附件过期。 |
| FTP | Transfer/TransferFile、偏移量、重复文件策略、retry attempt、NextRetryAt、租约和远端校验结果。 | worker 丢失、断点续传冲突、同一文件被两 worker 传输。 |
| 企业微信 | SendLog、template/config 版本、接收人快照、渠道消息 ID、attempt、错误分类和幂等键。 | 渠道已接收但超时、Token 刷新并发、人工重试覆盖历史。 |

跨通道都应在 API 返回中区分：`accepted`、`completed`、`failed`、`unknown`。网络超时场景先用 job/log ID 查询最终状态，绝不能前端或调用方自动再发一次。

## 迁移验收清单

- [ ] 所有可靠后台路径已从 Web `asyncio.create_task` 清单迁出；剩余本地协程仅用于请求生命周期内可取消、无持久副作用的工作。
- [ ] API 在返回 `202` 前已有可查询的 job/log/outbox 记录；broker 发布失败、发布后进程崩溃、worker 未注册和消费失败都有补偿路径。
- [ ] task decorator、`send_task`、Beat、route 和历史兼容 alias 使用精确一致的名称；worker 启动校验覆盖每个生产队列。
- [ ] task payload 仅含 JSON 稳定 ID/有限参数；worker 重新读库并以租约或条件更新保证幂等，不使用跨 loop 的 session/ORM 对象。
- [ ] engine、session、HTTP client 和 loop 的创建/关闭在同一 task scope；commit、rollback、close、dispose 在异常和超时下都执行。
- [ ] `nest_asyncio`、私有 SQLAlchemy monkey patch、stderr/error 文本过滤均已移除或隔离在可证明安全的临时诊断环境；未预期异常会变为可观测失败。
- [ ] retry 耗尽后的 Celery state 与持久化业务状态一致；监控同时告警 publish 失败、task failure、业务失败、卡住租约和最老待处理记录。
- [ ] 邮件、FTP、企微分别验证重复请求、重复消息、worker 丢失、软/硬超时、数据库回滚、broker 中断、渠道已执行但响应超时和人工重试。
- [ ] 以真实 worker、broker、测试库和一个 Beat 实例完成端到端演练，并检查没有 unregistered task、连接泄漏、跨 loop RuntimeError 或被过滤的 callback error。
