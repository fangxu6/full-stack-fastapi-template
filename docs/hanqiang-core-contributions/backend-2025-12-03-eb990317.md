## 根因：两个不同生命周期的 ID 被混为同一个字段

前一提交 `9158d8fe` 将 `POST /api/email/send` 从同步调用 `EmailSendService.send_email()` 改为发布 `send_email_async_task`：

```text
HTTP 请求
  -> Celery send_task("send_email_async_task")
  -> 立即取得 broker task_id
  -> 返回 { success: true, message_id: null, task_id }

Celery worker
  -> EmailSendService.send_email()
  -> 生成 uuid.uuid4().bytes
  -> 写 Sys_Email_SendHistory.MessageID
  -> SMTP 发送并更新 sent / failed
  -> 返回字符串 UUID 的 message_id
```

但原来的 `EmailSendResponse.message_id` 是必填 `str`。broker 已经接受任务后，路由返回 `message_id: null` 会在 FastAPI 的 `response_model` 序列化阶段触发响应校验错误，最终可能对客户端表现为 500。`eb990317` 将该字段改为可空并新增 `task_id`，修复了这个协议断裂。

这里的两个 ID 不能互换：

| ID | 产生时机 | 当前存放位置 | 客户端含义 |
| --- | --- | --- | --- |
| `task_id` | `send_task()` 成功返回后 | Celery broker/result backend；当前邮件历史未保存它 | 某次异步执行的调度标识，只能说明发布已被 broker 接受。 |
| `message_id` | worker 内开始领域发送时 | `Sys_Email_SendHistory.MessageID`，MySQL `BINARY(16)` | 一次邮件发送历史的领域主键，可用于查历史和重试。 |

当前 `EmailSendService.send_email()` 内部使用 `uuid.uuid4().bytes` 写历史记录和附件关联，返回 API 前才转为 `str(uuid.UUID(bytes=message_id))`。`EmailSendHistoryResponse` 的 Pydantic validator 也将 `bytes`/`bytearray` 转为 UUID 字符串。因此数据库、服务内部和 HTTP/Celery JSON 边界应始终遵循：

```text
数据库 BINARY(16) <-> 服务内部 bytes <-> URL / JSON 字符串 UUID
```

不要把 `bytes` 放入 Celery payload 或 JSON 响应，也不要在任务投递阶段伪造尚未存在的 `message_id`。

## 推荐的异步邮件契约

`message_id: null` 是对旧响应模型的兼容修复，不足以让调用方可靠追踪一封邮件。跨进程任务应有独立、持久化的工作项，而不是只依赖短生命周期的 broker task：

```text
POST /mail-deliveries
  -> 同一数据库事务创建 DeliveryJob(status=accepted, idempotency_key, request snapshot)
  -> 写 Outbox(task_name, job_id)
  -> 提交
  -> publisher 投递 job_id，并记录 celery_task_id
  -> HTTP 202 { job_id, status: accepted }

worker(job_id)
  -> 条件领取 job / 获取租约
  -> 创建 EmailSendHistory(message_id) 与 attempt
  -> 发送并写领域终态
  -> job.status = sent | failed
```

建议的对外模型应把“受理”和“发送完成”分开：

| 场景 | 推荐响应 | 不应表示的含义 |
| --- | --- | --- |
| 异步受理 | `202 Accepted`，必填 `job_id`，可选 `celery_task_id`，状态 `accepted` | SMTP 已连接、邮件已被接收或最终会成功。 |
| 查询进度 | `job_id` 对应的 `accepted/running/sent/failed/unknown`、attempt 和关联 `message_id` | 只读 Celery `SUCCESS` 就认为领域发送成功。 |
| 同步发送（确有需要） | 成功时必填字符串 `message_id` | 与异步响应共用一个“可能为空”的成功语义。 |

业务事务与 broker 发布不是原子操作。应使用 transactional outbox 或等效重放机制，保证“已写 job 但尚未发布”“broker 已发布但 API 超时”“worker 在发送后崩溃”等状态都有可观测、可恢复的处理路径。Celery payload 只传 `job_id` 等 JSON 字符串；worker 重新读库，不传 ORM 对象、`bytes` UUID、SMTP 密码或附件正文。

## Fernet 密钥统一的正确边界

原始提交让 `settings.fernet_cipher` 以 `ftp.fernet_key` 优先、全局 `encryption_key` 兜底。它解决了未配置 FTP 专用 key 时的使用障碍，但这只是**配置回退**，不等于安全的密钥统一。

当前 `PasswordEncryption` 的实际来源顺序是：`ENCRYPTION_KEY` 环境变量、`settings.encryption_key`、开发环境临时生成 key。它被 CodeGraph 定位为以下敏感数据的公共加解密层：

| 领域 | 加密调用 | 解密调用 |
| --- | --- | --- |
| 邮件 SMTP 密码 | `crud_email_config.create/update` | `crud_email_config.get_decrypted_password` |
| FTP 密码与私钥 | `ftp.config_service.encrypt_password/encrypt_private_key` | 对应 decrypt 方法 |
| 数据源凭据 | `data_source_service.create/update`、报表配置 | `datasource_engine_factory.build_url`、报表配置读取 |
| 其他使用 `app/utils/encryption.py` 的机密 | `encrypt_secret` | `decrypt_secret` |

因此，变更 Fernet key、优先级或序列化格式会同时影响邮件、FTP 和数据源的已存密文。复用时应满足下列规则：

1. 由部署环境的 secret manager 或显式环境变量提供一个受控 key；应用启动时校验格式，生产环境缺失时失败，绝不为持久化数据临时生成 key。
2. 每份密文带格式版本和 `key_id`，例如 `v1:<key_id>:<token>`；新写入只使用活动 key，解密按 `key_id` 选择允许的 key。
3. 轮换期间保留旧 key 的只读解密能力；成功读取旧密文后按需重加密，或通过可审计批处理轮换。不得直接替换部署 key 后期待旧密文自动可读。
4. 将 key 选择封装为唯一的加密提供者；FTP、企业微信等子模块只能引用该提供者，不能各自引入“专用 key 优先”的第二事实源，除非业务隔离有明确的 key-id 和迁移方案。
5. 保留现有 Fernet token 的双重 Base64 编码兼容路径，直到全部旧密文迁完；序列化格式变更必须有版本判别，不能靠异常回退或吞解密错误猜格式。

当前 `PasswordEncryption` 在没有 key 时仍会生成临时开发 key。这在进程重启后必然无法解密之前写入的密文，生产复用时必须移除该持久化风险；本地开发可以由显式的开发配置提供固定、非生产 key。

## 当前实现的已知缺口

以下结论来自当前代码和 CodeGraph，**不属于** `eb990317` 的原始差异：

| 当前路径 | 现状与复用影响 |
| --- | --- |
| `app/api/v1/routes/email_send_routes.py` | `POST /api/email/send` 发布到 `email` 队列后返回 HTTP 200、`message_id: null` 与 `task_id`；没有创建可由该 `task_id` 查询的持久化 job。历史查询只能在 worker 已创建 `Sys_Email_SendHistory` 后按 `message_id` 使用。 |
| `app/tasks/email_send_task.py::send_email_async_task` | task 直接携带配置、目标、变量和附件 payload；重试耗尽时返回 `{success: false}` 而不是抛出，Celery state 可能仍为 `SUCCESS`。监控不能只看 task state。 |
| `app/services/email/email_send_service.py` | worker 生成 `bytes` `message_id`，创建历史、附件记录并发送 SMTP，最后返回字符串 UUID；这是领域 ID 唯一可信的生成点。 |
| `app/models/email/email_send_history.py` | `MessageID`、关联 ID 和审计 ID 都为 `BINARY(16)`；模型和 schema 在对外边界转换为字符串 UUID。 |
| `app/core/config.py` 与 `app/utils/password_encryption.py` | FTP cipher 的 key 优先级和密码加密器的 key 优先级并不完全相同；仍存在环境变量、配置文件、子模块专用 key 三套来源。 |

与关联提交 `9158d8fe` 一样，当前邮件 worker 以 `NullPool` 创建 engine 后未显式 `dispose()`。这属于 Celery/async 资源生命周期问题，应按关联文档的“每个 task loop 自行创建、关闭 session/client/engine”规则处理，不应因本提交的响应模型修复被忽略。

## 复用验收清单

- [ ] 生产启动在没有受控 Fernet key、key 格式无效或 key-id 未配置时立即失败；不会写入由临时 key 加密的持久化数据。
- [ ] 固定 key 下，邮件、FTP、数据源的历史密文可在应用重启后解密；轮换期间旧 key 密文仍可读，新写入带新 `key_id`，轮换进度可审计。
- [ ] 加密 key 来源、优先级和密文格式仅由一个公共组件决定；子模块不存在未声明的私有 fallback。
- [ ] 异步受理接口返回 `202` 和持久化 `job_id`；客户端不会把 `celery_task_id` 或空 `message_id` 当作邮件已发送。
- [ ] worker 只接收 JSON 形式的稳定 ID，从数据库重新读取请求快照；重复投递不会产生重复的 SMTP 发送或重复历史。
- [ ] `message_id` 在服务/数据库内部始终为 16 字节 UUID，在 HTTP 与消息 payload 中始终为标准字符串 UUID；转换测试同时覆盖历史查询、附件关联和重试。
- [ ] broker 发布失败、outbox 未发布、worker 崩溃、SMTP 超时、重试耗尽分别写入可查询的业务终态；重试耗尽后 Celery state 与领域失败语义一致。
- [ ] 用真实测试数据库、broker 和 worker 完成一次端到端演练：受理、查询 accepted、发送成功、SMTP 失败、重复请求、worker 中断和 key 轮换均有预期结果。
