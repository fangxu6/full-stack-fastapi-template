## 原始调用链

```text
FileMonitor 配置创建/更新
  -> ConfigValidator.validate_regex()
  -> validate_regex_pattern()
  -> 通过后保存 SenderPattern/EmailTitlePattern/FileNamePattern

邮箱处理
  -> FileMatcher / FileMonitorFileProcessor
  -> RegexMatcher.match(pattern, sender|subject|filename)
  -> _get_compiled()（缓存 + 安全校验）
  -> regex.search(..., timeout=100ms)
  -> RegexMatchResult(matched, reason)
```

`RegexMatcher` 当前由以下路径共享：

## 当前安全参数与语义

| 参数/规则 | 当前值或行为 | 复用注意 |
| --- | --- | --- |
| `MAX_PATTERN_LENGTH` | 500 字符；实例参数最低限制为 32。 | 长度不是复杂度证明，仍需编译/匹配预算。 |
| `MAX_NESTED_QUANTIFIER_DEPTH` | 2；使用正则启发式检测常见嵌套量词。 | 对复杂语法、转义括号、条件分支可能误判；不能替代 parser 或隔离执行。 |
| `MAX_CAPTURE_GROUPS` | 10；通过括号计数并排除 `(?:`。 | `(` 计数会受转义、lookaround 等语法影响，属于近似规则。 |
| 黑名单 | `(.*)+`、`(.+)+`、`(a+)+`、`(a*)*`、`(a|a)*`、`(a|aa)+` 等字符串模式。 | 子串黑名单会有误报/漏报；日志只记录截断 pattern。 |
| `REGEX_MATCH_TIMEOUT_MS` | 100ms；`regex` 可用时传给 `search`。 | timeout 是每次匹配预算，不等于请求级总 CPU 预算。 |
| 文本长度 | 默认截断到 2048 字符。 | 截断可能改变业务匹配语义；应在契约中明确或按字段设置上限。 |
| 编译 | 当前 `validate_regex_pattern`/`_get_compiled` 使用 `regex.compile`，但工作树版本未对 compile 传 timeout。 | 提交主题包含 compile timeout，当前实现并未完整保留该能力。 |
| 依赖缺失 | import `regex` 失败时降级到 `re`，并记录 warning；`re` 没有 timeout。 | 不可信配置必须 fail closed，不能把依赖缺失当成安全可接受的 fallback。 |
| 缓存 | `RegexMatcher` 默认 `cache_size=256`，LRU 淘汰；空 pattern 直接匹配成功。 | 需要限制 pattern 数量、缓存内存和租户隔离，避免缓存污染。 |

## 配置验证与运行时匹配边界

- 保存配置时验证语法和危险模式，避免任务队列中出现明显坏配置；运行时仍必须再次调用 `RegexMatcher.match`，因为数据库、导入脚本和历史配置可能绕过保存 API。
- `pattern=None/""` 当前表示无约束并匹配成功；不同字段若需要“必须配置”，应在配置 Schema 另行声明，不能靠 matcher 猜测。
- `RegexMatchResult.reason` 应使用稳定错误码（如 `PATTERN_TOO_LONG`、`PATTERN_REDoS`、`MATCH_TIMEOUT`），不要让页面或告警依赖异常文案。
- 超时、编译失败和黑名单命中应记录 pattern hash、配置 ID、字段名、文本长度和规则版本，不记录完整邮件主题/正文或完整用户输入。
- 匹配 timeout 只保护单次 search；邮箱批处理仍需总任务 deadline、并发上限和取消机制。

## 不能原样复制的历史行为

| 历史行为 | 风险 | 新项目要求 |
| --- | --- | --- |
| 缺少 `regex` 时降级到 `re` | 恶意模式重新获得无界 CPU 时间。 | 生产启动时强制依赖存在；不可信配置路径 fail closed。 |
| 只用黑名单/括号计数判断危险模式 | 复杂正则可绕过启发式，普通合法正则也可能误报。 | 使用受限正则语法、静态复杂度分析、timeout 和进程级资源隔离。 |
| 当前版本 compile 没有 timeout | 编译阶段可能先于 search 消耗 CPU。 | 使用支持 compile budget 的实现，或在独立 worker/进程中编译。 |
| 截断文本到 2048 字符 | 合法文件名/主题被截断后语义改变。 | 按字段定义最大长度，超限返回明确错误或在业务上允许截断。 |
| `file_processor._compile_pattern` 另建 `re` 缓存 | 调用路径绕过统一安全策略。 | 删除第二套缓存，所有匹配经过 `RegexMatcher`。 |
| 把 pattern 原文写入日志 | 正则可能包含业务名称、邮箱、路径和敏感信息。 | 记录 hash、字段、配置 ID、规则版本和截断后的安全摘要。 |

## 推荐的可复用设计

| 组件 | 职责 |
| --- | --- |
| `PatternPolicy` | 长度、语法、允许特性、复杂度、捕获组和字段级文本上限。 |
| `SafeRegexCompiler` | 在依赖可用且有编译预算的环境中编译；编译失败/超时返回稳定错误码。 |
| `SafeRegexMatcher` | 单次匹配 timeout、取消和结果分类；不暴露底层异常对象。 |
| `PatternCache` | 按租户/版本隔离的有界 LRU，限制模式数量和内存。 |
| `MatchBudget` | 单次请求/批处理的总匹配次数、CPU deadline 和并发上限。 |
| `PatternAudit` | 保存配置 ID、pattern hash、字段、拒绝/超时次数和规则版本。 |

对真正不可信的正则，最好使用独立进程或受限 worker；线程 timeout 不能阻止 C 扩展或 Python 解释器占用整个进程。

## 复用验收清单

- [ ] `regex` 依赖在构建和启动阶段强制检查；缺失时生产服务拒绝加载不可信正则。
- [ ] 配置保存和实际匹配均经过同一个 `PatternPolicy/SafeRegexMatcher`，没有 `re.search` 或第二套缓存绕过。
- [ ] 长度、语法、嵌套量词、捕获组、递归/子程序和不允许的高级特性有明确错误码。
- [ ] 编译和匹配都有独立时间预算；超时不会吞掉异常或进入无限重试。
- [ ] pattern、文本、配置和租户的最大长度/数量/内存有总预算，批处理有 deadline 和取消。
- [ ] timeout、编译失败、黑名单命中和缓存淘汰都有安全指标与脱敏日志。
- [ ] 文本截断是否改变语义有字段级契约；文件名、主题、发件人和正文分别测试边界。
- [ ] 使用典型灾难模式、变体模式、合法复杂模式、Unicode、空 pattern 和依赖缺失环境完成回归。
- [ ] 至少在真实 worker/容器中验证 CPU 峰值、并发邮箱处理和超时后的任务状态收敛。
