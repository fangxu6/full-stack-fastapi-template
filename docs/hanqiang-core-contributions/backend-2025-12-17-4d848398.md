# FileMonitor 附件处理的异步 I/O 与 MD5 复用

> 来源总览：[hanqiang 通用与核心提交整理](../hanqiang-core-contributions.md)
>
> 复用定位：提交优化了附件处理的本地写入和摘要计算，并为大文件增加并发门控、上传辅助和正则缓存。当前架构已把 `FileMonitorFileProcessor` 演进为协调器，委托 `FileMatcher`、`DuplicateDetector`、`AttachmentLifecycleHandler`、`FileUploadCoordinator`、`ApiCallPreparator` 等专职服务。性能优化不等于真正的流式内存模型：当前附件入口仍持有完整 `bytes`，大文件上传 helper 也调用 `upload_bytes`，迁移时必须重新定义内存和生命周期边界。

## 原始变更范围

| 能力 | 原始改动 | 复用意义 |
| --- | --- | --- |
| 异步本地写入 | 使用 `aiofiles.open(..., "wb")` 替换同步 `Path.write_bytes()`。 | 避免在 async worker 中直接阻塞事件循环；仍需限制 bytes 内存和磁盘 I/O 并发。 |
| MD5 复用 | 在附件处理早期计算一次 MD5，供去重、历史和后续上传使用。 | MD5 只用于去重/索引，不可作为安全完整性证明；应在记录中保存算法用途。 |
| 大文件门控 | `LARGE_FILE_THRESHOLD=10MB`、`MAX_CONCURRENT_LARGE_FILES=3`、`STREAMING_CHUNK_SIZE=5MB`，增加 MinIO 上传辅助。 | 用有界并发保护内存和存储服务；阈值需按部署压测而非照搬。 |
| 正则缓存 | 增加 `_compile_pattern()` 的 `re` 字典缓存。 | 减少重复编译，但与后续 `RegexMatcher` 形成第二套缓存，不能继续并存。 |

## 原始处理链路

```text
FileMonitorFileProcessor.process_attachment()
  -> 读取附件 bytes / 文件大小
  -> 计算 MD5（去重和历史复用）
  -> 四层匹配（发件人 -> 主题 -> 文件名 -> 大小）
  -> DuplicateDetector / 已有 MD5 查询
  -> aiofiles 写入本地临时路径
  -> API 占位符替换与外部 API 调用
  -> MinIO success/failed/temp 上传
  -> ParseHistory / ReceiveHistory
```

大文件路径使用信号量限制同时处理数量；提交中的“streaming”主要是上传分支和并发门控命名，原始函数仍接收完整 `file_bytes`。

## 当前 CodeGraph 链路

当前 `FileMonitorFileProcessor` 是 7 步协调器：

```text
process_attachment()
  -> AttachmentLifecycleHandler.safe_filename()
  -> 文件大小前置检查（MAX_ATTACHMENT_SIZE=50MB）
  -> _md5_hex(file_bytes)
  -> FileMatcher.match_attachment()
       -> RegexMatcher（发件人/主题/文件名）
  -> DuplicateDetector.is_duplicate()
  -> AttachmentLifecycleHandler.download_and_save()
       -> aiofiles 写本地日期/UUID 路径
  -> ParseHistoryRecorder.create_download_history(ParseType=1)
  -> ApiCallPreparator.prepare_file_for_api()
  -> FileMonitorApiCaller.call_target_api()
       -> URLValidator + API 重试 + ParseHistory(ParseType=2)
  -> FileUploadCoordinator.upload_to_minio()
       -> success/failed/temp 桶和对象状态
  -> archive backup（配置存在时）
  -> ensure_receive_history()
```

`process_mailbox()` 还会预索引 sender/title/filename，缓存正则结果和 MD5 集合，减少批量处理中的重复查询与匹配。

## 当前性能参数与实际限制

| 参数/实现 | 当前行为 | 复用注意 |
| --- | --- | --- |
| 单文件上限 | `MAX_ATTACHMENT_SIZE=50MB`，超限记录历史后跳过后续处理。 | 限制应在 IMAP/API 下载前和内存分配前生效；不能只在 bytes 到手后检查。 |
| 大文件阈值 | `LARGE_FILE_THRESHOLD=10MB`。 | 阈值与容器内存、MinIO 带宽、并发和附件来源耦合，应配置化。 |
| 大文件并发 | 全局 `asyncio.Semaphore(3)` 或注入 semaphore。 | 单进程限制不等于集群总限制；多 worker 需配额/队列级门控。 |
| chunk size | `5MB` 常量；当前 `_upload_file_streaming` 仍把完整 bytes 传给 `upload_bytes`。 | 这不是端到端流式读取；真正流式应从 IMAP/HTTP 到临时文件/分片上传。 |
| 本地写入 | `aiofiles` 异步文件写；附件数据仍在内存。 | async I/O 只避免事件循环阻塞，不解决内存峰值和磁盘背压。 |
| MD5 | `_md5_hex(bytes)` 用于重复检测/历史；安全完整性仍需 SHA-256/ETag。 | 记录算法用途，避免把 MD5 当签名或防篡改校验。 |
| 正则缓存 | `file_processor._compile_pattern` 使用 `re` 缓存；主匹配器另有 `RegexMatcher` LRU/timeout。 | 必须统一到 ReDoS 安全匹配器，避免性能缓存绕过安全策略。 |
| 文件留存 | 当前 `process_attachment` finally 记录“本地文件已留档保留”，不自动删除。 | 需独立生命周期、磁盘配额和敏感附件清理策略。 |

## 内存、I/O 和状态边界

### 真正的背压

`aiofiles` 把阻塞文件操作放到线程池，但调用方仍先取得完整 `attachment["data"]`。若要支撑大文件，应让下载、哈希、MinIO 上传和 API 发送共享流式接口，至少做到：

1. 附件输入有最大长度和读取 deadline，超过限制时停止读取并写失败历史。
2. 临时文件采用服务端生成的路径、`.part` 后缀和原子 rename；未完成文件不进入 API/MinIO 成功状态。
3. 哈希在流式读取中一次计算，去重查询使用摘要；上传失败可从临时文件恢复，不重新把全文件读入 bytes。
4. 全局/集群并发、磁盘空间、线程池和 MinIO multipart 并发都有上限和指标。

### 处理结果与审计

性能优化不能改变 `ParseHistory` 和 `ReceiveHistory` 的状态语义：

- 匹配失败、重复、超大文件、下载失败、API 失败、MinIO 失败和成功必须有不同 reason/status。
- MD5、大小、文件名、任务 ID、ParseID、MinIO 对象名和归档 URL 要在同一记录链关联。
- API 调用失败和安全 URL 拒绝不得被吞掉；局部 fallback 只能记录明确的非成功状态。
- 本地附件留存是数据保留决策，不是性能实现细节；必须有清理、加密和访问审计。

## 不能原样复制的历史行为

| 历史行为 | 风险 | 新项目要求 |
| --- | --- | --- |
| 先把所有附件读成 bytes 再称“流式处理” | 大文件和多 worker 仍会产生内存峰值。 | 端到端流式读取/分片上传，或用临时文件作为背压边界。 |
| 全局 semaphore=3 | 只限制单进程；多副本仍可能压垮磁盘/MinIO。 | 结合租户/队列配额、集群限流和容量指标。 |
| MD5 作为唯一摘要 | 碰撞和篡改风险，不适合安全校验。 | MD5 仅去重；完整性使用 SHA-256/ETag/签名。 |
| `file_processor` 自己编译 `re` | 可能绕过 RegexMatcher 的 timeout/黑名单。 | 所有正则调用经过统一安全服务。 |
| finally 保留本地文件且无统一清理 | 敏感附件、磁盘和备份无限增长。 | 配置化保留期、加密、删除审计和失败重试。 |
| 异步写入失败只记录日志 | 业务可能继续调用 API 或返回伪成功。 | 写入失败立即停止后续副作用，状态进入明确失败终态。 |

## 推荐模块拆分

| 组件 | 职责 |
| --- | --- |
| `AttachmentSource` | 从 IMAP/HTTP/对象存储提供受限流；负责大小和读取 deadline。 |
| `DigestingStream` | 边读边计算 SHA-256（可另算 MD5 去重），返回摘要和大小。 |
| `AttachmentMaterializer` | `.part` 文件、原子发布、租约、清理和符号链接防护。 |
| `FileMatcher` | 四层匹配，统一调用 `SafeRegexMatcher`，不做 I/O。 |
| `DuplicateDetector` | 按配置/租户/算法摘要查重，明确 skip/fail 语义。 |
| `ExternalApiCaller` | URL 安全策略、请求超时、重试矩阵和审计。 |
| `ObjectUploader` | multipart/ETag、success/failed/temp 桶和幂等对象 key。 |
| `FileMonitorOrchestrator` | 只编排时序、状态和错误，不直接实现存储/正则/HTTP。 |
| `RetentionWorker` | 按 ParseHistory 状态和保留期清理本地/对象存储。 |

## 复用验收清单

- [ ] 附件大小在读取/分配前受限；超大文件不会先全部进入 Python heap。
- [ ] 本地写入使用安全路径、`.part`、原子 rename、可恢复清理和明确权限。
- [ ] `aiofiles`/线程池不会阻塞事件循环，线程数、信号量、磁盘和 MinIO 并发都有监控。
- [ ] 真正的大文件路径支持流式哈希和 multipart 上传；失败可恢复且不会发布半文件。
- [ ] MD5 只用于去重；安全完整性使用 SHA-256/ETag，算法和用途记录在审计中。
- [ ] 所有正则调用经过统一 ReDoS 防护；不存在第二套 `re` 编译缓存。
- [ ] 匹配、重复、下载、API、MinIO、归档和接收历史状态严格区分，失败不会继续执行副作用。
- [ ] 多 worker/多副本下有集群级并发和配额；单进程 semaphore 不作为唯一保护。
- [ ] 本地留存、MinIO 三桶和归档备份有保留期、加密、访问审计和磁盘/对象配额。
- [ ] 使用 0B、阈值边界、50MB 超限、并发大文件、磁盘满、MinIO 失败、API 超时和 worker 重启完成回归。
