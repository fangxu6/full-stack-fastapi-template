## 重构前后架构

```text
重构前（路由 import 旧路径）
app/api/v1/routes/file_monitor.py
  -> app.services.file_monitor.dependencies
       -> FileMonitorConfigService / FileMonitorFileProcessor

重构后（提交时）
app/api/v1/routes/file_monitor.py
  -> app.dependencies.file_monitor
       ├─ get_config_service()
       │    └─ FileMonitorConfigService(beat, validator, matcher, log, api)
       ├─ get_file_processor()
       │    └─ FileMonitorFileProcessor(matcher, minio, api, archive)
       └─ ConfigServiceDep / FileProcessorDep
```

路由函数只声明：

```python
async def create_config(
    config_service: ConfigServiceDep = ...,
):
    ...
```

这样路由不需要知道全局服务实例、构造参数顺序或基础设施客户端来源；测试可以在 FastAPI `app.dependency_overrides` 中替换 provider。

## 提交时的 provider 契约

### `get_config_service`

提交版本每次调用时构造一个 `FileMonitorConfigService`，参数来源如下：

| 参数 | 来源 | 生命周期/注意事项 |
| --- | --- | --- |
| `beat_scheduler_service` | `file_monitor_beat_scheduler_service` | 模块级单例；通常持有 Celery/数据库协作者 |
| `config_validator` | `config_validator` | 模块级校验器；负责配置冲突及字段安全校验 |
| `regex_matcher` | `regex_matcher` | 模块级匹配器；与 Validator 的职责需保持一致 |
| `operation_log_service` | `OperationLogService()` | 每次 provider 调用新建；不要误当作全局单例 |
| `api_caller` | `file_monitor_api_caller` | 模块级 API 调用器，可能包含 HTTP client 配置 |

FastAPI 默认会在单个请求内缓存同一依赖的结果（`use_cache=True`），但直接调用 `get_config_service()` 不会共享实例。需要跨请求共享状态时，应显式使用安全的单例/provider 生命周期，而不是依赖 FastAPI 的请求缓存。

### `get_file_processor`

提交版本把正则、MinIO、API Caller 和归档备份服务注入 `FileMonitorFileProcessor`。`FileProcessorDep` 在提交版本中没有被其他 Python 文件引用，属于预留的类型别名；迁移时应先确认真实路由/任务调用方，再决定保留或删除，避免产生无消费者的第二入口。

## 路由与包边界

提交时被修改的历史路由 `app/api/v1/routes/file_monitor.py` 同时承载配置、任务和解析历史端点，依赖模块只负责配置服务/文件处理器装配。当前分支已把它演进为聚合路由，配置端点位于 `file_monitor_config_routes.py`，任务和历史端点分别位于其他子路由。

迁移到其他项目时建议遵循：

1. `app/dependencies/` 只放 provider、类型别名和生命周期策略，不放业务逻辑。
2. 业务服务构造函数接收协作者，避免在服务内部 import 并实例化全局客户端。
3. 路由通过 `Annotated[T, Depends(provider)]` 声明依赖，Provider 的返回类型与路由响应契约保持一致。
4. 旧模块迁移后应在同一变更中删除或保留一个明确的兼容转发模块；不能让两个路径各自维护一套 provider。
5. 若包内存在 `__init__.py` 重导出，必须同步更新重导出和循环导入测试。

## 复用风险与不能原样复制的行为

| 当前/历史行为 | 风险 | 推荐做法 |
| --- | --- | --- |
| Git 只新增新路径，未删除旧路径 | 旧文件若仍存在会形成双事实源；旧 import 可能继续绕过新 provider | 迁移时用 `git grep` 清理旧 import；必要时保留单行兼容转发并标注废弃期限 |
| Provider 直接导入多个全局单例 | 导入时副作用、循环依赖和测试替换困难 | 通过参数或 provider registry 注入；默认值尽量运行时解析 |
| `OperationLogService()` 在 `get_config_service` 内部新建 | 每次请求可能创建新日志服务；连接/缓冲状态无法复用 | 明确日志服务的 request/scoped/singleton 生命周期，并在测试中断言实例策略 |
| 模块注释声称使用 dataclass | 提交源码没有 dataclass 实现，注释与事实不一致 | 文档描述真实依赖图，不把注释当作架构能力；需要 dataclass 时单独实现并测试 |
| FastAPI 请求缓存被当作应用级单例 | 跨请求状态、缓存和连接池可能重复创建或状态丢失 | 用 lifespan、显式 singleton provider 或容器管理生命周期 |
| `FileProcessorDep` 没有消费者 | 预留别名增加 API 表面积，后续改名成本上升 | 无调用方时删除；有调用方时补最小契约测试 |
| Provider 暴露完整 `FileMonitorConfigService` | 路由可能直接依赖过宽接口，难以替换和授权 | 按功能域定义窄接口/协议，或至少按路由拆分依赖别名 |
| 目录归位被误当作安全隔离 | `app/dependencies` 只是组织结构，不提供权限、事务或密钥保护 | 安全边界仍由权限依赖、配置校验、网络策略和秘密管理实现 |

## 推荐的可复用实现

```python
# app/dependencies/file_monitor.py
from typing import Annotated
from fastapi import Depends


def get_config_service() -> ConfigService:
    return config_service_provider.build()


ConfigServiceDep = Annotated[ConfigService, Depends(get_config_service)]
```

Provider 适配层可以按环境组合实现：

| 层 | 责任 |
| --- | --- |
| `providers.py` | 从应用容器/lifespan 取得共享客户端和服务 |
| `dependencies/<domain>.py` | 把协作者组合成领域服务，并定义 `Annotated` 别名 |
| `routes/<domain>_routes.py` | 只声明依赖别名、参数和 HTTP 错误映射 |
| `tests/conftest.py` | 通过 `dependency_overrides` 注入 fake service/provider |

不要让依赖模块读取请求体、执行数据库写入或捕获业务异常；这些都属于服务或路由层。Provider 创建失败应让应用启动/请求明确失败，不能返回伪造的“空服务”。

## 复用验收清单

- [ ] 全仓库不存在未迁移的旧依赖 import；若保留兼容模块，它只转发到唯一的新 provider。
- [ ] `ConfigServiceDep` 和 `FileProcessorDep` 的类型别名可被 FastAPI 正确解析，路由启动时不会出现循环导入。
- [ ] Provider 的返回对象满足路由使用的最小接口，构造参数和生命周期有文档与测试。
- [ ] FastAPI 请求内缓存、应用级单例和临时对象的生命周期已明确，不依赖隐含行为。
- [ ] 测试可通过 `app.dependency_overrides` 替换配置服务、文件处理器及其基础设施，不需要真实 MinIO、Celery 或外部 API。
- [ ] 配置服务的 Validator、Beat、日志、API Caller 等协作者不会因 import-time 默认参数导致测试替换失效。
- [ ] 文件处理器的大文件并发限制（如 semaphore）与 MinIO/API/归档客户端的关闭和超时策略有独立验收。
- [ ] 依赖模块只做装配，不包含权限绕过、数据库事务、缓存写入或异常吞噬逻辑。
- [ ] `FileProcessorDep` 若无消费者已删除；若有消费者，至少覆盖一个真实路由或任务调用。
- [ ] CodeGraph 已检查 provider、别名和路由的调用方，并回归配置、任务、解析历史三类端点。
