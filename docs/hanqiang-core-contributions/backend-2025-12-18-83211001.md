## 方法职责与契约

### 入口与模式选择

`call_target_api(db, config, task_id, file_name, file_size, local_file_path, extra_placeholders, operator_id, trigger)` 返回不可变 `ApiCallResult`：

```text
success: bool
status_code: int | None
response_text: str | None
error_message: str | None
attempts: int
last_duration_ms: int
```

当 `TargetAPIConfig.extra.excel.enabled=true` 且 `extra_placeholders` 中有非空 list 时，读取 `mode`/`callMode`/`rowByRow` 判断是否逐行调用；否则保持一次 HTTP 请求的兼容路径。即使是单次模式，首行也会补齐 `${TXN_ID}`、`${ROW_INDEX}=1` 和 `${EXCEL_ROW}` 供模板使用。

### 配置校验：`_validate_api_config`

- 清理 `TargetAPIUrl` 两端空格，调用 `_validate_target_url()`，最终委托 `url_validator.validate_url(require_https=False)`。
- 从 `TargetAPIConfig` 读取大小写兼容的 `headers`、`timeout`、`maxRetries`，默认分别为 `{}`、30 秒、3 次重试。
- URL 校验失败时写入 `ParseHistory(ParseType=2, IsSuccess=0)`，错误前缀为 `SECURITY_VALIDATION_FAILED`，并返回 `attempts=0` 的失败结果；不会建立 HTTP 连接。

### 负载构建：`_build_request_payload` / `_build_request_body`

- 使用 `PlaceholderValues` 替换 `${LOCAL_FILE_PATH}`、`${FILE_NAME}`、`${CONFIG_ID}` 及逐行扩展占位符。
- 兼容 `bodyTemplate`/`BodyTemplate`/`body`/`Body`，支持字典、列表或 JSON 文本。
- 对多重 JSON 字符串最多再解码 3 层；解析成字典时使用 `json=` 发送，否则使用 `content=` 发送原始文本。
- 非法 JSON 不会静默丢弃，作为 raw body 继续发送；迁移时要明确目标 API 是否允许非 JSON 请求体。

### 请求执行：`_execute_single_request`

- 使用 `httpx.AsyncClient(timeout=float(timeout))`，当前固定以 `POST` 发送。
- 字典负载走 `client.post(..., json=json_body)`；文本负载走 `client.post(..., content=raw_body)`。
- `2xx` 被视为成功；`httpx.TimeoutException` 和 `httpx.TransportError` 转换为 `NETWORK_ERROR`；其他 `httpx.HTTPError` 为 `HTTP_ERROR`；`ValueError/OSError` 为不可恢复的 `UNEXPECTED_ERROR`。
- 每次请求测量毫秒耗时，交给 `_record_attempt`。

### 重试状态机：`_handle_retry_logic` / `_execute_with_retry`

| 结果 | 是否重试 | 返回/记录行为 |
| --- | --- | --- |
| `2xx` | 否 | 成功 `ApiCallResult`，记录一次成功尝试 |
| `4xx` | 否 | `HTTP_<status>` 失败，记录一次尝试 |
| `5xx` | 是 | 记录失败，进入下一次尝试，直至 `max_retries` 用尽 |
| `NETWORK_ERROR` | 是 | 记录网络错误，指数退避后重试 |
| `UNEXPECTED_ERROR` | 否 | 记录后立即结束，避免对编程/数据错误盲目重试 |
| 无 status 且无 error | 否 | 构造 `UNEXPECTED_ERROR: EMPTY_STATUS_CODE` |

循环次数为 `max_retries + 1`（初次请求加重试次数）。退避为 `min(60, 2**attempt)` 秒，当前序列为 1 秒、2 秒、4 秒，无 jitter。每次尝试单独写 ParseHistory，最终 `ApiCallResult.attempts` 是实际请求次数。

### 逐次审计：`_record_attempt` / `_record_api_call`

每次尝试创建一个新的 ParseID，并写入：

- `TaskID`、`ConfigID`、文件名、文件大小、`ParseType=2`、成功标志、错误消息、操作人。
- `ParseDetail.targetAPIUrl`、`requestBody`、`responseCode`、`responseBody`、`callDurationMs`、`retryCount`、`trigger`。
- JSON 响应会递归脱敏并截断到 `MAX_JSON_TRUNCATE_LENGTH=4000`；非 JSON 响应只做长度截断。

逐行模式不并发使用同一个 `AsyncSession`：每行顺序调用并在行间 sleep 0.1 秒，最后返回总行数、成功/失败数和首个错误。该顺序约束是数据库会话安全要求，不只是限流策略。

## 当前实现中的重要边界

1. **安全校验不是完整 SSRF 防护。** `_validate_target_url` 依赖统一 URL 校验器，但是否允许 HTTP、域名白名单、DNS rebinding、重定向和端口策略由该组件决定；调用前和实际连接前都应复验。
2. **错误类型参数未进入结果结构。** `_build_error_result(error_type, error_msg)` 接收 `error_type`，但 `ApiCallResult` 只保存 `error_message`；调用方无法稳定按 `URL_VALIDATION_FAILED` 等机器码分支。新项目应使用显式 `error_code` 和 `retryable` 字段。
3. **请求体可能含秘密。** 当前响应体会脱敏，但 `ParseDetail.requestBody` 使用未脱敏的 JSON/raw body；模板若包含 Token、密码或个人信息，可能直接落库。请求头虽然未写入 detail，仍可能出现在底层 HTTP 日志。
4. **URL 和错误日志可能泄露敏感信息。** `_validate_target_url` 的日志包含原始 URL；URL userinfo、query token 和签名应先脱敏，只记录 scheme/host/port 和策略版本。
5. **重试参数缺少调用器层上限。** `timeout`/`maxRetries` 从配置直接转成整数；若绕过 Pydantic 直接写库，可能产生超大超时、无限制请求或异常负数。应在运行时钳制并拒绝无效值。
6. **5xx/网络错误的重试不具备幂等保证。** 当前固定 POST，重试可能重复创建业务数据；应要求幂等键（例如 `${TXN_ID}`/`Idempotency-Key`）或只对明确安全的方法重试。
7. **无 jitter 和熔断。** 多 worker 在同一秒重试会形成惊群；生产环境需 jitter、最大总耗时、熔断/限流和下游健康状态。
8. **逐行汇总只保留首个错误和最后状态码。** 207 只是应用层汇总值，不表示 HTTP 服务真实返回；若需要补偿，应持久化每行的稳定行号、事务 ID 和结果。
9. **单次 HTTP client 每轮重试复用。** 连接池复用有利于性能，但 DNS、代理、凭据和连接状态策略必须符合安全要求；新项目可注入 client factory 并在 lifespan 管理。

## 推荐的可复用模块

| 组件 | 最小职责 | 建议接口 |
| --- | --- | --- |
| `ApiConfigResolver` | 校验 URL、读取 headers/timeout/retry 参数并返回不可变配置 | `resolve(config) -> ResolvedApiConfig` |
| `PayloadRenderer` | 纯函数式占位符替换和 JSON/raw 选择 | `render(template, values) -> RenderedPayload` |
| `HttpTransport` | 执行一次请求，统一异常类型和耗时 | `send(payload) -> TransportResult` |
| `RetryPolicy` | 按状态/异常、次数、总耗时、jitter 决定下一步 | `decide(attempt, result) -> RetryDecision` |
| `ApiAttemptRecorder` | 脱敏、截断并保存每次尝试 | `record(attempt) -> awaitable` |
| `ApiCaller` | 协调单次/逐行模式和最终汇总 | `call(...) -> ApiCallResult` |
| `RowCallCoordinator` | 顺序/并发策略、行级幂等和补偿 | `call_rows(rows, call_one)` |

推荐把 `ApiCallResult` 扩展为稳定错误码、是否可重试、总耗时和逐行结果引用；让 `RetryPolicy` 与 HTTP transport 解耦，测试时不需要 sleep 或真实网络。

## 不能原样复制的历史行为

| 历史行为 | 风险 | 新项目要求 |
| --- | --- | --- |
| 所有请求固定 POST | 重试可能重复写入；无法调用 PUT/PATCH 等语义 | 配置允许的方法白名单，并按方法/幂等键决定重试 |
| 5xx 和网络错误均自动重试 | 下游慢、限流或业务不可用时放大流量 | 指数退避 + jitter + 总 deadline + 熔断/限流 |
| 只给响应做脱敏 | 请求模板和 URL query 仍可能含秘密 | 请求/响应/URL/headers 统一结构化脱敏，默认 deny sensitive fields |
| `maxRetries` 直接转 int | 数据库脏值可造成过长等待或资源耗尽 | schema 与运行时双重范围校验，设置总耗时上限 |
| 每次尝试写一条 ParseHistory | 大批量逐行调用会放大数据库写入 | 明确逐次审计保留期、批量落库/采样策略及查询索引 |
| 逐行固定 sleep 0.1s | 单任务吞吐受限，集群级限流仍缺失 | 将节流作为可注入策略，配合下游配额和并发控制 |
| 失败只返回最后状态和首个错误 | 无法精确补偿中间失败行 | 保存 row index/txn id/attempts，并提供可重放状态 |
| `error_type` 不进入结果 | 调用方只能解析错误文本 | 使用枚举错误码，禁止字符串猜测 |

## 复用验收清单

- [ ] URL 在保存配置和实际连接前都通过统一安全策略；禁止未授权 scheme、host、端口、重定向和私网访问。
- [ ] 请求方法、body 编码、headers、超时、最大重试次数和总 deadline 有 schema 与运行时双重校验。
- [ ] 2xx/4xx/5xx、超时、传输错误、协议错误和编程错误的错误码及 retryable 语义稳定。
- [ ] 重试策略包含最大次数、总耗时、指数退避、jitter、熔断/限流，并按幂等性决定是否重试。
- [ ] `ApiCallResult` 能区分安全拒绝、配置错误、下游失败和本地异常，不依赖解析错误文本。
- [ ] PayloadRenderer 对 dict/list/JSON/raw、多重编码和占位符缺失有契约测试。
- [ ] 日志、ParseHistory、指标和 trace 都对 URL、headers、请求体和响应体做字段级脱敏与长度限制。
- [ ] 每次尝试与 TaskID/ConfigID/ParseID/行号/幂等键关联；审计写入失败不会伪装成调用成功。
- [ ] 同一 `AsyncSession` 不被并发任务共享；逐行顺序、并发或独立 session 策略有明确选择。
- [ ] 逐行模式对空行、部分失败、重复重试、207 汇总和补偿重放有测试。
- [ ] HTTP client 生命周期、连接池、代理、DNS、证书校验和关闭策略可注入且可观测。
- [ ] 生产指标覆盖成功率、按错误码失败率、重试次数、耗时、下游状态和安全拒绝数。
