## 重构前后架构

```text
重构前
FastAPI Depends -> FileMonitorConfigService
                    ├─ 直接 CRUD/ORM 操作
                    ├─ Redis 缓存
                    ├─ 传输配置查询与 UUID 转换
                    ├─ 配置校验
                    ├─ 操作日志
                    └─ Beat 同步

重构后
FastAPI Depends -> create_file_monitor_config_service()
                -> FileMonitorConfigService（Facade）
                   ├─ ConfigValidator / RegexMatcher：校验与冲突检测
                   ├─ FileMonitorConfigManager：数据访问、缓存和关联对象
                   ├─ OperationLogService：审计
                   ├─ BeatSchedulerService：调度同步
                   └─ ApiCaller：保留给需要调用目标 API 的路径
```

拆分的核心不是新增业务规则，而是把“编排”和“状态持久化”分开：Facade 决定一次请求要做哪些步骤，Manager 决定配置如何读写和转换。这样路由可以继续依赖一个服务，测试则可以注入 Manager、Validator 或调度器替身。

## 当前 CodeGraph 调用链

```text
app/api/v1/routes/file_monitor_config_routes.py
  -> app/dependencies/file_monitor.py::get_config_service()
  -> create_file_monitor_config_service(FileMonitorConfigService)
  -> FileMonitorConfigService
       -> ConfigValidator（正则、传输配置、TargetAPIUrl、TargetAPIConfig、冲突）
       -> FileMonitorConfigManager
            -> crud_file_monitor_config
            -> Redis（file_monitor:config:{ConfigID}，TTL=300 秒）
            -> Email/FTP CRUD（解析 TransferConfigName）
            -> SysFileMonitorHeartbeat（创建配置时建立 idle 心跳）
       -> OperationLogService
       -> BeatSchedulerService.sync_one_file_monitor_config()
```

主要写入流程：

```text
create()
  -> model_dump(exclude force_save)
  -> 通用字段校验 + 冲突检测
  -> Manager.create()
       -> 生成 UUID bytes
       -> CRUD create + heartbeat
       -> commit
       -> UUID/传输名称归一化
       -> 写详情缓存
  -> 写 CREATE 操作日志
  -> 同步 Beat
```

更新、删除和启停沿用同一编排顺序：先取当前对象和校验所需的合并视图，再由 Manager 持久化并处理缓存，最后写操作日志并尝试同步 Beat。`force_save` 只绕过冲突拒绝，不应绕过正则、URL、传输配置 ID 或请求体结构校验。

## 组件职责与接口

### Facade：`FileMonitorConfigService`

保留对外公开方法：

- `validate_config(db, request)`：验证正则并调用 `ConfigValidator.detect_conflicts()`，把内部冲突对象转换为 `ConflictInfo`。
- `list_configs(...)` / `get_detail(...)`：委托 Manager，保持路由响应结构不变。
- `create(...)`：校验、冲突判断、Manager 创建、CREATE 审计、Beat 同步。
- `update(...)`：合并旧值与更新值用于冲突检测，规范化 UUID/布尔值，UPDATE 审计和 Beat 同步。
- `delete(...)`：逻辑删除、DELETE 审计和 Beat 同步。
- `toggle(...)`：启停、STATUS_CHANGE 审计和 Beat 同步。

Facade 还保留 `_build_validation_payload`、`_extract_update_dict`、`_merge_field_for_validation` 等小型辅助方法，避免更新路径再次复制创建路径的校验组装逻辑。

### Manager：`FileMonitorConfigManager`

- `list_configs`：调用 CRUD 分页，批量解析传输配置名称，并将 ORM 对象归一化为字典。
- `get_detail`：先查 Redis，未命中时查数据库、补充传输名称并回填缓存。
- `get_db_obj_or_404`：为更新/删除/启停提供统一的存在性检查。
- `create`：生成 UUID、设置创建/更新时间和状态、创建 `SysFileMonitorHeartbeat`，提交后返回归一化数据。
- `update`：补充 `UpdaterID`/`UpdateTime`，调用 CRUD，失效并重建详情缓存。
- `soft_delete`：调用 CRUD 逻辑删除，失效缓存并返回删除前快照。
- `toggle_enabled`：更新启用状态，刷新 ORM，失效并重建缓存，返回 before/after。
- `_resolve_transfer_config_name` / `_batch_resolve_transfer_config_names`：按 `TransferType` 从 Email 或 FTP 配置表解析展示名。

Manager 的构造参数可注入 `redis`、Email CRUD、FTP CRUD 和文件监控 CRUD，适合用内存替身测试，不必启动完整基础设施。

### Factory：`create_file_monitor_config_service`

工厂接收 `service_cls` 以及 `beat_scheduler_service`、`validator`、`matcher`、`operation_log_service`、`api_caller`、`config_manager`。`service_cls` 由调用方传入，避免工厂反向导入 Facade，降低循环依赖；默认依赖简化生产调用，显式参数则用于测试和多租户装配。

FastAPI 依赖层只保留：

```python
def get_config_service() -> FileMonitorConfigService:
    return create_file_monitor_config_service(service_cls=FileMonitorConfigService)
```

同时保留 `file_monitor_config_service` 全局单例，兼容 Celery 等非 API 调用方。

## 数据与行为契约

### 分页与查询

`crud_file_monitor_config.get_list()` 当前约定：

- 页码至少为 1，`page_size` 限制在 1-200。
- 默认过滤 `IsDeleted == 0`。
- 支持 `ConfigName`、`IsEnabled`、`TransferType` 过滤。
- 按 `CreateTime.desc()` 排序。
- Manager 对外返回 `{data, total, page, page_size}`，不是 CRUD 的 `{items, total, ...}`。

### UUID 与状态

- 数据库主键和关联 ID 是 MySQL `BINARY(16)`，API/缓存使用字符串 UUID；边界必须统一 `to_uuid_bytes`、`from_uuid_bytes` 和 `normalize_uuid`。
- `TransferType`：`1=IMAP`、`2=FTP`、`3=SFTP`；1 查询 Email 配置名称，2/3 查询 FTP 配置名称。
- `IsEnabled`、`IsDeleted` 是 MySQL `BIT`，写入时使用 0/1，响应时统一为可序列化值。
- 逻辑删除同时设 `IsDeleted=1`、`IsEnabled=0`，并清除详情缓存。
- 创建配置时建立 `SysFileMonitorHeartbeat(TaskStatus="idle", ErrorCount=0)`。

### 模型约束

`SysFileMonitorConfig` 与 Pydantic schema 共同约束：

- `ConfigName` 1-100 字符，`ConfigCode` 1-50 且匹配大写字母/数字/下划线。
- 文件名、发件人和邮件标题规则最长 255 字符；文件名规则必填。
- `TargetAPIUrl` 必填；`TargetAPIConfig` 包含 headers、bodyTemplate、timeout、maxRetries 及可选 Excel 扩展。
- `MonitorInterval` 为 1-60 分钟；数据库也有同范围 CheckConstraint。
- 数据库索引覆盖 `TransferType`、`IsEnabled`、`CreateTime`、`IsDeleted`。

## 一致性边界与迁移风险

这些行为是当前实现事实，但不能在新项目中无条件照搬：

1. Redis 读、写和失效失败主要记录 warning 后回退数据库；缓存是性能层，不是强一致事实源。缓存内容必须排除 `TargetAPIConfig` 中的 Header、Token、密码和连接凭据，或先做字段级脱敏。
2. 数据库提交、操作日志和 Beat 同步不在同一事务中。Beat 同步失败会记录 warning，可能出现“数据库已更新、调度器仍使用旧配置”。新项目应考虑 outbox、版本号或可重建的 reconciliation 任务。
3. 工厂参数的默认值在模块导入时绑定全局对象；测试运行时替换全局变量可能不会影响已绑定的默认值。测试应显式传入依赖，或改为运行时 provider。
4. `regex_matcher` 仍是 Facade 的注入参数，但主要正则校验由 `ConfigValidator` 执行。迁移时只保留一套正则规则和错误码，避免两个校验器漂移。
5. `_batch_resolve_transfer_config_names` 使用 `dict[bytes, int]` 建立 ID 到列表下标的索引；同一传输配置 ID 重复出现时只会回填最后一项。新实现应使用一对多索引或按 ID 写入所有匹配项。
6. Facade、CRUD、Schema 分别出现 `items` 与 `data` 等分页词汇。迁移时应在边界层统一响应契约，并为空页、越界页和无效 UUID 定义稳定错误行为。
7. 配置更新、逻辑删除、缓存失效和 Beat 同步需要幂等；重试不能重复写审计或产生多个调度任务。
8. `SysFileMonitorConfig` 当前被约 18 个后端模块引用，属于高 blast-radius 模型。修改字段、状态语义或 UUID 编码前必须做全局 CodeGraph 影响分析。

## 推荐的可复用拆分

| 可复用模块 | 最小职责 | 不应包含 |
| --- | --- | --- |
| `ConfigFacade` | 请求级校验编排、冲突策略、审计和调度同步 | ORM 细节、缓存序列化 |
| `ConfigManager` | CRUD、领域对象归一化、关联数据、缓存读写 | HTTP/FastAPI 依赖、用户展示文案 |
| `ConfigFactory` | 组合 provider 和测试替身 | 业务分支和持久化逻辑 |
| `ConfigValidator` | 正则、URL、传输引用和冲突规则 | 写数据库、写审计 |
| `ConfigRepository` | 分页、查询、写入、软删除和事务边界 | Beat 或缓存策略 |
| `ConfigCache` | 版本化 key、TTL、失效策略和敏感字段过滤 | 作为唯一事实源 |

建议将“数据库提交后发布调度变更”建模为可重放事件，并为读模型单独定义脱敏 DTO；不要直接把 ORM 对象或包含凭据的 JSON 放入 Redis/操作日志。

## 复用验收清单

- [ ] 路由只依赖 Facade；生产和测试均可通过 Factory 显式替换 Manager、Validator、日志和调度器。
- [ ] Facade 对外方法保持稳定，创建、更新、删除、启停的返回值和错误码有明确契约。
- [ ] 创建/更新在落库前执行正则、传输配置引用、TargetAPIUrl、TargetAPIConfig 和冲突校验；`force_save` 不绕过安全校验。
- [ ] Manager 的事务边界明确：配置与 heartbeat 是否同事务，异常是否 rollback，提交后缓存和调度事件如何补偿。
- [ ] 分页统一为 `data/total/page/page_size`，页大小上限、默认过滤和排序有测试覆盖。
- [ ] UUID 在 API、ORM、关联查询、缓存 key 之间可逆转换；非法 UUID 不会变成静默查询空结果。
- [ ] 逻辑删除会禁用配置、失效缓存并让调度器停止该配置；重复删除/重试是幂等的。
- [ ] Redis 故障可回退数据库且不会吞掉数据写入错误；缓存只存脱敏读模型并有 TTL/版本策略。
- [ ] 操作日志记录 before/after、操作者、资源 ID 和动作；敏感 Header、Token、密码不落日志。
- [ ] Beat 同步失败可告警、重试和重建，不会阻塞数据库主事务，也不会长期遗留旧任务。
- [ ] 批量解析传输配置名称能正确处理重复 ID、未知类型和关联记录缺失。
- [ ] CodeGraph 已检查 `SysFileMonitorConfig` 的全部调用方，并回归文件处理、Celery 任务和配置路由。
