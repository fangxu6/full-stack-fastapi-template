## 整体架构与数据流

```text
部署环境
  ├─ JSE_CONFIG_YAML / config.yaml
  └─ JSE_LOG_DIR_NAME 或 celery worker/beat argv
       ↓
app.core.config.settings
       ↓
app.core.logging
  ├─ LOG_BASE_DIR/logs/{current|celery_worker|celery_beat}
  ├─ Loguru app/error/operation/login/audit sinks
  └─ LOG_DIR_NAME
       ↓                         ↓
Celery signals               app.background.log_archiver
  └─ stdlib logging -> Loguru    ├─ daily zip
                                ├─ weekly/monthly 汇总
                                └─ 90 天清理

FileMonitor success/failed object
  -> ArchiveBackupService
       -> archive bucket（ArchiveConfigCode 规范化）
       -> MinIO copy_object + 1s/2s 重试
       -> archive_backup 结构化日志
```

## 配置文件加载契约

`Settings.load_from_yaml(yaml_path="config.yaml")` 的提交时行为：

1. 如果存在 `JSE_CONFIG_YAML`，去除空白后覆盖传入参数；空值回退 `config.yaml`。
2. 依次查找当前工作目录、`backend/JSECommon/{yaml_path}`、仓库上层的 `config.yaml`。
3. 找到文件后使用 `yaml.safe_load`，按 `server/frontend/database/jwt/logging/admin/redis/minio/ftp/wxwork` 构造子配置。
4. 找不到文件时打印包含 `yaml_path` 的提示并返回默认 `Settings`；数据库 URL、JWT secret 等字段的 validator 仍会决定是否允许启动。

环境变量和 YAML 的优先级不是所有字段都统一：该方法把 YAML 作为整体构造参数传入，子 Settings 的 env 前缀行为需在目标项目实测。生产环境不应把明文密码、Fernet key 或 JWT secret 放入仓库内 YAML。

## 日志分流契约

### 目录选择

`app.core.logging._detect_log_dir_name()`：

- `JSE_LOG_DIR_NAME` 非空时直接作为目录名。
- 否则扫描 `sys.argv`；命令包含 Celery 且包含 `worker` 时使用 `celery_worker`，包含 `beat` 时使用 `celery_beat`。
- 其余进程使用 `current`。

基础路径由 `Path(__file__).resolve().parents[2] / "logs"` 得到，避免依赖启动工作目录。模块导入时创建当前目录和 archive 目录，并预创建当天的 `app_*.log`、`error_*.log`；非 Celery 进程还预创建 operation/login/audit 文件。

### Loguru sink

`setup_enhanced_logger()` 会移除默认 handler，再注册：

- 控制台 sink：级别来自 `settings.logging.level`。
- `app_YYYY-MM-DD.log`：DEBUG 起，JSON 序列化，按天轮转，不在 current 目录压缩。
- `error_YYYY-MM-DD.log`：ERROR 起，含异常回溯。
- Web 进程额外写 operation/login/audit 分类文件；Celery worker/beat 提前返回，不生成这三类文件。
- ERROR sink 还会触发 Redis 窗口告警，但 sink 自身必须不抛异常。

Loguru 使用 `{}` 格式化参数；本提交修正的五处 `%s/%d` 日志是行为兼容修复，迁移时应统一 lint 规则，禁止两种格式混用。

### Celery 标准 logging 转发

`app.core.celery_app` 注册 `setup_logging`、`after_setup_logger`、`after_setup_task_logger` 三个 signal。只有 `LOG_DIR_NAME` 是 `celery_worker` 或 `celery_beat` 时才执行：

- 用 `_LoguruInterceptHandler` 替换 root logger 及 `celery/kombu/billiard/amqp` handlers。
- 将标准 `LogRecord` level、异常信息和调用深度转交 Loguru。
- root logger 级别跟随 `settings.logging.level`。

该方案避免 Celery 自己写到另一套文件，但会覆盖这些 logger 原有 handlers；引入项目必须确认第三方库的 handler、JSON 格式和集中采集要求。

## 日志归档行为

提交时 `archive_daily_logs(target_date)`：

- 扫描 `logs/current`、`logs/celery_worker`、`logs/celery_beat` 下匹配 `*_{YYYY-MM-DD}.log` 的文件。
- 写入 `logs/archive/daily/logs_daily_{date}.zip`；current 文件以文件名归档，Celery 文件带目录前缀以避免同名冲突。
- 文件加入 zip 后删除源日志文件。
- `_acquire_lock()` 通过原子创建 `logs/.archive_lock` 防止同一进程/主机上的并发归档；任务结束调用 `_release_lock()`。
- 每周、每月汇总包和 90 天前 daily 包清理保持原有流程。

当前工作树已进一步演进：会恢复历史 `.log.zip`、对已存在 daily zip 使用追加模式，并保留 source log，不再执行提交版本的删除。复用时必须明确“归档后删除还是保留”的数据保留策略，不要仅凭当前文件名判断历史行为。

## MinIO 归档备份服务

### 接口与时序

```text
copy_object_with_retry_async(source_bucket, source_object,
                             archive_config_code, target_object?)
  -> settings.minio.enabled=false: {skipped: true, reason: minio_disabled}
  -> 创建 Minio client
  -> build_archive_bucket(code)
  -> bucket_exists / make_bucket（asyncio.to_thread）
  -> copy_object_with_retry_loop（最多3次）
  -> {success, archive_bucket, target_object, error?}

copy_object_with_retry(...)
  -> 无运行中事件循环：asyncio.run(async 版本)
  -> 有运行中事件循环：抛 RuntimeError，提示改用 async 版本

schedule_backup_via_celery(...)
  -> send_task("app.tasks.file_monitor_tasks.archive_backup_copy_task", args=[...])
  -> 调度失败只写 warning，不向调用方抛异常
```

### 关键规则

- bucket 名由 `ArchiveConfigCode` 小写化、下划线转短横线、非法字符替换为短横线，并限制为 MinIO 允许的 3-63 字符。
- MinIO 的同步 SDK 操作通过 `asyncio.to_thread` 执行，避免阻塞事件循环。
- 复制失败最多尝试 3 次，间隔为 1 秒、2 秒；最后一次失败不再 sleep。
- 归档日志包含 source/archive bucket、object、attempt、status 和 error，并绑定 `archive_backup=True`。
- `ArchiveBackupService` 在模块导入时创建全局 `archive_backup_service`；Celery 任务复用同步包装。

当前 CodeGraph 显示该服务被文件监控依赖层、`file_monitor_tasks.py`、`file_processor.py`、`api_call_preparator.py` 和 G16 测试引用；复制结果和异常策略变化会影响 success/failed/temp 上传链路。

## 不能原样复制的历史行为

| 历史行为 | 风险 | 新项目要求 |
| --- | --- | --- |
| `JSE_LOG_DIR_NAME` 直接拼接到 `LOG_BASE_DIR` | 环境变量可包含 `../` 或绝对路径，越出日志根目录 | 只允许固定枚举目录名，拒绝路径分隔符和控制字符 |
| 通过 argv 子串猜测 worker/beat | wrapper、测试或自定义命令可能误判进程角色 | 启动入口显式注入 role，argv 仅作兼容回退 |
| `logger.remove()` 和 Celery handler 替换全局 handlers | 可能覆盖宿主应用/第三方采集 handler，造成日志丢失 | 在应用 lifespan 中集中配置，保留/链式转发既有 handler 并做重复初始化保护 |
| 归档后立即删除正在写入的日志 | 可能截断日志、丢失并发写入，删除失败也难补偿 | 轮转后只处理已封存文件，使用临时 zip + 原子 rename，成功后按保留策略删除 |
| `.archive_lock` 无超时和 owner 信息 | 进程崩溃会留下脏锁，后续任务永久跳过 | 使用带 TTL/租约的分布式锁或带 PID/时间的可恢复锁 |
| zip 目标已存在仍以 `w` 覆盖（提交版本） | 重跑可能丢失上次已归档文件 | 幂等归档：追加/跳过已存在成员并记录 manifest |
| 任意异常都重试 MinIO copy | 认证失败、权限错误、非法 bucket 会浪费三次等待 | 按错误码分类，可恢复错误才重试，并设置总 deadline/jitter |
| bucket 名由业务 code 直接生成 | 清洗碰撞、bucket 数量膨胀、跨租户命名冲突 | 使用稳定映射表或租户前缀+对象目录，校验最大数量和权限 |
| source/target object 未校验租户和路径 | 任务参数被篡改时可能跨 bucket 复制敏感对象 | 任务签名、资源授权、bucket allowlist 和 object key 规范化 |
| Celery 调度失败只写日志并返回 None | 主流程认为“已安排归档”但任务实际丢失 | 使用 outbox/可靠队列，返回 task id，提供补偿扫描 |
| `settings.minio.enabled` 为 false 时静默 skipped | 调用方可能把 skipped 当 success | 结果包含稳定状态枚举，业务明确区分 disabled、scheduled、copied、failed |
| 每次复制新建 MinIO client | 连接池无法复用，凭据/关闭生命周期不透明 | 注入 client factory 或应用级 client，统一超时、TLS 和关闭 |

## 复用验收清单

- [ ] 配置文件路径只能落在允许根目录，环境变量优先级、secret validator 和空 YAML 行为有测试。
- [ ] Web、Celery worker、Celery beat 的日志目录由显式 role 决定，不能通过路径穿越改变输出位置。
- [ ] Loguru 与标准 logging 只有一个事实源，重复初始化不会丢日志或增加重复 sink。
- [ ] 第三方 logger 的 handler、级别、异常 traceback 和 JSON schema 经验证后再做拦截。
- [ ] 日志轮转与归档只处理已封存文件；zip 使用临时文件/manifest，归档成功和删除成功分别可审计。
- [ ] 锁有租约、owner、超时和崩溃恢复；多副本部署使用分布式锁或单一归档 worker。
- [ ] 日志保留期、压缩、加密、访问权限和敏感字段脱敏符合合规要求。
- [ ] ArchiveConfigCode 到 bucket/object 的映射稳定、无碰撞、按租户隔离且数量受控。
- [ ] MinIO copy 使用连接超时、TLS、bucket/object allowlist 和幂等键；仅可恢复错误重试。
- [ ] async/sync/Celery 三个入口的返回状态、异常和事件循环约束有契约测试。
- [ ] Celery 调度失败不会静默丢任务，有 outbox、补偿扫描或可观测告警。
- [ ] 测试覆盖 MinIO disabled、建桶竞态、复制成功、部分失败、最终失败、重试退避、worker 重启和重复归档。
- [ ] Loguru 格式统一使用 `{}`；`crud_training_progress`、`main_refactored`、权限、RBAC、企微配置等调用点有日志回归。
