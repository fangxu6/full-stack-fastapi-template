## 3. 主流程状态与并发规则

### 3.1 工作流节点配置

WorkflowNodeCreate 约束：

- NodeLevel 必须匹配正整数.正整数，例如 1.1、2.3；
- ParallelPolicy 只允许 1=串行、2=并行 AND、3=并行 OR；
- IsSingleApproval=true 覆盖并行策略，强制单独执行；
- TimeoutHours >= 0，0 表示不启用超时；
- TimeoutAction 由超时服务归一化为 AutoApprove 或 Ignore。

工作流服务按 (stage, order) 数值排序节点，不能使用字符串排序，否则 10.1 会排在 2.1 前面。

### 3.2 节点分配

NodeAssignmentService 根据角色类型创建 Approve_Process_Detail：

- 普通角色：读取启用成员，节点采用抢单模式；
- 动态部门负责人：沿申请人所在部门向上查找有效负责人，跳过申请人本人；
- 部门审批人列表：按 ApprovalLevel 和创建时间排序，逐级生成同一 NodeID 的节点记录；
- 发起人自选：从业务数据读取选中的审批人并校验其有效性；
- AND/OR 并行：同阶段连续的同策略节点组成并行组；IsSingleApproval 会打断并行。

每个实例节点复制 NodeLevel、NodePosition、NodeGeneration 和 AssignTime，后续推进不应重新从当前配置猜测历史状态。

### 3.3 advance_process() 规则

ProcessService.advance_process() 不提交事务，由人工审批或超时服务在同一事务中调用：

1. 读取进行中的流程和当前 NodeLevel；
2. 对 AND 组确认组内无 ApproveStatus=1 待办后才进入下一阶段；
3. 对 OR 组将其他待办置为 ApproveStatus=5，立即进入下一节点/阶段；
4. 部门审批人列表在同一节点还有下一级时，只追加下一条待办；
5. 调用 NodeAssignmentService 创建下一阶段节点；
6. 没有下一节点时设置 ProcessStatus=3、EndTime。

在 MySQL 下，BIT(1) 可能返回 bytes，推进前必须显式转换；关键待办查询使用行锁读取最新状态，避免 REPEATABLE-READ 快照让已处理节点继续被当作待办。

## 4. 审批节点处理与超时处理

### 4.1 人工审批

ApprovalService.handle_approval() 的原子步骤：

~~~text
校验 process_node_id / operator_id
  -> 读取流程、节点、角色与轮次
  -> 校验角色成员或直接分配人
  -> UPDATE Process_Detail
       WHERE ProcessNodeID = ? AND ApproveStatus = 1
  -> 根据 APPROVE / RETURN / REJECT 计算流程状态
  -> 调用 advance_process()
  -> 在同一事务同步业务终态回写
  -> commit
  -> 发布 approval_node_* / approval_process_* 事件
~~~

UPDATE 的条件更新是抢单乐观锁；重复点击或多人同时处理时只有一个请求成功。PMS 特定锁冲突在未提交前可重试整次审批，已提交后的后置动作不能再次回滚主流程。

### 4.2 超时自动审批

ApprovalTimeoutService.handle_timeouts(db, batch_size=200)：

1. 扫描未删除、未处理、流程进行中的节点；
2. 先用 AssignTime <= 当前时间 - 1 小时粗过滤，再按 AssignTime + TimeoutHours 精确判断；
3. 仅 TimeoutAction=AutoApprove 自动通过，Ignore 不做任何操作；
4. 以流程主表行锁串行化超时处理与人工审批；
5. 使用 UPDATE ... WHERE ApproveStatus=1 防止重复处理；
6. 写入 SYSTEM 用户、审批时间和“超时自动通过”批注；
7. 调用同一个 advance_process() 推进流程；
8. 提交后写操作日志并发布节点通过、节点分配和流程完成事件。

默认调度器每 5 分钟运行一次；TimeoutHours 粒度为小时，因此轮询频率不等于业务超时时刻，验收时要接受分钟级延迟。

超时任务当前通过 get_db() 获取会话并处理单个批次；迁移到 Celery/Quartz 等平台时，应显式记录批次游标、失败重试和锁超时，避免扫描任务重入。

## 5. 数据与事件契约

| 字段 | 约定 |
| --- | --- |
| ProcessStatus | 1 待确认、2 进行中、3 已通过、4 已否决、5 已退回、6 已取消、7 已弃审 |
| ApproveStatus | 1 未处理、2 同意、3 否决、4 退回、5 失效 |
| NodeGeneration | 每次重新提交/重审递增，查询和更新必须带轮次 |
| ParallelPolicy | 节点配置快照，1 串行、2 AND、3 OR |
| TimeoutHours | 大于 0 才参与扫描 |
| TimeoutAction | AutoApprove 或 Ignore；输入应大小写和别名归一化 |

超时和人工审批都发布相同的领域事件，只额外携带 IsTimeout=true、TimeoutAction=AutoApprove 和 SYSTEM 操作者。事件发布失败不能撤销已提交的审批结果，应通过 CallbackStatus、回调日志和补偿任务追踪。

## 6. 复用风险

- **并发锁必须统一**：人工审批、超时自动审批、恢复/重放不能各自实现一套锁，否则 AND/OR 状态会被旧快照覆盖。
- **批处理要幂等**：超时扫描可能重入；状态条件、行锁和唯一处理标识必须同时存在。
- **时区必须统一**：AssignTime、当前时间和数据库 DATETIME 应使用同一时区和无时区比较策略。
- **角色解析依赖组织模型**：部门负责人、部门审批人列表需要 UserOrgRelation、Department、DepartmentApprover 等表，迁移前先定义接口。
- **自动审批是业务动作**：AutoApprove 可能触发业务回写、通知和下游事件，必须具备审计、幂等键和人工撤销策略。
- **并行组定义要稳定**：当前按同阶段连续同策略节点分组；若目标项目允许显式组 ID，应优先改为显式建模。
- **状态码不要散落**：将 ProcessStatus、ApproveStatus、ParallelPolicy 和 TimeoutAction 集中为枚举/常量。
- **测试状态**：提交主题写明“待测试”，且 CodeGraph 未发现 advance_process() 和 WorkflowNodeInfo 的完整覆盖，迁移前需补齐。
