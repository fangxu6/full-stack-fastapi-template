## 3. CodeGraph 调用链

```text
GET /approve/processes/{id}
  -> get_current_user()
  -> ProcessService.get_process_detail(current_user=...)
     -> 发起人放行
     -> 系统管理员放行
     -> FlowAdminRole 成员放行
     -> 否则校验节点直接审批人/角色成员
     -> Process_OperationLog 查询 ABANDON 详情
```

CodeGraph 显示 `get_process_detail()` 同时服务前端详情和多个业务集成调用；因此不能把授权只放到 FastAPI 依赖中，否则内部调用会绕过资源级校验。

## 4. 资源可见性契约

- 发起人可以查看自己的流程。
- 系统管理员可以查看所有流程。
- 工作流流程管理员可以查看其负责工作流下的流程。
- 其他用户必须是流程节点的直接 `ApproverID`，或属于节点绑定角色成员，否则返回“无权限查看该流程”。
- 详情响应保持流程主状态、回调状态、时间轴和已执行回调服务；当 `ProcessStatus=7` 时，读取最新 `ActionType=ABANDON` 操作日志的 `OperatorName/OperateTime/Content` 填入 `AbandonOperatorName/AbandonTime/AbandonReason`。

资源授权和数据查询应在同一服务方法中完成，避免“先返回流程，再补权限”的信息泄漏。

## 5. 权限码演进

本提交后的推荐读权限：

| 资源 | 权限码 |
| --- | --- |
| 流程监控列表 | `process_monitoring:read:list` |
| 审批角色列表 | `approval_roles:read:list` |
| 审批角色详情/审批人 | `approval_roles:read:detail` |
| 工作流列表/详情 | 至少要求登录；如需收紧，新增独立 `approval_workflows:read:*` |

写权限和审批动作权限沿用已有 `approve:*` 体系。迁移时应提供旧权限码到新权限码的映射或一次性数据迁移，避免线上用户突然失去只读权限。

## 6. 复用风险与验收

- [ ] 发起人、系统管理员、流程管理员、节点审批人、无关用户分别验证详情访问结果。
- [ ] 不能通过修改路由依赖或直接调用服务绕过资源级授权。
- [ ] 弃审详情从操作日志读取，缺少日志时字段安全返回空值。
- [ ] 新权限码与旧权限码的迁移策略可回滚，监控/角色读接口不会误用写权限。
- [ ] 流程详情中的 `CallbackStatus` 仍按 0/1/2/3 展示，不与 `ProcessStatus` 混淆。
