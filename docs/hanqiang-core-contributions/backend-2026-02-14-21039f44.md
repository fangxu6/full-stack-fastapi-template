这次提交的可复用主题有四个：

1. 用 ASGI 中间件统一生成 request id，并把 HTTP 请求和响应拆成结构化事件。
2. 将日志中的身份字段从混用的 `username`/整型占位 ID，统一为 `user_id`（稳定 ID）和 `user_code`（账号）。
3. 让 JWT 同时携带 `sub`、`user_id`、`user_code`，并允许日志场景在校验签名的前提下解析过期令牌。

提交没有配置 Elasticsearch、Index Template、Data Stream 或 Filebeat/Fluent Bit。它提供的是“可被 ELK 摄取的 JSON 日志契约”，传输和索引仍需由部署层完成。

## 4. HTTP 可观测性契约

### 4.1 请求生命周期

```text
ASGI http scope
  -> 读取/生成 X-Request-Id
  -> 读取 X-Forwarded-For、X-Real-IP 或 scope.client
  -> 从 Bearer JWT 提取 user_id/user_code
  -> 写入 event_action=http_request
  -> receive_wrapper 统计请求体大小并保留最多 8 KiB
  -> 应用发送 response.start
       ├─ 回写 X-Request-Id
       └─ status_code >= 400 才开启响应体预览
  -> send_wrapper 统计响应体
  -> finally 写入 event_action=http_response
```

非 HTTP scope（例如 WebSocket、lifespan）直接透传给下游应用，不生成 HTTP 日志。

### 4.2 逻辑事件字段

下表描述 `logger.bind(**extra)` 中的业务字段。Loguru 磁盘格式还会包一层 `record`，因此 ELK 摄取时应将 `record.extra` 展平或保留为嵌套对象。

| 事件 | 始终记录 | `status_code >= 400` 时增加 |
| --- | --- | --- |
| `http_request` | `event_action`、`request_id`、`user_id`、`user_code`、`http_method`、`url_path`、`url_query`、`client_ip` | 无 |
| `http_response` | 上述请求字段、`status_code`、`duration_ms` | `request_content_type`、`request_body_size`、`request_body_truncated`、`request_body_preview`（可解析时）、`response_content_type`、`response_body_size`、`response_body_truncated`、`response_body_preview`（可解析时） |

约束：

- `request_id` 优先透传请求头，缺失时生成 UUID，并在响应头回写同一值。
- `duration_ms` 是整数毫秒；计时使用单调时钟，不能用墙上时钟计算耗时。
- 请求体和响应体按字节计数，预览上限为 `8 * 1024` 字节；UTF-8 截断后通过 `*_truncated=true` 表示，不应依赖固定尾部标记。
- 成功响应不记录 body，只记录状态和耗时，避免日志量和敏感数据扩散。
- 中间件在 `finally` 中写响应事件；应用异常且尚未发送响应时，提交实现会使用初始状态码 `500`。

示例（逻辑字段，非完整 Loguru envelope）：

```json
{
  "event_action": "http_response",
  "request_id": "8f1c...",
  "user_id": "9b2d...",
  "user_code": "A001",
  "http_method": "POST",
  "url_path": "/api/training/plans",
  "url_query": "",
  "client_ip": "10.0.0.8",
  "status_code": 422,
  "duration_ms": 37,
  "request_content_type": "application/json",
  "request_body_size": 148,
  "request_body_truncated": false,
  "request_body_preview": "{\"name\":\"demo\",\"password\":\"***\"}",
  "response_content_type": "application/json",
  "response_body_size": 96,
  "response_body_truncated": false,
  "response_body_preview": "{\"detail\":\"invalid request\"}"
}
```

### 4.3 内容类型与脱敏边界

提交实现只预览以下内容类型：`text/*`、`application/json`、`+json`、`application/x-www-form-urlencoded`。JSON 对象和数组递归处理，表单通过 `parse_qs` 处理。

内置敏感键为：

```text
password, passwd, pwd, token, access_token, refresh_token,
secret, authorization, api_key, apikey, client_secret
```

迁移时必须补齐以下边界：

- 该提交对“格式错误的 JSON/表单”会回退原文；涉及凭证的接口应改为失败即 `***`，不能把解析失败当成安全。
- `url_query` 在提交中原样写入；查询参数可能含 token、签名或手机号，生产实现应按键名和 URL 规则脱敏。
- `OperationLogService._sanitize` 只把 UUID、日期、bytes、Decimal 等转成可 JSON 类型，不会识别 `password`、`token` 等字段。
- `X-Forwarded-For`/`X-Real-IP` 只有在反向代理可信时才能作为客户端 IP；否则只能记录直连地址或经过代理白名单校验。
- `X-Request-Id` 是关联键，不是认证凭据；若对外开放，建议限制长度/字符集并在日志中保留原值与规范化值的策略。

## 5. 统一身份与 JWT 契约

### 5.1 两个字段的含义

| 字段 | 含义 | 允许为空 | 典型来源 |
| --- | --- | --- | --- |
| `user_id` | 数据库稳定主键，统一序列化为 UUID 字符串 | 未认证、登录失败或旧 Token 可为空 | `CommonUser.UserID`、JWT `user_id` |
| `user_code` | 用户账号/业务可读标识 | 匿名请求可为空 | `CommonUser.UserCode`、JWT `user_code` 或 `sub` |

不要把 `user_id` 写入 `username`/`user_code`；也不要用整型 `0` 伪造已知用户。日志检索和审计关联以 `user_id` 为主，展示和人工排查以 `user_code` 为主。

### 5.2 Token 发行与解析

登录成功时发行：

```python
create_access_token(
    data={
        "sub": user.UserCode,       # 兼容旧消费者
        "user_id": to_uuid_str(user.UserID),
        "user_code": user.UserCode,
    },
    expires_delta=access_token_expires,
)
```

`decode_access_token(token, *, verify_exp=True)` 通过 JWT 库的 `options` 控制过期校验：

- 认证、授权、`/me` 和权限依赖必须使用默认 `verify_exp=True`。
- HTTP 观测为了定位过期 Token 导致的 401/403，可使用 `verify_exp=False`；签名仍然校验，不能据此放行请求。
- 只接受签名正确的 JWT；解析失败返回 `None`，不要把异常文本或 token 正文写入日志。

中间件优先读取 JWT 的 `user_id`，再读 `user_code`/`sub`。旧 Token 缺 `user_id` 时按 `Common_User.UserCode` 查询未删除用户，并使用进程内 TTL 缓存（命中 300 秒，达到 2000 条时清空）。查询失败会返回空 ID，不应阻塞业务请求；多 worker 进程之间缓存不共享。

`CurrentIdentity` 在提交中改为：

```python
@dataclass
class CurrentIdentity:
    user_id: str
    user_code: str
```

`get_current_identity_no_db` 只验证 JWT 并返回该结构，不访问数据库；是否需要权限仍应由单独的权限依赖决定。迁移时避免同时维护 `id/username` 和 `user_id/user_code` 两套事实源。

## 6. 日志 sink 与事件分类

### 6.1 目录、进程角色和轮转

`app/core/logging.py` 的提交实现：

- 根目录为 `app/core/logging.py` 上两级的 `logs`。
- `JSE_LOG_DIR_NAME` 可显式指定目录；否则从命令行识别 Celery `worker`/`beat`，默认 Web 使用 `current`。
- 应用和错误日志分别写 `app_YYYY-MM-DD.log`、`error_YYYY-MM-DD.log`；Web 进程另写 `operation_YYYY-MM-DD.log`、`login_YYYY-MM-DD.log`、`audit_YYYY-MM-DD.log`。
- 每日 `00:00` 轮转，`serialize=True` 输出 JSON；当前目录不压缩，归档由其他任务负责。
- Celery Worker/Beat 不生成 operation/login/audit 文件，避免把后台进程日志误当成人员操作。
- 重复错误告警 sink 捕获自身异常并返回，不能让告警故障中断主日志链路。

ELK 部署应按目录或 `event_action` 建立采集规则，并保留 `record.time`、`record.level`、`record.exception` 等 Loguru 元数据。提交本身没有 retention、压缩、索引生命周期或敏感字段索引模板。

### 6.2 三类业务日志函数

| 函数 | 固定 extra | 迁移调用示例 |
| --- | --- | --- |
| `log_operation` | `operation=true`、`event_action=operation`、`user_id`、`user_code`、`resource_id`、`action` | `log_operation(user_id=..., user_code=..., action=..., message=...)` |
| `log_login` | `login=true`、`event_action=login`、`user_id`、`user_code`、`ip`、`result` | 登录失败可传空 `user_id`，但仍保留尝试的 `user_code` |
| `log_audit` | `audit=true`、`event_action=audit`、`user_id`、`user_code`、`ip`、`action`、`result` | 关键业务动作和权限拒绝使用该入口 |

三个函数在提交中改为关键字参数；调用方若仍使用旧的 `username` 参数会直接失败。迁移顺序应是“先更新共享函数，再用 CodeGraph/搜索穷尽调用点”。

## 7. 操作日志与日志查询兼容层

### 7.1 `OperationLogService`

操作日志服务仍保留 `log_dir` 和旧文件路径方法以兼容构造代码，但提交后不再自行 `open(..., "a")` 写文件，而是：

1. 计算 `before`/`after` 差异（字段级 `old`/`new`）。
2. 递归把 datetime、Enum、UUID、bytes、集合、Decimal 转为可 JSON 值。
3. 通过 operation sink 写入 `event_action=operation`、`operation_type`、`resource_type`、`resource_id`、`user_id`、`user_code`、`action`、`ip`、`changes`、`before`、`after`、`extra_info`。
4. 写入失败只尝试记录错误，不向业务抛出异常。

“日志失败不影响业务”适合非关键审计，但如果法规要求不可抵赖，应改为可靠队列/数据库 outbox，并把失败状态纳入监控；不能仅靠 `try/except` 丢弃审计。

### 7.2 `parse_log_line` 与 API 模型

`app/api/v1/routes/logs.py:parse_log_line` 按以下顺序兼容：

1. Loguru JSON（含 `record`）：从 `record.extra` 读取 `user_code`、`user_id`、`ip/client_ip`、`action/event_action`。
2. 旧版 `OperationLogService` 自定义 JSON：读取 `user_name`、`user_id`、`before`、`after`、`changes`、`extra_info`。
3. 传统 `时间 | LEVEL | ...` 文本：使用正则提取用户、IP、操作。

`LogEntry.user_id` 在提交中由 `Optional[int]` 改为 `Optional[str]`；展示字段仍叫 `username`，但新日志优先映射 `user_code`。迁移到其他项目时建议直接把 API 字段改名为 `user_code`，或同时提供兼容别名并标记弃用日期。

## 8. 业务审计修复的调用链

提交修复的是“审计用户名字段误写 UUID/整型 ID”，而不是新增业务权限：

```text
HTTP 路由读取 current_user.UserID/UserCode
  -> 训练路由传 creator_code/updater_code/reviewer_user_code
  -> 训练服务调用 operation_log_service.log_operation
  -> user_id=稳定 UUID，user_name=UserCode
  -> Loguru operation sink
```

覆盖的训练动作包括创建/更新/删除计划、状态变更、补考计划、添加/移除参与人、考试结果回调、培训进度回调、提交/批改心得报告。系统回调显式使用 `updater_code="System"`，避免后台任务产生空账号。

其他管理路由（管理员、员工、部门、岗位、用户-员工绑定）同样将 `user_id=0` 替换为当前用户主键，并把 `username` 参数替换为 `user_code`。权限拒绝事件统一使用 `user_code`，返回状态仍为 403。

## 9. 跨项目最小迁移方案

### 第一步：先冻结字段契约

- 规定 `user_id` 为 UUID 字符串（或项目的稳定主键字符串），`user_code` 为账号。
- 约定所有事件都有 `event_action` 和 `request_id`（业务事件没有 HTTP request 时可为空）。
- 将日志中的秘密字段列成集中配置；不要散落在各个路由。

### 第二步：接入单一 ASGI 中间件

```python
app.add_middleware(HttpObservabilityMiddleware)
```

中间件应放在实际生产入口，并与异常处理、CORS、代理配置一起做一次端到端验证。不要保留旧 `@app.middleware("http")` 的重复请求/响应日志。

### 第三步：配置 JSON sink 和采集器

- 保留按进程角色分目录的策略，或改为 stdout JSON；二选一，不要同时写两份相同事件。
- Filebeat/Fluent Bit 解析每行 JSON，提取 `record.extra.event_action`，保留原始行用于回放。
- 在 Elasticsearch 中为 `request_id`、`user_id`、`user_code`、`url_path`、`status_code`、`duration_ms` 建立合适的 keyword/numeric 映射。
- 为错误事件设置告警，但告警 sink 必须隔离异常，不能反向影响请求。

### 第四步：更新所有调用方

- `log_operation/log_login/log_audit` 使用关键字参数和 `user_id/user_code`。
- 培训等跨层服务新增的 `creator_code/updater_code/reviewer_user_code` 必须从路由传到底层。
- 日志查询先兼容旧数据，再切换前端筛选字段；不要一次删除旧格式解析。

### 第五步：补安全和可靠性增强

- 查询参数、结构化日志 `extra_info`、before/after 数据都做秘密键脱敏。
- 对畸形 JSON/表单采用 fail-closed 预览策略。
- 对 `X-Forwarded-For` 采用可信代理白名单。
- 若审计不可丢失，使用数据库 outbox/消息队列；不要把“捕获异常后返回”当作持久化保证。
- 如需业务代码读取 request id，把它显式写入 ASGI scope state 或 ContextVar；目标提交本身只保证响应头和日志字段。

## 10. 验收清单

- [ ] 缺少 `X-Request-Id` 时服务生成 UUID，并在响应返回相同值。
- [ ] 非 HTTP ASGI scope 不被错误记录为 HTTP 事件。
- [ ] 每个请求恰有 `http_request` 和 `http_response` 事件；异常路径仍能看到响应事件。
- [ ] 成功响应不落 body；4xx/5xx 只落可预览类型且不超过 8 KiB。
- [ ] JSON 嵌套对象、数组和表单中的敏感键均被掩码；畸形敏感 payload 不回退原文。
- [ ] 查询参数、before/after、extra_info 中的 token/password 不会进入日志。
- [ ] `user_id` 始终是稳定 ID 字符串，`user_code` 始终是账号；匿名和登录失败场景的空值语义一致。
- [ ] 认证授权路径使用 `verify_exp=True`；只有观测路径允许解析过期但签名正确的 JWT。
- [ ] operation/login/audit 三类日志被分流且包含 `event_action`，Celery 角色不会生成错误的人员操作文件。
- [ ] 日志采集器能够解析 Loguru `record` envelope，并兼容旧操作日志 JSON/文本。
- [ ] 培训和管理路由的成功、失败、权限拒绝日志均带真实 `user_id/user_code`。
