## 3. 提交差异与控制流语义

### 3.1 修改前

父提交的关键结构为：

```python
async for db in get_db():
    try:
        result = await with_db_lock(
            db,
            lock_name="rbac_init_lock",
            func=do_init,
            timeout=30,
            skip_if_locked=True,
        )
    except Exception as e:
        logger.error(f"❌ Worker {worker_id}: 系统初始化失败: {e}")
        # 不阻止应用启动，仅记录错误
    finally:
        break
```

### 3.2 修改后

目标提交改为：

```python
async for db in get_db():
    try:
        result = await with_db_lock(
            db,
            lock_name="rbac_init_lock",
            func=do_init,
            timeout=30,
            skip_if_locked=True,
        )
    except Exception as e:
        logger.error(f"❌ Worker {worker_id}: 系统初始化失败: {e}")
        # 不阻止应用启动，仅记录错误
    break
```

`break` 仍然保证该 `async for` 只使用一次会话；变化在于它不再位于异常清理块中。这样做的边界是：

- 普通 `Exception` 仍按原策略记录并继续启动。
- `finally` 不再用 `break` 覆盖清理阶段可能出现的异常。
- `asyncio.CancelledError`、`KeyboardInterrupt` 等不被 `except Exception` 捕获的取消/退出信号，不会被 `finally: break` 意外吞掉。
- 会话关闭仍由 `get_db()` 内部的 `async with AsyncSessionLocal()` 和 `finally: await session.close()` 负责。

这里的“退出逻辑”不是主动关闭连接的新实现，而是让已有 `get_db` 资源管理逻辑在正确的控制流下执行。不要把该提交解读为连接池或事务策略变更。

## 4. 应用生命周期中的初始化顺序

目标提交版本的 `lifespan` 启动阶段按以下顺序运行：

1. 写入启动日志和服务器地址。
2. 检查 `encryption_key`；缺失时警告，但不阻止启动。
3. `await init_db()` 预热数据库连接池。该步骤异常会直接阻止进入后续启动流程。
4. 尝试初始化文件监控 MinIO 三个 bucket；异常只记录 warning 并继续。
5. 通过 `async for db in get_db()` 同步文件监控的 Celery Beat 配置，执行一次后 `break`。
6. 再通过一次 `async for db in get_db()` 执行系统配置、制造类型、企业微信模板和 RBAC 初始化：
   - `with_db_lock(..., lock_name="rbac_init_lock", timeout=30, skip_if_locked=True)` 防止多 worker 重复执行。
   - 获取不到锁时返回 `None`，当前 worker 记录跳过信息。
   - 初始化异常记录 error，但按现有策略不阻止应用启动。
   - 该次会话只用于初始化，不应泄漏到后台任务。
7. 尝试启动 APScheduler；失败只记录 warning。
8. `yield`，将控制权交回 FastAPI，应用开始接收请求。
9. 退出时停止调度器；停止失败只记录 warning。

启动阶段的“失败即终止”和“记录后继续”是不同策略，迁移时要逐项决定，不能用一个大 `try/except` 静默吞掉所有初始化错误。

## 5. 会话、事务与分布式锁边界

### 5.1 `get_db` 的资源契约

`app/core/database.py:get_db` 当前实现的关键语义是：

```python
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
        finally:
            await session.close()
```

因此，使用 `async for db in get_db()` 时应满足：

- 只在循环体内使用 `db`，不要把 session 交给将在 `yield` 之后继续运行的后台任务。
- `break` 放在业务处理和 `except` 之后，不要写进 `finally`。
- 不要在调用方再次 `close()` 同一个 session；如果确实需要手动事务边界，改用显式 `AsyncSessionLocal()` 上下文，并记录所有权。
- 重要：调用方在首次 `yield` 后立即 `break` 时，不要假定生成器中 `yield` 后面的 `await session.commit()` 一定执行；目标提交涉及的初始化服务大多自行提交，纯读/写任务必须通过测试确认事务结果。
- 若希望由生成器统一提交，应让生成器自然耗尽，或改用显式 `AsyncSessionLocal()` 上下文；不要把“谁提交事务”留给 `async for ... break` 的隐式行为。

### 5.2 `with_db_lock` 的连接所有权

`app/core/db_lock.py` 中的 `DBLock` 使用独立 `AsyncConnection` 执行 MySQL `GET_LOCK/RELEASE_LOCK`。原因是 MySQL 命名锁绑定连接，而 `AsyncSession` 在 commit/rollback 后可能切换底层连接。

迁移时应保持：

- 锁连接贯穿整个临界区，并在 `finally` 中释放。
- `skip_if_locked=True` 时释放临时锁连接，不能因为跳过初始化而泄漏连接。
- 锁只保证多 worker 的初始化互斥，不保证业务写入与其他外部系统原子提交。
- 锁获取失败、超时和释放失败必须可观测；不要把锁失败伪装成“初始化成功”。

## 6. 适合跨项目复用的实现模板

### 6.1 保持现有依赖生成器的最小改法

当项目已经把数据库会话封装成 FastAPI 依赖生成器时，最小迁移只需：

```python
async for db in get_db():
    try:
        await initialize_once(db)
    except Exception:
        logger.exception("startup initialization failed")
        # 只有在产品明确允许降级启动时才继续
    break
```

不要添加第二个 `finally: break`，也不要在 `except` 中无条件返回成功。该写法只适合 `initialize_once` 自己负责提交，或初始化仅包含读操作的场景；需要依赖 `get_db` 的生成器提交时改用显式会话上下文。

### 6.2 启动专用任务的更清晰写法

如果初始化代码不是 FastAPI 依赖，优先直接使用会话工厂，把事务所有权写清楚：

```python
async with AsyncSessionLocal() as db:
    try:
        await initialize_once(db)
        await db.commit()
    except Exception:
        await db.rollback()
        raise
```

两种写法不要混用：使用 `get_db` 时依赖生成器的提交/回滚契约；使用 `AsyncSessionLocal` 时由当前上下文负责提交、回滚和关闭。

### 6.3 初始化函数设计

- `do_init(db)` 只接收会话和必要配置，避免重新创建连接。
- 每个初始化子步骤返回明确状态（例如 `success`、`skipped`、`error`），日志同时记录步骤名和 worker ID。
- 分布式锁只包围需要互斥的数据库初始化，不要把网络调用、长时间文件操作或调度器启动放进锁临界区。
- 可选组件（MinIO、Beat、模板）单独捕获异常；核心数据库连接失败应保持失败可见。
- 初始化完成后不得保留 ORM 对象供应用运行期使用；应用请求应重新获取请求级 session。

## 8. 测试与验收建议

目标提交没有新增测试。跨项目迁移至少应覆盖：

1. `get_db` 只 yield 一次，初始化成功后循环退出，session 一定关闭；若使用 `async for ... break`，提交由初始化服务显式完成并被验证。
2. `initialize_once` 抛出普通 `Exception` 时，错误被记录，且按产品策略决定是否继续启动；session 仍关闭。
3. 初始化任务收到取消信号时，取消异常不会被 `finally: break` 吞掉，session 仍执行关闭。
4. 分布式锁返回“已占用”时不会执行初始化，锁连接会释放。
5. `init_db` 失败、可选 MinIO 失败、调度器启动失败分别符合各自的终止/降级策略。
6. 生命周期退出时调度器停止，即使停止函数抛错也不会阻止其他清理步骤。

可先运行现有后端测试，再针对生命周期增加小型 async 单元测试；不需要为移动 `break` 引入新的抽象层。
