## 4. 启动前后的行为差异

### 4.1 简版 app/main.py

提交前：

1. init_db() 初始化数据库连接/表。
2. 创建 AsyncSession(async_engine)。
3. 调用 manufacture_type_service.seed_preset_records(session)。
4. 调用 product_spec_service.seed_preset_records(session)。
5. yield 进入请求服务阶段。

提交后：

1. init_db()。
2. yield。

因此简版入口不再导入 AsyncSession、async_engine、manufacture_type_service 或 product_spec_service。部署时必须用迁移、显式 seed 命令或管理员接口预先准备必要数据。

### 4.2 重构版 app/main_refactored.py

重构入口仍会执行：

- 加密密钥配置告警；
- init_db()；
- MinIO 三桶检查；
- 文件监控 Beat 动态任务同步；
- 在 with_db_lock(..., lock_name="rbac_init_lock", skip_if_locked=True) 中初始化系统配置、企微模板和 RBAC；
- 启动定时任务调度器。

本提交只删除闭包中的：

~~~python
await manufacture_type_service.seed_preset_records(db)
await product_spec_service.seed_preset_records(db)
~~~

以及对应 import、日志和 all_results 条目。分布式锁仍保护其余初始化，数据库会话仍由 get_db() 提供；不能因为“取消 seed”而删除锁、会话或 RBAC 初始化。

### 4.3 预置服务的后续可用性

app/services/manufacture_type_service.py 和 app/services/product_spec_service.py 仍提供 seed_preset_records(db)。它们的职责是幂等地确保预置记录存在、恢复软删除记录并处理并发冲突；当前提交不改变这些算法。

- 制造类型预置：当前服务定义 CP/FT，兼容历史 ALL 记录。
- 产品规范预置：当前服务定义 AUTOMOTIVE/INDUSTRIAL/CONSUMER。
- 需要预置数据的环境，应在部署迁移、一次性初始化命令或显式运维任务中调用服务，并记录执行结果。
- 不要把 seed 又塞回每个 Web worker 的 lifespan；多进程启动会重复执行，且可能增加锁等待和数据库写入。

## 5. 为什么移除启动写入

启动阶段写库会带来几个可复用的工程问题：

- 隐式副作用：健康检查、滚动发布或扩容会触发业务数据写入，难以从部署日志判断谁修改了数据。
- 多 worker 重复执行：即使服务内部幂等，多个进程仍会竞争唯一键、锁和事务。
- 发布时序耦合：应用启动依赖预置表结构和写权限；只读运行账号、只读副本或数据库尚未迁移时容易启动失败或告警。
- 回滚不可见：代码回滚不一定会回滚已写入或被恢复的记录。
- 测试污染：导入 app 触发生命周期时，测试需要伪造数据库和 seed 依赖；移除后启动契约更容易隔离。

移除启动 seed 并不等于“忽略数据初始化”。正确做法是把一次性数据准备变成可观测、可重试、可审计的部署步骤。

## 6. 测试契约

文件：tests/integration/test_startup_seed_behavior.py

测试使用 pytest.mark.asyncio 和 monkeypatch：

1. 替换 init_db 为无副作用异步函数。
2. 将两个 seed service 替换为记录调用次数的 dummy。
3. 对 main.lifespan(app) 和 main_refactored.lifespan(app) 分别进入/退出上下文。
4. 重构入口额外 stub 数据库依赖、MinIO、Beat、RBAC、系统配置、企微模板和 scheduler，避免真实外部连接。
5. 断言 product_spec 与 manufacture_type 调用标志均为 False。

测试关键点不是断言“启动成功”本身，而是断言“启动期间没有调用两个预置写入入口”。迁移到其他项目时应保留这种负向契约测试，否则后续重构很容易把 seed 重新加回 lifespan。

建议补充的正向测试：

- 显式初始化命令调用两个 seed，并在重复执行后数据数量不增加。
- 预置服务失败时，部署步骤返回非零状态并记录可定位日志。
- Web lifespan 在只读数据库账号下仍能完成不写库的启动路径（其余确需写入的初始化需单独声明）。

- 测试目录本身；
- 目标测试文件；
- 必要的 __init__.py 或 fixtures（如果工具链需要）。

验证顺序建议使用 git check-ignore -v tests/integration/test_startup_seed_behavior.py，确认该文件未被更宽的规则重新忽略。

## 8. 跨项目迁移步骤

1. 盘点启动副作用：列出 lifespan/startup hook 中所有数据库写入、外部资源创建、缓存刷新和调度器启动；不要只搜索 seed。
2. 区分必须启动动作：保留数据库连接初始化、健康检查所需的只读准备和明确要求的基础设施检查；把业务预置数据写入移到迁移/部署任务。
3. 移除 wiring，不删服务：删除入口 import、session 创建、seed 调用、专属日志和结果字段；保留 seed service、管理员接口及其单元测试。
4. 处理多入口：主入口、重构入口、CLI、worker 入口和测试 app 都要检查，避免只修一条启动路径。
5. 设计显式初始化命令：使用一次性 job、Alembic data migration 或管理命令；必须可重复执行、可观测、失败可重试。
6. 确定数据就绪门槛：应用启动不再保证 CP/FT、产品规范等记录存在；需要这些记录的业务接口应返回清晰错误，或由部署流水线先完成初始化。
7. 保留必要锁的最小范围：如果其他系统配置/RBAC 初始化仍需要分布式锁，只缩小闭包内容，不要粗暴删除锁机制。
8. 写负向生命周期测试：mock 所有 seed 入口并断言未调用；同时为显式 seed 命令写正向幂等测试。
9. 放行测试文件：检查 .gitignore 与 CI 配置，确保生命周期测试真正提交和执行。
10. 记录历史边界：用 Git 历史确认“移除启动调用”而不是“删除服务实现”，用当前 CodeGraph 检查后续是否又出现新的启动写入。
