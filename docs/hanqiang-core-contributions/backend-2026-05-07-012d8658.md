## 能力边界

1. `ScheduledTaskService` 负责业务校验、审计和调度同步；路由只做权限、参数和 HTTP 错误映射。
2. 任务定义与投递配置、业务配置分表保存，执行主日志与执行明细独立保存。
3. Web 请求只创建 `pending` 执行记录并投递 Celery；实际 PMS 查询和邮件发送在 Worker 中完成。
4. Beat 从数据库读取当前有效任务，生成 `celery_sqlalchemy_scheduler` 的 `PeriodicTask`；禁用、删除、过期任务会被停用。
5. 首版只接受 `email` 投递和 `pms_maintenance` 任务，设备必须显式选择。

## 数据模型

| 表 | 关键字段 | 设计要点 |
| --- | --- | --- |
| `Sys_Scheduled_Task_Master` | `TaskType`、`TaskName`、`DeliveryMethod`、`ExpressionCron`、`EffectiveDate`、`ExpiryDate`、`IsEnabled`、`IsDeleted` | 任务生命周期和审计字段；按类型、启用状态、时间建索引 |
| `Sys_Scheduled_Task_Delivery_Detail` | `ScheduledTaskID` 唯一、`DeliveryType`、`ConfigJSON` | 邮箱配置/模板/收件人 ID 与变量的 JSON；与主表一对一 |
| `PMS_Scheduled_Task_Config_Detail` | `ScheduledTaskID` 唯一、`AdvanceRemindDays` | PMS 前置提醒天数 |
| `PMS_Scheduled_Task_Equipment_Relation` | `PMSConfigID`、`EquipmentID`、`IsDeleted` | 设备多选关系，配置设备唯一约束 |
| `Sys_Scheduled_Task_Execution_Master` | 快照字段、`TriggerSource`、`TaskTraceID`、状态、时间、计数、`ExecutionSummaryJSON` | 记录一次派发/执行，不依赖任务后续改名 |
| `Sys_Scheduled_Task_Execution_Detail` | `DetailType`、`DetailKey`、`SequenceNo`、状态、摘要、错误 | 记录匹配保养计划或跳过设备，支持逐条诊断 |

状态枚举：执行主表为 `pending`、`executing`、`success`、`failed`、`timeout`；明细为 `pending`、`success`、`failed`、`skipped`；触发来源为 `cron`、`manual`。

## 端到端调用链

```text
HTTP 路由
  -> ScheduledTaskService（UUID/Cron/时间/邮箱配置校验）
  -> CRUD 写入主表、投递表、PMS 配置和设备关系
  -> commit + sync_all_scheduled_tasks_beat_sync()

Celery Beat
  -> PeriodicTask(scheduled_task_<id>)
  -> dispatch_scheduled_task(task_id, cron)
  -> 校验启用和有效期，创建/读取 pending 执行记录
  -> send_task("...execute_pms_task", queue="scheduled_task")
  -> execute_pms_task
      -> 标记 executing
      -> PmsTaskQueryService.collect_due_plans()
      -> 写入 execution_detail
      -> 解析 ${NOW_*} 和 mtplan
      -> EmailSendService.send_email()
      -> 更新 success/failed、计数、耗时、MessageID
```

### Beat 同步规则

`sync_all_scheduled_tasks_beat_sync()` 使用固定前缀 `scheduled_task_` 和五段 Cron。只选 `IsDeleted=0`、`IsEnabled=1`、`EffectiveDate <= now < ExpiryDate` 的任务；同名 `PeriodicTask` 更新，不存在则创建；数据库中前缀匹配但不在活动集合的任务设置 `enabled=False`。Beat 使用独立同步 SQLAlchemy Engine/`NullPool`，避免阻塞异步 Web 会话。

### PMS 查询与邮件

- 设备只接受未删除设备；保养计划必须 `Status=Active`、`StartDate <= today + advance_remind_days`。
- 结果按计划日期、设备编号、设备名称、模板名排序。
- `mtplan` 同时生成纯文本 TSV 和 HTML 表格；计划状态映射为中文，额外输出“已逾期 N 天/今日/N 天后”。
- 每个匹配计划写一条 `maintenance_plan/success` 明细；无效设备写 `equipment/skipped` 明细和跳过原因。
- 邮件失败时，非 skipped 明细标为 failed，主记录保留错误摘要和统计后再抛出异常；外层异常处理再次兜底回填执行状态。

## 校验与并发边界

- 邮箱配置、模板、收件人必须存在、未删除且启用；投递方式仅允许 `email`。
- Cron 首版仅检查五段，目标项目应增加合法字段值和时区校验。
- 生效时间必须早于失效时间；UUID 在服务边界统一转换为 16 字节 BINARY。
- 手动执行前检查同任务 `pending/executing`；超过 10 分钟的 pending 自动标记 timeout，避免永久占槽。
- `send_task` 失败会把 pending 记录改为 failed；Worker 失败也会回填主表和明细。
- 创建/更新后调用 Beat 同步失败只记录 warning。生产环境若不能接受“数据库已成功但调度未更新”，应增加 outbox/补偿扫描。

## 跨项目复用步骤

1. 先确定任务类型、投递方式、时区和执行队列；保留 `TaskType`/`TriggerSource` 字符串枚举，避免把业务类名写入数据库。
2. 迁移 6 张表及索引，给执行日志增加租户/数据权限字段；所有外键关系按项目数据库能力补齐。
3. 实现 `TaskService`、`ExecutionService`、`BeatSchedulerService` 三个独立服务，路由不直接操作 Celery 或 ORM 关系。
4. 为每个任务类型提供 `collect -> build_details -> deliver` 适配器；邮件模板变量只接受白名单字段。
5. 在 Celery 启动入口注册任务模块和专用队列；Beat 启动时执行一次全量同步，随后由任务变更触发增量/全量同步。
6. 接入权限模块和操作日志，至少覆盖列表、详情、创建、更新、启停、删除、运行、日志查询。
7. 先跑数据库迁移，再用一个短周期 Cron 做冒烟：创建任务、Beat 生成、手动执行、邮件失败回填、日志详情读取。

## 复用验收清单

- [ ] 任务 CRUD 对无效 UUID、无效 Cron、时间倒置、禁用资源和越权资源返回明确错误。
- [ ] 任务修改后 Beat `PeriodicTask` 幂等更新；禁用、删除、过期任务不会继续触发。
- [ ] 同一任务并发手动执行不会产生两个活动执行；陈旧 pending 会可观测地 timeout。
- [ ] Worker 重试/异常不会吞掉错误；主日志、明细、邮件历史三者状态可关联。

- [ ] 执行摘要计数与明细状态之和一致，空结果也能生成 success 日志。
- [ ] Celery/Beat 进程使用独立队列和数据库连接，关闭时释放 Engine。
- [ ] 迁移脚本可重复执行；JSON 字段默认值、BINARY UUID 和索引在目标数据库验证。
- [ ] 具备 `TaskTraceID`、MessageID、操作日志和结构化错误，能够从 UI 追溯到邮件发送历史。
