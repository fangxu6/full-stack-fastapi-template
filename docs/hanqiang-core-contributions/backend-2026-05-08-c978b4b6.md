## 修复前后的生命周期

```text
修复前
  create/update -> flush -> refresh(task, [delivery_detail, pms_config])
                     -> service commit -> _to_detail(task)
                     -> 访问 pms_config.equipment_relations 时隐式异步加载失败

修复后
  create/update -> flush（关系行已写入）
              -> get_by_id(selectinload(delivery, pms, equipment_relations))
              -> service commit -> _to_detail(fully_hydrated_task)
```

`get_by_id()` 以 `IsDeleted=0` 过滤主任务，并使用 `selectinload` 装载投递详情、PMS 配置和设备关系；执行日志 CRUD 也采用 `selectinload(details, task)`，两者共同避免异步上下文外的隐式数据库访问。

## 事务与关系语义

- 创建流程先 flush 主任务取得 `ScheduledTaskID`，写入 delivery/PMS/设备关系，再 flush，最后完整回读；外层 service 负责最终 commit。
- 更新流程更新主表和 delivery，按设备 ID 集合恢复已有关系、插入新关系、把移除关系设为 `IsDeleted=1`。设备范围模式是后续 `0350dc41` 才引入的；迁移时由上层决定是否传空集合，CRUD 本身只处理传入的关系集合。
- 回读失败抛出明确 `RuntimeError`，不会返回半装载对象；调用方可回滚事务并告警。
- 测试 fake session 只需实现 `add()`/`flush()`；通过 monkeypatch `get_by_id` 验证传入的是原始主键，避免测试被 SQLAlchemy 实现细节绑死。

## 迁移到其它项目

1. 列出每个 service 在 `commit()` 后、队列投递前、审计序列化前访问的关系字段。
2. 在对应 CRUD 的写入方法末尾执行一次显式查询，使用 `selectinload`/`joinedload` 明确装载图；不要在 Pydantic 序列化器里偷偷查库。
3. 统一规定 CRUD 返回“可脱离 session 序列化”的对象，或直接返回纯 DTO；二者选一，禁止调用方猜测关系是否已加载。
4. 对 BINARY UUID、软删除条件和一对多关系分别写回归测试；测试更新时要验证旧关系被软删、新关系可读。
5. 若采用延迟导入，记录实际循环依赖路径，并确保静态分析、类型检查和应用启动都能解析 singleton。

## 测试契约

必须覆盖：

- 创建后 `get_by_id(db, task_id)` 被调用，返回对象就是 service 后续使用的完整对象。
- 更新后同样回读；传入的 `task_id` 未被关系对象覆盖。
- 更新指定设备集合时，旧关系 `IsDeleted=1`，新设备关系加入 session。
- 回读返回 `None` 时抛错，不静默返回未装载对象。
- 真实数据库集成测试验证 `delivery_detail`、`pms_config`、`equipment_relations` 在 session 关闭后仍可被日志 DTO 读取。

## 不应照搬的做法

- 如果项目使用纯 DTO/Repository，不要为了“看起来一致”引入模块级 `__getattr__`。
- `selectinload` 不是无限关系加载器；关系图很大时按用例拆分查询，避免一次读取过多数据。
- 仅回读并不能解决并发覆盖；需要版本号/条件更新时，在同一 CRUD 边界增加乐观锁。
- 该修复只处理 scheduled task CRUD；其它异步 ORM 服务仍需逐一检查隐式 lazy load。
