## 3. 根因与并发协议

### 3.1 原有竞态

```text
事务 A（人工）                 事务 B（人工或超时）
普通读流程/待办旧快照            普通读流程/待办旧快照
更新节点 A=已通过                更新节点 B=已通过
判断并行组是否仍有待办            判断并行组是否仍有待办
都认为需要推进                    都认为需要推进
创建下一阶段/发送事件              创建下一阶段/发送事件
```

在 MySQL 默认 REPEATABLE-READ 下，事务第一次普通读取建立的快照可能不会因为等待锁结束而刷新；仅锁流程主表而继续使用普通读，也不足以保证看到最新节点状态。

### 3.2 提交后的协议

所有会改变流程推进结果的入口遵循同一顺序：

1. 读取节点上下文并确定 `ProcessID`。
2. `SELECT Approve_Process_Master ... FOR UPDATE` 获取流程级锁。
3. 确认 `IsDeleted=0` 且 `ProcessStatus=2`（进行中）。
4. `UPDATE Approve_Process_Detail ... WHERE ApproveStatus=1` 抢占当前待办。
5. 调用不提交事务的 `process_service.advance_process()`。
6. 在推进器内对关键待办查询使用 `FOR UPDATE`，读取锁等待后的最新状态。
7. 创建下一阶段或将流程置为完成，并由外层统一提交。

流程主表是互斥粒度；节点条件更新是幂等/抢占保护；推进器不自行提交，人工和定时任务因此能够共享完整事务边界。

## 4. 人工审批改动

`ApprovalService._handle_approval_once()` 在更新节点前锁定流程主表：

```python
proc_stmt = (
    select(Approve_Process_Master)
    .where(Approve_Process_Master.ProcessID == process_id)
    .where(Approve_Process_Master.IsDeleted == 0)
    .with_for_update()
)
proc = (await db.execute(proc_stmt)).scalar_one_or_none()
```

随后仍使用条件更新保护同一节点的重复处理：

```sql
UPDATE Approve_Process_Detail
SET ApproveStatus = 2, ApproverID = ?, ApproveTime = ?
WHERE ProcessNodeID = ?
  AND IsDeleted = 0
  AND ApproveStatus = 1;
```

`rowcount=0` 返回“已处理/已失效”。这两个层次不能互相替代：流程锁解决同一流程不同并行节点的推进顺序，节点条件更新解决同一节点的重复点击或抢单。

## 5. 推进器改动

### 5.1 MySQL BIT 字段

`Approve_Process_Master.IsDeleted` 在 MySQL `BIT(1)` 列上可能返回 `bytes`、`memoryview` 或整数。推进器改为使用 `_bit_to_int()` 判断删除标记，避免有效流程被误判为不存在。迁移到其他 ORM 时，应在数据库适配层统一布尔字段转换，不要在每个查询处猜测驱动返回类型。

### 5.2 AND 并行组

`advance_process()` 按当前 `NodeLevel` 找到连续的 AND 组，并查询同一 `ProcessID`、`NodeGeneration` 和组内层级的待办：

```python
select(Approve_Process_Detail.ProcessNodeID)
  .where(... ApproveStatus == 1)
  .limit(1)
  .with_for_update()
```

查询到任何待办就返回 `(proc, [])`，不创建下一阶段；只有组内不存在待办时才调用 `assign_next_stage()`。锁定读取的目的，是在等待流程主表锁后跳过旧快照，确认另一事务已经提交的节点结果。

### 5.3 串行/普通节点

非 AND 节点同样对当前层级的待办查询加 `FOR UPDATE`。这不是只为并行场景服务：同一事务可能已经建立普通读快照，若不锁定读取，部门审批人列表或串行节点也可能重复判断为待办。

### 5.4 OR 组与终态

OR 组保持原有短路规则：任一节点通过后，其他待办更新为失效（`ApproveStatus=5`），再创建后续节点。没有任何后续节点时才设置 `ProcessStatus=3`、`EndTime`。锁只负责序列化判断，不改变 AND/OR 的业务语义。

## 6. 超时自动审批改动

`ApprovalTimeoutService.handle_timeouts()` 与人工审批使用相同流程锁和节点条件更新：

1. 扫描 `ApproveStatus=1`、流程进行中且已到期的节点。
2. 对每个候选先锁定流程主表；流程不存在、已删除或不再进行中时回滚并跳过。
3. 以 `UPDATE ... WHERE ApproveStatus=1` 写入 SYSTEM 用户、审批时间和“超时自动通过”。
4. 调用同一个 `advance_process()`，因此人工和超时不会各自实现一套并行组判断。
5. 提交后再记录操作日志并触发节点通过、节点分配和流程完成事件。

锁等待失败、节点已被人工处理或流程状态已变化时，当前候选回滚并继续批次，不把竞争误报为业务失败。迁移到 Celery、Quartz 或 Cron 时必须保留这一“单候选失败不影响批次”的边界。

## 7. 事件回调影响面

该提交没有改动事件分发器，但改变了事件触发的前置状态：

```text
人工/超时审批
  -> 锁定流程主表
  -> 条件更新当前节点
  -> advance_process()
       -> created_next（只在真正创建下一节点时返回）
  -> 提交审批事务
  -> approval_node_approved
  -> 对 created_next 逐条发送 approval_node_assigned
  -> 若 ProcessStatus=3，再发送 approval_process_completed
```

因此回调层必须遵循：

- 只根据已提交的 `created_next` 发送节点分配事件，不能根据工作流配置猜测“可能创建”的节点；
- 并行竞态下同一流程的下一阶段只能有一份有效节点和一组分配事件；
- `approval_node_approved` 可携带 `IsTimeout=true`、`TimeoutAction=AutoApprove` 区分系统自动通过；
- 事件发布失败不应回滚已经提交的审批结果，应依赖 `CallbackStatus`、事件日志和恢复任务补偿；
- 事件回调和业务终态回写要有幂等键，避免 Worker 重试造成重复外部副作用。

事件字段、收件人和失败语义的独立迁移说明见[审批事件回调与并发推进复用指南](event-callback-approval-concurrency-2026-07.md)。

## 8. 集成测试契约

新增 `tests/integration/test_approval_parallel_advance_mysql.py`，测试显式要求：

- `RUN_MYSQL_INTEGRATION=1`；
- `JSE_CONFIG_YAML` 指向 `config_dev.yaml`；
- 数据库为 MySQL，且数据库名为批准的 `jselocaltest`；
- 事务隔离级别为 `REPEATABLE-READ`。

核心场景：

| 场景 | 断言 |
| --- | --- |
| 两个并行节点同时人工通过 | 两个节点均为 `ApproveStatus=2`；下一阶段 `3.1` 仅一条；仅一个 `approval_node_assigned` 事件。 |
| 一个节点人工通过、另一个节点超时自动通过 | 超时批次处理 1 条；下一阶段 `3.1` 仅一条；流程仍为进行中。 |
| 两个会话先建立普通读快照 | 锁等待结束后仍能看到最新状态，不因旧快照重复推进。 |

测试通过 monkeypatch 将超时扫描限制到隔离候选，并清理测试用户、角色、工作流、流程和节点；未显式设置环境变量时跳过写入，避免误操作其他数据库。

## 9. 跨项目迁移步骤

1. 先定义流程级锁的唯一粒度（通常为 `process_id`），并规定人工、超时、恢复、重放全部使用同一锁。
2. 在锁定流程主表后再做节点状态判断；不要先用普通读决定是否推进。
3. 所有“抢占待办”使用带状态条件的更新，并检查 `rowcount`。
4. 将推进器设计为不提交事务的纯编排服务，由入口统一提交或回滚。
5. 对 MySQL/不同驱动的布尔字段做集中转换；对关键待办查询使用锁定读或等价的当前读。
6. 让推进器返回实际创建的节点集合，事件层只消费该集合。
7. 事件发布、业务回写和外部通知分别定义幂等键、失败补偿和审计字段。
8. 在真实数据库隔离级别下运行人工/人工、人工/超时和重复重试竞态测试；SQLite 单元测试不能替代该验证。
