该提交修复手动执行/重试在成功调用 Celery `send_task()` 后的状态语义：派发成功只代表消息已提交到队列，业务执行尚未开始，因此 API 必须返回 `pending`，不能误报 `success`。真正的执行状态由后续 Worker 更新。

## 3. 调用链

```text
POST /scheduled-tasks/tasks/{id}/run
  -> ScheduledTaskService.run_task()
       -> claim_pending_execution(trigger_source="manual")
       -> commit 执行记录（Status=pending）
       -> _dispatch_pending_execution()
            -> celery_app.send_task(dispatch_scheduled_task,
                 [task_id_hex, "manual", execution_id_hex])
            -> 返回 {execution_id, status: "pending"}

POST /scheduled-tasks/executions/{id}/retry
  -> 校验源记录 failed/timeout
  -> 领取新的 pending 执行槽并沿用 TaskTraceID
  -> 同一派发入口，trigger_source="retry"
```

Celery 的 `dispatch_scheduled_task` 再读取任务和执行记录，领取或复用执行槽，并派发具体 `execute_<task_type>` Worker；该异步链路成功后才会把执行记录更新为 `executing`，完成后更新为 `success`/`failed`/`timeout`。

## 4. 状态与失败语义

| 阶段 | 状态 | 含义 |
| --- | --- | --- |
| 创建执行槽并提交 | `pending` | 等待调度任务被 Worker 消费。 |
| `send_task()` 成功返回 | 仍为 `pending` | 仅确认消息交接到 Celery，不代表业务执行。 |
| `send_task()` 抛异常 | `failed` | 记录结束时间、耗时、错误摘要并提交。 |
| Worker 开始 | `executing` | 已进入实际任务处理。 |
| Worker 完成 | `success` / `failed` / `timeout` | 由执行器根据业务结果回写。 |

不要在 `_dispatch_pending_execution()` 中设置 `success` 或 `executing`。如果 Broker 接受消息但 Worker 尚未运行，提前设置终态会导致日志、重试按钮和监控产生错误判断。

## 5. 失败路径与可重试性

派发异常时，服务使用 `queued_time` 或 `CreateTime` 计算至少 1 秒的 `DurationSeconds`，写入 `ErrorSummary="调度派发失败: ..."`，提交后抛出 `BusinessException`。调用方可将该执行记录作为失败记录展示或允许重试。

消息提交成功但响应丢失时，客户端重试请求可能创建第二个执行槽；因此 `run_task()` 和 `retry_execution()` 必须继续依赖 `claim_pending_execution()` 的数据库锁/唯一活动槽约束，前端写请求也应关闭网络自动重试。若需要更强保证，应引入请求幂等键并在服务端持久化。

## 6. 与 Beat、Trace 和 Worker 的边界

- Beat 的 `last_run_at` 是调度基线，不是执行成功时间；见 [a3b3ddff](backend-2026-07-15-a3b3ddff.md)。
- `execution_id` 是业务执行记录 ID，Celery task id 仅是消息任务 ID，二者分别审计。
- 重试创建新 `execution_id`，但可沿用源记录的 `TaskTraceID` 聚合链路；不要覆盖原始失败记录。
- Celery 任务接收 `execution_id_hex` 后必须检查记录仍为 `pending`，并在异常时只条件更新 `pending -> failed`，避免覆盖 Worker 已开始的执行。
- Worker、恢复任务和人工重试都要遵守活动状态集合 `{pending, executing}`，避免并发重复执行。

## 7. 跨项目迁移步骤

1. 将状态枚举集中定义：`pending`、`executing`、`success`、`failed`、`timeout`。
2. 先持久化执行槽，再发送统一 `dispatch_task` 消息；API 返回 `pending`。
3. `send_task` 异常只把仍未开始的记录改为 `failed`，保存错误和时间。
4. Worker 开始时条件更新 `pending -> executing`，结束时按当前状态回写终态。
5. 手动执行、Cron 和重试统一传递 `task_id + trigger_source + execution_id`。
6. 以数据库锁、条件更新或唯一约束防止 active execution 重叠；必要时增加请求幂等键。
7. 将业务 execution_id、TaskTraceID、Celery task id 和消息历史分开保存。
8. 监控中区分“已入队”“执行中”“业务成功”，不要把队列确认当作业务成功。

## 8. 验收清单

- [ ] `send_task()` 成功后 API 返回 `status=pending`。
- [ ] 返回的 `execution_id` 与已持久化执行槽一致。
- [ ] 发送参数包含任务 ID、触发来源和执行 ID，Cron/manual/retry 均可区分。
- [ ] Broker 派发异常将记录置为 `failed`，保存结束时间、耗时和错误摘要。
- [ ] Worker 后续能把 pending 更新为 executing 和终态。
- [ ] 手动执行或重试请求不会因网络重试创建重复活动执行槽。
- [ ] 源失败记录保留，重试使用新执行 ID；Trace 聚合规则明确。
- [ ] 前端按钮和日志文案将 pending 显示为“已排队/等待执行”，而非“执行成功”。
