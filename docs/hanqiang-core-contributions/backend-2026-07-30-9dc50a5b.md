## 列表查询行为

`GET /api/approve/roles` 与 `GET /api/approve/workflows` 的服务层现在按以下顺序工作：

1. 查询当前页数据（沿用 `page/page_size/keyword/is_enabled/role_type` 筛选）。
2. 执行一次 `get_list_statistics()` 条件聚合查询。
3. 对当前页 ID 使用 `GROUP BY ... IN (...)` 批量查询成员数或节点数；空页不执行该查询。
4. 组装分页数据和统计字段。

这把旧的“列表查询 + 独立 count”收敛为“列表查询 + 一次统计聚合”，并保持详情计数为批量查询，避免在循环中产生 N+1。`count_multi()` 仍可供其它调用者使用，不应把列表统计逻辑复制到路由或前端。

## API 响应契约

两个列表接口都返回同一形状：

```json
{
  "items": [],
  "total": 12,
  "page": 1,
  "page_size": 20,
  "total_pages": 1,
  "statistics": {
    "total": 18,
    "enabled": 14,
    "disabled": 4
  }
}
```

- 顶层 `total` 等于当前筛选结果的 `filtered_total`，用于分页。
- `statistics.total/enabled/disabled` 先应用 `IsDeleted=0` 以及关键字（角色还包括 `role_type`），再统计全部状态；故传入 `is_enabled=true/false` 时，启用/停用统计不会被当前状态筛选污染。
- 空结果通过 `COALESCE` 返回 0；前端不应再用当前页数据估算全局统计。
- 新项目若使用 DTO，应将 `statistics` 设为必填，并把 `filtered_total` 作为服务层内部字段或显式命名，避免把两个 `total` 混用。

## 请求级可观测性

`app/core/approval_list_timing.py` 使用 `ContextVar` 保存请求级计时，只对以下精确路径和方法生效：

- `GET /api/approve/roles`
- `GET /api/approve/workflows`

阶段按固定顺序写入 `Server-Timing`：`auth_user`、`auth_roles`、`permission`、`list_query`、`status_summary`、`detail_count`、`total`。认证、角色加载和权限依赖只增加计时，不改变原有 401/403 语义。`main_refactored.py` 将该响应头加入 CORS `expose_headers`，浏览器端才能读取。

总耗时超过 `300ms` 时，HTTP 观测中记录 `event_action=approval_list_slow_request`，并附带 `request_id`、路径、状态码、总耗时及各阶段毫秒数。阈值是可调的观测策略，不应把它改成静默降级或自动重试。

## CodeGraph 调用链证据

```text
GET /api/approve/roles     -> get_role_list -> RoleService.list_roles
GET /api/approve/workflows -> get_workflow_list -> WorkflowService.list_workflows
                                   ├─ CRUD.get_multi
                                   ├─ CRUD.get_list_statistics
                                   └─ 当前页 ID 的批量 GROUP BY 计数
HttpObservabilityMiddleware.__call__
  -> begin_approval_list_timing -> 依赖/服务阶段计时 -> Server-Timing/慢请求日志
```

CodeGraph 还确认 `get_list_statistics()` 只由对应列表服务调用；因此统计字段应继续由服务层组装，避免在路由、前端或其它 CRUD 中出现第二事实源。

## 跨项目复用步骤

1. 先定义统一的 `ListStatistics(total, enabled, disabled)` DTO，并约定顶层 `total` 始终服务于当前筛选分页。
2. 在角色/工作流各自的 CRUD 中实现一条条件聚合查询：外层筛选不包含 `is_enabled`，状态筛选通过 `CASE` 计算 `filtered_total`。
3. 服务层保留“列表一次 + 统计一次 + 当前页批量计数一次”的边界；用 `IN` 和 `GROUP BY` 批量取成员/节点数。
4. 前端列表页只调用一次列表接口并消费 `statistics`；状态变更成功后重新拉取列表，避免本地行状态与全局统计分叉。
5. 在请求上下文中加入阶段计时，并仅对白名单 GET 路径注入 `Server-Timing`；在统一 HTTP 中间件按 request ID 记录慢请求。
6. 为聚合语义、空页、状态筛选、批量计数和响应头各保留最小回归测试；迁移到其它框架时保持字段含义，不必复制 FastAPI/SQLAlchemy 的目录结构。
