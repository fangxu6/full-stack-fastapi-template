## 详情读取契约

### 查询与序列化

`WorkflowService.get_workflow_detail(db, workflow_id, timings=None)` 先严格解析 UUID，再按固定顺序完成读取：

1. 检查当前 `WorkflowService` 实例的详情缓存；命中且未过期时返回 `deepcopy`，避免调用方修改缓存对象。
2. 对 `Approve_Workflow_Master` 只选择详情接口需要的列，并过滤 `IsDeleted=0`；不存在时抛出 `NotFoundException`。
3. 对 `Approve_Workflow_Detail` 只选择节点展示和运行配置字段，过滤软删除节点；按数值 `(stage, order)` 排序，因此 `1.2` 排在 `1.10` 前。
4. 收集去重后的 `RoleID`，使用单条 `IN` 查询角色名称，不在节点循环中查询角色。
5. 将 BIT/bytes 标记统一转换为布尔值，组装稳定的工作流详情 DTO，并缓存一份深拷贝。

详情读取不访问 `Approve_Process_Master`、`Approve_Process_Detail` 或审批历史 JSON 关系；工作流配置页面不应因为 ORM `selectin` 关系加载运行流程数据。字段投影是性能和数据边界的一部分，新增返回字段时必须显式加入投影及序列化映射。

### 短缓存与失效

- 缓存位于服务实例内存，键为规范化后的 `WorkflowID` bytes，TTL 为 5 秒。
- 缓存命中仍返回独立对象；过期条目在读取时删除。
- 工作流创建完成节点位置重算并提交后、工作流更新提交后、工作流软删除提交后，都调用 `invalidate_workflow_detail_cache(workflow_id)`。
- 无效 ID 的失效调用安全返回；该缓存不是跨进程/跨实例共享缓存，也不是一致性锁。

短 TTL 只覆盖管理页面短时间内的重复详情读取。若部署为多进程或多副本，必须改成共享缓存或发布失效事件；不能把本地缓存当作跨实例一致性保证。

## 可观测性契约

详情路由在 `finally` 中写入 `Server-Timing`，阶段顺序固定为：

```text
cache, workflow, nodes, roles, serialize, total
```

每个阶段使用毫秒 `dur` 值；若异常发生在中途，已完成阶段仍可输出，`total` 始终追加。`timings` 是服务层可选参数，业务调用方不传时不承担计时字典开销。

`app/main.py` 将 `Server-Timing` 加入 CORS 暴露头；否则跨域浏览器只能收到响应，前端 JavaScript 无法读取诊断信息。该响应头只用于诊断，不改变 401/404/业务异常语义，也不触发自动重试或降级。

## CodeGraph 调用链证据

```text
GET /api/approve/workflows/{workflow_id}
  -> workflow_route.get_workflow_detail
     -> WorkflowService.get_workflow_detail
        -> _workflow_detail_cache (5s, deepcopy)
        -> Approve_Workflow_Master 字段投影
        -> Approve_Workflow_Detail 字段投影 + NodeLevel 数值排序
        -> Approve_Role_Master IN 批量名称查询
        -> DTO 序列化/缓存
     -> finally: Server-Timing(cache/workflow/nodes/roles/serialize/total)

create_workflow / update_workflow / delete_workflow
  -> commit
  -> invalidate_workflow_detail_cache(workflow_id)
```

CodeGraph 显示 `get_workflow_detail` 的生产入口集中在工作流路由，服务内部的缓存失效由三个写操作复用；测试直接实例化 `WorkflowService` 验证查询次数和缓存行为。迁移时应保持“路由负责 HTTP 头、服务负责查询和缓存、写操作负责失效”的边界。

## 跨项目复用步骤

1. 先定义详情 DTO 的字段白名单，再为主表、节点表和角色表各写一条显式投影查询；不要直接返回带关系的 ORM 实体。
2. 对节点排序使用结构化数值键（例如 `1.2 -> (1, 2)`），不要使用字符串排序；同时固定 BIT/bytes 到布尔值的转换规则。
3. 角色名称等共享维度数据使用去重 ID 的 `IN` 批量查询，确保节点数量增长不会产生 N+1。
4. 在服务实例增加短 TTL 缓存时返回深拷贝，并在所有成功写操作提交后统一调用失效函数；多实例环境改用共享失效机制。
5. 让路由通过可选 timings 上下文输出固定阶段的 `Server-Timing`，并在 CORS 中显式暴露响应头；不要把观测逻辑散落到每条 SQL 或前端页面。
6. 保留投影边界、缓存命中/失效、空节点、软删除和认证依赖测试；查询次数和不加载流程历史关系是可迁移的验收指标。

## 历史边界

- 本提交只优化工作流配置详情读取和 HTTP 诊断，不改变工作流创建/更新业务校验、节点版本规则、审批推进或事件回调语义。
- 详情接口仍返回当前未删除的工作流节点；已运行流程使用的历史节点版本由其它流程服务/CRUD 逻辑负责，本提交未改变其版本选择。
- 缓存是单个 Python 服务实例内的 5 秒快照；不提供跨进程、跨副本或跨客户端一致性。
- `Server-Timing` 仅是可观测性头，不能作为权限、错误处理或性能 SLA 的业务依据。
- 本提交没有新增前端 service；前端若消费 `Server-Timing`，仍需自行处理跨域头缺失和浏览器兼容性。
