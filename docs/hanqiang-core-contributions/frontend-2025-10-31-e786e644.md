## 本次提交建立的前端能力

该提交首次将后端 RBAC 接入 Vue 管理端：新增 `rbac.service.ts`、角色和功能类型、`PermissionTree.vue`、权限指令和 Pinia 用户权限判断，并把全局指令注册、路由元数据和用户管理页面接入同一权限模型。

当前系统已经在此基础上演进：`PermissionTree.vue` 仍存在且有单元测试；角色管理和功能范围配置目前主要使用 `JsePermissionTreeEl.vue`。因此迁移到其它项目时，应选择一个授权树组件作为唯一实现，复用其数据契约而不是同时保留多个树控件。

## 端到端数据流

```text
登录/Token 校验
      ↓
Pinia user store 保存用户、角色和有效 FeatureKey
      ↓
usePermission() / hasPermission()
  ├─ 路由守卫：拒绝无菜单权限的页面访问
  ├─ 导航：过滤无权菜单
  ├─ v-permission：隐藏无权操作
  └─ 角色授权页：读取功能树，提交 feature_ids
      ↓
rbacService -> 后端 /features、/rbac/roles、/users 权限 API
```

前端只负责减少无效操作和改善可用性。所有 API 都必须由后端 `require_permission(...)` 再次校验；删除 DOM、禁用按钮或跳转 `/403` 不是安全控制。

## 功能树组件契约

`PermissionTree.vue` 的可复用公共输入和输出如下：

| 项目 | 契约 |
| --- | --- |
| `treeData` | `FeatureTreeNode[]`，节点至少含 `FeatureID`、`FeatureName`、`FeatureType`，子项为 `children`；当前兼容后端可能返回的 `Children`。 |
| `v-model` | 已选 `FeatureID[]`，用于角色授权提交。 |
| `cascade` | 是否在父子节点间级联选择；启用时计算全选与半选状态。 |
| `flattenButtons` | 是否将按钮权限以内联复选框方式展示，而不是作为独立树行。 |
| `change` | 输出 `(checkedKeys, halfCheckedKeys)`，父组件可据此展示或保存状态。 |

组件按 `FeatureType` 区分 `module`、`menu` 和 `button`，并维护 feature/parent 映射以实现搜索、展开、级联和半选。复用时保留“选中值始终是稳定 ID、显示名称只是文案”的原则；不要用路径或中文名称作为授权写入值。

当前 `RoleDialog.vue` 的完整调用链是：`rbacService.getFeatureTree()` 取树、读取角色的 `feature_ids` 回填、确认后调用 `assignRolePermissions(roleId, { feature_ids })`。这是一条适合复制到新项目的最小闭环。

## 权限状态与路由契约

### 用户状态

`stores/user.ts` 负责持有 token、用户、角色和权限，并向 `usePermission()` 暴露 `hasRole`、`hasPermission`、任一/全部权限判断。应用启动时，`bootstrap.ts` 注册 Pinia、Router、Element Plus 和两个权限指令；发现缓存 token 后会验证 token 并加载最新权限。

统一权限键格式，例如：

```text
menu:roles
role:read:list
role:write:create
role:write:update
```

路由的 `meta.featureKey` 表示页面所属菜单功能，页面操作使用更细粒度的动作键。登录、刷新 token、管理员切换角色或后台修改授权后，都必须刷新用户权限状态；否则路由、按钮和服务端事实会短暂不一致。

### 声明式指令

| 指令 | 输入 | 当前行为 | 合适场景 |
| --- | --- | --- | --- |
| `v-permission` | 一个权限键或权限键数组 | 单键检查；数组按任一满足（OR）；无权限时移除元素。 | 不应出现的危险/无意义操作。 |
| `v-permission-disabled` | 一个权限键或权限键数组 | 无权限时保留元素但禁用。 | 需要让用户理解操作存在但暂不可用的场景。 |

数组是 OR 语义，若界面需要“同时具备多项权限”，应由 `usePermission().hasAllPermissions()` 计算后再用条件渲染，或为指令设计显式的 `all` 选项，不能依赖读者猜测。

## 迁移到其它 Vue 项目的最小清单

1. 定义 `FeatureTreeNode`、`RolePermissionAssignment` 和当前用户权限响应类型；ID 和 `FeatureKey` 必须与后端一致。
2. 封装一层 `rbacService`，只暴露功能树、角色权限读写和当前用户权限读取，不让页面拼装 URL。
3. 在认证恢复完成后再运行路由守卫，避免首屏因权限尚未加载被误重定向。
4. 将 `hasPermission` 作为唯一的客户端判断入口，菜单、路由、指令和页面操作共用它。
5. 在角色编辑中加载功能树和已分配 ID，保存时只提交 `feature_ids`；不要提交整棵树或展示文本。
6. 为树的搜索、级联、半选、外部 `v-model` 更新，以及指令的允许/拒绝/数组场景保留单测。

## 不应原样复制的历史实现

- 当前 `PermissionTree.vue` 含 `@ts-nocheck` 和为旧引用保留的 `collectCascade` 空实现；它们是兼容债务，不是组件 API。新项目应使用完整 TypeScript 类型，并删除无调用的兼容占位。
- `v-permission` 通过移除 DOM 实现隐藏，权限在运行期变化后不一定能自动恢复已移除节点。权限热更新场景优先用响应式 `v-if` 包装或重新挂载权限作用域。
- 前端目前存在旧的 `/permissions`、`/roles/permissions/tree` 和数据库 RBAC 三套接口痕迹。新项目只选择数据库 `Feature` 树及一个前端服务入口，避免权限树来源分裂。
- 前端的层级兼容匹配不能替代服务端精确授权。新项目应先定义一个跨端一致的权限匹配规则，并以服务端实现为准。

## 迁移验收清单

- 首次打开受保护页面时，权限加载完成后再决定放行或跳转，刷新页面行为一致。
- 未拥有权限的用户既看不到/不能操作前端入口，也无法通过直接请求绕过后端。
- 角色授权树回填、父子级联、半选显示和保存后再次加载保持一致。
- 权限键数组在指令和 `usePermission` 中都有明确、测试过的 OR/AND 语义。
- 授权变更后，重新认证或明确刷新权限即可同步菜单、路由和操作控件。
