## 原始端到端链路

```text
/system/enum 路由 + AppSidebar 菜单
        |
        v
EnumManagement.vue
  getCategories() -> getAllEnums()
  按分类分组 -> useEnumTree.buildTree()
        |
        +--> 分类/节点筛选、详情、展开折叠
        +--> EnumFormDialog：创建/编辑
        +--> deleteEnum / enable / disable
        |
        v
enumService.ts
  ApiResponse<T> 解包 + URL 编码
        |
        v
apiClient (JWT 请求头、全局错误处理、原始重试逻辑)
        |
        v

```

管理页不是直接使用后端的 `/tree/{category}`；它先获取分类和全量枚举，再在浏览器按分类重建树。这使页面可以同时展示多个分类，也让树完整性、排序、范围与加载量成为前端必须明确的契约。

## 原始类型与 API 契约

`enumService.ts` 以 `ApiResponse<T>` 统一解包：

```ts
interface ApiResponse<T> {
  code: number
  message: string
  data: T
}
```

`Enum` 保持数据库/API 的 PascalCase 字段，并把 `IsEnabled`、`IsSystem` 声明为 `boolean | number`，兼容 MySQL `BIT(1)` 可能的序列化形式。其它项目应在 API 边界一次性归一为布尔值，而不是让每个组件自行依赖 JS truthy 语义。

| 客户端函数 | 原始请求 | 作用 |
| --- | --- | --- |
| `getCategories` | `GET /enum/categories` | 分类列表。 |
| `getByCategory`、`getTree` | `GET /enum/category/{category}`、`GET /enum/tree/{category}` | 单分类列表/后端树。动态分类以 `encodeURIComponent` 编码。 |
| `getByName`、`getById`、`search`、`batchQuery` | `GET /enum/value/{name}`、`/{id}`、`/search`、`/batch` | 单项、检索和批量读取。 |
| `getAllEnums` | `GET /enum/all` | 管理页的全量数据源；这是后端版本依赖。 |
| `create`、`update`、`deleteEnum` | `POST`、`PUT`、`DELETE /enum` | 管理写操作。 |
| `enable`、`disable` | `PATCH /{id}/enable`、`/{id}/disable` | 单节点状态切换。 |
| `refreshCache`、`clearCache`、`getCacheStatus` | `/enum/cache/*` | 缓存管理接口；原始页面未接入。 |

服务模块直接返回 `res.data.data`，不检查响应壳中的 `code`。这个约定只在 HTTP 非 2xx 与 `code=0` 一一对应时安全；若后端可能以 HTTP 200 返回业务失败，客户端必须在唯一的 API 解包层把它转为 reject，不能让页面把失败载荷当成枚举数据。

## 前端树构建契约

`useEnumTree()` 是原始提交中最可复用的部分：先以 `EnumID` 建 `Map`，再把能找到父节点的项挂到 `children`，其余项作为根节点，最后按 `DisplayOrder` 递归排序。它还提供 `flattenTree()` 和 `findNodeById()`。

| 数据情况 | 原始行为 | 复用时的明确规则 |
| --- | --- | --- |
| 正常父子 | 子节点挂到父节点的 `children`。 | 后端仍应是父子合法性的唯一事实源。 |
| 父节点不在本批数据中 | 项被当作根节点。 | 只能作为“范围过滤导致父节点缺失”的展示策略；应带诊断标记，不能静默掩盖脏数据。 |
| 父子循环 | 环中的节点没有根，最终不会显示。 | 写入前由服务端阻断；前端应显示加载错误/数据异常，而不是把节点无声丢失。 |
| 相同 `DisplayOrder` | 只比较该字段，顺序不稳定。 | 使用稳定次序，例如 `(DisplayOrder, CreateTime, EnumID)`，并与后端排序一致。 |
| 重复 `EnumID` | `Map` 后写覆盖前写，结果不可预期。 | 在 API 数据契约或开发诊断中拒绝重复 ID。 |

当前 CodeGraph 显示 `useEnumTree` 只由 `EnumManagement.vue` 调用，且未发现覆盖测试。抽到新项目时应保持它是纯函数，并为上述异常输入和不改写源数组增加单元测试。

### 管理页的虚拟分类根

`EnumManagement.vue` 为每个 `EnumCategory` 合成一个仅用于显示的根节点：它的 `EnumID` 等于分类字符串，并通过 `isCategoryRoot` 禁止详情、编辑、启停和删除。分类根还用于筛选下拉和父级选择器分组。

这让一个表格可展示多个分类，却混入了两种 ID：真实 UUID 与虚拟分类字符串。复用时应使用判别联合或显式 `kind: 'category' | 'enum'`，不要把虚拟节点传入 `getById`、更新、删除、权限判断或持久化负载。原始页面用 `any[]` 保存树选项和父级选项，类型约束无法防止这一类误用。

页面先顺序调用分类和全量接口，再在每个分类对全量数组做一次 `filter`。分类或枚举数量较大时，这会有多次扫描和较长首屏等待；新项目应视数据量选择服务端树/分页分类加载，或先用 `Map<category, Enum[]>` 单次分组，并允许请求并行。不要无上限地把所有枚举暴露给管理页以换取实现简单。

## 表单与交互边界

原始 `EnumFormDialog` 暴露 `modelValue`、`mode`、`initialData`、`parentOptions`、`parentMeta`、`categories`，并在保存后发出 `saved`。父级一旦选中，就从 `parentMeta` 回填并锁定分类；没有父级时，分类选择支持 `allow-create`，因此新分类由首条枚举项隐式创建。

原始校验与限制如下：

- `EnumCode` 的 UI 和表单规则接受 `0..255`，而 2025-11-27 后端服务实际限制 `0..127`。同一字段在前后端不一致会产生“页面校验通过、提交失败”。
- 只有创建页的 `ParentEnumID` Schema 在后端验证 UUID；页面的父级候选没有主动排除当前节点及其后代，循环最终依赖后端拦截。
- 编辑系统枚举时，页面禁用名称、代码和显示顺序；其余字段仍可能可编辑。此行为只是用户体验，系统项保护必须由服务端执行。
- 创建时页面允许提交 `IsSystem=true`。原始后端路由没有身份/权限依赖，因此不能把该开关交给普通管理用户。
- 原始页面没有分类时直接返回，导致表单的 `allow-create` 无法被使用。`f6ad3e6f`（2026-01-09）才补上空数据时的新建入口。

### 名称唯一性的前端预检缺口

表单在失焦和提交前调用：

```ts
search({ keyword: name, category: form.EnumCategory })
```

然后只检查返回项是否有同名项。原始后端模型却将 `EnumName` 设为全表唯一，且搜索会应用分类筛选。因此另一个分类存在同名项时，前端可能预检通过，服务端才拒绝写入。

新项目应选定一种语义：

1. 全局唯一：预检不传分类，或者干脆只把客户端检查作为提示，最终以服务端 409 为准。
2. 分类内唯一：数据库和 API 都使用 `(EnumCategory, normalizedName)`，并要求全部查询调用方携带分类。

无论哪种，前端预检都不能作为正确性或并发控制。网络错误时原始实现把“校验失败”视为不可提交；更稳妥的做法是提示预检不可用，但让服务端进行最终校验并返回可读冲突信息。

## 权限与菜单边界

原始路由声明了：

```text
path: /system/enum
permissions: [enum:read:list]
featureKey: menu:enum_management
componentPath: EnumManagement
```

模板中的 `data-component-path` 与 `data-permission-key` 是页面元数据，能支持扫描、翻译和 UI 约定，但不是授权。所有写按钮仍须依赖路由/权限指令控制可见性，以及后端 API 的实际 `require_permission`。

原始 `AppSidebar.vue` 对 `enum_management` 和 `system-settings` 特判为可见，绕开了自己的菜单权限判断；而当时的后端首版也尚未给 `/api/enum` 加认证或授权。路由守卫可以拦住常规前端导航，却不能保护直接请求 API。复用时应删除这种“菜单永远可见、假定后端已保护”的分叉逻辑：菜单、路由和 API 应使用同一权限键注册表，API 作为最终安全边界。

权限设计还要区分后台管理与业务消费：业务表单的非敏感枚举下拉，不应因为用户没有“枚举管理”页面权限而失效；有租户、工厂或密级范围时，读接口需在服务端按范围过滤，而不是依赖前端隐藏分类。

## 同次提交的全局重试风险

原始 `src/services/api.ts` 为“无响应或 5xx”统一增加最多两次重试，等待 1 秒、2 秒。它不区分 HTTP 方法，并且在取消请求判断之前决定是否重试。

这会把 `POST /enum`、`PUT`、`PATCH`、`DELETE` 与所有其他业务写请求一起重放。若服务器已完成写入但响应在网络中丢失，重试可能创建重复数据、重复触发外部副作用，或覆盖后续更新。取消的请求也可能先进入重试分支。

新项目的最低安全策略：

- 默认只自动重试 `GET`、`HEAD`、`OPTIONS`，并先排除取消、离线、认证失败和业务 4xx。
- 写请求只有在服务端支持幂等键、去重记录或条件版本号时才可重试；幂等键必须随重试保留，不应每次生成新值。
- 重试逻辑先检查 `AbortSignal` / cancel，再按方法、状态码、`Retry-After` 和最大总时限决定等待；登录排除规则应匹配 `config.url` 的真实形式，而非猜测 `baseURL` 已拼接后的字符串。
- 请求重试、超时和用户提示应集中在 API 客户端，页面只处理业务错误和 loading 状态。
