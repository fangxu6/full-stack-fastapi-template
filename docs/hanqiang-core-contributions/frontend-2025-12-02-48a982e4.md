## 原始前端链路

```text
AppSidebar 菜单
  -> router: /wxwork/configs | /wxwork/templates | /wxwork/send-logs
  -> 三个管理页：加载、筛选、表单、详情、状态提示
  -> wxworkApi（Axios 客户端）
  -> 后端 /api/wxwork/*
  -> 配置 / 模板 / 发送主日志 / 发送尝试明细
```

| 路由 | `featureKey` | 页面职责 |
| --- | --- | --- |
| `/wxwork/configs` | `menu:wxwork_config` | 配置企业微信应用、测试连接、启停。 |
| `/wxwork/templates` | `menu:wxwork_template` | 管理卡片 JSON、参数和渲染预览。 |
| `/wxwork/send-logs` | `menu:wxwork_send_log` | 查询投递结果、查看尝试明细、发起人工重试。 |

`featureKey`、菜单显示、路由守卫和按钮禁用只负责前端体验；发送、读取日志、修改模板与查看配置仍必须由后端动作权限保护。不要把“用户看不到菜单”当成访问控制。

## 原始类型和客户端契约

首版的 `wxworkApi` 把所有调用集中起来，避免页面自行拼 URL。它返回 Axios 原始响应，页面再读取 `response.data`；新项目应在服务层统一解包成功壳和错误壳，页面只接收领域 DTO，避免每页猜测 `data/items/records` 层级。

| 客户端方法 | 原始请求 | 说明 |
| --- | --- | --- |
| `getConfigs`、`createConfig`、`updateConfig`、`deleteConfig` | `GET`、`POST`、`PUT`、`DELETE /wxwork/configs` | 配置列表和 CRUD。创建类型将读 DTO 与写入 `Secret` 混在一起。 |
| `testConfig`、`toggleConfig` | `POST /configs/{id}/test`、`PATCH /configs/{id}/toggle` | 连接测试和启停；`toggleConfig(id, isActive)` 的形参仍叫 `isActive`，但 body 实际为 `{ is_enabled }`。 |
| `getTemplates`、`createTemplate`、`updateTemplate`、`deleteTemplate` | `/wxwork/templates` | 模板 CRUD。 |
| `testTemplateSend`、`toggleTemplate` | `POST /templates/{id}/test-send`、`PATCH /templates/{id}/toggle` | 前者只请求后端渲染，不会投递到企业微信；后者同样保留 `isActive` 形参命名残留。 |
| `sendMessage` | `POST /wxwork/send` | 传 `config_code`、`template_code`、`dynamic_data`、`recipient_config`。首版后端虽然响应 202，实际会同步发送。 |
| `getSendLogs`、`getSendLogDetail`、`retrySendLog` | `/wxwork/send-logs` | 日志列表、尝试详情和人工重试。 |

初版读 DTO 使用后端 PascalCase，如 `ConfigID`、`TemplateCode`、`IsEnabled`、`SendStatus`；发送请求却使用 snake_case。新项目可以选择任一种统一风格，但必须在一个 API 适配层完成转换，不能让每个页面同时操作 PascalCase、camelCase 和 snake_case。

### 首版 DTO 的业务含义

| DTO | 关键字段 | 前端规则 |
| --- | --- | --- |
| `WXWorkConfig` | `ConfigCode`、`AgentID`、`IsEnabled`、`TokenExpiredTime` | 列表不能包含 `Secret` 和 Token。写入时单独声明 `CreateConfigRequest`、`UpdateConfigRequest`，不要用 `Partial<ReadModel>`。 |
| `WXWorkTemplate` | `TemplateType`、`CardContent`、`ParamDefinitions`、`Version`、`IsEnabled` | `CardContent` 是对象而非 textarea 字符串的事实源；编辑器只在输入边界解析/序列化。 |
| `ParamDefinition` | `param_name`、`param_type`、`required`、默认值、描述 | 后端仍须作最终校验，页面只能做即时提示。 |
| `SendLog` | 模板、动态数据、接收人、状态、错误、重试、渠道消息 ID 和 `details` | 这是审计数据，不是可无条件展示的普通业务记录；动态数据和接收人要做字段级脱敏。 |
| `TemplateTestSendResponse` | `rendered`、`test_user` | 应命名为“渲染预览”；`test_user` 在首版仅回显，不代表任何人收到消息。 |

## 三个页面的复用契约

### 配置管理

配置页应区分“可安全展示的配置元数据”和“仅一次写入的密钥”：

- 列表只显示编码、名称、`AgentID`、启用状态、更新时间和脱敏后的连接状态；编辑既有配置时默认不回填 `Secret`。
- “测试连接”是有副作用的管理动作，按钮应有独立 loading、防连点和失败文案，不应把 Token 或渠道原始响应渲染到页面。
- 启用/禁用需乐观更新前保存旧值，失败时回滚并提示；发送端必须以服务端实时状态为准。
- 删除前显示关联模板/未完成日志的影响。若服务端是软删除，页面不能把历史日志当作不存在。

### 模板管理和 JSON 编辑

首版模板页负责维护卡片 JSON 和 `{{variable}}` 占位符。可复用的重点不是某个 Element Plus 表单，而是三项边界：

1. 输入时只做 JSON 解析、格式化、必填/长度提示；保存时保留服务端返回的版本和参数定义，不能由浏览器宣称模板一定可发送。
2. “测试发送”在首版仅渲染卡片，页面文字、结果态和测试报告必须称为“预览”或“渲染校验”，不能显示“发送成功”。真实测试投递必须是另一条显式 API，并选择隔离的测试接收人。
3. JSON 预览中的动态数据、URL 和可点击链接属于不可信内容。不要用 `v-html` 直接渲染任意字符串；展示前做结构校验、转义和链接白名单处理。

当后端采用结构化模板渲染时，前端同样应把 JSON 解析为对象再编辑。不要自行用正则把用户输入拼回 JSON 字符串，否则带引号、反斜杠或换行的变量会让预览和实际消息出现不同结果。

### 发送日志和人工重试

日志页的最小状态流应为：提交后展示“已受理（含 `log_id`）”，刷新或轮询直到终态，再展示 `SUCCESS`、`FAILED` 或 `PARTIALLY_FAILED` 及最新 attempt。`202` 只说明服务接受任务，不等于渠道已送达；如果后端仍同步发送，则页面不能伪造异步进度。

- 日志筛选要与后端参数一致：首版为 `template_code`、`send_status`、`start_time`、`end_time`、`page`、`page_size`。筛选切换、分页和刷新不能丢失当前条件。
- 详情区分逻辑发送和每次 attempt；状态、渠道错误码、失败摘要、重试次数和时间应来自 API，不要在浏览器自行推断。
- 只对服务端允许的失败/部分失败记录显示重试；提交期间禁用按钮，成功后重载详情和列表，失败后保持旧数据并显示可读错误。
- 默认展示脱敏的接收人和动态参数。查看原文、导出或用自定义接收人重试应是独立权限和可审计动作。

首版的后端人工重试只投递 Celery 占位任务，不能保证真的再次发送；因此首版页面的“重试已提交”只能代表请求已接受，不能直接标为“重试成功”。

## `is_active -> is_enabled` 前端迁移

该提交同时改动用户、员工、邮件目标、邮件模板、权限树、菜单与本地用户状态。页面字段替换如果只改开关文字，会留下 API payload、筛选条件、本地缓存和路由权限中的旧契约。

推荐迁移顺序：

1. **确认语义。** `is_enabled` 表示可用状态，不要替代已删除、锁定、审批中或在线状态；不同资源的禁用行为需要产品定义。
2. **统一边界类型。** API 读 DTO、表单值、筛选 query 和写入 payload 都使用 `is_enabled`；对后端 PascalCase 字段只在 adapter 中映射。布尔值必须归一，不能依赖 MySQL `BIT(1)`、`0/1` 或字符串的 truthy 行为。
3. **迁移持久化客户端状态。** 当前用户 store、JWT 解码缓存、`localStorage`、URL query、草稿、导入导出和离线队列都要识别旧 `is_active`。过渡期可读取 `is_enabled ?? is_active`，但新写入只写 `is_enabled`，并记录旧值命中量。
4. **同时发布服务端。** 前端字段替换必须与后端 model、Schema、认证、权限依赖、邮件/通知收件人过滤的版本兼容；隐藏/禁用控件不能取代服务端验证。
5. **删除兼容。** 缓存 TTL、旧前端活跃版本和外部消费者都越过窗口后，再移除别名和旧字段搜索结果。

首版服务客户端的 `toggleConfig` / `toggleTemplate` 仍以 `isActive` 命名参数，这是重命名未完成的信号。复用代码时应直接改为 `isEnabled`，并为请求 body 和列表筛选写一条契约测试，防止再次把旧字段传到后端。

## API、权限与可靠性边界

- 权限信息可用于菜单和按钮可见性，但读取配置、维护模板、查看日志、发送、测试和重试必须由 API 独立拒绝无权请求。数据有组织/租户范围时，前端 query 不能代替服务端范围过滤。
- 全局 HTTP 重试不能无差别重放 `POST /wxwork/send`、模板写入和重试请求。只对安全读请求重试；若写操作需要网络重试，必须与服务端幂等键协同。
- 配置、模板和日志接口的响应壳、分页格式、时间格式和错误格式要统一。首版配置/模板使用 `skip/limit`，日志使用 `page/page_size`，这是后续维护成本，不是值得复制的灵活性。
- 前端收到网络超时不代表消息未发出。保留并查询 `log_id`，而不是自动再发一次；用户必须看见“结果未知，正在核对”的状态。

## 不能原样复制的历史行为

| 首版行为 | 风险 | 新项目要求 |
| --- | --- | --- |
| `POST /send` 视为异步入队 | 配套后端实际同步直发，页面进度和重复提交判断会错误。 | 依后端真实 outbox/worker 契约实现轮询；否则明确显示同步提交中。 |
| `test-send` 被称为测试发送 | 后端只渲染并回显，用户可能误以为收到企业微信。 | 文案为“渲染预览”；真实发送另设受控 API。 |
| 写 DTO 使用 `Partial<WXWorkConfig>` | 容易把服务端生成字段、Secret 或 Token 误传/误展示。 | 读写 DTO 分离，Secret 只在新值提交时出现。 |
| 状态切换参数仍叫 `isActive` | 新旧契约混用，重构时易发错字段。 | 全链路改为 `isEnabled` / `is_enabled`，只在兼容 adapter 保留旧别名。 |
| 直接展示动态数据、接收人、错误详情或渠道响应 | 可能泄露 PII、业务内容和 Token。 | 字段分级脱敏；敏感明细需独立权限、审计和最小展示。 |
| 仅靠菜单/按钮权限 | 可绕过 UI 直接调用 API。 | API 为安全边界，前端只做体验控制。 |
| 页面各自处理 Axios 响应壳和失败 | 后端演进到 V1/list 后易出现空表、总数错误或误报成功。 | 一个服务 adapter 统一解包、归一分页和翻译错误。 |

## 迁移验收清单

- [ ] 菜单、三条路由、按钮权限和 API 权限键一致；无权限直接请求 API 必定被拒绝。
- [ ] 配置读 DTO 永不含 Secret/Token；创建、更新、测试连接和删除各自有 loading、取消、失败和审计反馈。
- [ ] JSON 模板可格式化、校验、保存、预览；特殊字符变量不会破坏 JSON；预览明确不代表投递成功。
- [ ] 所有列表分页、筛选、时间格式、错误壳和布尔值都经过一个 API adapter；页面不自行猜测响应结构。
- [ ] 发送后以 `log_id` 查询真实状态；超时、刷新、重复点击、部分成功、未知结果和失败重试的 UI 行为明确。
- [ ] 日志详情默认脱敏，敏感内容、自定义接收人重试和导出有独立权限及操作记录。
- [ ] `is_enabled` 已覆盖类型、表单、query、写入 payload、store、缓存、URL 与导入导出；旧 `is_active` 的兼容读取有到期删除计划。
- [ ] 自动请求重试不会无幂等保证地重放发送、模板写入、删除或人工重试。
- [ ] 管理页面及模板/发送调用方完成契约回归，特别验证后端从首版接口演进至 V1/list 或自定义接收人重试后的兼容性。
