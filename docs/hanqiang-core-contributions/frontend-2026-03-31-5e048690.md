## 3. 类型契约

提交前：

~~~ts
const hasAnyPermission = (permissions: string[]): boolean => {
  return permissions.some(permission => hasPermission(permission))
}
~~~

提交后：

~~~ts
const hasAnyPermission = (permissions: readonly string[]): boolean => {
  return permissions.some(permission => hasPermission(permission))
}
~~~

四个方法的运行时语义保持不变：

| 方法 | 规则 | 空数组结果 |
| --- | --- | --- |
| hasAnyRole(roles) | 至少一个角色通过 hasRole | false |
| hasAllRoles(roles) | 所有角色都通过 hasRole | true（every([])） |
| hasAnyPermission(permissions) | 至少一个权限通过 hasPermission | false |
| hasAllPermissions(permissions) | 所有权限都通过 hasPermission | true（every([])） |

readonly 是 TypeScript 编译期约束：

- 普通 string[] 仍可传入。
- as const 元组、ReadonlyArray<string>、只读 props 和冻结配置可以直接传入。
- 函数体不能使用 push、splice 等修改操作。
- 不会在运行时调用 Object.freeze，也不会改变数组对象。

标量接口 hasRole(role: string) 和 hasPermission(permission: string) 没有改变。本提交解决的是候选列表可变性，不是服务端权限载荷格式。

## 4. 典型问题与调用方式

权限候选常量通常写成：

~~~ts
const CREATE_PERMISSIONS = [
  'feature:write:create',
  'menu:feature'
] as const
~~~

旧签名下，直接传入只读元组可能报错，需要无意义的展开复制：

~~~ts
hasAnyPermission([...CREATE_PERMISSIONS])
~~~

提交后可以直接传入：

~~~ts
const canCreate = computed(() =>
  hasAnyPermission(CREATE_PERMISSIONS)
)

function canAccess(candidates: readonly string[]) {
  return hasAnyPermission(candidates)
}
~~~

迁移时不应为满足旧类型到处创建 [...permissions] 副本；只读签名既保留普通数组兼容性，也让调用方明确“此函数只读取候选集合”。

## 5. 与权限状态和安全边界的关系

### 5.1 候选集合不等于用户权限载荷

| 概念 | 例子 | 本提交是否改变 |
| --- | --- | --- |
| 调用方候选集合 | ['feature:read:list', 'menu:feature'] as const | 是，只读集合可传入 |
| 用户接口权限载荷 | ['feature:read:list'] 或 { 'feature:read': true } | 否，仍由 useUserStore 解析 |
| 单个权限判断 | hasPermission('feature:read:list') | 否 |
| 后端 API 鉴权 | 端点的角色、权限和数据范围校验 | 否 |

hasAnyPermission 只是遍历候选键并调用标量 hasPermission，不会把传入数组当成“已拥有权限”，也不会绕过管理员、通配符、权限版本或缓存。

### 5.2 空集合策略必须明确

JavaScript 的 some([]) 是 false，every([]) 是 true：

- hasAnyPermission([]) 适合表示“没有任何候选权限则不可见”。
- hasAllPermissions([]) 会返回 true；如果产品语义要求空配置拒绝，调用方必须先判断数组非空。
- 角色方法同理。不要在公共 composable 中偷偷改变空数组语义。

### 5.3 前端不是安全边界

usePermission 只控制按钮、菜单或页面入口的显示/禁用。后端仍需对每次请求执行认证、角色、权限和数据范围校验；只读数组签名不会增加授权能力。

## 6. 跨项目迁移步骤

1. 确认函数只读性：只有实现不修改入参时，才使用 readonly string[]。
2. 在权限 composable 或等价 helper 的四个批量方法上一次修改公共签名。
3. 保留已有可变数组兼容；删除为绕过旧签名而存在的展开复制。
4. 权限候选集合优先使用 as const 或 ReadonlyArray<string>。
5. 把空数组的 any/all 结果写入调用方测试或产品约定。
6. 不要把本提交扩展为修改用户 store 的权限载荷解析、缓存刷新、管理员绕过或 API schema。
7. 如果公共包生成 .d.ts，确认声明文件也暴露 readonly string[]。
8. 补一个只读元组类型样例，并运行既有角色/权限单元测试。

## 7. 可复用实现模板

~~~ts
export function usePermission() {
  const userStore = useUserStore()

  const hasAnyRole = (roles: readonly string[]): boolean =>
    roles.some(role => userStore.hasRole(role))

  const hasAllRoles = (roles: readonly string[]): boolean =>
    roles.every(role => userStore.hasRole(role))

  const hasAnyPermission = (permissions: readonly string[]): boolean =>
    permissions.some(permission => userStore.hasPermission(permission))

  const hasAllPermissions = (permissions: readonly string[]): boolean =>
    permissions.every(permission => userStore.hasPermission(permission))

  return {
    hasAnyRole,
    hasAllRoles,
    hasAnyPermission,
    hasAllPermissions
  }
}
~~~

模板只展示本提交的类型边界；真实项目仍应保留自己的响应式状态、管理员规则、缓存失效和错误处理。不要因参数只读而在这里新增权限推导或服务端调用。
