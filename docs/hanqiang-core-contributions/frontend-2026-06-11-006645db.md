## 3. Composable 契约

```ts
type ListRefreshHandler = () => void | Promise<void>

interface UseListRefreshOptions {
  refreshOnActivated?: boolean // 默认 true
  skipFirstActivate?: boolean  // 默认 true
}

const { refreshList } = useListRefresh(refresh, options)
```

行为规则：

1. `refreshOnActivated=false` 时不注册激活刷新，但仍返回可供按钮调用的 `refreshList`。
2. `skipFirstActivate=true` 时首次 `onActivated` 只记录已激活，不调用 refresh；之后每次激活调用一次。
3. `skipFirstActivate=false` 时首次激活也调用 refresh。
4. `refreshList()` 使用 `void refresh()` 触发同步或异步处理，不向模板暴露未处理 Promise。
5. composable 不管理 loading、错误提示、分页重置或请求取消；这些仍由页面的 refresh handler 负责。

该设计依赖 Vue `onActivated`，只有组件被 `<KeepAlive>` 缓存并重新激活时才会触发。未被缓存、每次路由都重新挂载的页面不会通过该钩子获得额外刷新，应在 `onMounted` 或路由守卫中完成首次加载。

## 4. CodeGraph 调用链

```text
KeepAlive 缓存标签切换
  -> Vue onActivated()
  -> useListRefresh.refreshList()
  -> 页面 refresh handler
       ├─ MyProcesses.fetchList()
       ├─ PendingApprovals.fetchPending()
       ├─ StudentExamList.fetchExamList()
       └─ StudentLearningPage.handleRefresh() -> loadPlanList()

手动刷新按钮 / 空状态重试 / 审批成功
  -> 同一个 refreshList()
```

`PmsPageShell` 还形成一层组件转发：`JsePageShell @refresh → PmsPageShell refreshList → emit('refresh') → 页面加载函数`。因此 Shell 不应直接请求 API，页面仍是数据加载和错误处理的所有者。

## 5. 各页面的特殊边界

### 5.1 审批页面

- `MyProcesses` 直接把刷新按钮和空状态操作改为 `refreshList`，保留原 `fetchList()` 的分页、权限和错误处理。
- `PendingApprovals` 在 `hasDeepLinkTarget` 为真时跳过普通列表刷新，避免打开带 `process_id/process_node_id` 的深链时覆盖定向解析；审批弹窗成功后再调用同一刷新入口。
- 刷新只更新列表事实，不改变审批授权。详情抽屉和审批动作仍须由后端权限、流程状态和节点状态校验。

### 5.2 培训页面

- `StudentExamList` 的手动刷新改为 `refreshList`，保留 `loadingList` 禁用和考试 store 会话恢复逻辑。
- `StudentLearningPage` 以 `refreshPlanList` 别名接入，统一刷新计划、考试概览和报告状态概览；课件完成、报告提交成功等已有调用仍可直接触发 `loadPlanList()`，迁移时可逐步收敛到别名。

### 5.3 PMS Shell

`PmsPageShell` 不知道具体列表 API，只把 `JsePageShell` 的刷新事件转成 `emit('refresh')`。任何使用该 Shell 的页面都应提供幂等、可重复调用的 refresh listener，并自行维护请求竞态和 loading 状态。

## 6. 测试契约

提交新增 `src/composables/__tests__/useListRefresh.spec.ts`，通过 `KeepAlive` 测试：

| 场景 | 断言 |
| --- | --- |
| 首次挂载/激活 | 默认不调用 refresh。 |
| 切换到其它组件再切回列表 | refresh 恰好调用一次。 |
| 点击返回的 `refreshList` 按钮 | refresh 调用一次。 |
| `skipFirstActivate=false` | 首次激活调用一次。 |

建议在复用项目中再增加：异步 reject 不被全局 unhandled rejection 污染、快速切换时的请求取消/序列号、组件卸载后不更新状态、刷新按钮 loading 与重复点击保护。

## 7. 跨项目迁移步骤

1. 确认应用使用 Vue `KeepAlive` 或等价的缓存标签机制，并定义“首次加载”和“再次激活”的产品语义。
2. 复制 `useListRefresh`，保持 handler 只接收一个无参刷新函数；把分页、筛选、权限和错误处理留在页面。
3. 将页面的手动刷新、空状态重试、保存/审批成功后的 reload 统一指向 `refreshList`。
4. 对公共 Shell 只做事件转发，不在 Shell 内引入 API 或页面状态。
5. 为每个列表补充首次激活/再次激活测试；对深链、详情页和非缓存路由明确例外。
6. 若 refresh 需要取消旧请求或保证最新响应获胜，在页面 service 层加入 AbortController/请求序列号；不要把并发策略偷偷塞入通用 composable。

## 8. 不能原样复制的历史行为

- `void refresh()` 不会等待或处理 reject；如果项目的 refresh 可能抛出异常，应在页面 handler 内捕获并展示错误，或由统一请求层处理。
- `skipFirstActivate` 只按组件实例记录，组件被真正卸载后重新创建会再次跳过首次激活；需要跨标签持久化时应使用路由/Pinia 时间戳，而不是修改 composable 的局部 ref。
- 自动刷新没有节流、去抖或最小间隔；高频标签切换场景需在请求层增加缓存/取消策略。
- composable 不判断页面是否仍有深链、未保存表单或正在编辑；这些业务条件必须由调用方决定（如 `PendingApprovals` 的深链保护）。
- 手动刷新不会自动重置筛选和页码；只有产品明确要求时，才在页面 refresh handler 中重置。

## 9. 与现有标签和权限体系的关系

CodeGraph 显示 `useNavigationTabs` 负责路由切换、标签身份和 `isTabbableRoute` 判断，`useListRefresh` 只监听 Vue 激活生命周期，两者没有共享状态。迁移时不要在刷新 composable 中直接操作标签 store。

页面刷新仍应遵循现有权限边界：

- 前端可在 refresh handler 中检查 `hasPermission`，改善提示和避免无效请求；
- 路由守卫和后端 API 才是最终访问控制；
- 切回标签时若权限/用户状态已变化，刷新失败应清理或提示，而不是静默显示旧缓存数据。

## 10. 复用验收清单

- [ ] 使用 KeepAlive 的列表首次激活不重复请求，切回时恰好触发一次刷新。
- [ ] 手动按钮、空状态重试、保存/审批成功回调使用同一个 refresh action。
- [ ] refresh handler 自行处理 loading、错误、分页、筛选、取消和请求竞态。
- [ ] 深链、详情抽屉、未保存编辑和非缓存页面不会被自动刷新误伤。
- [ ] 公共 Shell 只转发 refresh 事件，不持有 API 或业务状态。
- [ ] 异步 refresh 的 reject 可观测且不会产生 unhandled rejection。
- [ ] 路由/菜单/后端权限仍是事实源，缓存列表不会绕过权限变化。
- [ ] Vitest 覆盖首次激活、再次激活、手动调用和选项开关。
