## 问题与解决契约

### 动态导入失败恢复

Vite 将页面路由写成 `component: () => import(...)` 的懒加载模块。部署更新后，旧标签页可能仍请求已失效的 chunk，浏览器通常抛出以下错误之一：

- `Failed to fetch dynamically imported module`
- `Importing a module script failed.`

`isDynamicImportFetchError(error)` 只匹配这两个错误文本（大小写不敏感），其它网络错误、业务错误或普通导航失败返回 `false`，交由原有错误处理继续处理。

`recoverDynamicImportFailure(error, targetFullPath)` 的行为是：

1. 非动态导入错误直接返回 `false`，不刷新页面。
2. 动态导入错误先把目标路径解析为绝对 URL。
3. 若 `sessionStorage['jse:route-dynamic-import-recovery']` 尚未记录该 URL，则写入 URL 并调用 `window.location.assign(targetUrl)`，让浏览器重新获取入口和 chunk。
4. 若同一 URL 已记录，说明整页恢复仍失败；不再调用 `assign`，仅提示“页面加载失败，请刷新浏览器后重试。”，从而避免无限刷新循环。
5. 任意成功导航在 `router.afterEach` 中调用 `clearDynamicImportRecovery()`，删除旧标记；下一次独立故障仍可恢复一次。

这是“同一目标 URL、同一会话最多一次”的恢复策略，不是通用重试器，也不保证 CDN、Service Worker 或部署版本最终一致。跨标签页共享 `sessionStorage` 不是目标，跨客户端也不会互相去重。

### 导航 Tab 一致性

`useNavigationTabs` 新增内部 `pushRoute(location): Promise<boolean>`：

```text
router.push(location)
  ├─ 成功 -> true
  ├─ 动态导入失败 -> false（router.onError 负责整页恢复）
  └─ 其它错误 -> 继续抛出
```

以下操作都只有在 `pushRoute` 返回 `true` 后才改变 Tab store：

- `openRouteInTab`：导航成功后才同步当前路由，失败返回 `false`。
- `activateTab`：导航成功后才设置 active Tab。
- `closeTab`：活动 Tab 只有在成功导航到 fallback 后才关闭；非活动 Tab 仍可直接关闭。
- `closeAllTabs`：只有成功导航到保留的非关闭 Tab 后才批量关闭。
- `replaceCurrentRouteInTab`：目标路由加载失败时直接返回，不关闭来源 Tab。

因此一次失效 chunk 不会留下“地址栏仍在旧页面、Tab 却已切换/删除”的半完成状态。调用方若关心结果，应处理 `openRouteInTab` 返回的 boolean；旧的 `void` 调用方式仍可兼容，但无法感知失败。

## CodeGraph 调用链证据

```text
懒加载路由 component: () => import(...)
  -> router.push()
  -> Vue Router onError
  -> recoverDynamicImportFailure(error, to.fullPath)
     -> sessionStorage 标记
     -> window.location.assign(targetUrl)（首次）
     -> ElMessage.error（同 URL 再次失败）

AppTabs / 页面导航调用
  -> useNavigationTabs.openRouteInTab / activateTab / closeTab / closeAllTabs
  -> pushRoute
  -> isDynamicImportFetchError
  -> 成功后才写入 navigationTabs store
```

CodeGraph 显示 `useNavigationTabs` 被 `AppTabs` 以及多个审批、Tooling、培训页面调用；恢复工具的生产调用点只有 `src/router/index.ts`，测试分别覆盖工具和 Tab 行为。不要把该恢复逻辑复制到每个菜单点击处理器。

## Vite 依赖预构建边界

本提交将 `optimizeDeps.include` 从仅包含 `xlsx` 调整为 `dayjs`、`xlsx`。目的是在开发服务器启动时预构建两个会被懒加载页面首次使用的第三方依赖，降低菜单跳转时触发依赖哈希变化、旧页面请求到失效模块的概率。

`optimizeDeps` 不是运行时恢复机制：它不能替代 `router.onError`，也不保证生产 CDN 部署或浏览器缓存永远一致。当前 `vite.config.ts` 可能已由后续提交继续扩充依赖列表，复用时应以目标提交的差异为准，不要把后续列表误归因于本提交。

## 测试覆盖

- `routeDynamicImportRecovery.spec.ts`：识别两类浏览器错误；首次失败调用一次 `location.assign`；同一 URL 第二次只提示不刷新；调用 `clearDynamicImportRecovery()` 后允许再次恢复。
- `useNavigationTabs.spec.ts`：`router.push` 抛出动态导入错误时，`openRouteInTab` 返回 `false`，当前 Tab 仍为 Dashboard，目标路由没有写入 Tab store。
- 其它导航测试继续覆盖关闭活动 Tab、关闭全部 Tab、来源 Tab 保护和显式空查询行为；这些不是本提交新增的恢复规则。

## 跨项目复用步骤

1. 在共享路由工具中集中定义动态导入错误识别函数，只匹配目标浏览器和构建工具实际产生的错误文本，并为新增浏览器文案补测试。
2. 在 Router 实例的错误钩子中调用恢复函数；用“目标绝对 URL + 会话存储标记”限制同一目标只整页恢复一次，成功导航后清理标记。
3. 把所有 Tab 导航入口收敛到一个 `pushRoute` 包装器：识别动态导入失败返回 `false`，其它异常继续抛出；只有成功才提交 Tab store 变更。
4. 对关闭、替换、激活等有副作用的操作采用“先导航、后修改状态”；导航失败时保留来源 Tab 和 active key。
5. 在 Vite 开发配置中只预构建确实会由懒加载路径首次使用且容易触发依赖重建的包；不要把完整依赖树无条件加入 `optimizeDeps`。
6. 分别保留恢复工具测试和 Tab 状态测试；不要只测试 `location.assign`，还要验证重复失败不会进入刷新循环。

## 历史边界

- 本提交只处理前端懒加载模块失效后的恢复和导航 Tab 一致性，不改变后端 API、权限守卫、登录状态或业务路由定义。
- `router.onError` 只对匹配的动态导入错误执行恢复；401/403、权限拒绝、业务异常和普通网络错误仍走原有流程。
- `window.location.assign` 会触发整页导航，未引入 Service Worker、版本清单、缓存失效 API 或自动多次重试。
- `vite.config.ts` 中后续新增的其它 `optimizeDeps` 包不属于 `a9032985`；迁移时只复制本提交明确的 `dayjs`/`xlsx` 预构建意图。
