## 问题与解决契约

### KeepAlive 缓存 Tab 的 route 隔离

`AppLayout` 的缓存分支现在是：

```text
router-view slot (Component, viewRoute)
  -> shouldCacheRoute(viewRoute)
  -> KeepAlive :max="30"
  -> TabRouteScope :route-component="Component" :route="viewRoute"
     :key="resolveRouteViewKey(viewRoute)"
```

`TabRouteScope` 不直接修改全局 Router，而是：

1. 以 `shallowReactive({ ...props.route })` 创建当前缓存实例的 route 快照。
2. 监听 `props.route`，在活动实例的路径、参数或查询变化时 `Object.assign` 更新快照。
3. 通过 Vue Router 的 `routeLocationKey` 提供该快照，使子页面调用 `useRoute()` 时读取所属 Tab 的 route。
4. 用 `routeComponent` 渲染原始页面组件，保持页面本身无需改造。

这样被 `KeepAlive` 保留的旧 Tab 不会因为全局当前路由切换而读取新 Tab 的参数；活动 Tab 仍能响应自身 query 更新。非缓存路由继续使用 `:is="Component"` 和 `viewRoute.fullPath`，不引入额外作用域。

这是“每个缓存实例一份浅层 route 作用域”的方案，不复制 Router、Pinia 或页面状态。若页面把深层 `route.meta` 或自定义对象原地修改，应继续遵循 Router 的只读约定；该组件只负责隔离引用和响应式更新。

### 审批流程详情的请求去重与过期响应保护

`ProcessDetail.vue` 的 `loadPage(targetProcessId)` 以 `[route.name, targetProcessId, processNodeIdQuery]` 生成签名，并维护：

- `pendingPageLoad`：同一签名已有请求时直接返回同一个 Promise，重复刷新不会再发起详情请求。
- `latestPageLoadVersion`：每次新签名加载递增版本。
- `isCurrentPageLoad(signature, version)`：只有签名和版本都仍为最新时，异步响应才能写入详情、上下文、父流程、工作流详情、加载状态或 Tab 标题。

加载顺序保持为：流程详情 -> 待审批/我的流程上下文 -> 可选父流程详情 -> 工作流详情。任一旧请求在路由参数切换后返回，都会被丢弃，不清空或覆盖当前 Tab 的数据；错误提示也只对当前请求生效。无 `processId` 时会递增版本并结束 loading，阻止旧请求继续提交结果。

### PMS 清单提交页的请求去重与过期响应保护

`useWorkOrderChecklistSubmitPage` 以 `workOrderId` 作为进行中请求的复用键，并使用 `latestChecklistLoadVersion` + `isChecklistLoadCurrent()` 保护状态写入：

```text
loadChecklistPage()
  ├─ 无 workOrderId -> 递增版本、结束 loading
  ├─ 同一工单已有 pending Promise -> 直接复用
  └─ 新工单/刷新
       -> loadWorkOrderDetail
       -> 并发 loadChecklist / 模板详情 / 操作记录 / 附件
       -> 仅最新工单版本写入表单、草稿、附件和路由动作状态
```

运行清单、共享模板、操作记录和附件仍并发请求；改动只增加请求生命周期控制，不改变这些服务的接口或业务字段。旧工单响应不会覆盖新工单，当前工单的错误才会清空页面状态并提示用户。

## 测试覆盖

- `TabRouteScope.spec.ts`：初始 `A:1`，活动 Tab query 更新为 `A:2`，切换到 `B:3` 后事件序列为 `A:1 -> A:2 -> B:3`，证明缓存实例不会共享错误 route。
- `ProcessDetail.spec.ts`：将详情请求挂起，连续触发两次“立即刷新”，断言 `getProcessDetail` 只调用一次；请求完成后继续完成页面加载。
- `WorkOrderChecklistSubmit.spec.ts`：连续刷新清单页时详情请求只执行一次，详情完成后运行清单请求仍只执行一次。
- 页面测试补充的 `router.onError` mock 仅用于兼容应用 Router 已注册的错误钩子，不代表本提交修改了动态导入恢复逻辑。

## 跨项目复用步骤

1. 先确认路由缓存是按页面实例 key 隔离的；在 `KeepAlive` 内增加轻量包装组件，通过 Router 的 route 注入 key 为缓存实例提供局部 route，不要为每个 Tab 创建新的 Router。
2. 包装组件只复制 route 对象并监听父级 route 更新；缓存 key、缓存上限和页面组件仍由应用壳统一管理。
3. 对详情页或编辑页的初始加载定义稳定签名（路由名 + 主 ID + 会影响请求的关键 query），用 `pending Promise` 复用同签名请求。
4. 为每次新加载递增版本，并在每个异步边界后检查“签名仍匹配 + 版本仍最新”；旧响应直接返回，不修改数据、错误提示和 loading。
5. 并发请求可以继续使用 `Promise.all`，但要在聚合结果写入前再次检查版本；清理 pending Promise 时只清理仍指向当前 Promise 的记录。
6. 测试至少覆盖：两个缓存 Tab 的参数隔离、同一页面重复刷新只请求一次、路由/主 ID 切换后旧响应不会覆盖新数据。

## 历史边界

- 本提交只处理前端 KeepAlive route 作用域和两个页面的异步加载竞态，不改变后端 API、数据库、权限策略或业务状态机。
- `TabRouteScope` 解决的是缓存页面读取 `useRoute()` 时的参数串页问题；它不隔离页面自己的 Pinia store、全局事件监听或未清理的定时器。
- `ProcessDetail` 与 `useWorkOrderChecklistSubmitPage` 的去重是页面实例内存级 Promise 复用；刷新浏览器、跨标签页或跨客户端不会共享请求状态。
- 请求去重不会取消已经发出的旧 HTTP 请求，只会阻止旧响应写入当前页面；若需要节省网络资源，应另行引入 AbortController，并保持响应版本校验。
- 本提交未改变 `useNavigationTabs` 的缓存 key 生成策略；迁移时必须保留“缓存 key 唯一标识页面实例”的前提。
