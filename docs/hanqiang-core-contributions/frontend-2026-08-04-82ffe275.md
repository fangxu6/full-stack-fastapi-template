## 详情请求契约

`getWorkflowDetail(workflowId)` 在浏览器内存中维护两张表：成功结果缓存和进行中的 Promise。

- workflow ID 先转字符串并去除首尾空白；缓存键为 `access_token + NUL + workflowId`，不同登录用户不会共享详情。
- 成功结果 TTL 为 30 秒；同一 token、同一 workflow 的并发调用复用同一个 Promise，因此只发出一次 HTTP 请求。
- 请求成功后，仅当 pending Map 仍指向当前请求且 access token 没有变化时写入缓存；旧请求即使稍后完成，也不能污染新用户或已失效的缓存。
- 请求成功或失败都会清理仍指向当前请求的 pending 记录；失效函数不会取消已经发出的 HTTP 请求。
- `invalidateWorkflowDetailCache(workflowId?)` 无参数清空全部缓存和 pending，有参数则清理该 workflow 的所有 token 条目。
- `updateWorkflow`、`deleteWorkflow` 成功返回后自动失效详情缓存；创建流程不需要清理既有详情。
- 命中缓存时直接返回缓存对象。跨项目迁移应约定调用方只读，或在边界处自行复制；若调用方可变，改为返回深拷贝。

`ProcessDetail.loadPage(..., { force: true })` 在重新拉取详情前调用 `invalidateWorkflowDetailCache(processDetail.WorkflowID)`。确认、审批成功、取消/中止等会改变页面上下文的操作使用强制刷新，普通导航仍可复用 30 秒缓存。

## CodeGraph 调用链证据

```text
ProcessDetail.loadPage
  -> getProcessDetail
  -> getWorkflowDetail
     -> workflowDetailCache / workflowDetailPending

ProcessDetail.force refresh
  -> invalidateWorkflowDetailCache(workflowId)
  -> getWorkflowDetail(workflowId)

WorkflowConfig / WorkflowNodeConfig / 其它详情页
  -> getWorkflowDetail
```

缓存位于共享 service 模块，因此所有详情页都能复用同一份去重逻辑；页面只决定何时强制失效，不在组件内复制缓存。

## 测试覆盖

- `workflowService.spec.ts`：两个并发详情调用只触发一次 GET；成功后 30 秒内再次读取命中缓存；更新和删除成功后再次读取会重新发请求。
- `ProcessDetail.spec.ts`：强制刷新时断言 `invalidateWorkflowDetailCache('wf-p1')`，确保刷新针对当前流程的工作流。

## 跨项目复用步骤

1. 在唯一的前端 API service 中实现“规范化 ID → token 隔离键 → TTL 缓存 → pending Promise 合并”的顺序，并把 TTL 作为常量配置（本提交为 30 秒）。
2. 所有成功写操作统一调用按 workflow ID 的失效函数；登出、切换账号或权限上下文变化时调用无参数失效。
3. 在会改变详情上下文的页面动作后先失效再读取；普通列表导航直接读取 service，避免组件级缓存和第二事实源。
4. 保留并发、命中、写后失效、token 隔离和旧请求不回写测试；若目标项目支持可变响应对象，明确复制策略。
5. 多标签页或多前端实例需要共享缓存/失效事件时另行接入；本提交只覆盖单页面运行时内存。

## 与后端详情缓存的边界

- 前端本提交是浏览器 service 级 30 秒缓存和请求合并；后端 [`cdf8843a`](backend-2026-08-04-cdf8843a.md) 是服务实例级 5 秒投影查询缓存。两者可叠加，但不能互相替代。
- 前端失效只影响当前标签页；后端写操作失效只影响其服务实例（多副本需共享失效机制）。
- 两个提交都不改变 API、认证/权限、工作流版本快照或审批状态机；前端也不取消已发出的请求。
