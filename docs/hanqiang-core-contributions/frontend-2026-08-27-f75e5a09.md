## 场景与字段契约（本提交时）

| 场景 | `scenario_code` | `contract_code` | 变量/映射字段 |
| --- | --- | --- | --- |
| 设备新增 | `ft_equipment_created` | `pms.equipment.created.v1` | `EquipmentCode`、`EquipmentCategory`、`EquipmentName`、`EquipmentModel`、`SerialNumber`、`CanSchedule`、`IsAutomotive`、`FTProcesses`、`ManufactureTypeCode`、`HandlerStatus`，以及事件信封变量 |
| 设备信息编辑 | `ft_equipment_updated` | `pms.equipment.updated.v1` | 与设备新增相同 |
| 设备报废 | `ft_equipment_scrapped` | `pms.equipment.scrapped.v1` | 仅 `EquipmentCode`；内部仍可用事件 ID/类型等路由上下文，但不放入对外变量目录 |

设备新增/编辑的默认 Body 示例为：

```json
{ "BODY": { "EQUIPMENT_CODE": "${EquipmentCode}", "FT_PROCESSES": "${FTProcesses}" } }
```

该示例只是起步模板，不能替代目标系统的字段契约。变量值语义由后端事件生产器决定，例如 `CanSchedule` 固定为 `Y`，`IsAutomotive` 根据产品规格得到 `Y/N`，`FTProcesses` 是按设备类型生成的逗号分隔工序字符串。

## 设计边界

- 变量目录、默认 Body 和映射字段都以 `scenario_code`/`contract_code` 为键，不能用一个“设备事件”列表覆盖报废场景。
- 事件映射只允许改写对外报文中的登记字段；不修改 PMS 设备主数据，也不把数据库列名直接暴露给用户。
- 报废只输出设备编号，设备类型、制造类型等信息仅用于内部路由筛选；这是删除后仍能投递的最小事实集合。
- 本提交没有改变 Profile 的 URL、Header、Body JSON、响应状态码、敏感绑定和脱敏校验；只增加目录和示例选择。

## 跨项目迁移步骤

1. 先定义每个生命周期事件的 contract 和最小对外数据集，尤其单独定义报废/删除场景。
2. 将变量说明、字段映射白名单和默认 Body 示例放在同一纯数据模块，以场景码索引。
3. 让 Profile composable 通过 `eventScenario` 返回变量与示例，组件只渲染 computed 结果。
4. 后端事件生产器必须对照同一 contract 生成数据；前端帮助中出现的变量不得超出后端运行时集合。
5. 为完整主数据场景与最小报废场景各写一条正向和一条反向测试，确保场景切换不会残留上一场景变量。
