# prod：审批工作流

## 决策与启动门槛

`defer`。只有真实业务需要多级、可配置或并行审批时才新建任务；首个消费者可评估库存纠错，但业务字段和状态仍由业务模块拥有。前置是稳定事件出口、审批适配器边界和明确的状态矩阵。

## 目标与非目标

提供版本化工作流、节点实例、待办、审批动作、超时和审计。非目标是跨领域全局状态机、在内核存放业务字段、无业务依据的 AND/OR/退回/催办全量实现，或在没有用户场景时建设编排 UI。

## 所有权、数据与状态

审批内核拥有 workflow version、node definition、process、stage、task 和 action log；业务模块通过适配器提交业务代码、资源 ID、只读快照和执行命令。状态转移必须由表驱动的矩阵定义，动作以 process/stage/task 版本或行锁串行化；平行阶段只能由一个成功提交者推进。

## IAM、安全与并发

候选审批人由服务端根据角色/组织策略解析，前端不传可信审批人。审批、退回、撤回、催办和管理权限分离；所有判断校验任务归属、流程版本、资源版本和租户。重复命令、超时扫描和陈旧 Worker 结果通过幂等键、租约和条件更新处理，流程终态不可被重试任务复活。

## 事件、观测与恢复

审批事实先提交，再通过事件/Outbox 发送通知或触发业务适配器；失败不回滚已审批事实，而进入可观测恢复状态。记录流程、节点、动作、操作者、候选解析、业务关联、原因和 trace；告警覆盖超时、卡住、并发冲突和适配器失败。

## 迁移、测试、发布与回滚

新工作流定义版本化，运行中实例绑定旧版本；发布从一个业务/串行流程开始。验收覆盖无权、候选变化、重复审批、并行竞争、超时、退回/撤回、失败通知、业务适配器幂等和前端权限显示。回滚停用新定义，运行中实例按绑定版本继续或显式迁移，绝不直接改写历史步骤。

## 启动门槛、后续拆分与运维检查

只有首个真实业务适配器、状态矩阵和候选人来源获确认后才建独立任务；任务至少拆为版本/节点模型、待办与动作、超时扫描、业务适配器、事件通知和前端待办。运维检查卡住流程、超时、并发冲突、适配器失败和待办积压；此前禁止创建通用编排 UI 或审批字段。
