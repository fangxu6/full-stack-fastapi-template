# prod：通知 Adapter

## 决策与启动门槛

`defer`。模板已有可靠邮件 Outbox；只有组织明确采用额外渠道、收件人策略和凭据托管方式后，才为具体渠道建立 Adapter 任务。

## 目标与非目标

将业务通知意图映射为渠道投递，而不让业务模块直接调用 WeCom/HTTP。非目标是自建跨渠道万能模板 DSL、公开渠道配置或为未使用渠道保留 Token 刷新任务。

## 所有权、状态与接口

业务模块只提交事件/通知意图；通知模块负责模板版本、收件人解析、渠道 Adapter、投递记录和恢复。投递状态使用 durable Outbox 语义，区分 queued、leased、retry_wait、delivered、failed；渠道回执只更新该投递尝试。

## 安全、幂等与恢复

渠道 Secret 由密钥管理托管，数据库至多保存不可回显的引用或加密版本；Token 缓存有过期、锁和轮换策略。以业务事件和渠道/收件人/模板版本建立幂等边界，重试接收人必须由服务端审计授权。固定错误、无效收件人和权限失败进入终态，暂时错误退避并可人工重放。

## 观测、迁移、测试与发布

记录业务 ID、渠道、模板版本、收件人数量、状态、attempt、错误类别和 trace，不记录 Secret 或完整敏感正文。测试覆盖 Token 并发刷新、过期、限流、重复投递、模板校验、收件人权限、失败恢复与脱敏。发布先 shadow/测试频道，回滚禁用 Adapter 而不丢失 Outbox 记录。

## 启动门槛、后续拆分与运维检查

只有明确渠道、收件人来源、模板责任人和 Secret 轮换方式后才建独立任务；任务至少拆为通知意图、渠道 Adapter、Token 生命周期、Outbox 投递和人工重放。运维检查失败率、限流、Token 刷新竞争、Outbox 积压和敏感日志扫描；没有组织渠道时禁止创建通知菜单或空 Token 配置。
