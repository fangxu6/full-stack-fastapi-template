# prod：审计、请求关联与可观测性

## 目标与非目标

让关键变更可回答“谁在什么请求中对什么资源做了什么”，并让 HTTP、任务和数据库生命周期可运维。非目标是强制采用某个日志供应商或把完整请求体写入日志。

## 所有权与契约

业务模块拥有动作语义，平台审计模块拥有 `AuditEvent` 写入和查询出口；Request ID 在入口生成/透传并进入日志、审计和异步上下文。日志 schema、级别、时间和错误类别必须稳定。

## 状态与配置

审计事件至少区分已登记、成功、失败和重试中的动作结果；日志采样、保留期、脱敏规则、出口和告警阈值由环境配置管理，不能由业务请求覆盖。

## 安全与数据边界

日志和审计只保存必要摘要，令牌、密码、密钥、完整 Cookie、原始上传内容和敏感响应必须脱敏或禁止记录。审计写入失败的处理策略按动作风险定义：安全/合规动作不得无声成功，普通诊断日志不得拖垮业务请求。

## 幂等、异步与观测

同一业务命令的审计事件应有可追踪业务 ID；重试可产生 attempt 记录但不能伪造新的业务事实。Worker 继承 trace/request correlation，并记录排队、开始、结束和失败；指标至少覆盖请求错误、任务延迟、审计失败、数据库池和外部依赖。

## 发布、回滚与验收

先以向后兼容字段扩展日志 schema，再启用新消费；日志管道不可用时保留本地受控 fallback 和告警。测试覆盖 request ID 缺失/透传、异常脱敏、审计关联、重试、结构化字段和采样。回滚不得删除已写入审计事实。

## 迁移与运维检查

迁移先追加字段和索引，再切换查询/告警消费者；旧日志保持可解析，回滚关闭新消费者但保留审计事实。运维检查 Request ID 覆盖率、审计写入失败、日志积压、脱敏命中和存储保留量。
