# 前端开发规范

## 1. 目的与适用范围

本规范用于指导当前仓库 `frontend/` 的后续开发、评审与 AI 协作。

- 适用范围：`frontend/src/**` 下的业务代码、路由、页面、hooks、通用组件与测试。
- 不适用范围：生成代码与受上游工具管理的文件。
- 本文以当前代码为基线，分为两类内容：
  - **现有约定**：已经在仓库代码中成立，新增代码应默认遵循。
  - **增强要求**：为减少后续分歧与返工而补充的强约束或推荐实践。

## 2. 技术栈基线

当前前端以如下组合为准：

- React 19 + TypeScript strict
- Vite 7
- TanStack Router（文件路由）
- TanStack Query（服务端状态）
- Tailwind CSS v4
- shadcn/ui + Radix UI
- React Hook Form + Zod
- Playwright
- Biome
- Bun

现有约定：

- 构建和开发入口来自 `frontend/package.json`。
- 使用 `@/*` 指向 `frontend/src/*`，由 `tsconfig.json` 与 `vite.config.ts` 共同定义。
- 使用文件路由与自动生成的 `routeTree.gen.ts`。

增强要求：

- 除特殊说明外，前端新增功能不得引入第二套状态管理、路由或 UI 基础框架。
- 对外 API 调用默认复用生成客户端与现有 query/mutation 模式，不手写并行方案。

## 3. 基础约束

### 3.1 禁改目录

以下目录或文件禁止手动修改：

- `frontend/src/client/**`
- `frontend/src/routeTree.gen.ts`
- `frontend/src/components/ui/**`

如果后端 OpenAPI 发生变化，应执行仓库根目录命令重新生成客户端：

```bash
bash ./scripts/generate-client.sh
```

### 3.2 开发命令

常用命令以仓库现状为准：

```bash
cd frontend
bun install
bun run dev
bun run build
bun run lint
bunx playwright test
```

增强要求：

- 提交前至少运行 `bun run lint`。
- 影响路由、鉴权或关键 CRUD 路径时，应补充或回归 Playwright 测试。

## 4. 目录职责与文件组织

现有约定：

- `src/routes/`：页面入口、路由守卫、页面级布局与数据边界。
- `src/components/`：可复用业务组件与通用显示组件。
- `src/hooks/`：横切行为与状态复用，例如鉴权、toast、复制。
- `src/lib/`、`src/utils.ts`：通用工具函数。
- `src/client/`：OpenAPI 生成客户端。

增强要求：

- 路由文件只负责页面编排、路由元信息、守卫和 Suspense 边界，不承载可复用业务逻辑。
- 可复用逻辑优先抽到 hooks 或通用组件，不在多个页面中复制 mutation/query 细节。
- 同一业务域的列表、列定义、操作菜单、表单弹窗应尽量放在同一组件目录下，保持聚合。

## 5. 命名与导入规范

现有约定：

- 组件文件使用 `PascalCase`，例如 `AddItem.tsx`、`ErrorComponent.tsx`。
- hooks 使用 `useXxx.ts` 命名。
- 路由文件遵循 TanStack Router 约定，例如 `_layout.tsx`、`login.tsx`、`_layout/items.tsx`。
- 字符串使用双引号，语句分号遵从 Biome 当前配置。

增强要求：

- `src` 内跨目录导入默认使用 `@/` 别名；仅同目录极短相对路径可以保留相对导入。
- 类型导入优先使用 `import { type Foo } from "..."`。
- 新增业务代码避免使用 `any`；确实无法避免时，只能出现在边界层，并补充原因。
- hooks 名称必须以 `use` 开头；组件名称必须与导出语义一致，避免缩写和含糊命名。

## 6. TypeScript 与 React 编码约定

现有约定：

- `tsconfig.json` 开启 `strict`、`noUnusedLocals`、`noUnusedParameters`。
- 项目全部使用函数组件和 Hooks。
- Provider 与全局能力在 `main.tsx` 统一注入。

增强要求：

- 新代码优先使用显式类型和推导结合的方式，避免为了“省事”退回弱类型。
- 非引导代码中尽量避免非空断言；如果必须使用，应能明确证明其安全性。
- 衍生状态优先通过表达式、查询结果或表单状态直接计算，不额外创建冗余 state。
- 副作用应围绕真实外部交互展开；纯数据推导不要放进 `useEffect`。

## 7. 路由、页面与鉴权

现有约定：

- 使用 TanStack 文件路由。
- 页面标题通过 `head()` 定义。
- 鉴权守卫放在路由的 `beforeLoad` 中，例如已登录跳转、未登录拦截。
- 页面布局由 `_layout.tsx` 这类布局路由承载。

增强要求：

- 新增需要登录态的页面，优先挂载在已有受保护布局下；不要在组件内部临时做登录跳转。
- 页面组件负责拼装页面结构、调用页面级组件，不直接内联复杂列表列定义、表单 schema 或通用错误处理。
- 新页面必须明确以下三类表现：
  - 加载态
  - 空态
  - 错误态

## 8. 数据获取与服务调用

现有约定：

- API 调用通过 `src/client/**` 生成客户端完成。
- 服务端状态使用 TanStack Query。
- 全局 401/403 处理在 `main.tsx` 中集中拦截。
- 页面或 hooks 中使用 `useQuery`、`useSuspenseQuery`、`useMutation`。
- query key 使用数组形式，例如 `["items"]`、`["currentUser"]`。

增强要求：

- 新增接口调用不得绕过生成客户端直接拼接 URL，除非当前生成客户端无法表达。
- 查询参数与 mutation 函数应保持靠近业务域，可复用时提取为局部 query options/helper。
- mutation 成功后应根据影响范围精确失效相关 query，避免无差别刷新。
- 页面 JSX 中不要直接编写请求细节；请求逻辑应位于 hooks、query options 或事件处理函数内。
- 错误展示应复用统一错误处理工具和 toast 机制，不在每个页面重复拼装错误文案。

## 9. 表单规范

现有约定：

- 表单统一采用 `react-hook-form + zod + zodResolver`。
- 默认值通过 `defaultValues` 声明。
- 表单字段优先复用 `components/ui/form`、`input`、`password-input`、`loading-button`。

增强要求：

- 新表单默认必须定义 Zod schema，表单类型从 schema 推导。
- 提交事件必须处理重复提交问题，例如在 `isPending` 时阻止二次提交。
- 表单提交成功后要明确后续动作：关闭弹窗、重置表单、跳转页面或刷新列表。
- 必填项、校验错误与提交中状态必须有可见反馈，不能只依赖控制台或隐式行为。

## 10. UI、样式与主题

现有约定：

- 基础 UI 组件来自 `components/ui/**`，业务层在其上组合。
- 样式以 Tailwind 原子类为主。
- 全局主题 token 与亮暗色变量定义在 `src/index.css`。
- 项目已接入深色模式与 `ThemeProvider`。

增强要求：

- 新增业务界面优先复用现有 `components/ui` 和 `components/Common`，不要平行造一套按钮、表单、表格或弹窗。
- 样式优先通过现有 token、语义色和 Tailwind 类组合表达，不硬编码零散颜色值。
- 复杂视觉结构优先抽出小型展示组件，不让单个页面堆积过长 className 和重复布局片段。
- 图标应服务于信息表达，不为装饰而随意增加。

## 11. 加载态、空态、错误态

现有约定：

- 列表页面使用 `Suspense + Pending...` 组件承接加载态。
- 全局存在 `ErrorComponent` 与 `NotFound` 作为公共兜底。
- 业务列表页已体现“空数据提示 + 主操作入口”的模式。

增强要求：

- 新增页面必须至少覆盖以下状态：
  - 请求中有明确占位或骨架屏
  - 无数据时给出可理解的空态文案
  - 失败时可定位问题并保留下一步操作
- 空态优先给出下一步动作，例如“新增”“返回”或“刷新”。
- 错误提示文案优先面向用户描述结果，不直接暴露原始异常对象。

## 12. Hooks 与状态边界

现有约定：

- 鉴权、toast、复制等横切逻辑已抽为 hooks。
- 本地交互状态使用组件内 `useState`，例如弹窗开关。

增强要求：

- 仅影响单个组件的临时 UI 状态放本地 state。
- 跨页面共享且来自服务端的数据优先交给 Query 管理，而不是自建全局 store。
- 可复用的副作用流程，如鉴权、统一 toast、剪贴板操作，应优先抽为 hook。

## 13. 测试与质量门槛

现有约定：

- 当前前端自动化测试以 Playwright 为主。
- `bun run build` 会先做 TypeScript 构建检查再执行 Vite build。
- `bun run lint` 由 Biome 执行检查与格式修复。

增强要求：

- 新增关键流程至少考虑以下测试覆盖点：
  - 登录/退出或鉴权跳转
  - 列表加载、空态、错误态
  - 创建/编辑/删除的主路径反馈
  - 表单校验与禁用重复提交
- 如本次改动影响 OpenAPI schema，必须重新生成 client 并验证构建通过。

## 14. 前后端联调规范

现有约定：

- `VITE_API_URL` 用于指定后端地址。
- 后端 OpenAPI 变更后通过根目录脚本生成前端 client。

增强要求：

- 后端接口字段、必填项或错误结构变化时，前端改动应以重新生成后的 client 类型为准。
- 不要在前端手动“兼容猜测中的接口返回”；应先确认 OpenAPI 契约。
- 对接口变更敏感的页面，至少执行一次本地联调或构建校验。

## 15. 开发自检清单

提交前至少检查以下内容：

- 是否误改了生成文件或 `components/ui`。
- 是否使用了 `@/` 别名和清晰的命名。
- 是否为新增页面补齐加载态、空态、错误态。
- 是否通过 query/mutation 调用生成客户端，而不是手写请求。
- 是否为表单补齐 schema、默认值、错误提示和提交态。
- 是否运行了 `bun run lint`。
- 涉及关键路径时，是否补充或回归了 Playwright 测试。
