# 数据库规则

## 1. 目的与适用范围

本规则用于指导当前仓库在 PostgreSQL 上的数据建模、Schema 演进、迁移执行与文档协作。

- 适用范围：
  - `backend/app/models/**`
  - `backend/app/schemas/**`
  - `backend/app/alembic/**`
  - 与数据结构变更相关的 `docs/specs/**`
- 不适用范围：
  - 其他数据库产品的专有规则
  - 独立的数据字典平台或外部企业规范模板

## 2. 当前仓库基线

当前仓库的数据层以以下组合为准：

- PostgreSQL
- SQLModel
- Alembic
- psycopg
- FastAPI / OpenAPI
- 前端生成式 OpenAPI client

数据库相关决策必须同时满足：

- PostgreSQL 语义正确
- SQLModel 模型可表达
- Alembic migration 可落地
- FastAPI schema 与前端 client 可以保持同步

## 3. 事实来源与兼容原则

数据库结构的事实来源按以下优先级理解：

1. `backend/app/models/**` 中的 SQLModel 模型
2. Alembic migration 文件
3. `backend/app/schemas/**` 中的输入输出 schema
4. `docs/specs/<feature>/02_interface.md` 与 `03_implementation.md`

说明：

- 文档用于说明设计意图、约束和迁移方案，不替代真实模型和 migration。
- 文档中的 SQL 片段必须以 PostgreSQL 语法为准。
- 新规范优先给出 PostgreSQL 默认推荐做法；如果当前仓库已有实现存在兼容性例外，文档必须显式写出例外，不得假装不存在。

当前仓库的兼容性例外：

- 现有模板模型 `user.id` 与 `item.id` 使用 `UUID` 主键。
- 引用既有 UUID 表的外键必须保持 `UUID`。这不要求新表自身的主键也成为 UUID：
  新独立实体可以有 `BIGINT` 主键和 UUID 外键。
- 这不改变 PostgreSQL 规范对新业务表的默认推荐，只说明仓库现状的兼容边界。

## 4. PostgreSQL 设计总原则

- 先做规范化设计，默认做到 3NF；只有在明确测量出读性能瓶颈时才考虑反规范化。
- 语义上必填的列必须使用 `NOT NULL`。
- 常见默认值应使用 `DEFAULT`，但要避免在大表上引入会触发表重写的易变默认值。
- 索引只为真实访问路径服务，不为“可能以后会查”预建索引。
- 明确区分热字段与冷字段，避免在宽表上高频更新造成 MVCC 膨胀。
- 标识符统一使用小写 `snake_case`，不要依赖带引号的混合大小写名称。

## 5. 命名规范

### 5.1 表、列、约束命名

- 表名、列名、索引名、约束名统一使用 `snake_case`
- 主键列默认命名为 `id`
- 外键列命名为 `<entity>_id`
- 布尔列优先使用 `is_*`、`has_*`
- 时间列优先使用 `*_at`
- 范围列优先使用 `*_range`、`*_period`

### 5.2 模型命名

- Python 模型类名使用 `PascalCase`
- 数据库对象仍落为小写 `snake_case`

### 5.3 避免的命名方式

- 不使用带引号的驼峰表名或列名
- 不使用与 PostgreSQL 关键字冲突且必须加引号的名字
- 不使用 `CreateTime`、`IsDeleted` 之类与当前仓库风格冲突的 PascalCase 字段名

## 6. 数据类型规则

### 6.1 主键与标识符

- 新的独立业务实体、单据、台账和可独立引用的明细行默认使用：

  ```sql
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
  ```

- PostgreSQL 使用有符号 64 位 `BIGINT`；正向 identity 的上限为
  `9223372036854775807`（`2^63 - 1`）。不要使用 MySQL 风格的
  `BIGINT(20)`，也不要把 PostgreSQL 主键视为无符号 `2^64 - 1`。
- 每张表拥有自己的 identity sequence。技术主键不可变、不可复用且允许因
  回滚、删除或并发而跳号；它不承担业务单号或严格时间顺序。
- 纯多对多关联表若没有独立生命周期，可用两个外键组成复合主键。能被其他
  表引用、审计、单独修改或作为 API 资源返回的明细行仍应有自身主键，并可用
  `(parent_id, line_no)` 作为额外唯一约束。
- 仅在以下场景允许 UUID 主键，并在对应 feature 的设计文档写明原因：
  - 需要跨系统合并或离线生成全局唯一 ID
  - 需要对外暴露不透明标识符
  - 一对一扩展表以既有 UUID 父键作为共享主键
- 若使用数据库端生成 UUID：
  - PostgreSQL 18+ 优先 `uuidv7()`
  - 其他版本优先 `gen_random_uuid()`
- 当前仓库已有模型允许继续使用应用端 `uuid.uuid4`
- 禁止新增 `serial` / `bigserial`；统一使用 identity
- 业务编号是独立的人可读字段，生成方式和唯一范围由领域定义；不得把它或
  identity 主键作为对方的替代品。
- 常规 create/update API 不得接收技术 `id`。输入 DTO 用
  `extra="forbid"` 拒绝这类字段，返回 422；只有受控迁移或修复脚本可使用
  `OVERRIDING SYSTEM VALUE` 显式写入 ID，并负责校正 sequence。
- 现有内部 API 将 BIGINT 作为 JSON number 返回。每表 `MAX(id)` 达到
  `9007199254740991`（`2^53 - 1`）时只告警、不阻断；超过该阈值的 JavaScript
  精度风险是已接受的运营风险，不能被描述为安全保证。

### 6.2 整数、数值与金额

- 整数优先 `BIGINT`
- 一般浮点优先 `DOUBLE PRECISION`
- 金额、汇率、精确小数统一使用 `NUMERIC(p,s)`
- 禁止使用 `money`

### 6.3 字符串与二进制

- 字符串优先 `TEXT`
- 长度限制优先作为业务约束表达：
  - API 层可用 `max_length`
  - 数据库层可用 `CHECK (length(col) <= n)`，而不是滥用 `varchar(n)`
- 固定长度字符串不要使用 `char(n)`
- 二进制内容使用 `BYTEA`

### 6.4 时间与日期

- 时间戳统一使用 `TIMESTAMPTZ`
- 日期使用 `DATE`
- 时长使用 `INTERVAL`
- 禁止使用无时区 `timestamp`
- SQLModel 中时间列应显式映射为 timezone-aware 类型，例如 `DateTime(timezone=True)`

### 6.5 布尔、枚举与状态

- 布尔列优先 `BOOLEAN NOT NULL`
- 小而稳定的值集可使用 PostgreSQL `ENUM`
- 业务状态更推荐：
  - `TEXT + CHECK`
  - 或 lookup table
- 不默认把状态压成无语义数字

### 6.6 JSONB、数组、范围

- 半结构化数据优先 `JSONB`，并配合约束限制形态，例如：
  - `CHECK (jsonb_typeof(config) = 'object')`
- `JSONB` 默认使用 GIN 索引；若查询几乎全是 `@>` 包含判断，可考虑 `jsonb_path_ops`
- 需要对 JSONB 内某个标量做等值或范围查询时，优先抽出生成列或表达式索引
- 数组只用于有序值集合，不用于关系建模；关系请建中间表
- 时间段、数值区间优先使用 PostgreSQL range type，并通过 GiST 或 exclusion constraint 保证不重叠

### 6.7 禁止使用的类型

- `timestamp`（无时区）
- `timetz`
- `char(n)`
- `varchar(n)` 作为默认字符串策略
- `money`
- `serial` / `bigserial`
- `timestamptz(0)` 之类精度特化写法作为默认约束

## 7. 约束与关系规则

### 7.1 主键、唯一性、检查约束

- 参考表、主数据表必须定义主键
- `UNIQUE` 只表达真实业务唯一性，不作“顺便防重”使用
- 需要把 `NULL` 也视为唯一的一部分时，优先使用 `NULLS NOT DISTINCT`
- 所有有业务意义的取值约束都应使用 `CHECK`
- 仅写 `CHECK (price > 0)` 不足以禁止空值；语义必填时必须再加 `NOT NULL`

### 7.2 外键与删除策略

- 允许并鼓励使用真实外键约束
- 每个外键列都必须显式创建索引；PostgreSQL 不会自动为外键建索引
- `ON DELETE` / `ON UPDATE` 行为必须按业务语义选择：
  - `CASCADE` 仅用于从属生命周期对象
  - `RESTRICT` / `NO ACTION` 适用于必须保护父记录的场景
  - `SET NULL` 仅在列可空且业务允许脱钩时使用
- SQLModel 中关系需同时表达：
  - `foreign_key`
  - `Relationship`
  - 必要时的 `ondelete`

### 7.3 审计与软删除

- 不强制所有表都带一整套审计列
- 常见审计列：
  - `created_at`
  - `updated_at`
  - `created_by`
  - `updated_by`
- 软删除不是默认策略；只有在业务明确需要恢复、保留引用或审计时才加：
  - `deleted_at`
  - `deleted_by`
  - `is_deleted`
- 一旦采用软删除，查询、唯一索引和业务校验必须一并设计，不能只加字段

## 8. 索引规范

### 8.1 何时建索引

- 主键和唯一约束带来的索引由数据库自动生成
- 以下列通常需要手动建索引：
  - 外键列
  - 高频过滤列
  - 高频排序列
  - 高频 join 键
  - 热门状态子集对应的部分索引

### 8.2 索引类型选择

- B-tree：等值、范围、排序
- 复合索引：按最常见过滤路径排列列顺序
- INCLUDE covering index：用于减少回表
- Partial index：仅覆盖热点子集
- Expression index：例如 `LOWER(email)`
- GIN：JSONB、数组、全文检索
- GiST：范围、几何、exclusion constraint
- BRIN：超大且与物理顺序高度相关的时间序列表

### 8.3 索引设计约束

- 不为低选择性且少用的列机械建索引
- 高频写入表应严格控制索引数量
- 需要 `ON CONFLICT` 的 upsert，必须先有精确匹配的唯一索引
- 大表新增索引时，优先评估 `CREATE INDEX CONCURRENTLY`

## 9. PostgreSQL 特性使用边界

### 9.1 JSONB

- 核心关系数据仍应落在规范化表中
- `JSONB` 仅用于可变、稀疏、扩展性强的属性
- 若某个 JSONB 字段已成为稳定查询条件，应考虑提升为正式列

### 9.2 分区

- 只有在满足以下条件时才考虑分区：
  - 数据规模极大，例如上亿行
  - 查询持续按分区键过滤
  - 或数据清理/归档天然按时间或离散键进行
- 优先使用 declarative partitioning
- 不使用 table inheritance 模拟分区
- 当前仓库普通业务表默认不引入分区

### 9.3 RLS

- 只有在数据库层需要承担租户隔离或用户级访问控制时启用 RLS
- 若启用 RLS，必须同步定义角色、策略、测试和运维方案
- 不能把 RLS 当作应用层鉴权缺失的替代品

### 9.4 临时表与 UNLOGGED 表

- `TEMPORARY` 仅用于会话级临时计算
- `UNLOGGED` 仅用于可重建的缓存或 staging 数据
- 常规业务表使用默认 logged table

## 10. Schema 演进流程

数据库结构发生变化时，默认遵循以下顺序：

1. 更新或新增 `docs/specs/<feature>/`
   - `01_requirement.md`：为什么改、范围和验收标准
   - `02_interface.md`：涉及哪些表、模型、接口和前端契约
   - `03_implementation.md`：改哪些文件、迁移策略、回填策略
   - `04_test_spec.md`：验证点、回归点、迁移检查点
2. 更新 SQLModel model、schema、CRUD、service、route
3. 生成并审查 Alembic migration
4. 执行迁移并验证 upgrade 路径
5. 若 OpenAPI 契约变化，重新生成前端 client
6. 更新测试与 `docs/decisions/AI_CHANGELOG.md`

### 10.1 安全演进要求

- 避免在大表上直接添加带易变默认值的 `NOT NULL` 列
- 回填型变更要写清分步策略：
  - 先加可空列
  - 回填数据
  - 再加约束
- 可能长时间阻塞写入的 DDL，要评估窗口期或并发方案
- 变更文档必须写清是否影响旧数据兼容、接口兼容和回滚策略

## 11. 与前后端契约的联动

数据库变化不能只停留在表结构层，必须同步评估：

- `backend/app/schemas/**` 是否变化
- FastAPI request / response model 是否变化
- OpenAPI schema 是否变化
- `frontend/src/client/**` 是否需要重新生成
- 前端 Query、表单、列表列和筛选项是否受影响

如果数据库变更最终影响前端可见字段或请求参数，必须执行生成 client 的标准流程。

## 12. SQLModel / PostgreSQL 实施建议

- 使用 SQLModel 明确表达：
  - `primary_key`
  - `foreign_key`
  - `nullable`
  - `index`
  - 需要时的 `sa_type`、`sa_column_kwargs`
- PostgreSQL 特性超出 SQLModel 简单字段表达能力时：
  - 在 migration 中补充数据库级约束或索引
  - 在 spec 中明确说明原因
- 不要把 PostgreSQL 约束只写在文档里却不落到模型或 migration

## 13. 当前仓库兼容说明

- 现有模板模型仍以 `UUID` 主键为准：
  - `backend/app/models/user.py`
  - `backend/app/models/item.py`
- 如果后续引入新的独立业务域表，可按本规则默认优先评估 `BIGINT IDENTITY`
- 新表关联现有 UUID 主键实体时，关联列继续使用 UUID；新表自身是否使用
  BIGINT 取决于它是否有独立生命周期。
- 不在没有明确迁移方案的情况下，把既有表从 `UUID` 强行改回 `BIGINT`

## 14. 自检清单

提交前至少检查以下内容：

- 是否使用 PostgreSQL 正确类型，而不是沿用其他数据库习惯
- 是否把语义必填字段声明为 `NOT NULL`
- 是否为所有外键列显式创建索引
- 是否说明主键策略，以及为何选择 `BIGINT` 或 `UUID`
- 新表是否让数据库独占 identity 生成权，并拒绝 API 请求中的技术 `id`
- 是否定义业务编号与技术主键的边界，以及资源访问域
- UUID 例外是否在设计文档中说明原因
- 是否避免了 `timestamp`、`money`、`serial`、`char(n)` 等禁用类型
- 是否把 JSONB、数组、范围类型用于合适场景，而不是偷懒代替关系建模
- 是否评估了迁移回填、锁影响和兼容性风险
- 若 OpenAPI 契约变化，是否同步前端 client 与相关页面
- 是否同步更新对应 spec 与 `AI_CHANGELOG.md`
