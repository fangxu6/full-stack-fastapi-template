# 数据库规则

## 1. 目的与适用范围

本规则用于指导当前仓库后端的数据建模、schema 变更、迁移与文档协作。

- 适用范围：
  - `backend/app/models/**`
  - `backend/app/schemas/**`
  - `backend/app/alembic/**`
  - 与数据库变更相关的 `docs/specs/**`
- 不适用范围：
  - 其他项目的 MySQL 手写建表规范
  - 独立的数据字典中心或 `/Doc/dataDict` 目录体系

## 2. 当前仓库基线

当前仓库的数据库相关技术栈以以下组合为准：

- PostgreSQL
- SQLModel
- Alembic
- psycopg
- Pydantic v2 / SQLModel schema

因此，数据库设计与变更规则必须围绕：

- Python 类型系统
- SQLModel model 定义
- Alembic migration
- FastAPI/OpenAPI 契约
- 前端生成式 OpenAPI client

不再沿用 MySQL、`BINARY(16)`、`BIT(1)`、`ENGINE=InnoDB`、`Common_Enum` 之类的旧项目约束。

## 3. 数据库事实来源

当前仓库中，数据库结构的事实来源按以下优先级理解：

1. `backend/app/models/**` 中的 SQLModel 模型
2. Alembic migration 文件
3. `backend/app/schemas/**` 中与输入输出相关的 DTO / schema
4. `docs/specs/<feature>/02_interface.md` 与 `03_implementation.md` 中记录的业务与实施说明

说明：

- 文档用于解释“为什么改”和“影响什么”，不是数据库结构的唯一真相来源。
- 如果文档里出现 SQL 片段，应视为说明性内容，且语法必须以 PostgreSQL 为准。
- 不要求为每个表单独维护独立的数据字典文件；复杂功能如确需补充结构说明，应写在对应 feature spec 中。

## 4. 命名与字段规则

### 4.1 模型与字段命名

- Python 模型类名使用 `PascalCase`，例如 `User`、`Item`
- 数据库字段与 schema 字段使用 `snake_case`
- 主键默认使用 `id`
- 外键字段使用 `<entity>_id`，例如 `owner_id`
- 布尔字段优先使用 `is_*`、`has_*` 语义命名，例如 `is_active`
- 时间字段优先使用 `*_at` 命名，例如 `created_at`

### 4.2 UUID 规则

- 主键优先使用 `uuid.UUID`
- 默认模式优先采用：

```python
id: uuid.UUID = Field(default_factory=uuid.uuid4, primary_key=True)
```

- 不要为当前仓库引入 `BINARY(16)` 这类特定数据库存储规则
- UUID 的序列化与数据库适配由当前 ORM/驱动栈处理，不手写额外转换协议

### 4.3 时间字段规则

- 时间字段优先使用 timezone-aware UTC
- 与现有模型一致时，复用统一时间辅助函数
- 不要在不同模型里混用本地时间、无时区时间和自定义字符串时间格式

## 5. 约束、关系与完整性

### 5.1 约束表达

- 长度、唯一性、索引、可空性等约束优先在 `Field(...)` 或底层 SQLAlchemy 配置中明确声明
- 例如：
  - `max_length`
  - `unique=True`
  - `index=True`
  - `nullable=False`

### 5.2 外键与关系

- 当前仓库允许并鼓励在合适场景下使用外键约束
- 关系字段应通过 SQLModel `Relationship` 和 `foreign_key` 明确表达
- 删除策略（如 `CASCADE`）必须按业务语义决定，不一刀切

这意味着：

- 不采用“全面禁止外键”的旧规则
- 不要求所有关系都由后端逻辑手动维持

### 5.3 审计与软删除

- 当前仓库不强制所有表拥有同一组审计字段模板
- 新功能只添加确有业务价值的审计字段
- 如需新增审计或软删除字段，保持 `snake_case`，例如：
  - `created_at`
  - `updated_at`
  - `deleted_at`
  - `created_by`
  - `updated_by`
  - `is_deleted`

不要沿用旧项目的 `CreateTime`、`CreatorID`、`IsDeleted` 等 PascalCase 强制模板。

## 6. 枚举、状态和值建模

- 简单枚举优先使用 Python `Enum` 或受约束的字符串字段
- 仅当多个业务域确实共享且需要数据库层统一维护时，才考虑独立 lookup table
- 不默认创建通用 `Common_Enum` 表
- 不把 MySQL 的 `TINYINT`、`BIT(1)` 当作通用状态字段规则

原则上：

- 业务可读性优先于“所有状态都压成数字”
- OpenAPI 和前端消费的可理解性优先

## 7. Schema 变更流程

当数据库结构发生变化时，默认遵循以下顺序：

1. 更新相关 feature spec
   - `01_requirement.md`：为什么变
   - `02_interface.md`：影响哪些模型、接口、页面
   - `03_implementation.md`：具体改哪些文件、是否要迁移/回填
2. 更新 SQLModel model / schema / service / route
3. 生成并审查 Alembic migration
4. 执行 `alembic upgrade head`
5. 如 OpenAPI 契约发生变化，重新生成前端 client
6. 更新测试与 `AI_CHANGELOG.md`

## 8. 与前后端契约的联动

数据库变化不能只停留在表结构层。

需要同步评估：

- `backend/app/schemas/**` 是否变化
- FastAPI `response_model` / request body 是否变化
- OpenAPI schema 是否变化
- `frontend/src/client/**` 是否需要重新生成
- 前端 Query / 表单 / 列展示是否受影响

如果数据库变更最终会影响前端可见字段或请求参数，则必须执行：

```bash
bash ./scripts/generate-client.sh
```

## 9. 文档要求

与数据库相关的 feature spec 至少应说明：

- 涉及的模型或表
- 新增/修改/删除的字段
- 约束、默认值、唯一性、索引或关系变化
- 是否需要数据回填或兼容旧数据
- 是否影响 OpenAPI client 和前端页面

推荐写法：

- 在 `02_interface.md` 写数据模型和接口影响
- 在 `03_implementation.md` 写 migration、文件路径和执行顺序
- 在 `04_test_spec.md` 写验证项和迁移后检查点

## 10. 自检清单

提交前至少检查以下内容：

- 字段命名是否符合当前仓库 `snake_case` 习惯
- 主键、外键、时间字段和布尔字段是否使用了与当前仓库一致的类型和命名
- 是否错误套用了 MySQL/旧项目专属规则
- 关系和删除策略是否有明确业务理由
- Alembic migration 是否已生成并审查
- 若接口契约变化，是否重新生成前端 client
- 对应 spec 和 `AI_CHANGELOG.md` 是否已同步
