# 需求文档编号规范示例

本文展示当前仓库推荐的需求文档组织方式。

与旧的 `00_目录 / 101 / 201 / 301` 体系不同，当前仓库统一采用：

```text
docs/specs/<feature>/
  01_requirement.md
  02_interface.md
  03_implementation.md
  04_test_spec.md
```

## 示例功能：Item 增加 `notes` 字段

### 示例目录

```text
docs/specs/item-notes-field/
├─ 01_requirement.md
├─ 02_interface.md
├─ 03_implementation.md
└─ 04_test_spec.md
```

## 1. `01_requirement.md` 示例

```markdown
# Requirement Spec - Item notes field

## Background
- 现有 Item 仅支持 `title` 和 `description`，无法记录更长的补充备注。
- 后续页面需要在创建和编辑 Item 时支持备注录入与展示。

## Goals
- 为 Item 新增 `notes` 字段。
- 后端 API、前端表单和详情展示保持一致。

## Scope
- In scope:
  - Item 模型、schema、接口与前端表单增加 `notes`
- Out of scope:
  - 富文本编辑器
  - 备注历史版本

## Acceptance Criteria
- AC1: 新增和编辑 Item 时可以提交 `notes`
- AC2: 查询 Item 时返回 `notes`
- AC3: 前端表单、列表或详情页不会因为字段新增而报错

## Constraints
- 保持与当前 `SQLModel + PostgreSQL + OpenAPI client` 流程一致
- 如接口契约变化，必须重新生成前端 client
```

说明：

- `01_requirement.md` 负责说明为什么做、做什么、做到什么算完成
- 不在这里罗列具体代码文件

## 2. `02_interface.md` 示例

```markdown
# Interface Spec - Item notes field

## Data Model Impact
- `backend/app/schemas/item.py`
  - 在 `ItemBase` 中新增 `notes: str | None`
  - `ItemCreate`、`ItemUpdate`、`ItemPublic` 同步继承或显式暴露 `notes`
- `backend/app/models/item.py`
  - 仅当该字段需要额外数据库级配置时，再补充显式声明

## API Impact

### Affected Endpoints
- `POST /api/v1/items/`
- `PUT /api/v1/items/{id}`
- `GET /api/v1/items/{id}`
- `GET /api/v1/items/`

### Request / Response Changes
- `ItemCreate` 增加 `notes`
- `ItemUpdate` 增加可选 `notes`
- `ItemPublic` 与 `ItemsPublic.data[]` 返回 `notes`

### Error Considerations
- 继续沿用当前 FastAPI 校验与错误返回方式
- 如果 `notes` 设置最大长度，需明确 `422 Validation Error` 的行为

## Frontend Impact
- `frontend/src/components/Items/AddItem.tsx`
- `frontend/src/components/Items/EditItem.tsx`
- 如页面展示该字段，还需同步列表列或详情展示

## Client Generation Impact
- OpenAPI schema 变化后，需执行 `bash ./scripts/generate-client.sh`
```

说明：

- `02_interface.md` 关注契约、边界、影响面
- 当前仓库默认写真实 FastAPI / OpenAPI 契约，不使用额外 `code/message/data` 包装模板

## 3. `03_implementation.md` 示例

```markdown
# Implementation Spec - Item notes field

## Goal Summary
- 为 Item 新增可选备注字段，并保持前后端契约与生成 client 同步。

## Planned Changes
- 更新 `backend/app/schemas/item.py`
- 更新 `backend/app/services/item.py`
- 如该字段需要额外数据库级选项，再更新 `backend/app/models/item.py`
- 如需数据库结构变更，新增 Alembic migration
- 重新生成 `frontend/src/client/**`
- 更新前端表单组件

## Execution Order
1. 更新 spec
2. 更新后端 model / schema / service / route
3. 生成并审查 Alembic migration
4. 重新生成 frontend client
5. 更新前端表单与页面展示
6. 运行验证命令

## Notes
- 如果数据库已有 Item 数据，确认 `notes` 为可空字段，避免额外回填
```

说明：

- `03_implementation.md` 关注“准备怎么改”
- 应明确 migration、生成 client 和执行顺序

## 4. `04_test_spec.md` 示例

```markdown
# Test Spec - Item notes field

## Validation Scope
- 验证 `notes` 在后端 schema、接口和前端表单中的一致性

## Review Checklist
- TC1: `ItemCreate` / `ItemUpdate` / `ItemPublic` 已同步新增 `notes`
- TC2: Item 相关接口在 OpenAPI 中暴露 `notes`
- TC3: 已重新生成前端 client
- TC4: 前端表单能提交并展示 `notes`
- TC5: 不会破坏现有 Item 列表和编辑流程

## Suggested Verification
- `cd backend && uv run pytest tests/`
- `cd frontend && bun run lint`
- `cd frontend && bun run build`
```

说明：

- `04_test_spec.md` 关注验证方式，而不是复述需求背景
- 命令要与当前仓库实际工具链一致

## 什么时候可以更轻量

如果改动是：

- 很小的 bugfix
- 纯文案或纯文档修正
- 不涉及接口、模型、页面结构变化

则可以只更新相关 spec 的部分文件，甚至只补 `AI_CHANGELOG.md`。

但只要改动涉及：

- 数据模型
- API 契约
- 前后端联动
- 关键流程

就仍建议完整使用 `01~04` 结构。
