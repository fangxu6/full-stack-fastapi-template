## 1. 需求文档的模块化编号规范

### 1.1 编号体系
每个功能需求按照以下编号进行文档拆分，确保内容清晰、易于维护和跨功能引用：

| 编号 | 文件名 | 内容描述 | 关键信息 |
|------|--------|--------|----------|
| **00** | 00_目录.md | 功能的总体目录 | 汇总所有编号文档、核心链接、更新日志 |
| **101** | 101_业务概述.md | 业务层整体说明 | 功能背景与目标、用户与角色、版本信息、功能与其他模块的关联关系 |
| **102** | 102_流程图.md | 业务流程可视化 | 核心业务流程、状态流转、关键决策点 |
| **2xx** | 2xx_后端逻辑需求.md | 后端实现需求 | 后端模块划分、业务逻辑、接口定义（含返回包）、跨功能依赖 |
| **201** | 201_后端概述.md | 后端总体说明 | 后端模块架构、核心业务流程、与其他功能的依赖关系 |
| **202+** | 202_xxx逻辑.md | 具体后端逻辑需求 | 数据操作逻辑、业务规则、状态流转、异常处理 |
| **3xx** | 3xx_前端场景需求.md | 前端实现需求 | 前端页面、用户交互、数据展示 |
| **301** | 301_前端概述.md | 前端总体说明 | 页面结构、菜单导航、页面间跳转关系、与其他功能的页面集成点 |
| **302+** | 302_xxx场景.md | 具体前端场景需求 | 页面交互、UI设计、数据绑定、委托流程 |

### 1.2 编号范围说明
- 每份功能需求为一个独立编号范围（如功能A的文档编号为 A_00 到 A_3xx）
- 同一功能的所有文档统一存放在功能对应的文件夹中
- 编号放在文件名的最前方，便于文件列表排序和查找

### 1.3 文档结构示例

详见《需求文档编号规范示例.md》，该文档提供了完整的实例展示，包括：
- 文件夹结构与文件清单
- 各编号文档（00、101-102、201-203、301-304）的详细内容示例
- 文档间的引用关系与链接方式
- 关键注意事项与常见误区

**示例文件位置**：[需求文档编号规范示例.md](./需求文档编号规范示例.md)

## 2. 文档编写规范

### 2.1 业务概述（101）
- **功能背景和目标**：详细描述功能开发的背景原因和预期达成的目标
- **业务价值和适用场景**：说明功能对业务流程的优化价值及具体使用场景
- **主要参与角色和用户群体**：列出所有相关角色及其职责
- **功能与其他模块的关联关系**：描述该功能与系统中其他模块的依赖和交互关系
- **版本信息**：记录文档版本号、更新日期、变更内容

### 2.2 流程图（102）
- **核心业务流程**：可视化表示主要业务流程
- **状态流转**：明确各状态的转换条件和触发事件
- **关键决策点**：标注重要的业务决策和分支逻辑

### 2.3 后端逻辑需求（2xx）

#### 后端概述（201）
- **后端模块划分**：说明后端实现的模块化结构（Service、CRUD、Route 等）
- **核心业务流程**：参考 102 流程图，说明后端的关键处理步骤
- **与其他功能的依赖关系**：明确引用的其他功能的接口和服务（格式：[功能名](../功能名/201_后端概述.md)）

#### 具体逻辑需求（202+）
- **功能描述**：该逻辑模块的目的和业务背景
- **数据操作**：涉及的数据表及其字段（引用数据字典：[表名](../../../dataDict/模块/表名.md)）
- **业务规则**：详细的处理逻辑和规则
- **接口定义**：
  - 接口路径、请求方法
  - 请求参数（含参数名、类型、是否必填、说明）
  - **返回包定义**（含正常返回和异常返回）：
    ```json
    正常返回 (code=200):
    {
      "code": 200,
      "message": "成功",
      "data": { ... }
    }
    
    异常返回 (code=400/500):
    {
      "code": 400,
      "message": "具体错误描述",
      "data": null
    }
    ```
- **异常处理**：异常情况的处理机制和返回包
- **状态流转**：如涉及状态变更，明确流转条件

### 2.4 前端场景需求（3xx）

#### 前端概述（301）
- **页面结构与菜单**：列出前端的页面树形结构、菜单项
- **页面间的跳转关系**：描述不同页面之间的跳转逻辑、触发条件和展示方式
- **与其他功能的页面集成点**：明确跳转到其他功能页面的触发条件（格式：[功能名页面](../功能名/301_前端概述.md)）
- **共用组件或模块**：说明页面中复用的公共组件

#### 具体场景需求（302+）
- **页面名称与功能**：该页面的业务功能和使用场景
- **页面交互设计**：
  - **页面按钮列表**：使用表格形式详细列出页面上的所有按钮（按钮名称、功能描述、操作流程）
  - **页面间跳转关系**：描述当前页面的跳转触发条件
- **数据绑定与展示**：
  - 表格列及其数据源：[表名字段说明](../../../dataDict/模块/表名.md)
  - 表单字段及其数据类型
  - 后端接口引用：引用对应的 2xx 文档中的接口定义
- **委托设计**（如适用）：
  - **委托支持说明**：明确说明页面功能是否支持委托操作
  - **委托流程**：如需支持委托，详细描述委托的设置、审批和执行流程
  - **角色分配**：说明委托过程中涉及的角色及其权限范围

## 3. 特定逻辑要求

### 2.1 业务逻辑
详细描述功能在业务流程中的关键节点处理规则：
- 数据创建、修改、删除的时机和条件
- 状态变更的触发条件和处理方式
- 业务数据的计算逻辑和规则
- 异常情况的处理机制

### 2.2 额外逻辑
- **特殊业务逻辑**：特定业务场景下的特殊处理规则和例外情况
- **技术实现细节**：涉及特定技术实现时需明确技术选型和实现方式
- **审批流程和状态流转规则**：如涉及审批流程，需详细说明节点、审批人设置及状态流转路径
- **校验规则和约束条件**：详细描述业务层面的数据验证规则
- **数据同步或更新要求**：如需与其他系统进行数据交互，需明确同步时机、方式、映射关系及异常处理机制
- **报表生成和数据统计**：如需支持报表或统计功能，需明确类型、统计维度、计算逻辑及展示方式
- **数据权限控制**：描述功能相关的数据访问权限控制规则

## 4. 技术规范要求

- **前端**：React + TypeScript + Vite + npm

### 3.3 安全要求

2. 认证授权机制
3. 常见安全风险防范
4. 日志记录要求

## 5. 代码规范要求

### 4.1 命名规范
#### 文件命名
- 前端组件文件使用 PascalCase（如 `UserList.tsx`）
- 前端非组件文件使用 kebab-case 或 camelCase（如 `use-user.ts` / `formatDate.ts`）
- 后端文件命名采用 snake_case 风格（下划线分隔）
- 通用配置文件保持语义化命名

#### 变量命名
- 前端变量采用camelCase风格
- 后端变量采用snake_case风格
- 常量命名采用全大写+下划线分隔

#### 函数/方法命名
- 前端函数采用camelCase风格
- 后端函数采用snake_case风格
- 类命名采用PascalCase风格

### 4.2 接口命名规则
1. 所有涉及ID的命名中，ID为正常大小写（如masterID、detailID、USER_ID）
2. 接口方法名称中的ID需使用全大写形式（如getByID、getDetailList）
3. 主表接口命名直接用功能描述

### 4.3 参数命名规范
1. 当同时需要提交或获取主从表数据时，参数名为fullData
2. 当只需要主表结构数据时，参数名为masterData
3. 当只需要从表结构数据时，参数名为detailData

## 6. 单据规则

### 5.1 基础规则
- 单据有固定的数据库规则，定义在数据库规则里
- 单据有较为固定的操作和接口逻辑规则，定义在代码规则里

### 5.2 操作规则
- 单据的每一项操作均需要考虑可逆性，重要操作应支持撤销/重做机制
- 单据的所有操作均需要保留操作记录，包括操作人、操作时间、操作类型、操作内容等
- 当单据锁定时，不允许修改单据内容
- 单据的主从表的主键不显示

## 7. 固定接口规范

### 7.1 单据基本操作接口
| 操作 | 请求方式 | 接口方法 | 备注 | 变量参数 |
|------|----------|----------|------|----------|
| 查询列表 | GET | getList | 支持分页、排序、筛选 | skip, limit, sortBy, sortOrder, filters |
| 查询单条 | GET | getByID | 根据主表ID查询详情 | masterID |
| 新增记录 | POST | create | 创建新记录及从表数据 | fullData (包含主表和从表数据) |
| 更新记录 | PUT | update | 更新记录信息 | masterID, fullData |
| 删除记录 | DELETE | delete | 逻辑删除记录 | masterID |
| 锁定记录 | POST | lock | 锁定记录使其不可修改 | masterID |
| 解锁记录 | POST | unlock | 解锁记录允许修改 | masterID |
| 提交记录 | POST | submit | 提交记录 | masterID |

### 7.2 从表操作接口
| 操作 | 请求方式 | 接口方法 | 备注 | 变量参数 |
|------|----------|----------|------|----------|
| 查询从表数据 | GET | getDetailList | 根据主表ID查询从表数据 | masterID |
| 新增从表记录 | POST | addDetail | 向主表添加从表记录 | masterID, detailData |
| 更新从表记录 | PUT | updateDetail | 更新从表记录 | detailID, detailData |
| 删除从表记录 | DELETE | deleteDetail | 删除从表记录 | detailID |

## 8. 数据字典管理规范

### 8.1 数据字典版本管理
- **存储位置**：`/Doc/dataDict/` 按模块（Sys、Common、DataFile 等）分类存放
- **文件命名**：按表名命名（如 `Sys_Email_Config.md`）
- **版本号管理**：
  - 每个数据字典文件需维护版本号（格式：v1.0、v1.1、v2.0 等）
  - 版本号放在文件开头的元数据中
  - 遵循语义化版本规则：
    - **MAJOR**（主版本）：表结构发生破坏性变更（删除字段、字段类型改变）
    - **MINOR**（次版本）：新增字段或新增约束
    - **PATCH**（修订版本）：字段说明、注释、长度调整等非结构性更新

### 8.2 版本变更记录
每个数据字典文件需包含"版本变更日志"章节，记录每次升版本的详细内容：

```markdown
## 版本变更日志

### v2.0 (2025-12-17)
**变更类型**: MAJOR
**变更内容**:
- 删除了字段 `OldFieldName`
- 新增了字段 `NewFieldName` (VARCHAR(100))，用于...
- 修改字段 `StatusField` 类型从 INT 改为 ENUM

**影响范围**: 
- 需求文档: [邮件接收功能](../requirement/Sys/邮件接收功能/201_后端概述.md)
- 功能文档: [邮件管理模块](../function/Sys/邮件管理.md) （暂未纳入，后续补充）

### v1.1 (2025-12-10)
**变更类型**: MINOR
**变更内容**:
- 新增字段 `IsEnabled` (TINYINT)，用于标记记录是否启用

### v1.0 (2025-11-01)
**变更类型**: INITIAL
**变更内容**:
- 初始版本
```

### 8.3 数据字典与需求的关联
- **在需求文档中引用数据字典**：
  - 后端逻辑（2xx）中涉及数据操作的部分，必须明确引用对应的数据表
  - 引用格式：`[表名](../../../dataDict/模块名/表名.md#字段名)`（可选指定字段）
  - 前端场景（3xx）中的表格列、表单字段，也应引用对应的数据字典

- **数据字典变更的同步机制**：
  - 当修改数据字典时，需基于变更内容审查相关需求文档，确保需求与数据定义一致
  - 如数据字典发生 MAJOR 版本变更，需更新相关需求文档中的字段描述
  - 更新完成后，在数据字典的"版本变更日志"中记录"影响范围"，便于追溯

### 8.4 功能文档的集成（后续规范）
**说明**：当前项目中，"功能文档"（即实现指南、集成文档等）暂未纳入文档体系。

**后续规划**：
- 建立 `/Doc/function/` 目录，存放各功能的实现指南
- 功能文档中需明确引用相关的数据字典，说明各字段在实现中的使用方式
- 当数据字典更新时，同时更新相关功能文档中的字段使用说明
- 规范详见后续更新的"需求规则"v2.0 版本

## 9. 文档维护规范

### 9.1 需求文档更新方式
- **新增内容**：直接在对应的 2xx/3xx 文件中添加新的小节
- **修改内容**：
  - 小的文字或说明修改：直接修改对应位置
  - 重大逻辑或结构变更：需同时更新版本号、更新日志、101 业务概述中的"版本信息"、00 目录中的"更新日志"
- **全量替换**：若功能需求发生重构（如接口设计变更），允许全量替换对应的 2xx/3xx 文档，但需在 00 目录中明确标注"重大变更"

### 9.2 需求与数据字典的一致性检查
- 编写需求时，优先参考已有的数据字典
- 若需求涉及新的数据表或字段，应先创建/更新数据字典，再在需求中引用
- 需求交付前，必须检查所有引用的数据字典字段是否存在且类型正确
