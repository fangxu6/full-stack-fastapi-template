# 需求规则

本文件提供当前仓库需求文档的实操细则。原则以 [需求宪章.md](D:/Workspace/full-stack-fastapi-template/docs/rules/需求宪章.md) 为准；本文重点回答“怎么写”。

## 1. 当前仓库的需求文档结构

### 1.1 目录结构

当前仓库的功能需求统一放在：

```text
docs/specs/<feature>/
```

每个 feature 默认包含 4 份文件：

| 文件 | 作用 | 必填重点 |
|------|------|----------|
| `01_requirement.md` | 需求意图 | 背景、目标、范围、验收标准、约束 |
| `02_interface.md` | 契约与边界 | 接口、数据模型、页面/路由影响、错误场景 |
| `03_implementation.md` | 实施计划 | 变更文件、步骤顺序、迁移与生成 client 说明 |
| `04_test_spec.md` | 验证方案 | lint/build/test/人工验证范围 |

### 1.2 命名规范

- feature 目录名优先使用简洁、稳定的英文 `kebab-case`
- 文件名固定使用两位数字前缀：
  - `01_requirement.md`
  - `02_interface.md`
  - `03_implementation.md`
  - `04_test_spec.md`

## 2. 各文件怎么写

### 2.1 `01_requirement.md`

至少包含：

- `Background`
- `Goals`
- `Scope`
  - In scope
  - Out of scope
- `Acceptance Criteria`
- `Constraints`
- `Risks & Rollout`（如果确有需要）

写作要求：

- 先说为什么要做，再说做什么
- 范围边界必须明确
- 验收标准必须可验证
- 不要把具体文件改动塞到这里

### 2.2 `02_interface.md`

用于描述“外部可见边界”和“跨层影响”。

应按实际需要描述：

- 后端接口
  - path
  - method
  - request body / query / path params
  - response model
  - 关键错误状态码
- 数据模型变化
  - 涉及哪些 SQLModel model / 字段 / 关系 / 约束
- 前端影响
  - 涉及哪些路由、页面、组件、Query、表单
- 客户端影响
  - 是否需要重新生成 OpenAPI client

写作要求：

- 使用当前仓库真实接口风格
- 写真实的 FastAPI/SQLModel/OpenAPI 契约
- 不要发明并不存在的包装层

错误示例：

- 强行规定所有接口统一返回 `code/message/data`
- 强行规定所有 CRUD 都必须叫 `getList`、`getByID`
- 把接口契约写成另一项目的权限配置协议

### 2.3 `03_implementation.md`

用于回答“准备怎么改”。

建议包含：

- `Goal Summary`
- `Planned Changes`
- 关键文件路径
- 执行顺序
- 迁移、client 生成、测试、回滚或兼容性说明

对当前仓库尤其重要的内容：

- 数据模型变更是否需要 Alembic migration
- API 变化后是否需要执行 `bash ./scripts/generate-client.sh`
- 前端是否需要同步 Query、表单、列展示或空态/错误态

### 2.4 `04_test_spec.md`

用于回答“怎么证明它完成了”。

建议包含：

- `Validation Scope`
- `Review Checklist`
- `Manual Verification`
- 必要时列出对应命令

验证应与改动规模匹配，例如：

- 后端逻辑改动：`pytest` / `mypy` / `ruff`
- 前端页面改动：`bun run lint` / `bun run build` / Playwright
- 文档治理：一致性审查与手工核对

## 3. 当前仓库的契约写法

### 3.1 后端接口写法

接口文档应优先描述：

- 实际路由，例如 `/api/v1/items/`
- 实际 FastAPI method
- 实际 request model
- 实际 response model，例如 `ItemPublic`、`ItemsPublic`、`Message`
- 关键错误码，例如 `401`、`403`、`404`、`422`

不要把另一项目的接口命名或包装形式当成当前标准。

### 3.2 前端集成写法

前端相关需求说明应与当前仓库真实模式一致：

- 路由：TanStack Router 文件路由
- 数据获取：TanStack Query
- API 调用：生成式 OpenAPI client
- 表单：React Hook Form + Zod
- UI：Tailwind + shadcn/ui + Radix

如果需求会影响前端，应明确：

- 受影响的页面/组件
- 是否新增或修改 Query key
- 是否有加载态、空态、错误态变化
- 是否需要重新生成 client

## 4. 数据模型写法

### 4.1 不再使用独立 `/Doc/dataDict`

当前仓库默认不使用另一项目的数据字典目录体系。

如果需求涉及数据库结构，应在 spec 中直接说明：

- 模型名
- 字段变化
- 约束或关系变化
- migration 需求
- 对接口与前端的影响

### 4.2 数据模型变更必须联动说明

当需求涉及模型或字段变化时，至少要写清：

- 变更前后差异
- 是否需要 migration
- 是否需要回填或兼容旧数据
- 是否影响 response model
- 是否影响前端生成 client

## 5. 文档维护规则

### 5.1 什么时候更新 spec

默认规则：

- 非平凡变更：先更新或新建 spec
- 需求变化：先改 spec，再改代码
- 重大规则调整：回填 `AI_CHANGELOG.md`
- 架构级长期决策：必要时补 ADR

### 5.2 版本管理

当前仓库不强制给每份需求文档维护独立语义化版本号。

默认追踪方式：

- Git 历史
- `AI_CHANGELOG.md`
- 必要时 ADR

如果某个 feature 确实需要在 spec 内写版本信息，可以加，但不是默认要求。

### 5.3 临时草稿

当前仓库不强制建立 `/temp` 目录来承载需求流程中间产物。

更推荐：

- 在当前对话中完成澄清
- 必要时直接把稳定结果写入 `docs/specs/<feature>/`
- 不把大量短生命周期临时文件纳入正式规则

## 7. 自检清单

写完一个 feature spec 后，至少检查：

- 是否使用了当前仓库的 `01~04` 结构
- 是否把需求、契约、实施、测试拆清楚了
- 是否还残留旧项目路径或角色假设
- 是否把接口写成了当前 FastAPI/OpenAPI 的真实形态
- 是否说明了数据库、migration、client 生成影响
- 是否与现有前端/后端技术栈一致
- 是否需要补 `AI_CHANGELOG.md` 或 ADR
