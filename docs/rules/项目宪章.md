# JSEComplex 项目宪章 (Project Constitution)

## 第一部分：最高原则 (Fundamental Principles)

项目宪章分为三部分：**最高原则**（I-VII，所有工作阶段通用）、**需求宪章**（需求确认阶段）、**开发宪章**（开发执行阶段）。本部分定义 7 项不可协商的核心原则，是所有业务活动的基础。

---

### I. 兼容性优先 (Compatibility First) - 不可协商

**规则**:
- 所有新功能开发前**必须**评估与现有系统的兼容性
- **必须**遵循 `important/DEVELOPMENT_GUIDELINES.md` 中定义的 15 项兼容性规范
- 关键兼容性检查点包括:
  1. 日志系统统一使用 `app/core/logging.py`
  2. 权限检查使用依赖注入 (`dependencies/permission_check.py`)
  3. 前后端字段命名保持 PascalCase 一致性
  4. API 路径不重复 `/api` 前缀
  5. 配置文件驱动的功能与翻译管理
- 任何破坏兼容性的变更**必须**在 `BREAKING_CHANGES.md` 中文档化并经过 Code Review 批准

**理由**:
JSEComplex 是企业级生产系统，兼容性破坏会导致部署失败和数据不一致。通过强制兼容性优先，我们确保增量更新的安全性和可维护性。

---

### II. 规划与排期强制 (Mandatory Planning & Scheduling) - 不可协商

**规则**:
- 所有功能开发**必须**通过 `/speckit` 流程:
  1. `/speckit.spec` - 生成功能规格 (spec.md)
  2. `/speckit.plan` - 生成实施计划 (plan.md, research.md, data-model.md)
  3. `/speckit.tasks` - 生成任务列表 (tasks.md) 并分配优先级
- 每个 User Story **必须**标注优先级 (P1/P2/P3) 并可独立测试
- Tasks 按 Phase 组织: Setup → Foundational → US1 (MVP) → US2 → US3 → Polish
- **禁止**未经 tasks.md 排期的临时需求插入
- 跨功能变更**必须**评估对现有 specs/ 的影响

**代码一致性检查强制 (Code Consistency Verification Mandatory)**:
- 每个功能的 `tasks.md` **必须**在 Polish Phase 或开发完成后包含代码一致性检查任务
- 一致性检查**必须**覆盖以下方面:
  1. **模型导入路径**: 验证所有模型导入使用正确的文件路径和类名
  2. **字段名一致性**: 验证数据库字段、ORM 模型、Pydantic Schema、前端接口的字段名统一
  3. **API 路径一致性**: 验证路由定义、服务调用、前端请求的路径统一
  4. **依赖关系正确性**: 验证服务层、CRUD 层、路由层的依赖引用无循环依赖
  5. **对象访问方式正确性**: 验证对象属性访问方式与对象类型匹配 (dict vs SimpleNamespace vs ORM)
- 一致性检查工具:
  - 后端: `grep`/`rg`、`flake8`、`mypy`
  - 前端: `eslint`、TypeScript 编译器

**UserID/UUID 传递一致性 (Critical)**:
- 后端路由与服务层**必须**保持 `current_user.UserID` 的原始 bytes（或 UUID 对象）类型；**禁止**直接 `str(current_user.UserID)`
- 需要字符串入参时**必须**显式调用 `to_uuid_bytes(str_id)`；输出到日志/响应时使用 `from_uuid_bytes` 或 `normalize_uuid`
- 操作日志与审计字段写入时直接使用 bytes/UUID；仅在序列化输出时转换
- 审计字段写入（CreatorID/UpdaterID/DeleterID）必须复用服务/CRUD 已定义的 `user_id` 参数或在对象中设置，不得随意新增未声明的关键字参数（如给 `CRUDBase.create()` 传 `creator_id` 导致签名不匹配）
- 路由 → 服务 → CRUD 的 `user_id`/`creator_id`/`updater_id` 参数命名与类型**必须**保持一致；接口入参用字符串 UUID，内部统一转换为 bytes/UUID；禁止把 bytes 包装成形如 `"b'...'"` 的字符串
- 典型错误与示例:
  - ❌ `creator_id=str(current_user.UserID)` → 传入 `"b'...'"` 导致 UUID 解析错误
  - ✅ `creator_id=current_user.UserID`（bytes）或 `creator_id=to_uuid_bytes(user_id_str)`（当入参为字符串）

**前端菜单同步强制检查 (Frontend Menu Synchronization Mandatory Check)**:
- **检查时机**: Phase 1 前端路由配置完成后**必须**立即执行
- **规则**: 新增路由后必须同步更新 `AppSidebar.tsx` 和菜单配置文件（如 `src/config/menu.ts`）
- **检查内容**: 菜单配置包含新 `featureKey`；菜单 path/icon/权限一致；所需图标已导入；菜单名称与路由 `title` 一致

**理由**:
强制规划和一致性检查可在早期发现低级错误（字段名、权限键、菜单同步、UUID 类型错误），减少部署风险和返工成本。

### III. 配置驱动架构 (Configuration-Driven Architecture)

**规则**:
- 权限通过 `config/config_Feature.json` 管理，表头翻译通过 `config/config_HeaderTrans.json` 管理
- 前端路由配置**必须**包含 `featureKey` 和 `title`；按钮**必须**有 `data-component-path` 和 `data-permission-key`；表格列**必须**有 `data-field`
- 配置更新后运行生成脚本:
  ```bash
  python scripts/generate_feature_config.py
  python scripts/generate_header_trans_config.py
  ```
- 权限键匹配规则:
  - `featureKey` 与 `feature_key` 必须逐字一致
  - 菜单权限使用 `menu:` 前缀；操作权限使用 `<resource>:<action>:<operation>`

**理由**:
配置驱动让功能定义与实现解耦，便于权限动态调整和多语言扩展；严格的权限键匹配避免前端不可见或路由拦截问题。

---

### IV. 分层架构严格遵守 (Strict Layered Architecture)

**规则**:
- 后端分层: API → Service → CRUD → Model，禁止跨层调用、禁止在路由写业务逻辑
- 前端分层: Pages → Services → Stores → Hooks，禁止将业务散落在组件内部

**理由**:
分层确保关注点分离，便于测试与扩展，降低耦合。

---

### V. 审计与日志全覆盖 (Comprehensive Auditing & Logging)

**规则**:
- 所有表必须有审计字段: CreatorID, CreateTime, UpdaterID, UpdateTime, IsDeleted
- 关键操作使用 `utils/audit.py` 记录；日志按类型分文件存储并定期归档
- 日志输出 UUID/bytes 时使用 `from_uuid_bytes`/`normalize_uuid` 转换为可序列化形式
- **日志格式规范**:
  - **必须**使用 f-string 格式进行日志记录
  - **禁止**使用 `%s`、`%d` 等 printf 风格占位符
  - 示例:
    ```python
    # ✅ 正确：使用 f-string
    logger.info(f"用户 {user_id} 登录成功，IP: {ip_address}")
    logger.error(f"操作失败: {error_message}")

    # ❌ 错误：使用 %s 占位符
    logger.info("用户 %s 登录成功，IP: %s" % (user_id, ip_address))
    logger.info("用户 %s 登录成功" % user_id)
    ```

**理由**:
可追溯性是合规与问题定位的基础。f-string 格式更直观、类型安全且性能更优，统一格式便于代码审查和维护。

---

### VI. 权限检查前置 (Permission Check at Entry Point)

**规则**:
- 后端路由必须通过依赖注入完成权限检查；禁止在函数内手动判断
- 前端必须使用 `usePermission` 进行权限控制；按钮用 `:disabled` 控制体验
- 权限键格式统一为 `<resource>:<action>:<operation>`

**理由**:
前置检查明确安全边界，避免遗漏。

---

### VII. 测试优先 (Test-First for Critical Paths) - 选择性强制

**规则**:
- P1 用户故事核心路径必须有集成测试；P2/P3 可在 tasks.md 标注可选
- 后端测试用 `pytest`，前端用 `vitest`/`playwright`；测试必须独立可运行

**理由**:
平衡质量与效率，保障关键路径稳定。

### 前端开发规范

**React + TypeScript 规范**

- 必须使用函数组件 + Hooks，不使用 class 组件
- 路由配置必须包含 `featureKey` 与 `title`
- 权限控制统一用 `usePermission`
- 表格列标注 `data-field`，按钮标注 `data-permission-key` 和 `data-component-path`

**前端 UI 开发模式 (Frontend UI Development Pattern) - React 规范**

**技术组合**: Ant Design 组件 + 统一样式规范

**规则**:

1. **组件优先原则**:
   - 复杂交互组件（表格、表单、弹窗、日期选择器等）**必须**使用 Ant Design 组件
   - 统一样式优先使用 Ant Design Token/主题能力或局部样式

2. **混合使用规范**:
   ```tsx
   // ✅ 正确：Ant Design 组件 + 轻量布局
   <Space>
     <Input value={keyword} onChange={(e) => setKeyword(e.target.value)} placeholder="搜索" />
     <Button type="primary" onClick={search}>查询</Button>
   </Space>

   // ❌ 错误：用原生元素替代 Ant Design 组件
   <button className="btn">提交</button>
   ```

3. **风格定义**:
- **紧凑布局**: 表格密度偏高、表单布局双列/多列
- **专业配色**: 使用 Ant Design 默认主题色或统一的主题 Token
- **高信息密度**: 优先使用表格展示数据；避免无意义留白
- **操作反馈**: 所有 CUD 操作必须有 loading 状态和消息提示

4. **样式覆盖优先级**:
- 全局样式覆盖放在 `src/styles/antd-overrides.css`
- 组件局部样式使用 CSS Modules 或局部样式文件

5. **禁止行为**:
- ❌ 禁止用原生元素重写 Ant Design 已有组件（如 Button、Table、Form）
- ❌ 禁止混用多个 UI 框架（仅 Ant Design）

**理由**:
Ant Design 提供成熟的企业级组件与主题能力，统一 UI 体验，减少样式分叉。

**时间格式展示标准 (Datetime Display Format Standard)**

**规则**:
- 前端所有时间展示**必须**统一使用 `YYYY/MM/DD HH:mm` 格式
- **禁止**使用其他日期格式（如 `YYYY-MM-DD`, `MM/DD/YYYY`, `DD/MM/YYYY`）
- **禁止**使用 12 小时制（AM/PM），统一使用 24 小时制

**格式规范**:
```typescript
// ✅ 正确：使用统一格式
"2025/12/03 09:46"  // 年/月/日 时:分
"2025/01/15 14:30"  // 注意：月份和日期保持两位数

// ❌ 错误：其他格式
"2025-12-03 09:46"  // 使用连字符
"12/03/2025 09:46"  // 月/日/年顺序
"2025/12/03 09:46:23"  // 包含秒
"2025/12/03 9:46 AM"  // 12小时制
```

**实现方式**:

1. **表格列展示**:
```tsx
const columns = [
  {
    title: '创建时间',
    dataIndex: 'CreateTime',
    render: (value: string) => formatDateTime(value),
  },
]
```

2. **工具函数**（推荐创建 `src/utils/datetime.ts`）:
```typescript
/**
 * 格式化日期时间为 YYYY/MM/DD HH:mm
 * @param datetime - ISO 8601 字符串或 Date 对象
 * @returns 格式化后的字符串
 */
export function formatDateTime(datetime: string | Date | null | undefined): string {
  if (!datetime) return '-'

  const date = typeof datetime === 'string' ? new Date(datetime) : datetime
  if (isNaN(date.getTime())) return '-'

  const year = date.getFullYear()
  const month = String(date.getMonth() + 1).padStart(2, '0')
  const day = String(date.getDate()).padStart(2, '0')
  const hours = String(date.getHours()).padStart(2, '0')
  const minutes = String(date.getMinutes()).padStart(2, '0')

  return `${year}/${month}/${day} ${hours}:${minutes}`
}
```

3. **日期选择器默认格式**:
```tsx
<DatePicker.RangePicker
  showTime
  format="YYYY/MM/DD HH:mm"
  onChange={(value) => setDateRange(value)}
/>
```

**理由**:
- 统一时间格式提升用户体验一致性，避免不同页面格式混乱
- 斜杠分隔符（`/`）符合国际惯例，可读性优于连字符（`-`）
- 24 小时制避免 AM/PM 混淆，更适合企业应用场景
- 省略秒级精度减少视觉噪音，分钟级精度足够满足业务需求

### 后端开发规范

**分页参数标准**:
- 所有分页接口**必须**使用 `skip`/`limit` 参数格式（不使用 `page`/`page_size`）
- `skip`: 跳过记录数（类型: int，默认值: 0）
- `limit`: 返回记录数（类型: int，默认值: 10）
- 示例:
  ```python
  # ✅ 正确：使用 skip/limit
  @router.get("/users")
  async def get_users(
      skip: int = Query(0, ge=0),
      limit: int = Query(10, ge=1, le=100),
      db: AsyncSession = Depends(get_db)
  ):
      return await user_service.get_list(db, skip=skip, limit=limit)

  # ❌ 错误：使用 page/page_size
  @router.get("/users")
  async def get_users(
      page: int = Query(1, ge=1),
      page_size: int = Query(10, ge=1)
  ):
      ...
  ```

**理由**: `skip`/`limit` 参数格式更符合数据库与列表偏移语义，前端无需额外换算即可直接传递，接口更贴近实现。

**时间时区处理标准**:
- 所有模块**必须**使用 `app/utils/time_utils.py` 处理时间和时区
- **禁止**直接使用 `datetime.now()` 或 `datetime.utcnow()`
- **禁止**在业务代码中硬编码时区（如 `ZoneInfo("Asia/Shanghai")`）

**核心函数**:
- `get_local_now()`: 获取当前时间（上海时区，无 tzinfo，兼容 MySQL DATETIME）
- `to_local_naive(dt)`: 转换任意时间为上海时区的无 tzinfo 时间（支持 datetime/str）

**使用规范**:
```python
# ✅ 正确：使用统一工具
from app.utils.time_utils import get_local_now, to_local_naive

# 获取当前时间
now = get_local_now()

# 创建记录时设置时间
item = Item(
    CreateTime=get_local_now(),
    UpdateTime=get_local_now()
)

# 转换前端传入的时间
start_time = to_local_naive(request_data.get("start_time"))

# ❌ 错误：直接使用 datetime
from datetime import datetime
now = datetime.now()  # 时区不确定
now = datetime.utcnow()  # UTC 时区，与业务时区不一致

# ❌ 错误：硬编码时区
from zoneinfo import ZoneInfo
now = datetime.now(ZoneInfo("Asia/Shanghai"))  # 应使用统一工具
```

**理由**: 统一时区避免时间不一致问题（服务器、数据库、前端可能在不同时区）；中心化时区配置便于未来调整（如支持多时区）；与 MySQL DATETIME 类型兼容（无 tzinfo）；避免 `datetime.utcnow()` 与业务时区混用导致的时间偏移。

**数据库约束**

- MySQL 8.0+（生产）；SQLite（测试）
- 字段命名 PascalCase；索引命名 `IX_<Table>_<Field>`
- **禁止使用外键**，由后端逻辑保证关联一致性

### 开发流程规范 (Development Workflow)

**功能开发流程**

```
1. 需求确认 → 获得已确认的需求文档
2. /speckit.spec - 从需求文档提取功能规格 (spec.md)
3. /speckit.plan - 编制实施计划 (plan.md, research.md, data-model.md)
4. /speckit.tasks - 编制任务排期 (tasks.md) 并分配优先级
5. Code Review (包含 Constitution Check)
6. Phase 1: Setup → Foundational
7. Phase 1 前端完成检查（菜单同步）
8. US 实现 (P1→P2→P3)
9. Polish & 文档
10. 部署与验收
```

**Constitution Check 检查点**

- [ ] 与 `DEVELOPMENT_GUIDELINES.md` 兼容 (15 项)
- [ ] 权限定义/表头翻译已对齐配置 (`config_Feature.json` / `config_HeaderTrans.json`)
- [ ] **配置文件一致性检查**（新增前端路由、按钮、后端接口与 `config_Feature.json` 一致；`featureKey`/`data-permission-key` 与 `feature_key` 精确匹配；`component_path` 与组件名称一致；父子关系正确；运行检查脚本验证）
- [ ] 前端 `featureKey` 与 `feature_key` 精确匹配；菜单权限含 `menu:` 前缀
- [ ] API 路由无重复 `/api` 前缀；RESTful；参数命名一致
- [ ] **后端分页接口使用 `skip`/`limit` 参数**（不使用 `page`/`page_size`）
- [ ] **时间时区处理使用 `app/utils/time_utils.py`**（禁止直接使用 `datetime.now()`/`datetime.utcnow()`；禁止硬编码时区）
- [ ] **前端时间格式展示统一为 `YYYY/MM/DD HH:mm`**（禁止使用其他日期格式；禁止 12 小时制；使用 `formatDateTime()` 工具函数）
- [ ] 数据模型含审计字段 (CreatorID, CreateTime, UpdaterID, UpdateTime, IsDeleted)
- [ ] 后端路由使用权限依赖注入
- [ ] 前端使用 React 函数组件 + Hooks + `usePermission`
- [ ] Tasks 含代码一致性/对象访问方式检查 (模型/字段/API/依赖/访问方式)
- [ ] **UserID/UUID 传递一致性检查**：接口入参使用字符串 UUID；路由→服务→CRUD 统一转换为 bytes/UUID 并保持参数命名一致；输出/日志使用 `from_uuid_bytes/normalize_uuid`；审计字段写入复用已声明的 `user_id` 参数或对象字段，勿新增未声明关键字（如 `creator_id`）；禁止出现 `"b'...'"` 字符串
- [ ] **前端 UI 开发模式检查**：复杂交互组件使用 Ant Design；遵循统一风格（紧凑布局、专业配色、高信息密度）
- [ ] **日志格式检查**：日志记录必须使用 f-string 格式；禁止使用 `%s`、`%d` 等 printf 风格占位符

**Phase 1 Frontend Completion Check**:

**代码审查标准**

- 代码一致性检查通过；对象访问方式正确
- **配置文件一致性检查通过**；所有新增功能已配置权限

## 治理规则 (Governance)

### 宪章地位
- 宪章优先级高于其他开发规范；违反宪章的代码不得合并

### 修订流程
1. 提出修订 → 评估影响 → 团队 2/3 通过
2. 运行 `/speckit.constitution` 更新宪章
3. 同步更新受影响模板与文档
4. 通知全体并宣讲

### 版本控制
- MAJOR: 重定义/移除核心原则
- MINOR: 新增原则或显著扩展规则
- PATCH: 澄清/错别字/非语义调整

### 合规审查
- 每季度一次；检查 PR 违例、指南更新需求、配置生成使用、测试覆盖率趋势
- 结果记录在 `docs/compliance-reports/YYYY-QX.md`

### 豁免机制
- 紧急线上修复可豁免 `/speckit`，但需事后补文档
- 需 Lead 批准并记录 `docs/exceptions/YYYY-MM-DD.md`
- 单个 Sprint 最多 1 次豁免
