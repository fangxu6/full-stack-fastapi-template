# 当前仓库项目宪章

## 总体定位

本文定义当前仓库在开发执行阶段的最高原则。

它的作用不是替代具体开发规范，而是回答：

- 当前仓库以什么技术栈和流程为准
- 非平凡改动应如何推进
- 前后端、数据库、生成代码、测试和决策记录如何协同

需求确认阶段的详细原则见 [需求宪章.md](D:/Workspace/full-stack-fastapi-template/docs/rules/需求宪章.md)。

---

## 第一部分：最高原则

### I. 当前仓库事实优先

所有开发、评审和 AI 协作都必须以当前仓库真实基线为准，而不是照搬其他项目规则。

当前仓库的核心事实包括：

- 后端：FastAPI + SQLModel + PostgreSQL + Alembic
- 前端：Vite + React 19 + TanStack Router + TanStack Query + Tailwind v4 + shadcn/ui
- 前后端契约：OpenAPI + 生成式前端 client
- 需求流程：`docs/specs/<feature>/01~04`
- 决策记录：`AI_CHANGELOG.md` 为主，ADR 为补充

### II. 非平凡改动遵循 spec-first

当改动涉及以下任一情况时，应先创建或更新 feature spec：

- 多文件或跨层改动
- 接口、数据库、前端页面联动
- 迁移、兼容性或回滚风险
- 关键流程和测试策略变化

默认流程：

1. `01_requirement.md`
2. `02_interface.md`
3. `03_implementation.md`
4. `04_test_spec.md`
5. 实施代码
6. 回填 `AI_CHANGELOG.md`

小范围低风险修正可以走轻量流程，但不能让意图和决策失去可追踪性。

### III. 分层架构与职责边界必须清晰

当前仓库后端默认分层：

- API routes
- Services
- CRUD
- Models / Schemas

要求：

- 路由层不承载复杂业务逻辑
- 业务逻辑尽量放在 service 层
- 原子数据库操作收敛在 CRUD 层

当前仓库前端默认分层：

- Routes / page composition
- Components
- Hooks
- Generated client + Query layer

要求：

- 页面负责装配，不散落大量请求细节
- 数据获取优先集中在 hooks / query options / 事件处理
- 业务逻辑不要散落在大量页面 JSX 内

### IV. 契约变化必须贯穿到生成 client

当前仓库不是“后端自己改、前端自己猜”的协作模式。

默认链路是：

```text
SQLModel / schema / route
-> OpenAPI
-> generated frontend client
-> frontend Query / form / page updates
```

因此：

- 后端接口变化必须反映在 OpenAPI 契约上
- 前端默认通过生成 client 调接口
- OpenAPI 契约变化后必须重新生成 client

### V. 生成文件边界与聚焦改动不可破坏

以下文件或目录不得直接手改：

- `frontend/src/client/**`
- `frontend/src/routeTree.gen.ts`
- `frontend/src/components/ui/**`

此外：

- 改动应聚焦当前任务
- 不进行无关的大规模格式化或重构
- 不为了迁就文档去修改现有技术栈

### VI. 验证强度与风险匹配

所有改动都应有与风险匹配的验证方式。

后端常用验证：

- `uv run pytest`
- `mypy`
- `ruff`

前端常用验证：

- `bun run lint`
- `bun run build`
- `bunx playwright test`

文档治理改动至少应做一致性审查，确认文档与现有代码和主规范不冲突。

### VII. 决策必须可追溯

当前仓库的默认决策记录方式：

- 普通功能、规则和实现取舍：`docs/decisions/AI_CHANGELOG.md`
- 架构级、长期且回滚成本高的决策：额外使用 ADR

如果规则改了但没有留下决策痕迹，后续团队和 AI 很容易重复争论已做过的取舍。

## 第三部分：开发执行约束

### 1. 后端开发约束

- 代码结构遵循 route -> service -> crud -> model / schema
- 类型标注是默认要求；`mypy` 为严格模式
- 局部更新优先使用 `model_validate` / `model_dump` / `sqlmodel_update`
- 使用 `HTTPException` 时提供清晰 `status_code` 与 `detail`
- 不使用 `print`，需要输出时使用 logging
- 数据结构变化通过 Alembic migration 管理

### 2. 前端开发约束

前端细则以 [前端开发规范.md](D:/Workspace/full-stack-fastapi-template/docs/rules/前端开发规范.md) 为准。

本宪章层面的硬约束是：

- 使用函数组件与 Hooks
- 路由基于 TanStack Router 文件路由
- 服务端状态默认交给 TanStack Query
- API 调用默认复用生成 client
- 不引入第二套路由、状态管理或 UI 基础框架
- 不直接编辑生成文件

### 3. 数据库与接口协作约束

数据库细则以 [数据库规则.md](D:/Workspace/full-stack-fastapi-template/docs/rules/数据库规则.md) 为准。

执行时必须牢记：

- 数据模型变化不能只改数据库层
- 需要同步评估 schema、route、OpenAPI、client 和前端页面影响
- 不再沿用外来项目的固定 `code/message/data` 包装、MySQL 类型规则或单据主从模板

### 4. 需求与文档协作约束

需求细则以 [需求规则.md](D:/Workspace/full-stack-fastapi-template/docs/rules/需求规则.md) 为准。

执行时默认要求：

- 非平凡改动先更新 spec
- 需求变化先改 spec 再改代码
- 重要规则或取舍更新 `AI_CHANGELOG.md`
- 架构决策必要时补 ADR

### 5. 提交前自检

提交前至少检查：

- 是否与当前仓库技术栈一致
- 是否误改生成文件
- 是否遗漏 migration / client regeneration
- 是否对关键路径执行了足够验证
- 是否需要更新 spec、`AI_CHANGELOG.md` 或 ADR
