# 复杂重构规划 Prompt 模板

用于在复杂重构开始前建立当前代码证据、设计目标边界和可验证的
Trellis 规划包。它不直接实施重构。

## 使用方式

替换调用模板中的 `{{...}}` 占位符后发送给 AI。范围不清楚时保留为空，
由证据调查确认，不要用猜测补齐。

## 调用模板

```text
我要规划一次复杂代码重构。

目标：{{REFACTOR_GOAL}}
已知范围：{{KNOWN_PATHS_OR_FLOWS}}
约束：{{COMPATIBILITY_SECURITY_ROLLOUT_CONSTRAINTS}}
预期结果：{{TARGET_OUTCOME}}
当前 HEAD：{{HEAD_SHA}}
相关历史任务、设计或提交：{{HISTORY_REFERENCES}}

先进入“证据调查与方案设计”模式。本轮是 report-only：
- 不修改代码、配置、迁移、测试或项目文档；
- 不创建 Trellis task，不启动实现，不派发实现或检查代理；
- 所有结论以当前 HEAD 为准；代码事实优先于历史文档和记忆；
- 不确定的事实必须标记为 `unknown`，不得补全猜测。

请按以下顺序工作：

1. 建立当前证据基线
   - 确认 HEAD、工作区状态、相关历史提交和任务。
   - 找到入口、调用方、数据流、数据所有者、现有测试和兼容性约束。
   - 区分 `confirmed`（源码或测试已证实）、`inference`（有证据的推断）和
     `unknown`（尚未证实）。
   - 每个关键结论给出文件路径、符号或行号；不要依据文件大小、目录名或
     历史报告措辞判断问题。

2. 描述问题和边界
   - 说明当前行为、真正的责任混乱或重复点，以及不重构的具体风险。
   - 使用 deletion test：删除或合并候选模块后，复杂度是否真正减少，还是
     只被移动到另一个文件。
   - 写出必须保持的不变量，例如 API 兼容性、权限语义、数据完整性、审计、
     延迟或上线窗口。

3. 建立影响矩阵
   对每项填写 `changed`、`unchanged` 或 `unknown`，并给出当前证据、目标影响
   和验证方式。未涉及的项必须明确标记 `unchanged`，不得默认扩大范围：

   | 影响面 | 状态 | 当前证据/所有者 | 目标影响 | 验证方式 |
   | --- | --- | --- | --- |
   | API 与公开 Schema | | | | |
   | route / service / CRUD / domain ownership | | | | |
   | 数据模型、迁移、历史数据与回滚 | | | | |
   | 认证、权限、审计与日志 | | | | |
   | 配置、异步任务、缓存与外部集成 | | | | |
   | 前端调用、生成客户端、路由、菜单与状态 | | | | |
   | 单元测试、集成测试、E2E 与人工验证 | | | | |

4. 设计候选方案
   - 给出当前职责分布和目标职责分布。
   - 优先选择最小、可逆、一次迁移清楚所有调用方的责任调整；不要为了未来
     可能性引入新框架、仓储层、适配器或抽象。
   - 如存在多个合理方案，最多保留两个：说明推荐项、收益、代价、兼容性和
     不采用另一项的原因。
   - 为推荐项写出迁移顺序、回滚点、数据切换策略和每一步的可验证完成标准。

5. 判断 Trellis 任务边界
   - 只有能独立验收、独立提交或可并行的交付物才拆为子任务。
   - 后端、前端和集成边界不是天然子任务；强依赖改动保留在同一任务，按
     实施切片排序。
   - 若涉及公开 API 或跨层行为，指出是否需要 `e2e-api-tests.md`。

6. 输出规划包
   - 证据摘要：confirmed / inference / unknown。
   - 影响矩阵。
   - 推荐设计：边界、不变量、兼容性、迁移和回滚。
   - PRD 草案：目标、范围、非目标、验收标准、风险。
   - Design 草案：契约、数据流、关键取舍和测试策略。
   - Implement 草案：按最小可验证切片排序，包含每步验证命令。
   - 仅保留必须由我决定的未决问题；代码能够回答的问题先自行调查。

完成后停止。不要创建 Trellis task，不要修改文件，也不要开始实现。
最后只问：
“是否确认该规划，并允许创建 Trellis task 进入正式实施准备？”
```

## 使用边界

- 此模板适用于现有复杂代码的职责迁移、跨模块重组、兼容性改造和高风险
  技术债清理。
- 小型局部修复、纯命名整理或不改变职责边界的提取，不需要强制套用完整矩阵。
- 规划获确认后，才按项目 Trellis 流程创建任务、持久化 PRD/design/implement
  工件并开始实施。
