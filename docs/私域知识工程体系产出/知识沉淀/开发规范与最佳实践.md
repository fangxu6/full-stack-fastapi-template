## 开发规范与最佳实践

### 关键结论

- ✅ 平台基线已经建立：后端统一异常结构、`request_id` 追踪、前端 `app/platform/features/shared` 分层开始落地。
- ✅ 新增业务能力时，优先接入现有平台骨架，而不是继续把实现堆回旧的 `routes/`、`components/`、`crud.py` 单点大文件。
- ⚠️ 当前仓库仍处于“批次 0 骨架 + 局部真实迁移”阶段，后续新增代码如果不遵守边界，结构会迅速回退。

### 本次应沉淀的项目级规则

#### 1. 统一异常返回不是可选项

适用范围：`backend/app/**`

- 业务失败优先抛 `AppError` 体系，而不是在服务层直接抛裸 `HTTPException`。
- 框架异常、校验异常、未处理异常都必须收口到统一 JSON 结构：
  - `detail`
  - `request_id`
- 未处理 `500` 不能只返回通用错误，必须同时在服务端保留 traceback 日志。

反例：

```python
from fastapi import HTTPException

if not user:
    raise HTTPException(status_code=404, detail="User not found")
```

推荐：

```python
from app.core.exceptions import UserNotFoundError

if not user:
    raise UserNotFoundError()
```

#### 2. 请求追踪 ID 必须贯穿响应与日志

适用范围：后端入口、中间件、全局异常处理

- 统一通过中间件生成或透传 `X-Request-ID`。
- 所有错误响应都返回同一个 `request_id`。
- 记录未处理异常时，日志必须带上 `request_id` 和请求路径，保证前后端可对账。

#### 3. 前端新增页面不能继续直接长在 `routes/`

适用范围：`frontend/src/**`

- `routes/*` 应保持“薄路由文件”角色，只负责路由声明和导出页面模块。
- 页面实现应按职责下沉：
  - 应用壳与全局导航放 `app/*`
  - 跨业务平台能力放 `platform/*`
  - 业务功能放 `features/*`
  - 真正共享 UI 放 `shared/*`

反例：

```tsx
// routes/login.tsx
export default function LoginPage() {
  // 在路由文件里直接写完整页面实现
}
```

#### 4. 共享组件优先按分组目录暴露

适用范围：`frontend/src/shared/components/**`

- 优先使用分组 barrel，如 `@/shared/components/feedback`、`@/shared/components/layout`。
- 不要新增一个平铺的大杂烩 `Common` 目录。
- 共享层只放纯共享 UI，不要塞业务权限、业务上下文、页面级编排。

#### 5. 菜单权限与路由守卫要集中

适用范围：前端导航与鉴权

- 菜单项装配放 `app/navigation/*`
- 权限判断入口放 `shared/permissions/*`
- 路由保护逻辑放 `app/router/guards.ts`

不要在页面组件里散落 `is_superuser ? ... : ...` 作为长期方案。

#### 6. 新业务模块先接平台骨架，再写业务

适用范围：后端新增模块、前端新增业务域

后端建议顺序：

1. 在 `backend/app/modules/<module>/` 建立模块入口与边界
2. 在 `services/*` 或后续模块内服务承接业务逻辑
3. 复用 `core/exceptions.py`、`api/dependencies/*`、`infra/*` 能力
4. 补测试，锁定统一错误结构与权限行为

前端建议顺序：

1. 明确是 `platform` 能力还是 `features` 业务
2. 页面放 `pages/`
3. 页面私有组件放对应 `components/`
4. 只有跨域复用后再上升到 `shared/*`

### 当前项目结构建议

#### 后端

- `core/*`：横切治理能力，如配置、异常、日志、分页、可观测性
- `infra/*`：基础设施抽象
- `modules/*`：面向未来模块化拆分的业务边界入口
- `api/*`：HTTP 路由与依赖
- `services/*`：当前主要业务实现承载层

#### 前端

- `app/*`：应用框架、全局导航、路由守卫
- `platform/*`：认证、系统管理、文档等跨业务平台能力
- `features/*`：具体业务功能
- `shared/*`：共享 UI、hooks、utils、permissions

### 常见陷阱

- 只统一了 `AppError`，却忘了 `401/404/422` 这类框架异常也要统一结构。
- 把 `500` 包成统一 JSON 后忘了记录 traceback，导致 `request_id` 无法回查。
- 新建页面时图省事直接在 `routes/*.tsx` 写完整实现，后续再迁移成本更高。
- 把业务组件先丢进 `shared/components`，造成“共享层被业务污染”。
- 新增菜单权限时直接散落在页面里，而不是集中在导航配置和权限入口。
