### 关键架构决策

#### 1. 后端统一异常与请求追踪

- `backend/app/core/exceptions.py` 已成为统一异常入口。
- 请求级 `X-Request-ID` 由中间件生成或透传。
- `401/404/422/500` 都应收口为统一 JSON：

```json
{
  "detail": "...",
  "request_id": "..."
}
```

#### 2. 前端从“路由承载页面实现”转向“边界分层”

- `routes/*` 退回为薄路由文件
- 应用壳和导航归 `app/*`
- 平台能力归 `platform/*`
- 业务功能归 `features/*`
- 共享能力归 `shared/*`

#### 3. 后端模块化处于“骨架先行”

- `core/*`、`infra/*`、`modules/*` 已建立目标边界
- 真实业务实现目前仍主要在 `services/*`
- 这代表当前是过渡态，但目标边界已经明确

### 核心调用链

#### 登录链路

- 前端：`routes/login.tsx` → `platform/auth/pages/LoginPage.tsx` → `hooks/useAuth.ts`
- 后端：`api/routes/login.py` → `services/auth.py::login_access_token` → `crud.authenticate` → `core/security.py`

#### 统一异常链路

- `app/main.py`
- `RequestIdMiddleware`
- `AppError / HTTPException / RequestValidationError / Exception handlers`
- 返回统一 `request_id`
- 未处理 `500` 记录服务端 traceback

#### 条目页链路

- 前端：`routes/_layout/items.tsx` → `features/items/pages/ItemsPage.tsx`
- 后端：`api/routes/items.py` → `services/item.py` → `crud/item.py`

### 风险与缺口分析

- ⚠️ `Item` 仍是模板型实体，真实业务域尚未展开。
- ⚠️ `modules/*` 与 `infra/*` 目前大多还是占位骨架，说明架构目标先于迁移完成。
- ⚠️ 仍需持续防止前端新页面回流到 `routes/*`、共享 UI 回流到平铺式 `components/Common/*`。
- ✅ 统一异常与请求追踪已经形成较稳定的平台基线。

### 文档维护规则

- 后端新增横切能力时，同步更新后端依赖图和异常/可观测性说明。
- 前端新增平台域或业务域时，同步更新前端依赖图与分层说明。
- 如果 `modules/*` 开始承接真实业务，需要把“骨架先行”改写为实际模块职责图。
